# 缺失模块与风险清单

## P0：上线阻断

| 问题 | 证据 | 影响 | 处理策略 |
|---|---|---|---|
| 仓库含明文敏感配置 | Boot dev 配置与 Nacos SQL 种子含数据库、加密、短信、任务调度等值 | 凭证泄露和生产误用 | 立即确认值是否有效；有效则轮换；改为环境变量/密钥服务；提交前做 secret scan |

## P1：高风险缺口

| 问题 | 证据 | 影响 | 处理策略 |
|---|---|---|---|
| 生产 API 配置未落地 | UI/UniApp production 仍有 localhost，staging 是示例域名 | 发布后请求错误或错误环境 | 由部署注入真实地址并做构建产物检查 |
| 自动化测试不均 | 页面装修已有 Java/Vitest 契约测试，但 UniApp 无独立测试脚本，仓库也无 Playwright/E2E 约定 | 订单/支付/营销和跨端发布链路仍有回归风险 | 继续覆盖状态机、支付幂等、租户隔离，并建立仓库级 E2E 基线 |
| UniApp 构建工具链冲突 | Node 24 下 H5/微信构建均在 `unconfig` 的 CJS `require()` 加载 ESM 时失败 | 无法产出和视觉验收移动端构建 | 对齐 `@uni-helper/vite-plugin-uni-pages` 与 `unconfig` 版本后重新安装、构建 |
| 商城装修 Gate 3 未闭环 | 三端功能与契约已落地，但无 E2E、MySQL 迁移演练和 H5/微信视觉验收 | 不能声明完整发布链路可上线 | 需求和执行计划保持 `active`，补齐环境与发布演练后再归档 |
| 历史 Harness 当前不可用 | `scripts/`、`harness/` 在工作树处于删除状态 | Agent 可能误报验证完成 | 恢复前只用 Maven/pnpm 原生命令并如实记录 |
| 会员加固迁移未做真实库演练 | Boot/Cloud 已增加 `14member_management_hardening.sql`，本机未验证存量 MySQL 数据形态 | 重复关系或异常存量值可能阻断唯一索引迁移 | 上线前备份并在 MySQL 8 克隆库演练迁移、校验行数和唯一键 |
| 订单加固迁移未做真实库演练 | Boot/Cloud 已增加 16、17、18 号订单链路迁移，本机仅完成静态 SQL 校验 | 重复订单号、重复有效购物车/评价或异常历史数据可能阻断唯一索引；漏建消费表会使商品销量消息失败 | 上线前在 MySQL 8 克隆库按编号演练，核对回填、逻辑删除行数、唯一索引和消费记录表 |
| UniApp 全量类型检查基线失败 | `apiDefinitions/createApis` 生成类型和全局 `ImportMeta.env` 声明缺失导致 22 条错误 | 无法用全量 type-check 作为移动端发布门禁 | 修复 API 生成物与 Vite 环境类型；当前按错误路径确认订单确认页未新增类型错误 |

## P2：维护风险

| 问题 | 影响 | 处理策略 |
|---|---|---|
| Boot/Cloud 双套 SQL 与配置 | 新表或字段容易只更新一种形态 | 每个数据需求验收同时列 Boot/Cloud 迁移 |
| `xxl-job-3.2.0` 上游源码在根目录 | 全仓扫描噪音、误修改、升级责任不清 | 明确 vendor 策略；商城需求默认不改该目录 |
| 构建产物存在于本地 | 静态工具可能扫描 `target/classes` 造成重复节点 | 图谱配置排除 target，结论以源码为准 |
| UA 语义图尚未生成 | 暂无 architecture dashboard/tour | 重启 Codex 后运行 `$understand ... --language zh` |

## 当前没有独立后端模块的功能

- 管理端 `home` 是跨 user/order/product/promotion 的统计聚合，不存在独立 `aryn-home` 服务。
- 商品品牌、独立仓库/库存服务未在当前模块和核心表中发现；若需求涉及这些能力，先确认是否有未提供仓库或计划新增完整业务切片。
- XXL-JOB Admin 不是 `aryn-boot` 内置模块，需要独立部署或使用外部调度服务。

## 已建立的租户隔离门禁

- Boot 白名单与 62 张含 `tenant_id` 的业务表一致，各 Nacos 微服务配置与本服务 schema 子集一致。
- `TenantSchemaValidator` 启动时双向检查缺配表和误配表，空白名单也会失败；白名单变更需重启，不能通过 Nacos 热刷新绕过校验。
- 仓库测试校验 Boot/Cloud SQL、Nacos 内容及 MD5，并固定允许的租户拦截绕过点。
- 登录前按用户名、手机号和 `app_id` 定位租户依赖有效记录全局唯一的 MySQL 8.0.13+ 函数索引；逻辑删除后允许复用，存量库执行迁移前必须先处理检查结果中的重复有效记录。

## 已建立的会员安全门禁

- C 端资料修改只接受显式 DTO 并绑定 token 用户，管理端会员、等级、权益和标签接口显式鉴权，响应与分页 SQL 不再暴露密码。
- 积分、余额、累计消费和等级更新使用带租户及余额约束的原子 SQL；账变异常向上抛出并由事务回滚。
- 会员折扣、优惠券、免邮和积分倍率在下单及订单完成链路中按固定顺序处理，订单成长和专属券发放均有数据库唯一键幂等兜底。
- Boot 与 Cloud 的会员表、订单字段、优惠券来源字段、关系唯一键和租户白名单已同步；后续变更必须同时维护两种部署形态。

## 已建立的菜单种子门禁

- 菜单管理树接口返回原始数组，管理端包装为 `{ list }` 后必须同时配置 `proxyConfig.response.list`；该页关闭 VXE 封装的早期自动加载，并在挂载后显式查询，避免首次进入为空、手动刷新后才显示。
- Boot/Cloud 独立会员菜单脚本均显式使用 `SET NAMES utf8mb4`；存量乱码按确定菜单 ID 覆盖中文名称，不依赖错误文本反解。
- Boot/Cloud 同步维护会员与拼团菜单，契约测试固定 9 条拼团菜单 ID，并检查两种模式均存在幂等修复迁移。
- 动态菜单同时受 `sys_role_menu` 和普通租户的 `sys_tenant_menu` 过滤；新增菜单必须同步补齐管理员角色与非平台租户授权。

## 已建立的购物车与下单门禁

- C 端购物车、订单、订单项、退款、地址和物流详情均绑定 token 用户；客户端不能通过 ID 或订单号读取、修改、支付、取消、删除或确认他人数据。
- 购物车写入只接受 SKU 与数量，服务端刷新商品快照并校验在售/库存；有效 SKU 唯一键兜底并发新增，下单仅按已购 SKU 清理。
- 下单使用 `requestId` 和数据库唯一键防止重复建单；库存按足量条件原子扣减，优惠券按持有人、状态、有效期原子冻结并绑定订单。
- 创建、取消和跨服务库存/优惠券操作纳入 Seata 全局事务；支付、取消、收货使用状态条件更新，事务后才发送延迟取消或完成通知。
- 延迟取消、支付后商品处理、订单任务和物流回调均清理租户上下文；物流回调不再覆盖订单关联。Boot/Cloud 基础结构和 16 号存量迁移保持同步。
- 订单评价校验当前用户和完整订单项集合，服务端覆盖订单、商品和用户标识；商品域已关闭可绕过订单校验的直接写入口，17 号迁移用有效订单项唯一键阻止重复评价。
- 商品支付消费者用 `(tenant_id, order_id)` 唯一消费记录实现持久化幂等，记录插入与销量累加共用本地事务；重复投递不会再次增加销量，失败消息可重试。

## 处理原则

- “前端已有 API”不代表后端运行态已覆盖；先确认路径改写、Controller、权限和 SQL。
- 缺少整个业务域时，先找缺失仓库/分支并询问用户；确认需要新建后再实现端到端切片。
- 风险修复应单独建需求包，尤其是租户隔离和凭证迁移，不要夹带在普通 UI 需求中。
