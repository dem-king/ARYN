# 分销资金链路加固设计

## 背景

当前分销模块已覆盖分享归因、佣金、退款和提现，但支付后立即把佣金计入可提现余额，退款缺少二级回退与幂等，提现审核没有打款凭证，配置、租户上下文和移动端契约也存在缺口。本次修复以资金正确性和可审计性为优先，不接入仓库中不存在的外部商户转账 SDK。

## 已确认规则

- 佣金基数为商品实付金额，不包含运费。
- 支付后佣金先进入待结算余额，达到租户配置的结算周期后才进入可提现余额。
- 一级和二级佣金使用同一订单佣金基数，分别按配置比例计算。
- 退款按退款单幂等处理，同时回退一级、二级佣金；部分退款按可佣金退款金额占原佣金基数的比例回退。
- 已提现佣金发生退款时不能静默吞掉差额，差额进入佣金欠款，后续收入优先抵扣欠款。
- 提现采用线下打款确认：管理员完成真实打款后，填写唯一打款流水号确认；系统不伪造自动转账。

## 数据设计

### 分销用户

`distribution_user` 增加 `pending_commission` 和 `commission_debt`。待结算订单增加前者；到期结算时减少前者并增加可提现余额。退款后可提现余额不足的部分增加欠款，后续结算先抵扣欠款。有效用户唯一性改为租户内仅约束 `del_flag = '0'` 的记录，使逻辑删除后可以重新注册。

### 分销订单与退款

`distribution_order` 保存订单实付金额、运费、佣金基数、累计退款基数、累计退款佣金和计划结算时间。一级、二级记录使用相同业务订单号和不同佣金层级，通过租户、订单号、层级的联合唯一键保证幂等。

新增 `distribution_refund_record`，以租户和退款业务号唯一，保存订单号、退款佣金基数、应用状态和处理时间。退款事件由订单域显式携带不含运费的退款基数，分销域不再猜测运费口径；退款先到时由支付落单和定时任务重放。

### 提现

`distribution_withdraw` 增加 `payout_no`、`payout_time`、`payout_by`。通过状态 `1` 表示已完成线下打款并确认，确认时打款流水号必填且租户内唯一。收款账号使用环境变量 `DISTRIBUTION_WITHDRAW_ACCOUNT_KEY` 提供的 Base64 AES-256-GCM 密钥加密存储；列表和详情都只返回脱敏账号，历史明文由审核权限下的幂等接口逐租户重加密。

## 服务流程

1. 支付成功事件计算 `commissionBaseAmount = max(paymentPrice - freightPrice, 0)`，创建待结算的一、二级分销订单并增加待结算余额。
2. 定时任务按每笔订单的 `settle_at` 处理，不再硬编码 7 天。手工结算只接受分销订单 ID，不接受前端金额。
3. 到期结算按订单佣金余额入账；若用户存在欠款，先抵扣欠款，再增加可提现余额并写流水。
4. 退款事件以退款单号防重。待结算订单减少待结算余额；已结算订单减少累计佣金和可提现余额，不足部分转欠款。
5. MQ 处理失败必须向上抛出以触发重试，租户上下文始终在 `finally` 中清理。
6. 启用配置通过服务层统一切换，服务端校验比例、合计比例、提现门槛和结算周期，并由数据库生成列唯一键保证租户内单启用。
7. 有余额、欠款、待结算订单、待审核提现或下级的分销用户禁止删除；删除校验使用行锁，叶子删除回补上级计数，邀请链禁止成环。

## 前端设计

- 管理端配置补齐二级佣金比例和结算周期，使用明确类型并提交服务端校验。
- 管理端手工结算不再输入金额；提现通过时必须输入打款流水号，列表展示脱敏账号。
- UniApp 分销中心使用单个页面滚动容器，佣金和提现记录分别显式请求；流水按 `INCOME/EXPENSE` 显示正负号，展示待结算、欠款、邀请人数和提现状态。
- 页面仍为单路由视图，本轮不新增复杂组件树；数据请求和金额显示提取为小型纯函数，便于单测。

## 验证

- Java 单测覆盖佣金基数、待结算、到期结算、二级退款、退款幂等、欠款抵扣、配置约束、提现确认、用户删除约束和租户上下文清理。
- SQL 契约测试覆盖 Boot/Cloud/模块初始化脚本字段与唯一键一致性。
- Vitest 覆盖管理端请求契约和 UniApp 金额/状态格式化；UniApp 运行类型检查。
- 最终运行 promotion 聚焦测试、Boot 租户一致性测试、管理端单测/类型检查/lint、UniApp 类型检查及后端编译。
