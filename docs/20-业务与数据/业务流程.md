# 业务流程

> 证据：订单/营销/消息 Controller、Service、Job、MQ 处理器和三端页面；检查于 2026-09-06；置信度：已验证（静态流程），运行态未知。

## 角色

| 角色 | 使用端 | 主要动作 |
|---|---|---|
| 平台管理员 | 管理后台 | 租户、套餐、公共菜单、平台配置 |
| 租户管理员/运营 | 管理后台 | 商品、订单、会员、营销、页面装修、支付配置 |
| 消费者 | UniApp/H5/小程序 | 浏览商品、领券、下单、支付、售后、会员互动 |
| 分销员 | UniApp | 推广、查看佣金、申请提现 |
| 配送员 | UniApp 内配送页面 | 配货、出车、送达、上传凭证、上报异常 |
| 定时任务 | XXL-JOB -> 业务服务 | 订单关闭、优惠券过期、拼团过期、分销结算 |

## 认证与租户

```text
管理端 -> /auth/token/* -> ToB token -> /upms/menu -> 动态路由
消费者 -> /auth/toc-token/* -> ToC token -> /app/* 业务接口

每次请求：tenant-id + satoken -> TenantContextFilter -> MyBatis TenantLineHandler
跨服务：tenantId 通过 Dubbo attachment 传播
```

平台管理员可通过管理端 `switch-tenant-id` 覆盖请求头；普通用户以 token 中的租户为准。新增表若未加入 `hx.tenant.tables`，MyBatis 会跳过租户条件。

## 商品到订单

```text
运营维护 SPU/SKU/分类/库存
  -> C 端读取商品与营销可用性
  -> 加入 shopping_cart
  -> 订单结算（价格、库存、优惠）
  -> 创建 order_info + order_item
  -> 发起 pay_trade_order
```

订单创建涉及商品、优惠券、会员和支付边界；单体模式可本地注入，微服务模式通过 `*-api` Remote Service/Dubbo。多表写入与库存/券核销必须保持事务或补偿一致性。

## 支付与退款

```text
订单待支付 -> 创建支付交易 -> 第三方支付
  -> 异步回调写通知记录（必须幂等）
  -> 订单变为待发货

售后申请 -> 订单退款审核 -> 支付域退款
  -> pay_refund_order -> order_refund 状态更新
```

回调以支付平台交易号和业务订单号防重；任何状态更新都要验证重复回调、超时和部分失败。

## 履约与售后

```text
待发货 -> 商家发货 -> 配送单/物流轨迹 -> 用户确认 -> 已完成
                 |-> 未发货仅退款 / 已发货退货退款
```

定时关闭待支付订单、确认收货等任务需要逐租户设置上下文，并在每次循环后清理。

### 商城自配送

```text
订单支付 -> 幂等创建 delivery_task -> 管理员批量派单并生成 delivery_trip
  -> 配送员逐项配货 -> 出发 -> 送达/异常 -> 用户签收或售后退回
```

出车单收车口径：任务进入**结清状态（5已送达 / 6已签收 / 7已取消）**且该出车单已无其他未结清任务时，出车单即置为 `4已完成`（`completeIfAllTasksSettled`，送达、签收、取消、退款自动关闭、退回确认、关闭异常六条路径都会触发）。**已送达即结清**——客户签收是订单域事实，不再决定司机的出车单是否结束；否则客户不点确认收货时，工作台「当前出车单」会永远停在「配送中」。`8异常`、`9待退回`不算结清：异常等管理员改派或关闭，退回等管理员确认商品回仓（转 7已取消）后才收车。

配送任务与订单状态分离，事实表在订单域；提醒、WebSocket 和微信订阅消息不应成为状态事实来源。配送工作台页面位于现有 UniApp，请求统一使用 `/mall-order/app/delivery/**` 首段（`VITE_OPEN_BOOT=true` 时由 `rewriteBootUrl` 改写为 `/boot/app/...`）。

配送员入口由资格体系控制：`delivery_account_binding` 绑定商城账号与员工账号，认证服务结合绑定状态、员工账号与 UPMS 配送角色判定资格（ACTIVE/UNBOUND/PERMISSION_MISSING/ACCOUNT_DISABLED/STAFF_INVALID），C 端可凭商城登录态免密换取独立 `deliveryToken`。角色的授予与回收走 `delivery_qualification_operation` outbox 表，失败由 `DeliveryQualificationRetryJob` 按指数退避补偿重试。

## 会员

- 消费、签到、注册等产生积分或成长值记录。
- 会员等级与权益是配置 + 关系表，不要只改等级主表。
- 余额充值跨用户、支付与订单域，必须校验支付回调幂等和账变流水。
- 会员相关表均含 `tenant_id`，当前租户表配置缺失是上线前阻断项。

### 积分闭环（发放 / 抵现 / 返还）

> 2026-10-22 积分闭环落地后固化；代码见 `PointsGrantServiceImpl` /
> `OrderPriceComputeService#orderPointsDeductHandler` / `RemotePointsServiceImpl`。

```text
注册 / 订单完成 / 签到 / 充值赠送
  -> IPointsGrantService#grant 读 points_config（trigger_scene + rule_type）
  -> points_record 落账（biz_no 租户内唯一，MQ 重投/并发幂等）
  -> user_info.point += N（total_point 仅在真实获得时增加）

下单 / 结算
  -> 活动价商品不参与会员折扣（PromotionPricePlan 命中即跳过）
  -> 会员折扣 -> 优惠券 -> 整船优惠 -> 运费 -> 积分抵现
  -> 抵现基数=商品应付（不含运费），单笔上限 20%，points_per_yuan 默认 100
  -> order_info.points_used / points_deduct_price
  -> order_item.points_price 按商品应付占比分摊（Σ分摊 == 订单抵扣额）
  -> 订单创建链路最后一步扣减：ORDER_DEDUCT:订单号

取消 / 整单退款
  -> ORDER_REFUND:订单号 返还（与取消共用幂等键，只退一次）
  -> 只恢复 point，不加 total_point；部分退款不返还，整单全退才返还
```

- 仅海员个人购买（`purchaseScene=1`）可抵现；船供采购是 B 端成本价，禁用积分抵扣。
- 管理端只有 `REGISTER`/`ORDER_COMPLETE`/`ORDER_DEDUCT` 三个场景可配；配置缺失时订单完成回退 1 积分/元，配置禁用时一律不发放。
- cloud 模式通过 Seata 全局事务保证「订单 + 优惠券/营销预占 + 库存 + 积分」原子：`aryn-common-seata` 内置 Apache Dubbo 3 的 XID 透传过滤器（seata-all 2.5 只带 Alibaba Dubbo 过滤器），下单/取消/退款回调均为 `@GlobalTransactional`，order/user/promotion/product 已接入 Seata RM（对应库 `undo_log` 基线已存在）；boot 模式 `seata.enabled=false` 走本地事务，行为不变。

### 会员等级与权益（2026-10-24 收口）

- 等级：注册、积分变动、订单完成触发 `recalculateLevel`；0 门槛档保证新用户注册后即有等级。
- 权益：`member_benefit` + `member_benefit_level_rel`；类型 1 折扣 / 2 免邮 / 3 专属券 / 4 积分倍率，权益必须至少关联一个等级。
- 折扣不与活动价叠加：`PromotionPricePlan` 命中的 SKU 不参与会员折扣；免邮与积分倍率不受影响。
- 专属券：等级变化时发放；后台「补发」按钮给存量同级会员补发；保存时校验模板存在、启用且有余量。
- 会员启停用：`user_info.status`（0 启用 / 1 禁用）；禁用后 C 端登录拒绝并踢出 TOC 会话。
- 示例种子：`db/{boot,cloud}/158member_management_incremental.sql`（五档权益、7 天签到、三档充值）；只绑定默认租户，其他租户改 `@tenant_id` 重跑。
- 退款口径：部分退款不返还积分，整单全退才返还。

## 营销

- 优惠券：券模板 -> 适用商品 -> 用户领券 -> 结算锁定/核销/退回。
- 拼团：活动 -> 开团记录 -> 成员 -> 成团或过期任务。
- 秒杀：活动 -> 场次 -> SKU 库存预扣 -> 秒杀订单 -> 支付确认或超时/取消回滚；库存和订单状态由处理器与定时任务共同收敛。
- 折扣：活动 -> 全场/指定商品范围 -> C 端读取活动价 -> 订单远程计价；活动状态由定时任务推进。
- 分销：用户绑定 -> 支付创建待结算佣金 -> 到期释放 -> 提现申请冻结 -> 线下打款确认；退款按退款号幂等回退两级佣金。
- 页面装修：管理端拖拽组件配置 -> `page_design` JSON -> C 端 `diy-*` 组件渲染。

### 船供营销计价与分摊口径

> 2026-10-14 船供活动治理落地后固化；代码见 `OrderPriceComputeService` /
> `PromotionEngineServiceImpl` / `PromotionReservationServiceImpl`。

- 计价顺序：阶梯价/新人价先改 SKU 成交基价（会员折扣与优惠券之前）-> 促销价链
  （拼团 > 秒杀 > 新人价 > 限时折扣 > 原价，限时折扣对新人价 SKU 跳过）-> 会员折扣
  -> 优惠券 -> 整船/整单优惠分摊 -> 运费。券与会员折扣必须基于促销后金额计算。
- 阶梯价门槛口径：「满 N 件」按**整单同 SKU 合计数量**判定（共享购物车按成员拆行后
  先按 SKU 聚合再交引擎）；档价仅对配置了 skuLadders 的 SKU 生效，未配档 SKU 不改价。
- 整船优惠口径：**已享活动价（拼团/秒杀/新人价/阶梯价/限时折扣）的 SKU 既不计入门槛、
  也不参与分摊**；分摊基数 = Σ(参与明细 totalPrice − 会员折扣)，**不含优惠券抵扣**；
  按各明细基数占比分摊（保留 2 位），尾差按分补给余数最大的明细；单明细 promo
  不超过该明细基数；`computeItemPayPrice` 单明细实付封 0（无整单底价配置）。
  营销试算与订单分摊共用同一份活动价计划（`PromotionPricePlan`），保证门槛与成交价同源。
  对账时 promoPrice 合计 = 整船优惠命中金额（被封顶时等于可折基数）。
- 买赠：赠品追加为 0 元独立明细（与付费明细同 SKU 时并存），按真实库存校验，
  库存不足不赠且不阻断付费商品；结算页 giftItems 与提交同口径。
- 叠加关系固定：单价类（拼团/秒杀/新人价/阶梯价/限时折扣）同 SKU 互斥；
  整船优惠只对未享活动价的明细生效，不再二次折活动价商品；买赠独立。
  `stackable` 字段废弃不暴露。
- 额度熔断：预算在 `promotion_activity.consumed_budget` 上原子扣减（reserve 条件 UPDATE，
  并发不超卖），取消/超时释放按锁金额归还；预算/每人限享/赠品额度不足时 `preview`
  剔除该活动并重算，确认页与下单价格一致，订单按其余优惠或原价成交，不再整单拦截；
  赠品仅降级为不赠，不影响付费商品。竞态窗口由 reserve 兜底：预算/每人限享冲突返回
  「刷新价格后重新提交」，赠品不足降级不赠。释放失败由 `promotionLockCompensateJobHandler`
  扫近 7 天已取消订单幂等补释放。

### 分销资金链路

```text
订单支付
  -> 佣金基数 = 实付金额 - 运费
  -> 按一级/二级比例创建 distribution_order（待结算）
  -> 增加 pending_commission
  -> settle_at 到期任务或按分销订单 ID 手工结算
  -> 先抵扣 commission_debt，再释放 available_commission

订单退款
  -> 退款事件携带 refund_no 与不含运费退款基数
  -> distribution_refund_record 按退款号幂等，未匹配到佣金订单时保留未应用状态
  -> 支付落单或逐租户定时任务按退款记录独立事务重放未应用退款
  -> 同时累计回退一级/二级佣金
  -> 待结算余额不足扣可提现余额，仍不足则形成 commission_debt

提现
  -> 申请时可提现转冻结，收款账号 AES-256-GCM 加密落库，选填备注同步保存
  -> 审核拒绝：冻结退回可提现
  -> 审核通过：必填线下打款流水号，扣冻结并累计已提现
```

支付和退款状态必须在事务内完整更新，成功 MQ 在事务提交后发送；监听器必须在 `finally` 清理租户上下文，处理异常必须向 RocketMQ 抛出以触发重试。退款先于支付到达时先保存退款事实，支付创建佣金订单后再重放，不能丢弃事件。定时任务按租户、退款记录和佣金订单分别捕获异常，单条坏数据不得阻塞后续处理。

历史明文提现账号上线后由管理员逐租户调用 `POST /distribution/withdraw/reencrypt-legacy-accounts` 重加密。接口复用提现审核权限，只处理不带 `v1:` 前缀的记录，因此可重复执行。
