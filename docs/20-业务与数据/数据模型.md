# 数据模型

## 通用字段规则

业务表通常使用 `id`、`tenant_id`、创建/更新时间与 `del_flag`。实际 Entity 并不完全继承同一个基类，新增或修改字段前必须同时核对 Java Entity、Mapper XML 和 Boot/Cloud 两套 SQL。

逻辑删除约定为 `del_flag`：`0` 正常、`1` 删除。不得用物理删除替代业务删除，除非表定义和业务明确要求。

## 核心表分组

| 域 | 核心表 | 关键关系/状态 |
|---|---|---|
| 权限租户 | `sys_user`、`sys_role`、`sys_menu`、`sys_user_role`、`sys_role_menu`、`sys_tenant*` | 用户 -> 角色 -> 菜单；租户套餐限制菜单 |
| C 端用户 | `user_info`、`user_address`、`social_account`、`social_user` | 用户与地址一对多；社交账号用于多平台登录 |
| 会员 | `member_level*`、`member_benefit*`、`member_tag`、`user_tag_rel`、`member_order_growth` | 等级/权益/标签均有关系表；订单成长按租户和订单幂等 |
| 积分签到 | `points_config/record`、`sign_in_config/record` | 配置决定发放规则，record 是审计依据 |
| 余额充值 | `balance_record`、`recharge_config`、`recharge_order` | 余额变更必须有流水；充值订单关联支付 |
| 商品 | `goods_spu`、`goods_sku`、`goods_category`、`goods_specs*` | SPU 一对多 SKU；规格值组合决定 SKU |
| 用户商品行为 | `goods_appraise`、`goods_collect`、`goods_footprint` | 评价/收藏/足迹按用户和商品关联 |
| 订单 | `shopping_cart`、`order_info`、`order_item`、`order_delivery*`、`order_refund`、`order_config` | 主单一对多明细；配送/退款独立状态 |
| 支付 | `pay_config`、`pay_trade_order`、`pay_notify_record`、`pay_refund_order` | 交易、回调和退款分表，需幂等 |
| 优惠券 | `coupon_info`、`coupon_goods`、`coupon_user` | 模板 -> 商品范围 -> 用户券 |
| 页面装修 | `page_design`、`page_design_version`、`page_design_template` | 页面身份与可变草稿、不可变发布快照、租户/系统模板 |
| 拼团 | `group_buy_activity`、`group_buy_record`、`group_buy_member` | 活动 -> 团记录 -> 成员 |
| 分销 | `distribution_config/user/order/commission_flow/withdraw/refund_record` | 分销关系、待结算佣金、退款回退、欠款、提现与打款确认 |
| 消息中心 | `message_notice/recipient/dispatch_task/conversation/participant/chat/agent/assignment_log` | 通知与收件状态分离；客服/工作人员会话、已读游标、坐席负载和分配审计 |
| 调度 | `xxl_job_*` | XXL-JOB Admin 自有表 |
| 配置/生成 | `config_info*`、`gen_*` | Nacos 与代码生成器，不是商城交易数据 |

## 数据库形态

- 单体：主要表合并到 `aryn_boot`，脚本位于 `db/boot/`。
- 微服务：按 `aryn_upms/user/order/pay/product/promotion/message` 等库拆分，脚本位于 `db/cloud/`。
- 新迁移必须同时维护两种形态；会员管理加固使用 `14member_management_hardening.sql`，页面装修依次使用 `10page_design_alter.sql`（页面类型）和 `11page_design_publish.sql`（草稿修订、发布版本与模板）。

商品品牌由 `19product_brand.sql` 维护：创建 `goods_brand`、为 `goods_spu` 增加可空 `brand_id` 与 `(tenant_id, brand_id)` 索引，并统一关键字符列为 `utf8mb4_general_ci`。Cloud 环境必须对 `aryn_product` 执行该迁移；仅部署包含 `brandId` 的新商品服务代码而未迁移数据库，会导致商品列表查询报 `Unknown column 'brand_id'`。

## 消息中心模型

- `message_notice` 保存通知事实、来源幂等键、受众快照、安全业务卡片和端内跳转参数；`message_recipient` 单独保存每位收件人的已读与隐藏状态，群发重试依靠收件人唯一键去重。
- `message_dispatch_task` 按目标身份空间保存游标和执行计数，XXL-JOB 可恢复中断任务；通知撤回只改变可见状态，不物理删除历史。
- `message_conversation` 通过生成列唯一键限制会员默认客服池及工作人员组合的活跃会话；`message_participant.last_read_seq` 与 `message_chat.seq_no` 共同形成会话未读游标。
- `message_chat` 以 `(tenant_id, conversation_id, seq_no)` 保证会话内顺序，以 `(tenant_id, sender_type, sender_id, client_message_id)` 保证发送重试幂等。
- `message_agent` 保存接待边界和负载快照，在线/忙碌/暂停状态在 Redis 中带 TTL；`message_assignment_log` 保存自动分配、领取、转交、关闭与重开审计。
- 订单创建、支付、退款和领券通知通过 RocketMQ `MessageSendCommand` 接入，`source_type + source_key` 与收件人唯一键形成双重幂等；交易域发送失败只记录日志，不回滚核心交易。

## 会员成长与权益模型

- `user_info.point` 是当前可用积分，`total_point` 是只增不减的累计获得积分；等级升级读取 `total_point`，消费积分不会导致降级。
- `member_order_growth` 以 `(tenant_id, order_id)` 唯一，记录订单完成时的实付商品金额和发放积分，防止 MQ 重投导致重复累计消费或积分。
- `member_benefit_level_rel` 和 `user_tag_rel` 均有租户内唯一约束；删除等级、权益、标签或用户时同步清理关系数据。
- 同等级的折扣权益取最小折扣值，积分倍率取最大值，免邮权益任一生效即将运费置零；折扣值范围为 `(0, 1]`，积分倍率不得小于 `1`。
- `order_info` 固化会员优惠总额和积分倍率，`order_item` 固化各明细会员优惠额。价格顺序固定为“会员折扣 -> 优惠券 -> 运费/免邮”，优惠券门槛和分摊都基于会员折扣后金额。
- 专属优惠券权益的 `benefit_value` 保存优惠券模板 ID。`coupon_user` 使用 `(tenant_id, user_id, source_type, source_id)` 唯一键保证首次进入等级时幂等发券，`source_id` 记录“等级 ID:权益 ID”。

## 页面装修版本模型

- `page_design.page_content` 保存可变草稿，`draft_revision` 用于乐观锁；保存草稿不改变公开页面。
- `page_design.published_version_id` 指向当前线上快照，`published_status/published_at` 表达发布状态，不直接复制草稿状态。
- `page_design_version` 是不可变快照，租户内 `(tenant_id, page_design_id, version_no)` 唯一；回滚会从历史快照创建新的版本号，不覆盖旧记录。
- `page_design_template` 保存系统或租户模板，只复制装修配置；应用模板时重新生成组件 ID，不复制商品、活动等业务记录。
- v2 文档根字段为 `schemaVersion/page/components`，组件字段为 `id/type/version/props`。旧 `{components, formData}` 在读取时转换，第一次保存后升级，原 JSON 保存在 `legacy_content_backup`。

迁移时先执行 `10page_design_alter.sql`，再执行 `11page_design_publish.sql`。后者会备份旧内容、为当前有效页面生成版本 1 并切换发布指针。回退应用版本时仍可用 `legacy_content_backup` 恢复旧编辑器数据；数据库结构回退前必须先保留版本与模板表数据，禁止直接删表。

## 购物车与订单一致性模型

- `shopping_cart.active_sku_id` 仅在 `del_flag = '0'` 时映射 `sku_id`，通过 `(tenant_id, user_id, active_sku_id)` 唯一键保证同一用户只有一条有效 SKU 记录，同时允许逻辑删除后重新加入。
- 购物车名称、价格、图片、SPU 和规格均由商品服务生成快照；新增、修改数量和切换规格都会重新校验在售 SKU 与实时库存，客户端快照不作为写入依据。
- `order_info.request_id` 是客户端下单幂等号，租户内 `(tenant_id, user_id, request_id)` 唯一；`order_no` 同样按租户唯一。新版 UniApp 在确认页生命周期内复用同一个请求号，旧客户端未传时后端生成随机值，只保证单次请求可用。
- 订单、订单项、购物车清理、SKU/SPU 库存和用户券占用由 Seata 全局事务协调。库存使用 `stock >= quantity` 条件扣减，重复 SKU/SPU 先聚合；用户券从待使用原子切换为冻结并绑定 `order_id`，取消时只释放该订单绑定的券。
- 取消、支付和收货均使用“当前状态 + 支付状态”的条件更新，禁止无条件覆盖并发状态。下单延迟取消消息在事务提交后发送，定时扫描继续作为消息投递失败的兜底。
- 订单、订单项、退款单、地址和物流详情的 C 端查询必须绑定 token 用户；物流回调不得修改 `order_delivery.order_id`，并必须在 `finally` 清理租户上下文。
- 订单评价只接受属于当前订单的完整订单项集合，`order_id`、`spu_id` 和 `user_id` 均由服务端订单快照覆盖；商品模块不再提供绕过订单校验的 C 端评价写入口。`goods_appraise.active_order_item_id` 仅映射未删除评价，并通过 `(tenant_id, active_order_item_id)` 唯一键阻止同一订单项重复评价。
- 商品服务使用 `product_order_pay_record` 按 `(tenant_id, order_id)` 记录支付消息消费结果；消费记录插入和 SPU 销量累加在同一本地事务中，重复投递直接跳过，异常会整体回滚并允许 RocketMQ 重试。
- 商品退款库存恢复使用 `product_refund_stock_record` 按 `(tenant_id, refund_no)` 记录消费结果；消费记录与 SKU/SPU 库存恢复处于同一本地事务，重复退款消息直接跳过。SKU 库存变化同步递增 `version`，管理端编辑必须携带版本并按库存差值原子更新 SPU，禁止用旧表单库存覆盖并发订单结果。

空库结构已写入 Boot/Cloud 基础 SQL；存量库按编号执行 `16order_checkout_hardening.sql`、`17order_appraise_hardening.sql`、`18product_pay_consumer_idempotency.sql` 和 `19product_refund_stock_idempotency.sql`。迁移会回填历史 `request_id`、逻辑删除重复有效购物车和评价、规范 SKU 版本列，并建立商品支付及退款库存消费记录表，生产执行前必须在 MySQL 8 克隆库核对重复数据和受影响行数。

## 分销资金模型

- `distribution_order.commission_base_amount` 是不含运费的佣金基数；新订单按 `payment_price - freight_price` 计算，历史值保持 `NULL`，不得用含运费订单额反填。
- 支付后佣金先进入 `distribution_user.pending_commission`，并由 `settle_at` 控制释放时间。到期或受控手工结算后才增加 `available_commission`；释放时先抵扣 `commission_debt`。
- 一级、二级佣金共享业务订单号，通过 `commission_level` 区分，租户内 `(tenant_id, biz_order_id, commission_level)` 唯一。
- `distribution_refund_record` 按租户和退款号唯一，记录含运费退款额、不含运费退款基数及 `applied/applied_time`。未应用记录由支付落单和定时任务重放，定时重放每条使用独立新事务；部分退款累计回退不超过原佣金，余额不足的回退差额进入 `commission_debt`。
- `distribution_withdraw.account_no` 保存带 `v1:` 版本前缀的 AES-256-GCM 密文，密钥来自 `DISTRIBUTION_WITHDRAW_ACCOUNT_KEY`（Base64 编码的 32 字节密钥）；API 只返回脱敏账号。
- 提现通过必须写入租户内唯一的 `payout_no`，同时记录 `payout_time/payout_by`；拒绝时冻结金额退回可提现余额。
- `distribution_config.active_config_key` 只为未删除的启用配置生成，通过 `(tenant_id, active_config_key)` 唯一键保证单租户仅一条启用配置。
- `distribution_user.active_user_id` 只为未删除记录生成，保证同租户有效用户唯一，同时允许逻辑删除后重新注册。有可提现、待结算、冻结、欠款、待审核提现、真实有效下级或状态为待结算/已结算的可退款佣金订单时禁止删除；存量迁移重算下级数，删除叶子用户时递减上级计数，邀请链禁止成环。

## 多租户约束

`ArynTenantLineHandler.ignoreTable()` 只对 `hx.tenant.tables` 中的表注入租户条件。Boot 覆盖含 `tenant_id` 的业务表全集，并包含 8 张消息表；各微服务只配置本库子集，旧表名已从白名单移除。

`TenantSchemaValidator` 默认在启动时读取 JDBC 元数据并双向校验：数据库含 `tenant_id` 但未配置会形成隔离缺口，配置表没有 `tenant_id` 会生成错误 SQL，两种情况都拒绝启动；启用校验时空白名单同样失败。租户白名单不支持热刷新，Nacos 修改后必须重启并重新校验。代码生成器没有租户表，因此显式设置 `validate-schema: false`。

登录前的用户名、手机号、社交账号 `app_id` 和支付配置 `app_id` 查询需要跨租户定位，因此依赖有效记录全局唯一的函数索引。逻辑删除记录按主键区分，允许标识后续复用。该索引要求 MySQL 8.0.13+；存量数据库执行 `db/*/12tenant_lookup_uniqueness.sql` 前必须先处理有效记录的重复检查结果，禁止自动删除或合并业务数据。

## 易混淆点

- `sys_user` 是后台用户，`user_info` 是 C 端用户。
- `pay_trade_order` 是支付交易，不等同于 `order_info` 商城订单。
- `order_refund` 表达商城售后，`pay_refund_order` 表达支付渠道退款。
- `coupon_info` 是券模板，`coupon_user` 是用户持有的券。
- `group_buy_record` 是一场团，`group_buy_member` 是参团成员。
- Nacos 的 `tenant_info` 与商城 `sys_tenant` 不是同一个租户模型。
