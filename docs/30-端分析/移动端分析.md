# 移动端分析

## 定位与技术栈

`aryn-mall-uniapp` 是 C 端商城，支持 H5、App 和多类小程序。核心技术为 UniApp、Vue 3、TypeScript、Alova、Pinia、uni-mini-router、Wot Design Uni 和 UnoCSS。

## 入口与分层

| 位置 | 作用 |
|---|---|
| `src/main.ts`、`src/App.vue` | 应用启动和生命周期 |
| `src/pages.json` | 主包、分包、tabBar 和页面元数据 |
| `src/pages/` | home、login 等主包页面 |
| `src/sub-pages/` | order、product、promotion、user 等业务分包 |
| `src/api/` | Alova core + distribution/order/pay/product/promotion/message/upms/user |
| `src/store/` | 认证、字典、商品、搜索历史、购物车、用户状态 |
| `src/components/` | 通用组件和 `diy-*` 页面装修渲染器 |

移动端已增加消息 API、Pinia 状态、通知列表/详情、客服聊天、消息气泡和业务卡片组件，并补充消息合并、游标与装修客服链接的 Vitest 回归。

## 请求链路

`src/api/core/instance.ts` 创建 Alova 实例：

- Base URL 来自 `VITE_API_BASE_URL`。
- 每次请求加入 `tenant-id`。
- 登录后加入 `satoken`，可通过 `skipToken` 跳过。
- 按平台加入 `platform-type`；微信小程序额外加入 `app-id`。
- `VITE_OPEN_BOOT=true` 时将业务域前缀改写为 `/boot`。
- 统一处理业务 code、token 失效和错误提示。

上传走 `uni.uploadFile`，需要单独保持相同的 base URL、tenant/token header 和 Boot 路径改写，不能只修改 Alova 拦截器。

## 页面与状态

- TabBar 和主包以 `src/pages.json` 为准，不要仅按文件目录判断是否可访问。
- `authStore.ts` 管理登录、token 和多种登录方式；持久化逻辑在 `persist.ts`。
- `shoppingCartStore.ts` 与订单 API 共同决定购物车状态，修改时检查登录前后同步。
- 首页装修由后端 `page_design` 配置驱动，`components/diy/index.vue` 负责按组件类型选择渲染器。

## 开发入口

UniApp 声明 Node `>=22`、pnpm 9.9.0。当前机器 Node 20 不满足，先切换运行时：

```powershell
cd aryn-mall-uniapp
pnpm install
pnpm dev:mp-weixin
pnpm type-check
pnpm test:unit
pnpm build:mp-weixin
```

`package.json` 当前提供 `test:unit`，仍没有 lint 脚本；微信小程序构建依赖原生可选包，缺失 binding 时需要修复依赖环境后重跑。

## 消息与客服

- 个人中心提供通知/客服入口和未读角标，消息分包位于 `src/sub-pages/message/`。
- 聊天支持文本、最多 6 张图片、商品/订单/退款/通知卡片与系统消息；断线期间仍可 HTTP 发送，重连后按最后 `seqNo` 补拉。
- 商品、订单和退款详情会把业务上下文作为服务端允许的卡片发送；`VITE_CUSTOMER_SERVICE_MODE` 可灰度回退微信原生客服。
- 装修 `customer-service` 链接统一解析为站内客服页，业务卡片点击只通过固定端内路由字段跳转。

## 已知风险

- 生产 `.env.production` 的 API 地址仍为 localhost，staging 仍是示例域名。
- `.env` 固定了默认租户 ID；不同商家部署或多租户 C 端需要明确租户解析策略。
- 业务页没有自动化测试，页面装修组件应至少做 H5 与微信小程序的手工/截图回归。
- 上传请求与普通 Alova 请求是两条链路，认证和路径改写容易漂移。
- 条件编译会产生平台差异；涉及登录、支付、分享和 app-id 的改动必须按目标平台验证。
