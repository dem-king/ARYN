# 需求来源与总览

## 原始请求

新增站内信功能，首期必须同时覆盖 C 端和后台工作人员两套收件箱，双方能够回复；客服会话使用共享客服池，自动分配优先，无可用客服时进入待领取池。

## 产品定位

本需求不是单一的公告 CRUD，而是由三部分组成的统一消息域：

1. **通知中心**：承载人工群发、系统通知和订单/支付/营销等业务通知。
2. **客服会话**：承载会员与客服的双向沟通、自动分配、领取、转交、关闭和重开。
3. **工作人员私信**：承载同租户工作人员之间的一对一沟通以及内部通知回复。

## 功能目标

- 提供会员和工作人员各自隔离的通知收件箱、未读数、详情、标记已读和隐藏能力。
- 支持按全部、指定对象、会员标签/等级、工作人员角色/部门进行群发。
- 支持 C 端发起客服会话，客服自动分配、手动领取、转交、关闭和主管介入。
- 支持客服主动联系会员，但不能绕过已有会话负责人或客服接待上限。
- 支持工作人员一对一私信，不进入客服池，也不占用客服负载。
- 支持实时推送、断线重连、离线补拉、发送幂等、会话内排序和已读游标。
- 支持商品、订单、退款和通知引用等结构化业务卡片。

## 非目标

- 不建设会员之间的社交私信。
- 不建设工作人员群聊、群成员管理和群公告。
- 不提供语音、视频、普通文件或富文本消息。
- 不允许一次操作跨全部租户群发。
- 不以 WebSocket、Redis 或 RocketMQ 作为消息事实来源。
- 不在首期引入专用 IM 产品、Elasticsearch、分库分表或事件溯源。

## 影响端

| 端/模块 | 主要影响 |
|---|---|
| Java 后端 | 新增消息 API/Biz、数据库、网关、Boot 聚合、WebSocket、群发任务、客服分配、业务事件接入 |
| 管理后台 | 通知管理、头部铃铛、客服工作台、工作人员私信、客服状态 |
| UniApp | 消息中心、通知详情、客服聊天、未读角标、商品/订单/退款客服入口 |
| UPMS | 工作人员受众查询、客服权限、部门/角色筛选、菜单与套餐权限 |
| 用户域 | 会员受众查询、会员标签/等级筛选、会员资料快照 |
| 订单/商品/营销/支付 | 业务卡片查询与业务通知事件 |

## 非功能目标

- 10,000 个同时在线 WebSocket 连接。
- 单租户最多 200 名在线客服。
- 峰值 200 条消息/秒。
- 普通 API p95 小于 200ms，消息写入 p95 小于 300ms。
- 正常实时推送延迟小于 1 秒。
- 单次群发支持 100,000 名收件人。
- 可用性目标 99.9%，消息历史默认保留两年。

## 关键约束

- 不同 biz 模块不得直接依赖实现模块，只能依赖 `*-api` 并通过 Dubbo 或 RocketMQ 通信。
- 所有消息表都包含 `tenant_id` 和 `del_flag`，并同步 Boot/Cloud 租户白名单。
- C 端与后台当前共用 Sa-Token `StpUtil`，但登录设备分别为 TOC/TOB；消息接口必须显式校验登录端类型。
- 管理端业务菜单由数据库动态下发，新增页面必须同步菜单、权限、套餐和存量租户授权策略。
- 当前工作树存在用户未提交修改，实施时必须只修改需求范围文件。
