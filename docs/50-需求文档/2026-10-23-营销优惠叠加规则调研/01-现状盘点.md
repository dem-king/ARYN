## 2. 价格计算链路（结算与下单同一顺序）

`OrderInfoServiceImpl.settlementOrder`（确认页，`:1117`）与 `createOrder`（提交，`:688` 起）使用同一套 handler：

```text
generateOrderItems（商品售价）
→ resolvePromotionPricePlan：拼团价 > 秒杀价 > 新人价 > 限时折扣 > 原价（OrderPriceComputeService:155-195）
→ applyPromotionLadder：阶梯价/新人价改基价、买赠（OrderInfoServiceImpl:747 / :1159）
→ applyPromotionPricePlan：落活动价（OrderPriceComputeService:119-143；OrderInfoServiceImpl:753 / :1163）
→ confirm order 金额汇总（computeOrderPrice:334-355）
→ orderMemberBenefitHandler 会员折扣（:537；OrderInfoServiceImpl:758 / :1168）
→ orderCouponHandler 优惠券（:559；OrderInfoServiceImpl:759 / :1169）
→ applyShipWholeDiscount 整船/整单优惠（:848；OrderInfoServiceImpl:761 / :1171）
→ 运费（orderFreightHandler:270）
→ orderPointsDeductHandler 积分抵现（:390；OrderInfoServiceImpl:797 / :1210）
→ expectedPaymentPrice 校验（OrderInfoServiceImpl:801-805）→ 落库
```

关键性质：

1. **活动价是「改基价」，不是「优惠行」**：`item.salesPrice` / `totalPrice` 被活动价直接覆盖
   （`OrderPriceComputeService.java:137-139`）。
2. **券的基数 = 活动价 - 会员折扣**：`verifyCoupon` 与 `discountedGoodsPrice` 都按 `totalPrice - memberDiscountPrice` 累计
   （`OrderPriceComputeService.java:630-648`）。
3. **积分基数是券后的商品应付**：`itemGoodsPayable = paymentPrice - freightPrice`（`:536`），
   且积分在**所有优惠之后、运费之后**计算。
4. 因此四类活动商品天然进入券/积分的计算范围——代码里没有任何「活动类型 → 是否可叠」的判断。

## 3. 活动价优先级与类型标记（可用于后续排除）

- 优先级：**拼团价 > 秒杀价 > 新人价 > 限时折扣 > 原价**
  （`OrderPriceComputeService.java:96-103` 注释 + `:119-143` 实现；秒杀可覆盖新人价）。
- 拼团价：由下单参数 `groupBuyRecordId` 反查，`resolveGroupBuyPrice` → `Map<skuId, price>`
  （`OrderInfoServiceImpl.java:1153` 附近；`OrderPriceComputeService.java:90-93`）。
- 秒杀价/折扣价：逐个 SKU 远程查询 `RemoteSeckillService.getSeckillPrice` / `RemoteDiscountService.calculatePrice`
  （`OrderPriceComputeService.java:197-222`）。
- 新人价：营销引擎 `PromotionCalculationVO.ladderOverrides` 中 `activityType = TYPE_NEWBIE_PRICE` 的 SKU 集合
  （`OrderPriceComputeService.newbiePriceSkuIds:724-735`）。
- **已有「活动价 SKU 集合」**：`PromotionPricePlan.activityPricedSkuIds`（`:229-241`），
  供整船优惠排除使用。缺的是「活动类型 + 活动是否允许叠加」的映射。

## 4. 优惠券现状

### 4.1 数据模型 [已实现]

- `CouponInfo.useRange`：`1.全部商品；2.指定商品`（`CouponInfo.java:77`），指定商品时 `spuId`（`:80`）+
  `CouponGoods` 明细；**没有「排除活动商品」「仅原价可用」字段**。
- 券类型：满减/折扣（`MallEventConstants.COUPON_TYPE_1/2`），门槛 `threshold`（`CouponInfo.java:49`）。
- 状态：未使用/已锁定/已使用等（`CouponUserStatusEnum`）。

### 4.2 券可用性判断分布 [已实现]

| 环节 | 位置 | 判断内容 |
|---|---|---|
| C 端弹层 | `CouponSelector.vue:40-67` | 前端按「门槛 ≤ 订单金额」「券指定 SPU 是否命中本单」置灰；**无活动维度** |
| 结算/下单后端 | `OrderPriceComputeService.orderCouponHandler:559-628` | 校验券持有、状态、有效期、门槛、使用范围；按明细比例分摊，单行不超过该行可折金额 |
| 券列表接口 | `AppCouponUserController.page:31-36` | 只按用户 + 状态查，**不接收订单/活动上下文** |
| 券列表字段（隐藏缺陷） | `CouponUserMapper.xml:12-16` 的 `pageResultMap` 只嵌套 `couponInfo`；`CouponInfo.couponGoodsList` 为 `@TableField(exist=false)`（`CouponInfo.java:118`），**接口不返回券适用商品明细**；而 `CouponSelector.vue:52` 用 `item.couponGoodsList` 判断 `useRange=2` | **指定商品券在确认页会被前端误判为「本单无可用商品」**（静态推断，待运行时验证）；新叠加规则不要依赖该字段 |
| 券列表服务端过滤（已有能力未用） | `CouponUserMapper.xml:85-90` `selectApiPage` 支持 `spuIds` 条件；`CouponUser.spuIds`（`CouponUser.java:90`）无 Java 调用方；确认页只传 `status`（`index.vue:327`） | 可复用该能力做「按本单商品过滤券」，无需新建接口 |

### 4.3 金额边界 [已实现]

- `couponTotalAmount = couponCompute(...).min(totalPrice)`（`:589`），券额不超过可折金额；
- 单行 `couponPrice = min(比例分摊, discountedItemPrice)`（`:604-610`）；
- `computeItemPayPrice` 对负值兜底为 0（`:356-367`）→ **不会出现负数**；
- 没有整单「最低实付 0.01 元」保护 → **可能出现 0 元单**（券额 = 可折金额时）；
  且系统支持 0 元单支付（`paymentPrice == 0` 走 `FREE_PAY`，`OrderInfoServiceImpl.java:1075-1077`）。
  折扣券没有「最高优惠金额」字段，理论上可把商品打到接近 0 元。

### 4.4 结论

券对四类活动商品**一视同仁**：只要券范围命中该 SPU、门槛用「活动价后金额」满足，即可使用。
不存在「活动商品不可用券」的代码路径。

## 5. 积分抵现现状

- 开关与比例：`points_config` 场景 `ORDER_DEDUCT`（`PointsGrantServiceImpl.getDeductContext:84-107`），
  每元所需积分 `pointsPerYuan` 可配，未配置则 `enabled=false`。
- 抵扣上限：商品应付的 **20%**（`MallOrderConstants.POINTS_DEDUCT_MAX_RATIO:50`）。
- 排除项：**仅船供采购**（`purchaseScene=2`）不支持（`OrderPriceComputeService.java:396-410`）；
  **没有任何活动维度排除**。
- 基数与顺序：会员折扣 → 券 → 整船优惠 → 运费 → 积分（`:390-490`），基数取 `itemGoodsPayable`（不含运费）。
- 严格模式：提交订单时 `strict=true`，请求额度与可用额度不一致直接拒绝（`:421-440`），
  防止确认页金额与实际扣款不一致。
- 分摊：按明细商品应付比例分摊到 `order_item.points_price`，尾差逐分补，保证 Σ = 订单抵扣额（`:500-535`）。
- 接口限制：`RemotePointsService.getDeductContext` 只收 `userId`（`RemotePointsService.java:15`），
  不带订单/活动上下文 → **活动维度的排除只能在 order 侧做**，用户域不需要改。
- 严格模式差异：结算 `strict=false`、提交 `strict=true`（`OrderInfoServiceImpl.java:797-799 / 1210-1212`）；
  船供采购在非严格模式下静默返回 0 额度（`OrderPriceComputeService.java:400-406`）。
- 会员折扣同样按**活动价后金额**计算（`OrderPriceComputeService.java:551`），且没有活动维度排除
  —— 即「活动价 → 会员折扣」当前也是叠加的。
  > 2026-10-25 复核修正：以上为 2026-10-23 盘点时的旧现状；2026-10-24 落地的叠加规则已收口为
  > **命中活动价的明细会员折扣恒为 0**（互斥，不再叠加），见 `docs/20-业务与数据/业务流程.md`「会员等级与权益」。
- 结论：**积分与券可以同时用**，四类活动商品照常参与积分计算。

## 9. 退款、分摊、快照现状

- 分摊粒度：券 → `order_item.coupon_price`；会员 → `member_discount_price`；整船 → `promo_price`；
  积分 → `order_item.points_price`（`OrderItemEntity.java:59-68`）；订单汇总字段在 `OrderInfo.java:70-93`。
- 退款：**只有整单全退**才退积分、恢复券（`ArynRefundListener.java:148-155` 全退分支；
  需求记录 2026-10-22 明确「部分退款不返积分」）；`order_item.points_price` 已落库
  （`db/boot/148points_closed_loop_incremental.sql:59-66`）但**退款链路未使用**逐行积分金额。
- 快照：`PromotionSnapshot` 只写营销引擎 `details` 的 9 个字段（`OrderInfoServiceImpl.java:866-883`），
  `priceBefore/priceAfter/appliedItemIds/giftItems` 均未赋值（`PromotionSnapshot.java:50-62`）；
  **秒杀/拼团/限时折扣没有引擎 detail → 不落快照**，券/积分也不落快照，只落订单字段。
- 结论：现有分摊机制可承载「按 SKU 排除」的改造，但**退款只处理整单全退**——若活动商品参与部分退款，
  券/积分是否按行回退需另行设计（本期若不改，至少要在规则上说明）；新增叠加策略建议快照化。
