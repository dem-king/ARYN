## 0. 目标与非目标

### 0.1 目标

1. **按活动类型控制叠加**：四类活动商品可分别配置「能否用券」「能否积分抵现」，默认值符合行业与悦航购现状（见 §1.2）。
2. **混合购物车按 SKU 排除**：同一单内活动商品与普通商品并存时，券门槛、券分摊、积分基数、积分分摊都只作用于「允许叠加」的明细。
3. **结算与提交一致**：确认页看到的金额、可用性，与提交订单后的实际扣款一致；不一致时由现有 `expectedPaymentPrice` 兜底。
4. **可配置、可灰度、可回滚**：活动级开关 + 全局特性开关；不改变存量订单。
5. **可解释**：C 端明确展示「为什么不能用券/积分」，管理端可配置、可审计。

### 0.2 非目标（本期不做，登记后续）

| 项 | 原因/去向 |
|---|---|
| 会员折扣的活动级策略（允许/互斥/取优） | 有赞矩阵里「限时折扣 × 会员折扣」是特殊折叠；当前系统对所有活动价再打会员折扣。风险已登记，作为 P2 单独治理 |
| 券 × 券叠加 | 当前订单模型只支持一张券（`order_info.coupon_user_id` 单值），本期维持 |
| 券级「仅原价购买可用」 | 有赞有该能力；本期先用活动级开关，二期加券级 `original_price_only` |
| 活动间互斥矩阵引擎化 | `promotion_activity.stackable` 长期是死字段；本期不复用其语义，另加清晰字段 |
| 全量营销价格监控看板 | 本期只做规则；监控对标抖音「营销价格风险管理」/京东「优惠监控」，登记 P2 |

## 1. 规则定义

### 1.1 优惠层序（保持现状，不调整）

```text
原价
→ ① 单品级活动价（拼团 > 秒杀 > 新人价 > 限时折扣 > 原价）
→ ② 阶梯价 / 新人价改基价（营销引擎）
→ ③ 会员折扣
→ ④ 优惠券
→ ⑤ 整船/整单优惠（仅非活动价明细）
→ ⑥ 运费
→ ⑦ 积分抵现（商品应付的 20% 上限）
→ ⑧ 金额一致性校验 → 落库
```

说明：①~⑦ 的顺序在结算（`settlementOrder`）与提交（`createOrder`）两个入口完全一致，本方案不改变层序。

### 1.2 默认规则矩阵（v1）

| 活动类型 | 优惠券 | 积分抵现 | 会员折扣（现状） | 可配置性 | 依据 |
|---|---|---|---|---|---|
| 拼团 | ✅ 可用 | ✅ 可用 | 照常 | 活动级开关，默认开 | 有赞「可配」；平台电商平行满减；与现状兼容 |
| 限时折扣 | ✅ 可用 | ✅ 可用 | 照常 | 活动级开关，默认开 | 有赞「可配」；与现状兼容 |
| 秒杀 | ❌ 不可用 | ❌ 不可用 | 照常 | **强制关，后台只读** | 有赞官方互斥（整行 ❌）+ 官方 FAQ；秒杀规则页已对外承诺 |
| 新人专享 | ❌ 不可用 | ❌ 不可用 | 照常 | 活动级开关，默认关 | 保护新客补贴、防 0 元单；**竞品无硬规则**（有赞体验价官方称可与秒杀/拼团搭配），属于悦航购自定策略 |
| 阶梯价 / 整船（既有） | 维持现状 | 维持现状 | 照常 | 本期不纳入 | 已有「整船优惠排除活动价 SKU」逻辑 |

> 秒杀、新人专享两项为「默认关」；拼团、折扣为「默认开」。若业务希望更保守（完全对标有赞/微盟 SaaS 默认「不叠」），
> 只需把租户级默认模板改成「全部关」，代码不变（见 §2.3）。

### 1.3 判定规则（逐条可测试）

1. **活动类型取最终生效者**：同一 SKU 同时命中多个活动时，按 ① 的优先级确定成交活动，
   叠加策略取**最终生效活动**的配置（例：秒杀 > 限时折扣，按秒杀策略）。
2. **资格按 SKU 判定**：`couponEligible = !activityHit || activity.couponStackable`；
   `pointsEligible` 同理。
3. **券门槛**（`useRange=1` 全场券）：基数 = Σ「券可叠 SKU」的 `totalPrice - memberDiscountPrice`；
   `useRange=2` 指定商品券：基数 = Σ「券指定 SPU ∩ 券可叠 SKU」的可折金额。
   门槛不满足 → 结算/提交给出可解释错误（复用 `ERROR_60060`，文案细化）。
4. **券分摊**：券额只分摊到「券可叠 ∩ 券范围」的明细，沿用现有「按可折金额比例 + 尾差逐分」算法；
   单行券额 ≤ 该行可折金额。
5. **积分基数**：`goodsPayable = Σ「积分可叠 SKU」的 (paymentPrice - freightPrice)`；
   单笔抵扣 ≤ 20% × 该基数；分摊只落在「积分可叠」明细。
6. **混合单**：券/积分的不可叠部分完全不参与门槛与分摊；不可叠明细的券额/积分额恒为 0。
7. **最低实付**（新增，可配置）：
   - 设 `base = 活动价+会员折扣后的商品金额`；
   - 若 `base ≥ 0.01`：`券额 + 积分额 ≤ base - 0.01`，超出部分按「先扣减积分抵扣、再扣减券额」回退；
   - 若 `base < 0.01`（活动价本身为 0 或极低）：不再允许券/积分作用于该 Base，避免 0/负金额；
   - 配置开关 `promotion.stack-policy.min-payable-enabled`（默认 `true`）可关闭，关闭后回退现行为（允许 0 元单，`FREE_PAY` 已支持）。
8. **全局回滚开关**：`promotion.stack-policy.enabled=false` 时，所有 SKU 视为可叠（等同当前行为），
   不读活动配置、不改变金额。用于灰度/线上回滚。
9. **秒杀强制关在服务端也要硬校验**：即使数据库/接口被改成可叠，秒杀类型一律返回不可叠（防配置错误）。

## 2. 数据模型

### 2.1 活动表新增字段（统一 4 张表）

| 表 | 实体 | 新增字段 | 默认值 |
|---|---|---|---|
| `seckill_activity` | `SeckillActivity` | `coupon_stackable char(1) NOT NULL DEFAULT '1'`<br>`points_stackable char(1) NOT NULL DEFAULT '1'` | 存量按 §2.3 回填 |
| `discount_activity` | `DiscountActivity` | 同上 | 同上 |
| `group_buy_activity` | `GroupBuyActivity` | 同上 | 同上 |
| `promotion_activity`（新人专享 type=9） | `PromotionActivity` | 同上；已有 `stackable` 保留但**标记 deprecated**，不再使用 | 同上 |

字段语义：`'1'`=允许叠加，`'0'`=不允许；空按默认值处理（见 §2.3）。

> 为什么不全表复用 `promotion_activity.stackable`：该字段语义是「活动间是否可叠」的泛化死字段，
> 直接复用会制造第二个含义；而四张表统一加两个具名字段，加载策略的代码可以完全一致，后续也便于加
> 「会员折扣策略」第三列。存量 `stackable` 保留不删，避免迁移风险。

### 2.2 默认值来源

V1 不新增配置表。默认值由**后端常量映射**（`ActivityType → 默认策略`）+ 管理端表单默认值共同表达：

| 活动类型 | coupon_stackable | points_stackable |
|---|---|---|
| 拼团 | 1 | 1 |
| 限时折扣 | 1 | 1 |
| 秒杀 | 0（且服务端强制） | 0（且服务端强制） |
| 新人专享 | 0 | 0 |

新建活动时：请求字段为空 → 按上表补默认值，并落库。编辑活动：只改显式提交的字段。
租户级「默认模板」放 P2（新增 `promotion_stack_default` 表或复用 `order_config` 风格），
本期若租户要求不同，可在活动级逐个调整。

### 2.3 存量数据回填（迁移脚本）

| 类型 | 回填值 | 说明 |
|---|---|---|
| 拼团、限时折扣（存量） | `1 / 1` | 与当前行为一致，不改价格 |
| 秒杀（存量） | `0 / 0` | **与规则页文案对齐**；上线前确认是否有用户已用券的客诉口径 |
| 新人专享（存量） | `0 / 0` | 保护新客价；上线后新单生效，已存在订单不受影响 |

回填 SQL 放增量脚本（见 §2.4），以 `activity` 类型 + 时间条件过滤，可重复执行。

### 2.4 DDL / SQL 交付

按 AGENTS.md 双模式要求，新增两份可重复执行的增量脚本（编号接在 155 之后）：

```text
aryn-mall-java/db/boot/156promotion_stack_policy_incremental.sql
aryn-mall-java/db/cloud/156promotion_stack_policy_incremental.sql
```

脚本内容（四张表各两次 `ALTER TABLE ADD COLUMN`，用 `information_schema` 判断存在性，风格参照
`148points_closed_loop_incremental.sql`）。注意：**存量回填只应在「本次刚加列」时执行一次**，
否则脚本重复执行会把运营后来改过的值重置——用 `@col_exists` 分支控制，而不是无条件 `UPDATE`：

```sql
-- 以 seckill_activity 为例（其余三张表同理）
SET @col_exists = (
  SELECT COUNT(1) FROM information_schema.COLUMNS
  WHERE TABLE_SCHEMA = DATABASE() AND TABLE_NAME = 'seckill_activity'
    AND COLUMN_NAME = 'coupon_stackable'
);
SET @ddl = IF(@col_exists = 0,
  'ALTER TABLE `seckill_activity`
     ADD COLUMN `coupon_stackable` char(1) NOT NULL DEFAULT ''1''
       COMMENT ''活动商品是否可用优惠券：1可用 0不可用'' AFTER `status`,
     ADD COLUMN `points_stackable` char(1) NOT NULL DEFAULT ''1''
       COMMENT ''活动商品是否可积分抵现：1可抵 0不可抵'' AFTER `coupon_stackable`',
  'SELECT 1');
PREPARE stmt FROM @ddl; EXECUTE stmt; DEALLOCATE PREPARE stmt;

-- 存量回填：仅在本次新加列时执行（@col_exists=0 的分支内追加 UPDATE），
-- 重复执行脚本时走 'SELECT 1'，不会覆盖运营后续修改。
-- 规则：seckill → 0/0；discount、group_buy → 1/1；promotion_activity type=9 → 0/0。
```

交付要求：

1. `db/boot/build-full-sql.mjs` 的 `sections` 登记 156 脚本，重新生成 `aryn_boot_full.sql`，跑 `verify-full-sql.mjs`。
2. `db/cloud/` 同名脚本与 boot 内容一致（cloud 各微服务基线脚本同步登记）。
3. 脚本必须可重复执行；`UPDATE` 只在首次迁移时执行，二次执行结果幂等（可加 `WHERE coupon_stackable IS NULL` 或依赖重复执行同值）。

### 3.3 计价流程改造（伪代码）

```java
// ① 活动价预取：返回带策略的 hits
PromotionPricePlan plan = resolvePromotionPricePlan(items, groupBuyPriceBySku, newbieSkuIds);
// hits 已由 seckill/discount/groupbuy/newbie 的远程上下文填充

// ② 券
List<OrderItemEntity> couponEligible = items.stream()
    .filter(i -> !plan.isActivityPriced(i.getSkuId()) || plan.hit(i.getSkuId()).couponStackable())
    .filter(i -> couponMatch(i))                      // 券范围
    .toList();
BigDecimal couponBase = sum(discountedGoodsPrice(couponEligible));
if (couponThreshold > couponBase) throw 无效优惠券（可解释文案）
BigDecimal couponAmount = min(couponCompute(couponBase), couponBase - minPayableFloor(couponBase));
allocateCouponOnlyTo(couponEligible, couponAmount);   // 现有比例+尾差算法

// ③ 积分
List<OrderItemEntity> pointsEligible = items.stream()
    .filter(i -> !plan.isActivityPriced(i.getSkuId()) || plan.hit(i.getSkuId()).pointsStackable())
    .toList();
BigDecimal pointsBase = sum(itemGoodsPayable(pointsEligible));
int maxPoints = min(availablePoints, base * 0.20 * rate);
allocatePointsOnlyTo(pointsEligible, deductAmount);

// ④ 最低实付兜底（券/积分之后）
applyMinPayableFloor(order, items);   // 超出部分先回退积分、再回退券
```

工程要点：

1. **结算与提交共用**：两个入口都调用同一组 handler，禁止在 createOrder 单独写一套判断。
2. **不可叠原因**：handler 把原因写入 `OrderInfo` 的派发字段（见 §3.4），结算返回给 C 端；提交时
   `strict=true`，若用户请求了不可叠的券/积分 → 抛业务异常（不静默改价）。
3. **券 eligible 为空**：结算返回 `couponStackReason`，不抛异常（页面要展示金额）；
   提交且 `couponUserId` 非空 → 抛「本单商品不支持使用优惠券，请取消选择」。
4. **积分 requested>0 但 eligible 为空**：同上报错；`useMaxPoints=false` 且未请求时返回 0 额度即可。
5. **优先级/兼容**：`promotion.stack-policy.enabled=false` 时 `plan` 的所有 `*Stackable` 视为 true，
   其余逻辑不变（等同现网行为）。

## 4. C 端交互与文案

### 4.1 订单确认页（`sub-pages/order/order-confirm`）

数据流：

```text
settlement 返回：
  - orderItemList[*].activityType / couponStackable / pointsStackable
  - couponStackReason / pointsStackReason / couponEligibleAmount / pointsEligibleAmount
→ 渲染：
  - 明细行活动标签（秒杀价/拼团价/新人价/折扣价）
  - 券行：可用 → 「选择优惠券」；不可用 → 置灰 + 原因
  - 券弹层：按「门槛 ≤ couponEligibleAmount」+ 券范围 + SPU 可叠性置灰
  - 积分行：pointsDeductMax > 0 才展示；副文案「活动商品不参与积分抵扣」按需出现
```

### 4.2 文案表

| 场景 | 文案 |
|---|---|
| 全部明细不可用券 | 「活动商品不支持使用优惠券」 |
| 混合单部分可用 | 「部分商品不参与优惠券，已按可叠加商品金额计算」 |
| 全部明细不可用积分 | 隐藏积分行；若用户开启过，撤销并提示「本单商品不支持积分抵现」 |
| 混合单积分部分可用 | 副文案「活动商品不参与积分抵扣，最多可抵 ¥X」 |
| 明细活动标签 | 「秒杀价」「拼团价」「新人价」「折扣价」 |
| 最低实付拦截 | 「优惠后应付金额低于 ¥0.01，已为你调整优惠」 |
| 券门槛不满足 | 「还差 ¥X 可用该券」 |

### 4.3 规则页

- `pages/promotion/seckill-rule.vue`：`秒杀商品不支持使用优惠券、不参与其他满减活动` →
  补充「同时不支持积分抵现」，与本方案一致。
- 拼团/折扣/新人专享：若后续新增规则页，按 §1.2 写；当前无独立规则页的，不强行新增。

## 6. 退款、快照与对账

1. **分摊**：券→`order_item.coupon_price`；积分→`order_item.points_price`；活动价→`sales_price/total_price`；
   排除逻辑保证不可叠明细的券/积分为 0，退款可按行还原。
2. **退款现状**：只有整单全退才退积分、恢复券（`ArynRefundListener` 全退分支）；部分退款不返积分、
   不恢复券。本方案不改变该行为，但需在规则页/客服口径说明。
3. **快照**：V1 建议新增下单快照行（`PromotionSnapshot`）记录「活动类型 + 叠加策略 + 券/积分金额」，
   便于客诉解释；`activityType` 枚举需扩展（当前 1~7 不含秒杀/拼团/折扣/新人）。
   P2 再做完整快照（`priceBefore/priceAfter/appliedItemIds` 补齐）。
4. **对账**：订单金额字段已固化 `coupon_price / points_deduct_price / promo_price / member_discount_price`，
   财务口径不变；新增字段仅用于规则判定，不进对账。
