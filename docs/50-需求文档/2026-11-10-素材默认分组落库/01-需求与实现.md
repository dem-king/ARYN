# 素材默认分组落库（「未分组」可改名）

> 状态：已实施（2026-11-10）；数据库脚本、后端单测、全量 SQL 构建与校验、前端类型检查与契约测试均通过。前后端**需同批上线**。

## 一、原始请求

管理后台「素材中心 → 分组管理」里第一行「未分组」不能改名：操作按钮被隐藏，点不动也改不了。

## 二、改造前现状

| 位置 | 现状 |
|---|---|
| `aryn-mall-ui` 分组管理页 | 拿到 `/upms/materialgroup/page` 结果后 `unshift({id:'-1'})` 造一条虚拟行，并用 `v-if="scope.row.id !== '-1'"` 把整行操作按钮隐藏 |
| `sys_material_group` | 没有「默认分组」概念，也没有 `is_default` 列 |
| `sys_material.group_id` | 列默认值就是 `'-1'`，DB 注释「分组ID -1.未分组」；这些素材在分组管理里没有任何归属 |
| 后端接口 | `/materialgroup` 增删改查没有默认分组语义；`/file/upload`、`/material` 直接信任请求里的 `groupId` |

## 三、设计口径（方案 B：把「未分组」做成真实记录）

| 项 | 口径 |
|---|---|
| 列 | `sys_material_group.is_default char(2) NOT NULL DEFAULT '0'`，注释「是否默认分组：1.是；0.否」 |
| 每租户唯一 | 函数唯一索引 `uk_material_group_default_tenant ((IF(is_default='1' AND del_flag='0', tenant_id, NULL)))`（MySQL 8.0.13+，与 `168payment_hardening_incremental.sql` 的 `uk_order_refund_active_item` 同写法） |
| 默认分组 id | **公式**而非雪花 ID：`MD5(CONCAT('material-default-group:', tenant_id))` → 32 位小写十六进制，正好等于 `id varchar(32)`。Java 侧 `MaterialDefaultGroupSupport#defaultGroupId` 与 SQL 一字不差，否则「脚本建的」与「懒创建建的」会变成两条默认分组并撞唯一索引 |
| 初始字段 | `name='未分组'`、`type='1'`、`sort=0`、`is_default='1'`、`del_flag='0'`、`tenant_id=该租户`、`create_by='system'` |
| 排序 | `page`/`list` 一律 `ORDER BY is_default DESC, sort ASC, create_time ASC, id ASC`——置顶靠 `is_default` 而不是 `sort`，否则运营把普通分组 sort 设成负数就能插到前面 |
| 权限 | 默认分组**可改名、不可删除**；删除普通分组时先把组内素材改挂默认分组，再逻辑删除分组 |
| 写入兜底 | 上传/新增/编辑素材时 `groupId` 为空、`'-1'`、或指向不存在/已删除/其它租户的分组 → 落到当前租户默认分组 |
| 创建时机 | **懒创建**：`page`/`list` 与 `resolveGroupIdForSave` 兜底时先查后插，捕获 `DuplicateKeyException` 视为并发已建再查一次。不改 `SysTenantServiceImpl` 构造参数（会连锁改测试），懒创建已覆盖新租户 |

## 四、改动清单

### 数据库（双模式各一份，内容除库名外一致）

- 新增 `db/boot/221material_default_group_incremental.sql`（`USE aryn_boot;`）
- 新增 `db/cloud/232material_default_group_incremental.sql`（`USE aryn_upms;`）
- `db/boot/build-full-sql.mjs`：sections 末尾（220 之后）登记 `['素材默认分组落库', '221material_default_group_incremental.sql']`
- `db/boot/verify-full-sql.mjs`：required 追加 `'ADD COLUMN `is_default`'`、`'material-default-group:'`、`'uk_material_group_default_tenant'`；sourceFiles 追加 221；boot/cloud 语义一致性比对追加 `221 ↔ 232`

脚本内容（可重复执行，无 DROP/TRUNCATE）：

1. 列存在性检查（`information_schema.columns`）+ `PREPARE/EXECUTE/DEALLOCATE` 加 `is_default`（`AFTER \`name\``）
2. 索引存在性检查（`information_schema.statistics`，`index_name='uk_material_group_default_tenant'`）再加函数唯一索引
3. 为所有有效租户补默认分组：`INSERT IGNORE ... SELECT MD5(CONCAT('material-default-group:', t.id)) ... FROM sys_tenant t WHERE t.del_flag='0'`（`sys_tenant.del_flag` 为 `char(1)`，取值 `'0'/'1'`，已按实际列核对）
4. 素材回填：`group_id` 为 `NULL`/`''`/`'-1'`，或指向不存在/已逻辑删除/跨租户分组的素材，按租户改挂到默认分组。只处理租户仍有效（`sys_tenant.del_flag='0'`）的素材——租户已删除时没有默认分组可挂；已逻辑删除的素材同样回填，恢复后仍应落在默认分组而不是一个已消失的分组
5. 末尾自检 SELECT：默认分组数 / `is_default` 非法值行数（应 0）/ `group_id` 仍为 `-1` 的素材数（应 0）/ 悬空分组引用数（应 0）/ 每租户默认分组数最大值（应 1）/ 无默认分组的租户数（应 0）

## 七、遗留风险

1. **部署顺序**：`is_default` 列必须先于代码上线（`SysMaterialGroup` 走 MyBatis-Plus 显式列清单，缺列时分组查询会 `Unknown column`）。列表接口已对 ensure 做降级，但 `SELECT ... is_default` 本身仍会失败——必须先执行 221/232 再发后端。
2. **函数索引要求 MySQL 8.0.13+**：低版本会直接报语法错误，需先升库（与 168 号脚本同一前提）。
3. **默认分组被逻辑删除后无自愈**：主键被占用 + `selectById` 走 `@TableLogic` 查不到，ensure 会抛业务异常提示人工恢复，不会静默造第二条默认分组。
4. **前端未改造前**：旧前端仍会 `unshift` 一条 `id='-1'` 的虚拟行，届时分组管理页会出现两条「未分组」（一条真实、一条虚拟）。前后端需同批上线。
5. **`sys_material.group_id` 列默认值仍是 `'-1'`**：本次不动基线表结构（改默认值会牵扯 `2aryn_boot.sql`/`2aryn_upms.sql` 基线）。后端所有写入路径都已兜底，因此该默认值只在绕过接口直接写库时才会产生脏值。
