## 一、结论摘要（5 条）

1. **【事实】现有批量接口是「同步、整批单事务、逐 SPU 无条件覆盖写」的接口**：没有预检、没有变更检测、没有前后差异、没有批次号与撤销；逐条结果只有 `success + message` 四个字段，同一批商品同规则重复提交仍然返回 `success=true / message="OK"`，前端无法区分「新增 / 更新 / 无变化 / 移出」。这是运营反馈「反复打标且无感知」的后端直接原因（证据：`PAPI/vo/GoodsZoneTagResultVO.java:24-30`、`PBIZ/service/impl/GoodsZoneTagServiceImpl.java:136-144`）。

2. **【事实】批量与单商品编辑对「出清标签」的校验互相矛盾，批量会造出单商品接口无法保存的状态**：批量允许「只打标、不配出清规则」（`GoodsZoneTagServiceImpl.java:786-794`、`822-827`），而单商品 `updateGoods` 要求「出清商品必须配置出清价或出清折扣」（`PBIZ/service/impl/GoodsSpuServiceImpl.java:433-436`）。商品编辑页提交整份表单（`UI/views/product/goods-spu/form.vue:569-573` 回填、`927-1013` 专区标签页签、`369-410` 提交），因此批量打标后的商品进编辑页保存会直接失败（P0）。

3. **【事实】两个「覆盖语义」与前端文案不一致，且重复打标会静默改变 SKU 级精调**：`overwriteSkuRules` 只在「同时提供了新规则 且 打标=true」时才清 SKU 覆盖（`GoodsZoneTagServiceImpl.java:117-135`），与前端复选框文案「所有规格统一按本次规则」（`UI/views/product/goods-spu/index.vue:727-729`）不符；而「重复打标」会把 SKU 显式排除（`is_member_item=0 / is_clearance_item=0`）重置为继承（`GoodsZoneTagServiceImpl.java:877-898`），运营无任何提示（P1）。

4. **【事实+估算】批量接口没有 `spuIds` 上限，逐 SPU 的 N+1 查询/更新包在一个事务里，提交后还要在响应前做一次「全租户」同步**：每件约 3–8 条 SQL，100 件约 400–800 条、635 件约 2500–5000 条 SQL、一个长事务；同步调用 `syncTenant` 读取租户全部专区 SKU 并重写两条系统活动（`GoodsSpuController.java:100-111` → `PRBIZ/service/impl/MallZoneActivitySyncServiceImpl.java:93-118`）。支撑「全选 635 件」前必须先做上限、分批/异步与同步异步化（P1）。

5. **【事实】审计链路既空白又会产生错误数据**：`@SysLog` 的切面与日志监听器在当前仓库内**没有注册为 Spring Bean**（`LogAopAspect` / `ArynLogEventListener` 均无 `@Component` 等注解，`AutoConfiguration.imports` 只登记了登录日志的 `ArynSysLogConfig`），与 README §1.2「本机 `sys_log` 0 条」吻合；`goods_price_history` 无 batchId、`operator` 从未赋值、不记录标签开关与出清折扣率、批量清 SKU 精调完全不落历史；更严重的是 `recordSpuTagChanges` 对「本次未触碰的专区」也会写「旧值→null」的**幽灵历史**（`GoodsZoneTagServiceImpl.java:843-848`、`853-856`），重复提交会重复写。审计不能支撑批次追溯，更无法支撑撤销（P1，其中幽灵历史影响数据可信度，按 P0 处理）。

另外有一个**未在用户反馈里出现但风险最高**的同步缺陷：`RemoteGoodsZoneTagServiceImpl#listZoneSkus` 捕获异常后返回空列表（`PBIZ/dubbo/RemoteGoodsZoneTagServiceImpl.java:32-49`），同步服务无法区分「没有打标商品」与「查询失败」，会把空规则写入系统活动并暂停活动（`MallZoneActivitySyncServiceImpl.java:273-335`，尤其 `329-331`）——一次瞬时 DB 故障即可清空全租户的专区价，且接口仍返回成功。

### 2.3 结果与失败语义

| 场景 | 现状行为 | 证据 |
|---|---|---|
| 已打标且规则完全相同再提交 | 照常 UPDATE（字段相同）；本次提供值的专区历史因 `sameValue` 跳过，但未触碰的专区可能写幽灵历史（G22）；返回 `success=true/"OK"` | `GoodsZoneTagServiceImpl.java:136-144`、`:843-856`；`GoodsPriceHistoryService.java:34-37` |
| 商品不存在/跨租户/已删除 | 该条 `success=false`，message「商品不存在或无权操作」，其余继续 | `GoodsZoneTagServiceImpl.java:107-111` |
| 入参规则非法（折扣率越界、固定价≤0、到期时间早于当前） | 写入前整单抛错，**没有任何逐条结果** | `:101`、`:918-938` |
| 单条业务异常（如缺原价按折扣算价） | 捕获后该条失败、其余提交（部分成功语义） | `:146-148`、`:786-794` |
| 非业务异常（DB 异常、空指针等） | 未被捕获 → 整批回滚，返回全局业务错误 | `:146` 仅 catch `ArynBusinessException` |

| 同步失败 | Controller 吞异常打 warn，接口仍返回全部 success | `GoodsSpuController.java:105-110` |
| 全部条目失败 | HTTP/业务码仍为成功，只有逐条 `success=false` | `GoodsSpuController.java:70-72` |

**结论**：现有契约只表达「写入是否被业务规则拒绝」，不表达「这次操作实际改变了什么」「哪些没变」「失败原因码是什么」「价格是否真的生效」。部分失败语义存在两处断点：请求级校验让整单失败、非业务异常让整批回滚且丢失已处理明细。

### 2.4 标签 / 规则 / 覆盖的解析规则

- **SPU 是选品单位，SKU 是同义覆盖，`NULL=继承 SPU`**：`toSnapshot` 用 `firstNonNull` 逐字段回落（`GoodsZoneTagServiceImpl.java:710-730`），`resolveTag` 对标签做 `null→回落 SPU / 0→否 / 1→是`（`:732-737`）。
- **取消标签是破坏性清空**：SPU 规则字段清空（会员 4 个、出清 3 个，`:801-828`）；SKU 全部规则字段清空且 SKU 标签写显式 0（`:900-916`），这些 SKU 行不再「继承」，而是「显式不属于」。
- **重新打标会把 SKU 显式 0 重置为 NULL**（回归继承）：`:877-898`；这是为「SPU 重新启用后全规格默认命中」设计的，但会**抹掉运营在单商品精调里做的 SKU 级排除**（见 G7）。
- **生效值来源不可见**：`GoodsZoneTagVO.SkuTagVO` 只返回 SKU 原始字段（null 表示继承），不返回「解析后生效值」与「是否有覆盖」标志（`PAPI/vo/GoodsZoneTagVO.java:43-76`）；内部快照 DTO 同样只给生效值、不给来源（`PAPI/dto/GoodsZoneSkuSnapshotDTO.java:13-27`）。
- **批量不接收会员价下限**：批量调用 `applySpuTags(..., memberFloor=null, ...)`（`GoodsZoneTagServiceImpl.java:113-116`），与操作手册「批量不提供会员价下限」一致（`DOC/2026-11-02-会员专区与低价捡漏规则化改造/操作手册.md:119`）。

### 2.5 为什么「标签存在 ≠ 价格生效」（同步链路语义）

打标结果通过 `syncTenant` 写入促销域两条系统托管活动（`SYS_MEMBER_ZONE` / `SYS_CLEARANCE_ZONE`），再由引擎/查价接口读取：

1. 只同步**在售**商品与 SKU：SPU `status=1`、SKU `status=0`（`GoodsZoneTagServiceImpl.java:266-278`）；
2. 专区开关关闭时 rules 为空（`MallZoneActivitySyncServiceImpl.java:151-152`、`:180`）；
3. 会员价需要「商品规则 × 等级折扣或专区默认折扣/固定价」至少一条可用，否则跳过（`:158-163`、`:215-243`）；
4. 出清价需要固定价或「原价 × 折扣」，并做倒挂校验（算出价 ≥ 售价则跳过）（`:186-197`、`:245-271`）；
5. 出清到期从 rules 移除并跳过（`:195-197`）；
6. C 端标签列表只看标签（`PMAP/GoodsSpuMapper.xml:179-187`），价格接口对无效项**静默过滤**（`GoodsZoneTagServiceImpl.java:586-595`），因此「已打标但没有价/已下架/已倒挂」在 C 端列表可能仍出现，运营侧无任何状态可见。

同步是最终一致：失败只记日志，另有每日 03:10 兜底 Job（`PRBIZ/job/MallZoneSyncJobHandler.java:23-35`；`BE/db/boot/184mall_zone_sync_job.sql:22`）。但当前失败路径存在「空快照清空」缺陷，见 G13。

## 三、缺口清单

> 编号 G1–G25，按「契约与结果 → 语义一致性 → 性能与同步 → 缺失能力 → 数据与审计 → 测试」排列。每条给：问题 / 代码证据 / 影响 / 严重度 / 建议契约（§四 对应条目）。

### A. 契约与结果反馈

#### G1 · 没有「变更类型 / 变化前后 / 无变化」识别（P0）

- **问题**：`batchSave` 无条件执行 UPDATE，逐条结果恒为 `success=true, message="OK"`；不返回 `changeType`、不返回 before/after、不返回变更字段。已打标且规则相同时，唯一「没变」的痕迹是价格历史被 `sameValue` 跳过——但接口层完全不可见。
- **证据**：`GoodsZoneTagServiceImpl.java:106-144`（无比较、无 diff）；`PAPI/vo/GoodsZoneTagResultVO.java:24-30`（仅 4 字段）；`GoodsPriceHistoryService.java:34-37`（同值跳过）。
- **影响**：运营无法判断「这次到底改了什么」；截图场景（10 件已打标再提交）只能看到「打标成功」，与用户诉求 1 完全对应；前端无法实现「无变化 8 件」的提示与按钮禁用。
- **建议契约**：§4.1（预检 changeType）、§4.2（执行结果 changeType/before/after/changedFields）。

#### G2 · 部分失败语义不完整：整单校验、整批回滚、无错误码、无原子模式（P1）

- **问题**：① 规则参数校验在循环前执行，一条非法参数让整批没有逐条结果（`GoodsZoneTagServiceImpl.java:101`、`:918-938`）；② 循环内只捕获 `ArynBusinessException`，其它运行时异常整批回滚（`:146`）；③ 失败只有自然语言 message，无 `errorCode`，前端无法分组/重试；④ 没有「全部成功或全部回滚」的 `atomic` 选项，运营无法选择。
- **证据**：同上；Controller 无 `@Valid`（`GoodsSpuController.java:69`）。
- **影响**：混合批次无法稳定得到「成功 N / 失败 M + 明细」；超时重试会重复执行（叠加 G22 的重复幽灵历史）。
- **建议契约**：§4.2（结构化失败码、`atomic` 选项）、§4.3（异步批次天然分离校验与执行）。

#### G3 · `spuIds` 无上限、无去重、空操作无校验（P1）

- **问题**：DTO 无 `@Size`、服务层无上限；重复 ID 会重复 SELECT/UPDATE 并返回重复结果行；若所有动作/规则均为空（只有 spuIds），接口返回「全部成功」但什么都没做——且会写入幽灵历史（G22）。
- **证据**：`PAPI/dto/GoodsZoneTagBatchDTO.java:31-59`；`GoodsZoneTagServiceImpl.java:98-100`（仅判空）、`:106`（不去重）、`:795-799`（无 touched 字段直接 return，但历史记录仍执行）。
- **影响**：一次请求可放大成上千条 SQL / 长事务；空操作成功误导运营；重复行让结果聚合不可信。
- **建议契约**：§4.2（上限 200/请求、服务端去重、空动作拒绝）、§4.3（超限转批次任务）。

#### G4 · 结果没有「专区维度」与「SKU 覆盖影响范围」（P1）

- **问题**：一次弹窗可同时改会员 + 出清两个专区，但结果按 SPU 一条、不区分专区；也不告诉前端本次会影响多少 SKU 精调（清除数量）。前端 `02` D6 因此无法分区呈现部分成功。
- **证据**：`GoodsZoneTagServiceImpl.java:136-144`；`PAPI/vo/GoodsZoneTagResultVO.java:24-30`；SKU 清理逻辑 `:117-135`、`:900-916`。
- **影响**：部分失败时无法判断是哪个专区失败；「取消标签」的影响范围不可见（与前端 A4 破坏性操作直接相关）。
- **建议契约**：§4.2（`zones` 汇总 + `willClearSkuRules` 计数）、§4.1（预检给出影响范围）。

### B. 语义一致性

#### G5 · 出清「只打标不配规则」与单商品编辑校验冲突（P0）

- **问题**：批量 `applySpuTags` 明确允许「只打标」，注释写着「P1 专区默认折扣率可在促销域配置」（`GoodsZoneTagServiceImpl.java:786-794`，`:822-827` 只 set 非 null 规则）；但单商品 `updateGoods` 的 `validateZoneFields` 要求「出清商品必须配置出清价或出清折扣」（`GoodsSpuServiceImpl.java:433-436`）。商品编辑页回填整份 `GoodsSpu`（`UI/views/product/goods-spu/form.vue:569-573`），提交时 `isClearanceItem=1` 且两规则为空 → 保存直接报错。
- **证据**：上述两处；另 `GoodsZoneTagServiceImpl.java:789` 注释、操作手册校验规则「出清必须至少有固定价或折扣率」（`DOC/2026-11-02-会员专区与低价捡漏规则化改造/操作手册.md:100`）。
- **影响**：批量打标造出「编辑页无法保存」的脏状态；运营只能先进编辑页补规则或手工取消标签，且没有任何提示；两种入口互相制造对方无法处理的数据。
- **建议契约**：§4.8 ADJ-1（抽统一校验器，先由产品确认「只打标」是否合法：合法则放宽单编辑，不合法则批量拒绝并提示）。**这是本次 P0 必改项**。

#### G6 · `overwriteSkuRules` 只在「提供新规则且打标=true」时生效，与前端文案不符（P1）

- **问题**：会员清理条件为 `memberRuleProvided && overwriteSkuRules`（`GoodsZoneTagServiceImpl.java:123-125`），出清同理（`:132-134`）。因此：① 勾选覆盖但没填任何规则（tag-only）→ 不清 SKU；② 只传规则没传 `memberTag`（`null`）→ 不清 SKU；③ 取消标签时不论是否勾选都会清 SKU（`:117-119`、`:127-129`）。前端文案是「同时清除已配置的 SKU 级精调，所有规格统一按本次规则」（`UI/views/product/goods-spu/index.vue:727-729`），语义为无条件清除。
- **影响**：运营按文案勾选后结果与预期不一致：该清的没清（部分规格价格沿用旧值），不该清的被清（取消标签时无提示清空 SKU 精调）；SKU 精调本身在列表/弹窗不可见，事后无法核对。
- **建议契约**：§4.1（预检给出「将清除 SKU 精调数量」）、§4.8 ADJ-2（明确语义：覆盖=清除本次动作对应专区的 SKU 规则，与是否提供新规则解耦，或前端按条件显隐）。

#### G7 · 重复「打标」会静默清掉 SKU 级显式排除（P1）

- **问题**：SPU 打标时 `resetSkuMemberTagIfNeeded` 把该商品所有 `is_member_item=0` 的 SKU 标签置 NULL（`GoodsZoneTagServiceImpl.java:120-126`、`:877-887`；出清同理 `:889-898`）。若运营此前在单商品精调里把某个规格排除（SKU 标签=0），任何一次「批量打标」（哪怕规则没变）都会恢复该规格。
- **证据**：上述行号；单商品精调可写 SKU 显式 0（`GoodsZoneTagServiceImpl.java:226-245`）。
- **影响**：与用户诉求 1 叠加——「反复打标」不只是无感知，还会静默改状态；SKU 级排除丢失后 C 端价格变化，但审计无记录（G22）。
- **建议契约**：§4.1 预检返回 `skuOverrideCount / willResetSkuExclusions`；§4.2 增加 `preserveSkuTagExclusions`（默认 true）或把「重置显式排除」作为独立动作。

#### G8 · 不传规则时保留旧规则、规则与标签状态分离，均无提示（P1）

- **问题**：打标只 `set` 本次非 null 规则（`GoodsZoneTagServiceImpl.java:807-814`、`:820-828`），因此同一批混选（部分商品已有旧规则、部分没有）会出现「同样操作、不同结果」：老商品沿用旧折扣、新商品走专区默认折扣或无价。另外 `memberTag=null + 提供规则` 会把规则写入但标签不启用（`:795-814`），接口返回成功，但同步侧不会产生价格。
- **影响**：运营以为「统一规则」，实际各商品规则不同；「规则已保存但未生效」的状态无人可见，C 端价格与预期不符。
- **建议契约**：§4.1（预检分组：已加入/未加入/规则将变/沿用旧规则）、§4.2（结果给出 `ruleSource: NEW|KEPT|DEFAULT_ZONE`）、§4.8 ADJ-2。

#### G9 · 「标签存在 ≠ 价格生效」不可见（P0 体验 / P1 数据一致性）

- **问题**：打标成功只代表标签落库；C 端价格是否生效取决于在售状态、专区开关、可用规则、倒挂、到期（§2.5）。批量结果与列表/编辑页都不返回生效状态与原因。
- **证据**：同步跳过分支 `MallZoneActivitySyncServiceImpl.java:151-152`、`:158-163`、`:186-197`；C 端价格接口静默过滤 `GoodsZoneTagServiceImpl.java:586-595`；列表 SQL 只看标签 `PMAP/GoodsSpuMapper.xml:179-187`。
- **影响**：运营打了标却发现 C 端没价、或专区里出现无价商品，只能逐个人工排查；对「打标成功」的信任度下降。
- **建议契约**：§4.6 价格/生效预览、§4.1 预检 `effectiveState`、§4.2 结果内嵌 `effective`。

### C. 性能、事务与同步

#### G10 · 逐 SPU N+1 + 整批单事务 + 无分批上限（P1）

- **问题**：每件商品执行 1 次 `selectById`，加 1 次 SPU UPDATE、1–2 次 SKU `SELECT COUNT`、0–2 次 SKU UPDATE、0–3 次价格历史 INSERT、出清打标时 1 次「先涨后降」COUNT，全部在同一事务内串行。**粗估每件 3–8 条 SQL**（【推断】按代码分支枚举，非实测）。
- **证据**：`GoodsZoneTagServiceImpl.java:96-151`、`:877-898`、`:900-916`、`:832-857`、`:140-143`；`@Transactional` 在 `:96`。
- **影响**：100 件约 400–800 条 SQL，635 件约 2500–5000 条 SQL、单个长事务（行锁持有时间长、超时风险）；一旦失败整批回滚，运营重试又重复执行（叠加 G22）。同步还会在同一请求内追加一次全租户重算（G11）。
- **建议契约**：§4.2（批量查询替代 N+1、上限 200）、§4.3（超限分批/异步）。

#### G11 · 同步在响应前阻塞，且每次打标都全租户重算（P1）

- **问题**：`batchTags` 在 `batchSave` 返回后同步执行 `syncTenant(tenantId)`，读取租户全部专区 SPU/SKU（2 条大查询）、会员等级、专区设置、出清规则，再 upsert 两条活动，全过程阻塞 HTTP 响应；即使本次没有任何变化（甚至全部条目失败）也会执行（Controller 无条件调用）。
- **证据**：`GoodsSpuController.java:70-72`、`:100-111`；`MallZoneActivitySyncServiceImpl.java:93-118`（`:101` 读取全量快照）；`GoodsZoneTagServiceImpl.java:260-291`（全量读取）。
- **影响**：商品越多越慢；cloud 模式下是跨域 Dubbo RPC（仓库内未给该 `@DubboReference` 配置 timeout/retries，见 `GoodsSpuController.java:62-63`，**默认超时/重试行为为框架默认【推断】**），可能出现「打标事务已提交、响应超时、前端重试」的重复提交。
- **建议契约**：§4.2 第 5 条（仅 `changed>0` 才触发同步 + 响应内嵌 `sync.status`）、§4.7（同步状态查询/手动重试）。

#### G12 · 系统活动 `rules` 为 TEXT，大租户/全选打标存在容量风险（P2，但「全选」方案上线前必须评估）

- **问题**：`promotion_activity.rules` 列为 `text`（上限 65,535 字节）。系统活动 rules 把租户全部专区 SKU 序列化进去；按每 SKU 约 60–100 字节估算，**约 650–1000 个 SKU 即接近上限**（出清 item 含 `expireTime`，更长）【推断】。若一次全选 635 件（多规格商品占一定比例），或租户持续累积，可能触发「Data too long」导致同步整体失败。
- **证据**：`BE/db/boot/53promotion_ship_supply_incremental.sql:11-18`（`rules text`）；序列化 `MallZoneActivitySyncServiceImpl.java:150-174`、`:198-209`、`:320-334`；快照全量读取 `GoodsZoneTagServiceImpl.java:260-291`。
- **影响**：同步失败无感知（G13），系统活动停更或更新失败，C 端价格长期不生效；若 MySQL 非严格模式截断则 JSON 非法，引擎解析异常风险更高【推断】。
- **建议契约**：§4.9 评估 `mediumtext`/分片存储/只同步差异；预检接口对大租户给出规模提示。

#### G13 · 同步失败语义危险：空快照会清空系统活动并暂停，接口仍返回成功（P0）

- **问题（两段）**：
  1. `RemoteGoodsZoneTagServiceImpl#listZoneSkus` 捕获所有异常后返回**空列表**（`PBIZ/dubbo/RemoteGoodsZoneTagServiceImpl.java:32-49`，`:42-45`）；`syncTenant` 无法区分「租户没有打标商品」与「快照查询失败」，会按「空选品」写 rules 并把已存在活动置为暂停（`MallZoneActivitySyncServiceImpl.java:273-335`，`:329-331`）。
  2. Controller 的 `syncZonesQuietly` 吞掉同步异常只打 warn（`GoodsSpuController.java:100-111`），接口对所有条目返回 success；前端因此展示「打标成功，专区价格已同步」（`UI/views/product/goods-spu/index.vue:184`），而实际可能没有价格或刚被清空。
- **影响**：**一次瞬时 DB/网络故障即可清空全租户专区价并暂停活动**，直到下一次成功同步（任何触发同步的商品保存，或最迟次日 03:10 兜底 Job）才恢复；期间 C 端专区价整体消失或回落原价，属资损/客诉级风险。
- **建议契约**：§4.7（`listZoneSkus` 失败必须抛错/带失败标记，同步事务禁止用空快照覆盖非空 rules；同步结果返回调用方）；§4.2（响应内嵌 sync 状态与失败原因，前端文案以服务端为准）。

### D. 缺失的能力

#### G14 · 缺「批量预检」接口（P0）

- **问题**：没有只读的「按 spuIds + 拟定动作/规则，返回当前状态、将发生的变化、影响范围、告警」接口。现有 `GET /tags/{spuId}` 只能单条查（N 次请求），`byIds` 不返回 SKU 覆盖，价格接口静默过滤无原因。
- **证据**：`GoodsSpuController.java:75-80`（单条）、`:137-140`（byIds）；`GoodsZoneTagServiceImpl.java:153-169`（单条实现）；`PMAP/GoodsSpuMapper.xml:62-104`（列表不含 SKU 覆盖）。
- **影响**：前端 `02` 的 A1/B1（状态不可见、无变化不可知）无法实现；运营只能盲写。
- **建议契约**：§4.1 `POST /product/goodsspu/tags/batch/preview`。

#### G15 · 缺「批量读取当前专区状态」接口（含 SKU 覆盖与生效值）（P0）

- **问题**：现只有单条 `getTags`；即便前端循环调用，返回的也只是 SKU 原始覆盖值（null=继承），没有「是否有覆盖 / 解析后生效值 / 生效或跳过原因」。`GoodsZoneSkuSnapshotDTO` 内部快照同样把来源抹掉（`GoodsZoneTagServiceImpl.java:710-730`）。
- **证据**：`PAPI/vo/GoodsZoneTagVO.java:43-76`；`PAPI/dto/GoodsZoneSkuSnapshotDTO.java:13-27`；`GoodsZoneTagServiceImpl.java:732-741`。
- **影响**：列表与弹窗无法展示「SKU精调 N」「沿用旧规则」「已下架/已到期/倒挂」等关键状态；前端 D1/D4 问题无法闭环。
- **建议契约**：§4.5 批量读取（`POST/GET /product/goodsspu/tags/query`），上限 200/页。

#### G16 · 缺「按筛选条件取 ID / 批量移出专区」能力（P0，「换一批」前置）

- **问题**：「换一批」最需要的两步——① 筛出当前专区商品并全选（需要服务端按筛选条件返回全部 ID）；② 对这批 ID 批量移出——后端都没有专属支持。现状只能用分页接口逐页拉全量实体再在前端拼 ID；且 `selectPageByAdmin` 没有固定 ORDER BY（`PMAP/GoodsSpuMapper.xml:62-104`，`</where>` 后直接结束），**分页遍历顺序不稳定**【推断：MySQL 无 ORDER BY 时顺序由执行计划决定】，翻页收集 ID 可能漏/重。
- **证据**：`GoodsSpuServiceImpl.java:73-92`（adminPage）；`PMAP/GoodsSpuMapper.xml:62-104`；无 ID 接口（`GoodsSpuController.java:48-218` 全览）。
- **影响**：会员专区 18 件也需分页勾选；600+ 商品时「换一批」不可行；前端 `02` C1/C2/C3 无法实现。
- **建议契约**：§4.4 `POST /product/goodsspu/ids`（固定 id 排序、上限 1000、返回 total/truncated）。

#### G17 · 缺批次号 / 操作记录 / 撤销（P1）

- **问题**：接口不返回 `batchId`；没有批次表、没有操作记录查询、没有撤销。`goods_price_history` 是逐字段价格流水，不是批次模型（见 G22）。
- **证据**：`PAPI/vo/GoodsZoneTagResultVO.java:24-30`（只有列表，无批次）；`GoodsSpuController.java:65-98`（无批次/撤销端点）；`PAPI/entity/GoodsPriceHistory.java:28-60`。
- **影响**：「换一批」误操作不可回滚；运营/主管无法查看「谁在什么时候对哪些商品做了什么」；配合 G22 的幽灵历史，追溯反而被误导。
- **建议契约**：§4.3 批次任务（preview→confirm→items→undo→list），存储建议新表或复用 `product_change_log`（§4.9 ADJ-5）。

#### G18 · 缺管理端价格/生效预览（P1）

- **问题**：C 端有 `/app/member/prices`、`/app/clearance/prices`（`PBIZ/controller/app/AppClearanceController.java:45-57`；`PRBIZ/controller/app/AppMemberPriceController.java:61-75`），但管理端没有「按 spuIds + 拟定规则」预览生效价的接口；C 端接口按展示口径静默过滤无效项、不返回跳过原因，且会员价依赖登录身份（管理端预览无法确定等级折扣口径）。
- **证据**：上述控制器；过滤逻辑 `GoodsZoneTagServiceImpl.java:532-608`（`:586-595` 静默跳过）；同步算价 `MallZoneActivitySyncServiceImpl.java:215-271`。
- **影响**：运营无法在提交前确认「这批商品最终卖多少钱」「为什么某件没价」，只能打标后去 C 端肉眼看。

## 四、建议新增或调整的 API 草案（只描述，不实现）

> 原则：**增强而不破坏**——新增字段向后兼容旧前端；新接口首段固定 `/product`（cloud 微服务域），boot 模式由 `context-path: /boot` 统一改写，禁止在 Controller 硬编码 `/boot`；租户一律由登录态/拦截器注入（`ArynTenantContextHolder`），**禁止从入参取 tenant**；所有列表/批量入参必须有显式上限；写接口返回统一的批次与同步状态。

### 4.2 API-2 批量执行增强（兼容旧契约）

- **方法/路径**：`POST /product/goodsspu/tags/batch`（不新增路径，字段扩展）
- **入参新增**（均可选，旧前端不带时行为不变）：

```json
{
  "...": "沿用 GoodsZoneTagBatchDTO",
  "clientRequestId": "uuid（幂等键，同 key 24h 内返回首次结果，防重试重复写）",
  "atomic": false,
  "expectedVersion": "可选：前端拿到的列表快照/ETag，校验选中集合未被他人改动",

```

- **服务端必须新增的校验/行为**：
  1. `spuIds` 去重后 ≤ 200（可配置），超限返回业务错误并提示改用批次任务接口（API-3）；
  2. 至少一个专区动作或规则，否则拒绝（`请选择会员或出清标签操作` 从服务端兜底）；

### 4.3 API-3 批次任务（大批量 / 可撤销；建议复用「导入任务」模式）

参考现有商品导入的 `preview → confirm → errors` 先例（`PBIZ/controller/admin/ProductImportController.java:59-81`；表 `product_import_job/product_import_error`，`BE/db/boot/48product_import_incremental.sql:11-45`），改造为专区打标批次：

| 方法/路径 | 作用 | 权限 | 关键出参 |
|---|---|---|---|
| `POST /product/goodsspu/tags/batch/jobs` | 创建批次：**只落批次与逐项 before/after 快照，不写商品**；入参同 API-1 拟定动作 + `idempotencyKey` | zone-batch | `batchId`、`batchNo`、`status`、`total`、`summary` |
| `POST /product/goodsspu/tags/batch/jobs/{batchId}/confirm` | 确认执行：按分片（建议 50–100 件/事务）执行；逐项记录结果与错误码；返回受理结果 | zone-batch | `acceptedAt`、`estimatedChunks` |
| `GET /product/goodsspu/tags/batch/jobs/{batchId}` | 查询状态与汇总（`PENDING_CONFIRM/EXECUTING/COMPLETED/PARTIAL/FAILED/CANCELLED`） | 读权限 | `status/summary/zones/sync` |
| `GET /product/goodsspu/tags/batch/jobs/{batchId}/items?page&size&result=ALL\|FAILED\|CHANGED` | 分页明细（商品名、changeType、失败码、before/after 摘要） | 读权限 | `records/total` |
| `POST /product/goodsspu/tags/batch/jobs/{batchId}/undo` | 按 before 快照回滚；逐项校验「当前值 == 批次 after 值」才回写，否则标记 `SKIPPED_CONFLICT` 并在结果中返回 | zone-undo | `restored/skipped/conflicts[]` |
| `GET /product/goodsspu/tags/batch/jobs?page&size` | 批次列表（操作人、时间、动作、商品数、状态、可撤销标记） | 读权限 | `records` |

- **存储建议**（二选一，需产品确认）：① 新增 `goods_zone_tag_batch` + `goods_zone_tag_batch_item`（batchNo、动作、规则快照、before/after JSON、operator_id/name、tenant_id、状态、成功/失败数、sync 状态）；② 复用 `product_change_log`（已有 before/after + operator，`BE/db/boot/48product_import_incremental.sql:47-62`）+ Redis/新表存批次聚合。方案 ① 更适合「批次列表 + 整批撤销」。
- **撤销边界**：只恢复本批次触碰的专区字段；批次之后被人工改过的商品默认跳过（避免二次覆盖）；撤销本身也是一个批次（可追溯）。
- **上限与异步**：`spuIds ≤ 200` 走 API-2 同步；`200 < N ≤ 1000` 走 API-3 异步；`> 1000` 直接拒绝并要求缩小筛选/拆分批次（阈值可配置）。

### 4.4 API-4 按筛选条件取 ID（支撑「全选筛选结果 / 换一批」）

- **方法/路径**：`POST /product/goodsspu/ids`（管理端；GET URL 放不下复杂筛选）
- **权限**：`product:goodsspu:page`
- **入参**：与 `GET /goodsspu/page` 相同的筛选对象（`name/categorySecondId/brandId/status/zoneType` 及后续新增），加 `limit`（默认 200、上限 1000）与 `cursor`（`lastId`，游标分页）。
- **出参**：`{ "total": 18, "ids": ["..."], "truncated": false, "nextCursor": null }`
- **服务端要求**：固定 `ORDER BY goods_spu.id ASC`（补齐现有 `selectPageByAdmin` 无排序的缺陷，G16）；只返回 `id`（不返回整行）；租户由拦截器注入。

### 4.5 API-5 批量读取专区状态（含覆盖来源与生效值）

- **方法/路径**：`POST /product/goodsspu/tags/query`（避免 URL 长度限制；也可提供 GET `?spuIds=a,b`，≤50 个）
- **权限**：`product:goodsspu:get`
- **入参**：`{ "spuIds": ["..."], "withSkus": true }`（去重后 ≤ 200）
- **出参**：`items[]` 每项：SPU 专区字段原值 + `resolved`（SPU/SKU 解析后的生效规则 + `source: SPU|SKU`）+ `skuOverrideCount` + `skuTagExclusionCount` + `skus[]`（`skuId`、`specsName`、`salesPrice`、`originalPrice`、覆盖原值、生效值、是否有覆盖）+ `effective`（同 API-1 的 `effective` 结构）。
- **服务端要求**：一次 SPU 批量查询 + 一次 SKU IN 查询；复用 `toSnapshot` 的 `firstNonNull` 解析但**保留来源标记**（新增字段，不改旧 DTO 语义）；上限 200。

### 4.6 API-6 价格与生效预览（管理端）

- **方法/路径**：`POST /product/goodsspu/tags/price-preview`
- **权限**：`product:goodsspu:edit`
- **入参**：`{ "spuIds": [...], "draftRules": { "memberDiscountRate": 0.9, "clearancePrice": null, "clearanceDiscountRate": 0.9, "clearanceExpireTime": "..." } | null, "includeLevelDiscount": false }`；`draftRules` 为空时按当前已保存规则预览。
- **出参**：按 SPU/SKU 列出 `salesPrice / originalPrice / memberPrice / clearanceBasePrice / clearanceTierRate / clearanceFinalPrice / expireTime / applied / skipReasons[]`；另附 `zoneSetting`（默认折扣、成本兜底、开关）与 `activitySyncHint`（「本次为静态预览，实际以同步后系统活动为准」）。
- **口径要求**：出清基础价复用 `ClearancePriceResolver`（`PAPI/util/ClearancePriceResolver.java`），最终价/分层复用同步服务的算价函数——**建议抽取为 `promotion-api` 或 `product-api` 的公共 Resolver**，禁止再复制一份（当前已有同步、`clearancePrices`、`clearanceSpuPrices`、`clearanceGoods` 多处口径，见 `GoodsZoneTagServiceImpl.java:443-608`、`MallZoneActivitySyncServiceImpl.java:215-271`）。
- **会员等级口径待产品确认**（见 §五-5）：`includeLevelDiscount=false` 时按「商品规则 + 专区默认折扣」预览；为 true 时需要显式传等级或按最低等级预览。

### 4.7 API-7 同步状态查询与手动重试

- **`GET /product/goodsspu/zone/sync-status?zoneType=member|clearance`**
  权限 `product:goodsspu:get`；出参：`{ zoneType, enabled, activityId, activityCode, activityStatus, rulesSkuCount, lastSyncTime, lastSyncResult, lastError, zoneDefaultDiscountRate }`。
  数据来源：`promotion_activity`（code/status/rules 反序列化计数/update_time）+ `mall_zone_setting`；若要精确「上次同步结果」需新增同步状态字段或表。
- **`POST /product/goodsspu/zone/sync`**
  权限 `product:goodsspu:edit`（或新 zone-batch）；同步触发当前租户重算，返回 `{ triggered:true, activityStatus }`；需限流（同租户 30s 内只允许一次）防止放大。
- **配套修复（必须）**：
  1. `RemoteGoodsZoneTagServiceImpl#listZoneSkus`：查询失败**抛异常**（或返回带 `failed` 标记的结构），禁止把失败当空列表（G13）；
  2. `syncTenant`：收到失败标记时**中止本次写入**，保留旧 rules；若必须清空（如专区关闭），只允许由「明确的开关状态」驱动，不得由「空快照」驱动；
  3. 同步结果返回给 `batchTags` 调用方（API-2 的 `sync` 字段），失败时前端不得再展示「价格已同步」。

### 4.9 双模式、租户、数据与容量约束（所有新增项适用）

## 五、待确认问题（需产品/Lead 决策，决定 G5/G2/G17 等修法）

1. **出清专区是否允许「只打标、不配规则」？** 这决定 G5 的修法：若允许（依赖专区默认折扣），单商品 `validateZoneFields` 必须放宽；若不允许，批量必须在 `clearanceTag=true` 且无规则时拒绝，并在 UI 标注必填。当前代码两种口径并存，必须二选一。
2. **批量规模上限与执行方式**：一次提交允许多少件？635 件全选是否接受异步批次（API-3）？阈值建议 200 同步 / 1000 异步，需确认。
3. **撤销粒度**：整批回滚？仅回滚未被后续修改的条目（冲突跳过）？是否允许撤销后再次撤销（撤销本身是批次）？
4. **是否允许批量覆盖 SKU 精调**：若允许，是否需要独立权限点 + 二次确认 + 影响范围提示？默认值是否从「清洗」改为「保留」？
5. **管理端价格预览的会员口径**：会员价 = `min(商品折扣率, 等级折扣率)`，管理端预览无法确定「哪个等级」；是按「商品规则 + 专区默认折扣（不含等级折扣）」预览，还是选择「最低等级/指定等级」预览？
6. **标签与规则是否允许分离**：`memberTag=null + 规则`、`clearanceTag=null + 规则` 是否属于合法运营动作（先存规则后启用）？若是，契约需显式 `ruleOnly` 并在 UI 提示「已保存未生效」；若否，直接拒绝。
7. **审计数据落点**：价格历史扩展 vs 统一复用 `product_change_log`；是否本期就做批次表（涉及双模式 SQL、`tenant.tables`、菜单/权限）。
8. **「换一批」是否需要一步式「替换」**：一步替换需要服务端在事务内完成「移出旧 + 加入新」并返回差异，复杂度高；若接受「两步（先移出、再加入）」则 API-2 + API-4 即可覆盖。
9. **批次保留期与合规**：批次/明细留多久？是否允许逻辑删除？撤销是否要强制填写原因？
10. **同步失败的对外语义**：批量接口是否应把「打标成功但价格未同步」作为部分失败返回（影响前端文案与运营心智）？还是仅展示同步状态、允许手动重试？
