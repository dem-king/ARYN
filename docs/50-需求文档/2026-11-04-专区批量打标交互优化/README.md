## 一、用户反馈与复现

### 1.1 原始诉求

用户（运营视角）反馈三条：

1. **同一批商品可以反复打标且无感知**：勾选这一页商品打标成功后，再勾选同一批商品，仍然可以继续打标，没有「已打标 / 无变化 / 将覆盖」的提示。
2. **「换一批」没有退出路径**：想把会员专区商品换一批时，无法快速清除之前打标的商品。
3. **整体交互问题多**：从截图与流程看，批量打标缺少预检、结果反馈和纠错手段。

### 1.2 截图与真实数据复现

截图（2026-11-04，`/product/goods/spu`，共 635 件商品、10 条/页）：

- 列表第 1 页 10 件商品**全部已带「会员」标签**，且 10 条全部勾选；
- 用户再次打开「批量专区打标」弹窗，选择「会员专区 = 打标、会员折扣率 0.9」准备再次提交；
- 弹窗只提示「已选 10 个商品」，**完全不展示这 10 件当前已在会员专区、当前规则是什么、本次是否有变化**。

本地库（`aryn_boot`）核对，证实这不是偶发场景：

| 证据 | 结果 |
|---|---|
| 商品总数 | 635 件（单租户） |
| 已打会员标签 | 18 件；已打出清标签 5 件 |
| 截图中的 10 件商品 | `南昌拌粉 216g×3盒`、`重庆小面 150g×5袋`、`花甲粉 200g×3桶` 等，均为 `is_member_item=1`、`member_discount_rate=0.9000` |
| 这批商品的打标来源 | `goods_price_history` 有 10 条 `member_rate / tag_save / 修改会员折扣率`，时间统一为 `2026-11-03 15:52:01`，正好对应一次 10 件的批量打标 |
| 再次提交是否留痕 | 同值字段不写历史（`GoodsPriceHistoryService#recordIfChanged` 同值跳过），但 `recordSpuTagChanges` 对**本次未触碰的专区**会写「旧值 → null」的**幽灵历史**（详见 03 G22）；`operator` 恒为 `NULL`；`sys_log` 表 0 条记录（`@SysLog` 切面未注册为 Bean，03 G21） |

结论：**用户截图的动作就是「对已经打标且规则相同的 10 件商品再打一次标」**，系统没有任何提示、没有「无变化」结果、也没有操作痕迹——这正是诉求 1 的现场。

另外，本次审计还发现两个未在截图中暴露、但风险比交互问题更高的后端缺陷（详见 [03 后端能力缺口与改造点](./03-后端能力缺口与改造点.md)）：

- **同步失败可能清空全租户专区价**：快照查询异常被吞成空列表（`RemoteGoodsZoneTagServiceImpl.java:32-49`），同步任务会把空 rules 写入系统活动并暂停（`MallZoneActivitySyncServiceImpl.java:273-335`），而批量接口仍返回成功——一次瞬时 DB/网络抖动即可让 C 端专区价整体消失，最迟次日 03:10 兜底任务才恢复（03 G13）。
- **审计数据不可信**：专区规则变更会写「未触碰专区」的幽灵历史（`GoodsZoneTagServiceImpl.java:832-857`），`operator` 恒空、`sys_log` 0 条，批量清 SKU 精调不落历史；这会让「谁、何时、把哪批商品改成了什么」无法回答，也无法支撑撤销（03 G21/G22）。

## 二、现状实现

### 2.1 当前交互时序

```
商品列表（全部商品）
  └─ 勾选当前页若干行（Element Plus 表格选择，仅当前页）
       └─ 点击工具栏「专区打标」
            └─ 弹窗：仅展示「已选 N 个商品」
                 ├─ 会员专区：[不修改 / 打标 / 取消标签] + 折扣率 / 固定价
                 ├─ 低价捡漏：[不修改 / 打标 / 取消标签] + 出清价 / 折扣率 / 截止时间
                 └─ 勾选框：同时清除已配置的 SKU 级精调
                      └─ 确认打标 → POST /product/goodsspu/tags/batch
                           └─ 弹一条 toast（成功 / 第一条错误 / 第一条警告）
                           └─ 关闭弹窗 + 刷新列表（选择被清空）
```

- 列表「专区」列：同文件 `554-580`，只显示「会员/捡漏」标签，无规则、无 SKU 精调、无生效状态

### 2.2 数据与规则语义（决定了 UI 必须展示什么）

- SPU 是选品单位（`is_member_item` / `is_clearance_item`），SKU 是价格精调覆盖（`NULL = 继承 SPU`）。见 `GoodsZoneTagServiceImpl.java:45-53`、`710-737`。
- 会员价 = `min(售价 × min(商品折扣率, 等级折扣率), 会员固定价)`，不低于成本兜底下限；
- 出清价 = 固定价，或 `原价 × 出清折扣率`，两者都没有则不产生出清价（C 端出清列表会直接过滤掉该商品）；
- 打标后由促销域同步到系统托管活动（`SYS_MEMBER_ZONE` / `SYS_CLEARANCE_ZONE`），失败不阻断打标，每日 Job 兜底。

由此可推出：**「标签存在」不等于「专区价格生效」**。缺失规则、倒挂（算出的专区价 ≥ 售价）、出清已到期、商品下架，都会让商品「有标签但不生效」，而当前列表与弹窗都没有任何这类状态提示。

## 四、根因分析

1. **模型错位**：专区运营本质是「维护一个商品集合（成员 + 规则）」的集合操作，而当前实现把它建模成「在通用商品列表上做一次性批量写」。没有 membership 视图、没有变更检测、没有批次概念，因此「重复打标」「换一批」这两个最自然的运营动作在现有模型里没有落点。
2. **状态不可见**：数据模型是「SPU 标签 + SPU 规则 + SKU 覆盖」两层，但 UI 只暴露 SPU 标签这一层，规则、SKU 覆盖、生效状态全部不可见，导致所有操作都是盲写。
3. **流程缺闭环**：提交 → toast → 刷新即结束。缺「预检 → 执行 → 结果明细 → 复核 → 纠错/撤销」的完整闭环，部分失败和警告被压缩成一句话。
4. **选择模型绑在页面上**：选择绑定当前页 DOM 行，不绑定「筛选结果集」，跨页/全量操作不可行；这直接卡死「换一批」。
5. **入口不一致**：批量接口与单商品编辑对同一份数据使用不同校验和不同清空语义（出清必须有规则 vs 批量允许无规则；null 清空 vs NOT_NULL 忽略；SKU 精调在批量里保留、在表单里不可见），两个入口会互相制造对方无法处理的状态。

## 五、改造方向

### 方案 A：现有列表页 + 弹窗增强（低成本，修复「盲写 + 无反馈」）

保留现有页面结构，把弹窗升级为「状态感知 + 影响预检 + 结果面板」：

1. **打开即预检**：根据所选 SPU 查询当前状态（新增预检接口），弹窗顶部显示分组：
   - 会员专区：已加入 8 件（9 折）、未加入 2 件、规则将变化 0 件、有 SKU 精调 3 件；
   - 低价捡漏：已加入 1 件（¥19.9，3 天后到期）、未加入 0 件；
   - 异常项：2 件已下架 / 1 件缺出清规则（不生效）。
2. **动作拆分为集合语义**：每个专区改为 `加入/更新规则`、`移出专区`、`不修改` 三选一；「移出」使用危险色并二次确认（列出将清空的 SPU 规则与 SKU 精调数量）；确认按钮文案随动作变化（`确认加入 2 件 / 更新 8 件`、`确认移出 10 件`）。
3. **无变化识别**：后端返回每条 `changeType`（新增/更新/无变化/失败）与汇总；全部无变化时按钮禁用并提示「所选商品均无需变更」。
4. **结果面板替代 toast**：复用同页「批量导入」已有的「预览 + 错误明细表」模式（`index.vue:759-775`），按 成功/无变化/失败/警告 分组展示明细（商品名、原因），支持复制失败清单、重试失败项、查看本次商品（打开结果明细，不依赖恢复表格选择）。
5. **列表专区列升级**：标签 + 规则摘要（`9折` / `¥29.9` / `SKU精调2`）+ 生效异常警示；页面响应已含规则字段，规则摘要可纯前端实现。
6. **选择增强（与方案 C 共用）**：跨页保留选择、显示「已选 N 件」悬浮条、支持「全选当前筛选结果」。这需要后端提供按筛选条件返回全部 ID 的接口。

### 方案 B：独立的「专区商品管理」页（推荐中长期，真正贴合运营心智）

入口：营销 → 专区管理（会员专区 / 低价捡漏），或商品列表专区筛选旁「管理此专区商品」。

- 顶部：专区开关、默认折扣、商品数、最近一次操作（人/时间/批次）；
- 商品表格：商品、当前规则、SKU 精调数、C 端生效状态（正常/倒挂/缺规则/已到期/下架）、加入时间、操作（改规则 / 移出）；
- 添加商品：商品选择器默认只看「未加入本专区」，支持全选筛选结果，添加时统一设规则，预览「新增 X / 跳过已存在 Y」；
- 移出：勾选 → 批量移出，二次确认影响范围；
- 「换一批」：移出旧批次 + 添加新批次（各自一步完成）；如确需一步替换，再单做「替换」向导（必须先预览再执行）；
- 操作记录：批次列表（操作人、时间、动作、商品数、成功/失败、明细、回滚）。

### 方案 C：列表页「专区操作模式」（过渡方案，解决「换一批」燃眉之急）

- 当专区筛选为 `会员专区` 时，工具栏显示「全选筛选结果（18 件）/ 批量移出专区 / 批量调整规则」；
- 表格启用跨页选择 + 顶部「已选 N 件（跨页）」条；
- 「专区」列升级为规则摘要 + 状态徽标，点击可打开单商品精调抽屉（复用已有 `GET /tags/{spuId}`、`PUT /{spuId}/tags`）。

## 六、推荐交互规格（P0 目标态）

### 6.1 选择与批量条

- 表格启用 `reserve-selection`（需 `row-key`，当前已有 `row-key="id"`），翻页/刷新后保留选择；
- 筛选条件变化时清空选择并给出轻提示（避免跨筛选误操作）；

## 七、后端/API 改造清单（建议契约）

> 详细证据与边界见 [03 后端能力缺口与改造点](./03-后端能力缺口与改造点.md) 第四章：API-1 批量预检、API-2 批量执行增强、API-3 批次任务（可复用现有商品导入的 preview→confirm→errors 模式）、API-4 按筛选取 ID、API-5 批量读取专区状态、API-6 价格与生效预览、API-7 同步状态查询/手动重试。

1. **预检接口**：`POST /product/goodsspu/tags/batch/preview`
   入参：`spuIds` + 拟执行动作/规则；出参：分组汇总 + 逐商品当前状态、`changeType`（ADD/UPDATE/NO_CHANGE/REMOVE/INVALID）、`skuOverrideCount`、`willClearSkuRules`、`effective.skipReasons`、`warnings`。只读、上限 200。
2. **批量接口增强**：`batchSave` 返回 `batchId`、汇总（成功/无变化/失败/变更数）、逐条 `changeType` 与变更前后摘要、`sync.status`；对同值操作返回 `NO_CHANGE` 而不是 `OK`；入参增加 `clientRequestId` 幂等键；错误码化（`SPU_NOT_FOUND / INVALID_RULE / NO_ORIGINAL_PRICE / EXPIRED_TIME / LIMIT_EXCEEDED / VERSION_CONFLICT`）。
3. **按筛选取 ID**：`POST /product/goodsspu/ids`（入参同分页查询，出参 `total + ids + truncated`，服务端固定 `ORDER BY id`，上限 1000，或游标分页），支撑「全选筛选结果」与「换一批」。
4. **批量移出**：复用 `tags/batch` 的 `memberTag=false` / `clearanceTag=false`，但补二次确认所需的「影响范围预检」（规则清空数、SKU 精调数）。
5. **批量上限与执行方式**：`spuIds` 去重后 ≤ 200/请求；服务端改批量查询（一次 `selectBatchIds` + 一次 SKU 分组查询）替代 N+1，缩短事务；200–1000 件走批次任务（分片执行、可查进度），>1000 拒绝。
6. **操作记录/撤销（P1）**：新增 `goods_zone_tag_batch(_item)`，或复用 `product_change_log`（已有 before/after 快照与 operator 字段，当前未被专区打标使用）；记录 operator、batchId、动作、规则、成功/失败，支持按批次回滚（回滚前校验当前值仍等于批次 after，冲突项跳过并报告）。
7. **统一校验**：批量与单商品共用同一校验器（出清 tag-only 口径必须二选一）；`operator` 从登录态写入价格历史；修幽灵历史（仅记录本次真正触碰且发生变化的字段）。
8. **同步安全（P0 必须先修）**：快照查询失败必须抛错/带失败标记，禁止用空列表覆盖非空 rules；同步失败不得再返回「已同步」；提供同步状态查询与限流手动重试（API-7）；评估 `promotion_activity.rules` 的 `text` 容量（API-3 超 200 件异步化前必须确认）。
9. **操作日志**：修复 `@SysLog` 切面/监听器 Bean 注册，并在 requestParams 中记录 batchId、动作、规则摘要、spuIds 截断，限制长度。

## 八、验收标准（建议）

- 对已打标且规则相同的商品再次提交：弹窗明确提示「所选商品均无需变更」，提交结果为「无变化 10」，不产生无意义写入；
- 混合选择（8 件已打标 + 2 件未打标）提交：预检显示「新增 2 / 更新 8」，结果面板与预检一致；
- 部分失败：结果面板列失败商品与原因，可复制/重试；成功商品不受影响；
- 「换一批」：筛选会员专区 → 全选 18 件 → 一次移出；筛选未加入 → 全选新批次 → 一次加入；两步内完成；
- 批量出清「只打标不配规则」被拦截或明确警告，与单商品编辑行为一致；
- 操作后可在列表直接看到规则摘要与生效警示，无需逐个打开商品；
- 同步失败时界面必须明确展示「标签已保存，价格同步失败/延迟，可重试」，不得再显示「价格已同步」；人为模拟快照查询失败时，系统活动 rules 不得被清空、C 端既存专区价不得消失；
- 只操作会员标签的批次，不得在价格历史里产生出清规则的变更记录（幽灵历史回归）；操作记录中能查到 operator 与 batchId。

## 九、待确认问题

**产品/运营口径（决定交互方案）**

1. **范围**：先做「列表页弹窗增强 + 选择增强」（P0，约 3-5 人日），还是直接做「专区商品管理页」（方案 B，约 4-6 人日 + P0）？
2. **「换一批」期望**：接受「先移出旧批次、再加入新批次」的两步批量流程，还是必须一步「替换」（需要更复杂的预检与回滚设计）？
3. **规则能力**：批量是否需要「按类目/价格区间设置不同规则」，还是当前「一批一个统一规则」够用？
4. **出清专区是否允许「只打标、不配规则」**：若允许（依赖专区默认折扣），需放宽单商品校验；若不允许，批量必须拦截并在 UI 标注必填。当前两种口径并存，必须二选一。
5. **批量规模与执行方式**：一次提交允许多少件？635 件全选是否接受异步批次（建议 200 同步 / 200-1000 异步 / >1000 拒绝）？
6. **撤销粒度**：整批回滚？仅回滚未被后续修改的条目（冲突跳过）？撤销是否本身也记为批次？
7. **审计/撤销数据落点**：价格历史扩展 vs 统一复用 `product_change_log`；是否本期就建批次表（涉及双模式 SQL、`tenant.tables`、菜单/权限）。
8. **价格预览口径**：会员价涉及等级折扣，管理端预览按「商品规则 + 专区默认折扣（不含等级折扣）」还是选择「最低等级/指定等级」预览？
9. **标签与规则是否允许分离**：`memberTag=null + 规则`（先存规则后启用）是否属于合法运营动作；若是需显式 `ruleOnly` 并在 UI 提示「已保存未生效」。

**技术/验证口径**

10. **同步失败对外语义**：批量接口是否应把「打标成功但价格未同步」作为部分失败返回（影响前端文案与运营心智），还是仅展示同步状态并允许手动重试？
11. **是否补齐组件级/接口级自动化用例**：现有测试未锁定选择保持、无变化识别、幽灵历史、同步失败不清空等交互与数据假设，改造必须同步补测试。

### 10.5 遗留与边界

1. 撤销目前只回滚标签/规则，不额外写一条「撤销」价格历史；如需完整价格流水，后续在 undo 中补记录（批次表已有 before/after 快照与操作人）。
2. 撤销批次后 Controller 会触发一次同步，但批次头 `syncStatus` 不回写撤销后的同步结果（页面以 `undoStatus` 与专区状态条为准）。
3. cloud 模式仅完成代码/双模式 SQL/静态校验，未在 cloud 集群实测；boot 已真实库 E2E。
4. `@SysLog` 全局启用后所有带注解的写接口都会异步落 `sys_log`，需关注日志量；参数摘要已脱敏并截断 2000 字符。
5. 未做「保留筛选结果 + 跨筛选选择」的更复杂选择模型（当前筛选变化清空选择是刻意约束）。
6. 本地 E2E 曾临时使用 captcha 跳过开关与 Playwright 注入会话，相关临时改动已在合并前移除；正式环境登录仍走图形验证码。
7. 验收回归修复（2026-11-04）：① 预检允许「尚未选择动作」，不再在弹窗刚打开时因缺动作报错；② 预检请求兼容契约中的 `memberAction/clearanceAction`（ADD/REMOVE/NONE），修复「切换动作后影响汇总不刷新」；③ 预检失败时动作选择区仍可用，用户可改动作后自动重试，不再死锁在错误页。
