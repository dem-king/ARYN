## 一、结论摘要（5 条）

1. **用户三条诉求都能在前端代码里找到直接根因**：勾选随翻页/刷新被清空且无跨页选择（A1）；打标弹窗只显示「已选 N 个商品」，不显示这些商品当前的专区状态（B1）；重复打标时后端逐条恒返回 `success=true / message="OK"`，前端恒提示「打标成功」，成功与「无变化」完全不可区分（C3）。
2. **结果反馈链路是当前最薄弱的一环**：逐条结果只取第一条失败/警告消息（C1）、不论部分失败都立即关窗并刷新（C2）、「专区价格已同步」这句文案不被后端保证（同步失败会被吞掉，C4）。失败时运营既看不到明细，也无法只重试失败项。
3. **列表信息不足以支撑「复核 / 换批」**：专区列只有「会员」「捡漏」两枚标签，规则值、SKU 覆盖、到期/倒挂状态全都不展示，而列表接口其实已经返回了全部专区字段（D1）；「专区」筛选只能看结果，不能在结果集上全选/批量移出（D2）。
4. **单商品编辑页与操作手册承诺不一致**：`getZoneTags` / `saveZoneTags` 两个 API 已写好但全仓无调用（E1），页签里没有 SKU 级精调 UI；清空/取消标签受 MyBatis-Plus `not_null` 更新策略影响不会落库（E2）。
5. **有低成本高收益的修复起点**：表格已经设了 `row-key="id"`，选择列加上 `reserve-selection` 即可解决跨页丢选；同一页面的「批量导入」已有「结果预览 + 错误明细表」模式（`UI/views/product/goods-spu/index.vue:759-775`），可直接复用到打标结果面板。

## 三、问题清单

> 编号说明：本文编号（A1…F3）仅用于本审计附录内部引用；与同目录 `README.md` 第三节的问题编号（A1…F4）是两套独立编号，请勿交叉引用。

### A. 列表选择生命周期（对应任务必须覆盖点 1）

#### A1 · P0 翻页 / 搜索 / 刷新 / 从编辑页返回都会清空已选，跨页批量做不了

- **现象**：当前页勾选后，只要翻页、点搜索、点重置、点刷新、或从商品编辑页返回列表，已勾选全部丢失；没有「全选筛选结果」或「跨页选择」。
- **代码证据**：
  - `UI/views/product/goods-spu/index.vue:478-487`：`ElTable` 已设 `row-key="id"`，但 `type="selection"` 列**没有** `reserve-selection`；
  - `UI/views/product/goods-spu/index.vue:257-274`：`initPage` 直接 `tableData.value = response.records`（每次都是新数组）；
  - `UI/views/product/goods-spu/index.vue:623-628`（页码/页长变化 → `initPage`）、`340-345`（搜索/重置 → `initPage`）、`469-474`（刷新按钮 → `initPage`）；
  - `UI/views/product/goods-spu/index.vue:334`：`useKeepAliveRefresh(initPage)`，从编辑页返回也会触发静默刷新 → 再次替换 data（实现见 `UI/composables/use-keep-alive-refresh.ts:14-23`）；
  - Element Plus 2.14.3 行为：`EP/components/table/src/store/index.mjs:27-41` 的 `setData` 中 `if (unref(states.reserveSelection)) assertRowKey(); else if (dataInstanceChanged) clearSelection();`；`EP/components/table/src/store/watcher.mjs:219-226` 的 `clearSelection` 清空并 `emit("selection-change", [])`；`reserveSelection` 选择列 prop 默认为 `false`，其注释明确「works when `type` is 'selection'；row-key is required」：`EP/components/table/src/table-column/defaults.mjs:113-115`。本页 `row-key` 已具备，开启 `reserve-selection` 成本很低。
- **事实/推断**：【已确认事实】上述代码与依赖源码均可复核；清空后 `handleSelectionChange` 会把 `multipleSelection` 置空（`index.vue:327-329`）。
- **用户影响**：18 个会员商品要分 2 页各选一次；100 个商品要重复 10 轮且每次从头勾；无法确认「上一页选了什么」。这是「换一批」操作变成苦力活的直接原因之一。
- **建议方向**：选择列增加 `:reserve-selection="true"`（`row-key` 已具备）+ 工具栏显示「已选 N 件 / 清空选择」；中期提供「全选当前筛选结果（共 N 条）」的服务端批量语义。

#### A2 · P1 选中态没有页面级反馈，也没有「清空选择」入口

- **现象**：勾选商品后，页面上除了相关按钮由 disabled 变可用外没有任何提示；唯一显示数量的是打标弹窗内的一行提示，关掉弹窗就看不到选了几件、选了谁。
- **代码证据**：`UI/views/product/goods-spu/index.vue:327-329`（`handleSelectionChange` 只赋值）；`423-467`（工具栏无已选计数/清空入口）；`455`（只有 `:disabled` 联动）；`UI/components/page/page-toolbar.vue:1-23`（工具栏只展示总数，无选中数 slot 约定）；数量唯一出现处：`index.vue:641`。
- **事实/推断**：【已确认事实】。
- **用户影响**：勾错一行只能肉眼回找；换批时不知道当前还挂着几次选择；批量操作前的「确认感」缺失。
- **建议方向**：在工具栏固定展示「已选 N 件（含跨页）」+「清空选择」+「全选本页」；危险操作按钮与选中数同区展示。

#### A3 · P2 搜索 / 重置不重置页码，依赖分页组件自动回退，会多打一次请求并短暂空列表

- **现象**：在第 3 页时修改筛选条件并搜索，请求仍带 `current=3`；若结果不足 3 页，会先渲染「暂无商品」，再由分页组件把页码钳回有效页并发起第二次请求。
- **代码证据**：`UI/views/product/goods-spu/index.vue:257-274`（`params.current = page.value.currentPage`，无重置逻辑）；`340-345` 搜索/重置直接 `initPage`；Element Plus 分页在总页数变小时会钳制当前页并 `emit("current-change")`：`EP/components/pagination/src/pagination.mjs:218-241`（注解：钳制后经 `Pagination` 封装 → `@change` → 再次 `initPage`，见 `UI/components/pagination/index.vue:21-28`）。
- **事实/推断**：【已确认事实】钳制与二次请求路径；「用户看到空列表闪烁」为【推断】（未运行浏览器验证）。
- **用户影响**：筛选后有明显的白屏/空态闪动，误以为没有数据。
- **建议方向**：搜索/重置时显式 `page.currentPage = 1`。

### B. 打标弹窗（对应任务必须覆盖点 2）

#### B1 · P0 弹窗不显示所选商品当前的专区状态，无法区分「新增 / 覆盖 / 无变化」

- **现象**：打开弹窗只看到「已选 N 个商品」，看不到这 N 个里多少个已打标、当前折扣率/固定价/出清价/到期时间是什么；用户对已全部带「会员」标签的 10 个商品再次选择「打标 0.9」提交时，界面没有任何「这些已经是会员商品」的提示。
- **代码证据**：
  - `UI/views/product/goods-spu/index.vue:128-143`：`openZoneDialog` 只做 `Object.assign(zoneForm, 默认值)` + `zoneDialogVisible=true`，**没有任何查询或行数据读取**；
  - `UI/views/product/goods-spu/index.vue:636-642`：弹窗顶部提示只拼接了 `multipleSelection.length`；
  - `UI/views/product/goods-spu/index.vue:643-687`：动作只有「不修改 / 打标 / 取消标签」，无现状字段；
  - 数据其实是现成的：管理端列表 SQL 已返回全部专区字段 `BE/aryn-product/aryn-product-biz/src/main/resources/mapper/GoodsSpuMapper.xml:53-60`（`is_member_item`、`member_discount_rate`、`member_price_fixed`、`member_price_floor`、`is_clearance_item`、`clearance_price`、`clearance_discount_rate`、`clearance_expire_time`），但列表只渲染了两枚标签（`index.vue:554-580`），弹窗未复用；
  - SKU 覆盖信息不在列表返回中，要按 SPU 逐个查 `GET /product/goodsspu/tags/{spuId}`（`BE/aryn-product/aryn-product-biz/src/main/java/com/aryn/cloud/product/controller/admin/GoodsSpuController.java:75-80`），无批量查询接口。
- **事实/推断**：【已确认事实】「不发请求、不读行数据、只显示数量」。
- **用户影响**：**用户反馈 1 的直接原因**：同一批商品重复提交，界面无法告知「已打标 / 无变化」，运营只能靠翻列表标签猜；也无法预判本次提交会覆盖掉哪些旧规则。
- **建议方向**：打开弹窗时基于选中行计算并展示现状摘要（如「6 个已打标（0.9 折）、2 个已打标（固定价）、2 个未打标」），每个字段展示「当前值 → 本次值」；SKU 覆盖数需要后端补批量查询接口（待确认问题 2）。

#### B2 · P1 「打标」与「取消标签」语义耦合在同一弹窗，「取消标签」无二次确认

- **现象**：一个下拉同时包含「打标」和「取消标签」，页面底部按钮恒为「确认打标」；选择「取消标签」后点确认会直接执行批量移除，没有任何二次确认或影响范围提示。
- **代码证据**：`UI/views/product/goods-spu/index.vue:643-648`（会员专区下拉含 `取消标签`）、`681-687`（低价捡漏同理）；`145-192`（`submitZoneTags` 直接发接口，无 `ElMessageBox.confirm`）；`730-739`（按钮文案恒为「确认打标」，且无 disabled 条件）。后端「取消」的实际影响面：SPU 规则被置空 `BIZ/service/impl/GoodsZoneTagServiceImpl.java:801-805`、`815-819`；SKU 规则被无条件清空 `117-119`、`127-129`（与 `overwriteSkuRules` 无关，实现见 `900-916`）。
- **事实/推断**：【已确认事实】。
- **用户影响**：误点两下即可批量清掉 10+ 商品的会员/出清规则，旧折扣率/固定价/截止时间不可恢复（只能凭记忆重配）；与「换一批」操作直接相关。
- **建议方向**：取消标签独立入口与独立按钮；提交前二次确认并列出「将移出 N 个商品，同时清空其 SPU/SKU 专区规则」；按钮文案随动作切换。

#### B3 · P1 `overwriteSkuRules` 文案与实际生效范围不一致，且一个开关同时控制两个专区

- **现象**：弹窗只有一个复选框「同时清除已配置的 SKU 级精调，所有规格统一按本次规则」，但它同时作用于会员专区和低价捡漏；勾选后是否真正清除 SKU 精调，取决于「该专区选择了打标且本次确实填了规则」；直接选择「取消标签」时反而不需要勾选也会清空 SKU 规则。
- **代码证据**：
  - `UI/views/product/goods-spu/index.vue:727-729`：单个 `ElCheckbox`，两个专区共用；`751` 提交时全局透传 `overwriteSkuRules`；
  - 后端判定：`BIZ/service/impl/GoodsZoneTagServiceImpl.java:103-105`（`memberRuleProvided` / `clearanceRuleProvided` 仅由价格/时间字段是否非空决定）、`123-125`（会员：`memberRuleProvided && overwriteSkuRules` 才 `clearSkuMember`）、`132-134`（出清同理）；
  - 取消标签路径无条件清 SKU：`117-119`、`127-129`；
  - `BIZ/service/impl/GoodsZoneTagServiceImpl.java:900-916`（`clearSkuMember` / `clearSkuClearance` 的实现）。
- **事实/推断**：【已确认事实】后端生效条件；「用户以为勾了就清」为【推断】（由文案与生效条件不一致推出）。
- **用户影响**：只打标不填规则时勾选无效（SKU 精调仍在，结果与「所有规格统一按本次规则」相反）；取消标签时没勾也会清掉 SKU 精调；两个专区绑死，无法只清会员的 SKU 精调。
- **建议方向**：按专区拆成两个复选框，并动态展示「将清除 X 个 SKU 精调」；未填规则时置灰/说明「本次无规则，SKU 精调保留」；取消标签的清理逻辑在文案里明确。

#### B4 · P2 弹窗无表单语义与内联校验：「打标」可以不填任何规则，默认口径只藏在小字/placeholder 里

- **现象**：弹窗未包裹 `ElForm`，没有必填标识、没有内联错误提示；「打标」动作可以不填折扣率/固定价直接提交，弹窗只有一行小字说明「会员价下限自动兜底」；「折扣率与固定价取低」只写在 placeholder 中。
- **代码证据**：`UI/views/product/goods-spu/index.vue:6-26`（import 列表没有 `ElForm`）、`636-729`（`ElFormItem` 直接挂在 `ElDialog` 下）；`146-148`（只校验「至少选了一个专区动作」，用 `ElMessage.warning`）；后端允许只打标签：`BIZ/service/impl/GoodsZoneTagServiceImpl.java:789-793`（注释「允许只打标签：P1 专区默认折扣率可在促销域配置」）；placeholder 文案：`index.vue:660`（`0.9 = 9折`）、`672`（`与折扣取低`）、`696`（`与折扣二选一`）、`710`（`对原价计算`）。
- **事实/推断**：【已确认事实】。
- **用户影响**：运营不知道「不填规则」会发生什么（沿用旧规则 / 用专区默认折扣 / 只打标签），提交后的价格结果不可预期；错误只能靠 toast 感知，没有字段级定位。
- **建议方向**：用 `ElForm + rules` 承载，按动作显示必填/可选；在弹窗内生成一行「本次将写入：会员折扣率 0.9；低价捡漏不变」的提交摘要。

#### B5 · P2 标题与按钮文案和实际行为不符

- **现象**：弹窗标题「批量专区打标」，但它同时执行「取消标签」；确认按钮恒为「确认打标」，即使当前选择的是取消标签。

- **事实/推断**：【已确认事实】。
- **用户影响**：语义误导，提高误操作概率（尤其与 B2 的无确认叠加）。
- **建议方向**：标题改为「管理专区标签」；按钮按动作显示「确认打标 / 确认取消标签」；两个专区动作不同时，按钮旁加动作摘要。

#### B6 · P1 弹窗允许「出清只打标、不填规则」，会造出单商品编辑页无法保存的状态

- **现象**：批量弹窗选择「低价捡漏=打标」时，出清价/出清折扣率/截止时间都可以留空并提交成功，商品被置为「出清商品」但没有任何出清规则；之后进单商品编辑页保存会报「出清商品必须配置出清价或出清折扣」，运营不知道是哪里来的脏状态。

- **用户影响**：批量操作制造「标签在、价格规则缺失」的半成品状态，C 端不出价；后续任意一次普通编辑都会被专区校验拦下，运营无法理解报错来源。

### C. 提交与结果反馈（对应任务必须覆盖点 3）

#### C1 · P1 部分失败 / 警告只弹第一条消息，逐条明细被丢弃

- **现象**：后端返回的是逐条结果数组，前端只取 `failed[0].message` 或 `warnings[0].message` 弹一个 toast；失败商品名、失败原因列表、成功条数都不展示。
- **代码证据**：`UI/views/product/goods-spu/index.vue:171-186`（`failed.length > 0` 只拼第一个 message；`warnings` 分支同理，且失败与警告同时存在时警告被忽略）；后端逐条结果结构：`BE/aryn-product/aryn-product-api/src/main/java/com/aryn/cloud/product/api/vo/GoodsZoneTagResultVO.java:20-38`（含 `spuId/spuName/success/message`）；接口：`BIZ/controller/admin/GoodsSpuController.java:65-73`；需求背景 `DOC/2026-11-02-会员专区与低价捡漏规则化改造/README.md:175`（批量接口「返回逐条结果」）、`392`（出清打标时逐条返回「先涨后降」提示）。
- **事实/推断**：【已确认事实】。
- **用户影响**：N 个商品里哪几个失败、为什么失败无从得知，只能全选重试；「先涨后降」这类安全警告也只会闪现一条，且不带商品名，无法据此决策。
- **建议方向**：结果面板按「成功 / 无变化 / 失败」分组列出逐条结果（商品名 + 原因），支持复制、导出、仅重试失败项。

#### C2 · P0 不论成功、警告还是部分失败，弹窗都立即关闭并刷新，失败明细无法回看、无法重试

- **现象**：`submitZoneTags` 在拿到结果后无条件关窗并刷新列表；即使有失败项也不停留、不展示明细，只留一个转瞬即逝的 toast。
- **代码证据**：`UI/views/product/goods-spu/index.vue:187-188`（`zoneDialogVisible.value = false; initPage();` 无条件执行）。
- **事实/推断**：【已确认事实】。
- **用户影响**：部分失败时运营很容易以为全部成功（只看到一条 warning，且和成功提示长得像）；要补救只能把整批重新选一遍（而 A1 让重新勾选成本极高），没有「只重试失败商品」的可能。
- **建议方向**：结果面板常驻弹窗内；存在失败时保持弹窗打开并高亮失败项，提供「仅重试失败」；成功时也明确展示「实际变更 N 条 / 无变化 M 条」；刷新列表但不清选择（配合 A1）。

#### C3 · P0 重复打标与「无变化」没有任何提示：后端恒返回 OK，前端恒提示成功

- **现象**：对已打标且规则相同的商品再次提交，后端会照常重写同一批值并逐条返回 `success=true, message="OK"`；前端统一提示「打标成功，专区价格已同步」，与真正新增/变更无法区分。
- **代码证据**：
  - `UI/views/product/goods-spu/index.vue:178-186`（无 warning 即成功提示）；
  - 后端成功消息恒为 `OK`：`BIZ/service/impl/GoodsZoneTagServiceImpl.java:139-144`；打标写入本身是幂等的 `780-830`（`applySpuTags` 直接 UPDATE，不比较旧值）；
  - 后端其实**有**变化判定能力但只用于价格历史：`BIZ/service/impl/GoodsPriceHistoryService.java:33-49`（`recordIfChanged` 对同值直接 return，不落历史），说明「是否变化」可计算但未回传给前端。
- **事实/推断**：【已确认事实】「无差异返回」；「用户因此反复提交」为【推断】，但与用户反馈 1 的描述一致。
- **用户影响**：**用户反馈 1 的直接原因**：运营无法确认本次提交是否真的产生变化，只能反复提交；也无法向业务方证明「这批已经打过了」。
- **建议方向**：接口结果增加 `changeType`（created / updated / unchanged）及变更前值；前端按类型分别提示（例如「打标 3 个、更新 5 个、无变化 2 个」）；对全量无变化的批次给出明确文案。

#### C4 · P1 成功提示声称「专区价格已同步」，但同步失败会被后端吞掉，前端无法感知

- **现象**：成功 toast 固定文案「打标成功，专区价格已同步」，而打标后触发的系统活动同步是「尽力而为」：异常只记日志、不回滚、不影响接口返回。
- **代码证据**：`UI/views/product/goods-spu/index.vue:184`（文案）；`BIZ/controller/admin/GoodsSpuController.java:100-111`（`syncZonesQuietly` 捕获异常仅 `log.warn`，注释「同步失败不回滚打标结果，每日兜底 Job 会重试」）、`71`（批量接口调用该同步）。

- **建议方向**：文案降级为「标签已保存」；若后端能返回同步状态则区分展示「价格同步成功 / 延迟生效（后台自动重试）」；不要在前端承诺「已同步」。

#### C5 · P2 整体请求失败时没有 catch：无内联错误、无重试，且可能留下过期选择

- **现象**：`submitZoneTags` 只有 `try/finally`，整包请求失败（网络错误、后端事务回滚 500）时靠全局拦截器弹 red toast，弹窗停留在原状态；`zoneSaving` 复位后按钮可再次点击。失败时不刷新列表，之前的选择保留且不提示：如果请求实际已在服务端生效但响应丢失（超时），界面选择会与库内状态不一致。
- **代码证据**：`UI/views/product/goods-spu/index.vue:169-191`（无 catch）；全局错误提示：`UI/api/request.ts:149-169`（`errorMessageResponseInterceptor` → `ElMessage.error`）。
- **事实/推断**：【已确认事实】代码结构；「未处理 Promise rejection / 超时后界面与库内不一致」为【推断】（依赖网络时序，未运行验证）。
- **用户影响**：用户不知道是全部失败还是部分成功，容易重复点击；错误提示与弹窗分离，无法定位字段问题。
- **建议方向**：`catch` 后保留弹窗，内联展示失败原因并提供「重试」；失败时同时刷新列表以校正现状。

#### C6 · P2 没有批次概念，也没有撤销入口：打错一批只能凭记忆重配

- **现象**：一次批量提交不产生批次号、不支持「撤销本次」；后端有价格历史查询接口，但前端没有 API 封装也没有入口。

- **事实/推断**：【已确认事实】无批次/无前端历史入口；「无撤销接口」为【推断】（本次只读审计未见相关接口，需后端确认）。

- **建议方向**：结果面板带批次号与「撤销本批次」；接入已有价格历史做抽屉追溯（撤销能力需后端补接口，见待确认问题 4）。

### E. 与单商品编辑页「专区标签」的一致性（对应任务必须覆盖点 5）

- **建议方向**：接 `getZoneTags` 回显 + `saveZoneTags` 保存，在页签内加 SKU 表格（SKU 名称、售价、会员折扣/固定价/下限、出清价/折扣/截止时间，空=继承 SPU）；或明确本期不做并同步修订手册。

#### E2 · P1 编辑页「清空 / 取消标签」不落库：null 被 MyBatis-Plus `not_null` 策略忽略，且与批量取消行为不一致

- **现象**：在编辑页清空「会员固定价/会员价下限/出清价」等输入框，或把「会员商品/出清商品」改为「否」后保存，相关规则字段不会被清空：清空的字段流为 `null`，而后端 `updateById` 默认 `not_null` 策略会跳过 `null` 字段；表单也不会在切换「否」时主动清空关联字段，整表提交仍带着旧值。
- **代码证据**：
  - 全局更新策略：`BE/aryn-boot/src/main/resources/application.yml:69-71`（`update-strategy: not_null`；cloud 各 biz 无本地覆盖配置，走 MP 默认 `not_null`）；
  - 保存路径：`BIZ/service/impl/GoodsSpuServiceImpl.java:190`（`super.updateById(goodsSpu)`）、`469-482`（注释明确「null 视为本次未提交，与 MyBatis-Plus NOT_NULL 更新策略一致」）、`295-304`（`prepareSpuForUpdate` 未做专区字段的空值显式处理）；
  - 前端：`UI/views/product/goods-spu/form.vue:935-940`（会员 radio 只改 `isMemberItem`，`import { defineAsyncComponent, reactive, ref }` 无 `watch`，`form.vue:6` 无联动清空逻辑）；`978-983`（出清 radio 同理）；`form.vue:572`（`state.form = response`，页面加载的是含旧规则字段的实体）；`form.vue:438`（整表提交）；
  - `ElInputNumber` 清空会回传 `null`：`EP/components/input-number/src/input-number.mjs:81-89`（`valueOnClear` 默认 `null`）、`EP/components/input-number/src/input-number.vue_vue_type_script_setup_true_lang.mjs:121-132`（清空时 `verifyValue` 返回 `null`）；`JSON.stringify` 会保留 `null`、丢弃 `undefined`；
  - 与批量取消的差异：批量取消会显式置空 SPU 规则 `BIZ/service/impl/GoodsZoneTagServiceImpl.java:801-805`、`815-819`，并清 SKU 规则 `900-916`；编辑页没有等价实现。
- **事实/推断**：【已确认事实】策略配置 + 前后端代码链路；「清空后刷新又回来」由代码链路可确定，但本次未在浏览器中复现。
- **用户影响**：运营清空固定价以为已删除，保存后刷新又出现；编辑页「取消会员标签」后旧折扣率仍留在库中，下次重新打标会沿用旧值，数据审计失真；与批量取消（会清空规则）产生两套语义。
- **建议方向**：编辑页改接 `saveZoneTags`（显式语义，可置空）；或后端对专区字段使用 `FieldStrategy.IGNORED`/显式 `set(..., null)`；前端切换「否」时同步清空该专区规则字段，并在保存前提示「将清除规则」。

#### E3 · P2 同一份专区规则存在两条保存路径，失败模式与校验完全不同

- **现象**：批量打标走 `POST /tags/batch`（专区专用校验）；编辑页走通用 `PUT /goodsspu`，要过整表单校验 + SKU 版本校验，只改专区标签也可能被无关字段/库存版本阻塞。
- **代码证据**：`UI/views/product/goods-spu/form.vue:369-411`（整表单 `validate` 后才提交）；后端通用保存的 SKU 版本校验 `BIZ/service/impl/GoodsSpuServiceImpl.java:151-166`（失败提示「商品库存已变化，请刷新后重试」）；两套错误文案/提示位置不同（批量在弹窗 toast，编辑页由全局拦截器 toast）。
- **事实/推断**：【已确认事实】；「实际阻塞频率」为【推断】。
- **用户影响**：运营只想改专区标签，却可能因商品名称/图片/库存版本等无关原因保存失败，且错误信息与专区无关，难以理解。
- **建议方向**：专区页签提供独立「保存专区标签」按钮，走专区专用接口，与商品主体保存解耦。

#### E4 · P2 编辑页保存成功后的确认框文案与默认动作别扭

- **现象**：编辑页保存成功后弹「修改成功」对话框，按钮是「新增商品 / 返回列表」——如果运营只是改了专区标签，会被引导去「新增商品」。
- **代码证据**：`UI/views/product/goods-spu/form.vue:437-455`（`ElMessageBox.confirm('修改成功', …, confirmButtonText:'新增商品', cancelButtonText:'返回列表')`）。
- **事实/推断**：【已确认事实】。
- **用户影响**：多一步无意义确认；「新增商品」作为默认按钮反而提高误触风险。
- **建议方向**：按入口来源/页签定制确认动作，或改为轻量 toast + 停留本页。

### F. 交互规范（对应任务必须覆盖点 6，只列真实影响操作效率的）

#### F1 · P2 弹窗没有表单语义：无必填标识、无内联校验、label 与控件的可访问性关联弱

- **现象**：打标弹窗的字段直接使用 `ElFormItem`，没有外层 `ElForm`，因此没有表单级 rules、必填星号、字段级错误定位；校验错误只能靠提交后的 toast。
- **代码证据**：`UI/views/product/goods-spu/index.vue:6-26`（未 import `ElForm`）、`636-729`；校验 `146-148`。
- **事实/推断**：【已确认事实】无 `ElForm`；「读屏/键盘用户感知不到必填」为【推断】（依赖 Element Plus 在无 Form 上下文时的 label 行为）。
- **用户影响**：错误反馈慢且弱，表单填写缺少引导；键盘操作时无法通过表单语义快速定位。
- **建议方向**：改造成 `ElForm + rules`；危险操作二次确认（与 B2 联动）。

#### F2 · P2 提交中只有按钮 loading：无进度、无阶段提示，取消按钮仍可点

- **现象**：批量提交期间只有「确认打标」按钮进入 loading，弹窗不展示进度；同屏「取消」按钮未禁用。后端逐条处理并对整租户做一次系统活动同步，商品多/同步慢时等待时间不可预期。
- **代码证据**：`UI/views/product/goods-spu/index.vue:169-191`（仅 `zoneSaving` 布尔）、`732-738`（loading）、`731`（取消按钮无 `:disabled`）；后端逐条循环 + 同步：`BIZ/service/impl/GoodsZoneTagServiceImpl.java:97-151`、`BIZ/controller/admin/GoodsSpuController.java:71`、`100-111`。
- **事实/推断**：【已确认事实】无进度；「同步耗时」为【推断】（未压测）。
- **用户影响**：用户不知道是卡住还是正在处理，可能重复点击/关闭弹窗；关闭后结果依旧静默生效，增加困惑。
- **建议方向**：提交中至少禁用取消与 ESC 关闭；商品量大时展示「处理中 i/N」（批量规模上限与异步化需后端评估，见待确认问题 9）。

#### F3 · P2 主操作入口视觉权重低，与「上架/下架」等即时生效操作平铺混排

- **现象**：工具栏 5 个按钮平铺，「专区打标」是 plain 主色，位于上架/下架之后；批量操作区没有「已选 N 件」的上下文，按钮只靠 disabled 变化。
- **代码证据**：`UI/views/product/goods-spu/index.vue:425-466`（新增/上架/下架/专区打标/批量导入同排）。
- **事实/推断**：【推断】属设计判断，非代码缺陷。
- **用户影响**：入口不易被发现；上下架是即时生效（无二次确认），与打标混排增加误点风险。
- **建议方向**：批量操作区独立分组；选中 N 件后把「专区打标 / 移出专区」升为主按钮，并在工具栏显示选中上下文（与 A2 同改）。

## 五、待确认问题

1. **`/tags/batch` 是否能在结果里返回变化类型与变更前后值？** 现状逐条结果只有 `success/message`（`VOAPI/GoodsZoneTagResultVO.java:20-38`），前端要实现「已打标/无变化」提示必须依赖这一字段（C3、B1）。
2. **是否需要后端提供「批量读取所选 SPU 专区状态」与「列表返回 SKU 覆盖数」的接口？** 现状只有单条 `GET /tags/{spuId}`（`GoodsSpuController.java:75-80`），弹窗展示 SKU 覆盖情况需要 N 次请求或新接口（B1、D1）。
3. **「全选筛选结果（N 条）」是否按服务端语义实现？** 若只在前端开 `reserve-selection`，跨页选择可保留，但「全选当前筛选结果（可能上千条）」仍需要后端接受筛选条件批量执行；否则只能限定「全选当前页」（A1、D2）。
4. **取消标签/撤销的能力边界**：取消标签会清空 SPU + SKU 规则且不可恢复（`BIZ/service/impl/GoodsZoneTagServiceImpl.java:801-805`、`900-916`）。是否需要「撤销本批次」接口？前端目前无批次号（C6）。
5. **单商品 SKU 级精调是否本期实现？** 手册已承诺（`DOC/2026-11-02-会员专区与低价捡漏规则化改造/操作手册.md:92-95`）但页面无入口；若不实现需同步修订手册，若实现建议直接接 `saveZoneTags`（E1）。
6. **批量弹窗中「不填规则只打标」是否是期望用法？** 后端允许（`BIZ/service/impl/GoodsZoneTagServiceImpl.java:789-793`）且会用专区默认折扣；但出清只打标会造成单商品编辑页无法保存的脏状态（B6）。需要产品确认：是禁止在 UI 空规则打标，还是统一放宽单商品校验并明确默认口径（B4、B6）。
7. **列表是否需要展示到期/倒挂状态？** 现行口径是「只看标签、不看到期」（`DOC/2026-11-03-商品列表专区筛选/README.md:38`），若维持口径则至少加视觉警示；若改口径需同步筛选与列表契约（D3）。
8. **是否需要为列表页/弹窗补充自动化用例？** 现有 `UI/components/list-page-contract.test.ts:22-39` 只校验 keepAlive 接入与面板/分页样式契约，未覆盖选择保持与打标结果反馈；交互改造后建议补组件级用例。
9. **批量规模上限与同步耗时是否需要前端进度/异步化？** 批量接口目前同步逐条处理并对整租户做一次活动同步（`BIZ/service/impl/GoodsZoneTagServiceImpl.java:97-151`、`BIZ/controller/admin/GoodsSpuController.java:71`），无批次任务 ID；若运营会一次提交上百商品，需要后端评估异步任务或前端分片（F2）。
