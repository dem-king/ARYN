# 生鲜商城库存必要性调研（对标小象超市）

> 调研日期：2026-10-21
> 背景：管理端「添加商品 → 规格信息」要求必填「商品库存」（`aryn-mall-ui/apps/web-ele/src/views/product/goods-spu/form.vue:194-200`、`:829-841`）。
> 问题：小象超市这种生鲜商城，建品时到底要不要填库存？我们要不要保留这个必填项？

## 结论速览

1. **小象超市的供应商建品时不填 C 端库存**。小象是美团自营即时零售，合作方是「供应商」而非开店商家；VSS 供应商系统建品只填商品资料和资质，库存相关动作只有报价时的「本期可供数量（**选填**）」和采购单确认时的「可供数量」。真正的可售库存由平台的大仓 / 前置仓 + 采购补货体系维护。
2. **生鲜商城必须有"可售量"控制，但不需要"建品时手填一个精确库存数字"**。生鲜库存天然不准（称重、损耗、短保、日清），关键能力是：售罄/补货中状态、限量与沽清、补货与盘点，而不是商品档案上的一个整数。
3. **对本系统的建议**：保留库存字段，但把「库存」拆成三层——建品时选**库存策略**（不限 / 固定 / 每日），数量日常在**库存管理**里维护；C 端不要外露精确库存数字。分三步走（见第五节），先做最小改造，不必一上来照抄前置仓。
4. **2026-10-21 补充确认**：业务模式为**供应商直发 / 以销定采，不做 30 分钟达**。据此选型为 **B 的轻量版（B-lite，只做「不限库存」模式 + 停售控制）**，既不做纯 A 的假库存，也不做完整 B 的日清/库存管理页、不做 C 的前置仓，详见第六节。

## 一、小象超市怎么做（一手证据）

### 1.1 模式：自营采销，不是商家入驻开店

- 官网定位：「小象超市（原美团买菜）是美团于 2019 年初推出的**自营**即时零售业务」，前置仓（便民服务站）+ 自建配送，30 分钟送达。
- 招商页明确是「美团**自营**生鲜零售业务」，合作步骤为：申请 → 审核通过成为**储备供应商** → 供应商准入评估 → 签合同 → 开始供货。**没有"开店/商家后台建品"这一层**。
- 来源：[小象超市官网](https://maicai.meituan.com/)、[小象超市合作招商](https://123.meituan.com/v3/biz-detail/service/252?source=mtmc_baidu)

### 1.2 供应商建品流程里没有库存字段

美团官方《小象超市商家培训 · 供应商管理中心》（2026-02，50 页 PPT）给出的主流程：

- **商家建品**：登录 VSS → 商品管理 → 创建新品 → 添加生产商 → 上传资质 → 提交。**全流程没有"库存"这一项。**
- **生鲜询比价（报价）**：报价内容 = **本期可供数量（选填）**、单价（必填）、建议零售价（必填）、SKU 备注及描述（选填）。
- **采购单确认**：供应商可「修改采购数量 / 填写可供数量 / 确认单据」。
- **实物侧**：预约送货 → 品控验收（品质扣损）→ 大仓入库 / 退货。库存的进、出、损、退都在平台仓配体系里闭环。

即：**供应商承诺的是"这一期能供多少"，不是"店里挂多少库存"；零售侧可售量由平台系统算。**
来源：[小象超市商家培训 PDF（s3plus.meituan.net）](https://s3plus.meituan.net/v1/mss_915cfe67c99b4651b81ca210670f9302/mall-fe-files/1770615356472.pdf)

### 1.3 前置仓的可售库存由平台补货体系维护

小象的公开业务描述是：平台统一采购、前置仓集中仓储、按销量预测补货；采购单驱动供应商送货、品控验收后入大仓，再调拨到前置仓。这套链路里，C 端看到的「有货 / 仅剩少量 / 售罄」是平台库存系统的输出，供应商侧不参与。

### 1.4 供应商系统里也有"库存"字样，但语义不同

部分第三方入驻攻略提到供应商"与后台供应链系统对接，以便接收订单、管理库存及对账"。这里的"库存"指**供货侧可供量**（我能供多少），不是门店/前置仓的可售库存。两种口径不要混用。
来源：[什么值得买·供应商怎么入驻小象超市](https://post.m.smzdm.com/zz/p/a86d4mzl/)、[知乎·2026 美团小象超市入驻全攻略](https://zhuanlan.zhihu.com/p/2012536954944770532)

## 二、生鲜商城与普通电商的库存差异

| 维度 | 普通电商 | 生鲜商城 |
|------|----------|----------|
| 库存形态 | 件数、精确 | 称重（kg/份）、非标、账实偏差大 |
| 生命周期 | 长保 | 短保、损耗、临期、当日出清 |
| 缺货频率 | 低 | 高（爆品/时令/天气都会断货） |
| 超卖代价 | 退款/补发 | 生鲜无法补发，体验伤害大 |
| 仓配结构 | 单仓或少量仓 | 门店/前置仓多，库存与配送地址强相关 |
| 采购方式 | 备货 | 以销定采、日配、供应商直发都很常见 |

因此生鲜的"库存"本质是三件事：

1. **可售状态**：在售 / 售罄 / 补货中 / 下架 —— 防超卖，必须有；
2. **可售量**：今天还能卖多少 —— 不必精确到账面，但要有上限和沽清；
3. **补货能力**：卖完了怎么补、怎么调 —— 靠库存管理/采购单，而不是靠改商品表单。

## 三、当前系统库存现状盘点

| 维度 | 现状 | 影响 |
|------|------|------|
| 建品 | 单规格必填「商品库存」（`form.vue:194-200`、`:829-841`）；多规格每个 SKU 必填（`components/sku/sku-table/index.vue:394-400`） | 生鲜运营建品被一个"拍脑袋数字"卡住，且数字很快失真 |
| 扣减 | 下单时按 SKU 汇总校验并原子扣减（`OrderPriceComputeService.java:183-206`），取消/退款返还；SPU 库存按差值汇总 | 机制正确，可复用 |
| C 端展示 | 商详「库存 N 件」（`GoodsInfo.vue:366`）、收藏「库存 N」（`collect/index.vue:83`）、足迹（`footprint/index.vue:74`）、列表「仅剩 N 件」（`goods-list-panel/index.vue:190-192`，阈值 10） | **精确库存直接外露**：暴露经营数据，且生鲜账实不符时反而伤害信任 |
| 预警 | 阈值硬编码 `stock < 10`（`ProductStatisticsMapper.xml:21,47`） | 生鲜不同品类阈值应不同，且应可配置 |
| 多仓/门店 | 无 SKU×仓/门店库存；`delivery_warehouse_config` 只是单仓发货地址配置 | 做不了"按地址显示可售"，30 分钟达模式不成立 |
| 运营动作 | 无独立库存管理页：没有补货、盘点、沽清、库存流水 | 日常只能编辑商品改库存，无审计、易覆盖并发扣减 |
| 计量 | `goods_sku.stock` 为 `int`（`GoodsSku.java:55`） | 不能按 kg 小数管理称重商品 |
| 表单冗余 | 前端有「重量/体积」（`form.vue:842-867`），但后端 `GoodsSku` 实体无对应字段，提交后被静默丢弃 | 无效字段，误导运营，需补齐持久化或删除 |

> 说明：`goods_sku` 表结构里保留了 `weight/volume` 列，但 Java 实体未映射，实际不会保存。若物流/船供需要计费重，应补 DTO 与写入。

## 四、建议：把「库存」拆成三层，而不是一个必填数字

### 4.1 建品时：选库存策略，不强迫填精确数量

| 策略 | 适用 | 行为 |
|------|------|------|
| 不限库存 | 现采现卖、供应商直发、船供按需采购 | 不做扣减校验，只受可售状态下架控制 |
| 固定库存 | 标品、烟酒、包装食品 | 当前逻辑（必填数量、下单扣减） |
| 每日库存 / 沽清 | 生鲜、烘焙、熟食 | 建品给默认值，按天重置或运营一键沽清，卖完显示「补货中」 |

建品表单必填收敛为：**名称、类目、单位、售价、可售状态、库存策略**；库存数量仅在「固定库存」策略下必填，且给默认值（如 999）。

### 4.2 日常运营：独立「库存管理」

- 按 SKU 补货 / 盘点 / 沽清 / 批量改库存，留库存流水（谁、何时、改前改后、原因）；
- 售罄一键化：列表页支持「售罄 / 恢复售卖」，不必进编辑页；
- 预警阈值按类目/商品配置，生鲜可设更高阈值；
- 后续按需加每日自动重置任务（类目维度）。

### 4.3 C 端：只展示状态，不展示精确数字

- 「有货 / 仅剩少量 / 补货中 / 售罄」替代「库存 N 件」；
- 多规格弹层保留"所选规格是否有货"的禁用态；
- 收藏/足迹/榜单去掉精确库存。

### 4.4 多门店/前置仓：商品主数据与仓级库存分离（后置）

若要做"30 分钟达/按地址可售"，必须新增 `sku_store_stock`（租户、门店/仓、SKU、可售量、版本）与门店表，商品表只做主数据。这属于新领域能力，不建议本期做。

## 五、分档实施方案

| 方案 | 内容 | 改动量 | 触发条件 |
|------|------|--------|----------|
| **A. 最小改造** | 库存字段默认 999、非必填；商品列表加「售罄/恢复」；C 端去精确数字；预警阈值配置化 | 前端为主，无 DB 改动，约 1 天 | 立即做 |
| **B. 生鲜化** | 库存策略字段（不限/固定/每日）+ 每日沽清任务 + 库存管理页 + 库存流水；需按规范补 `db/boot`、`db/cloud` 双份增量 SQL | 前后端 + SQL，约 2-3 天 | 生鲜 SKU 正式上线前 |
| **C. 前置仓** | 门店/仓维度库存、按地址可售、调拨、补货建议 | 1-2 周，新领域 | 确定要做 30 分钟达/多门店时 |

推荐节奏：**先 A，生鲜品类上量前做 B，C 等门店/前置仓业务确认后再立项。**

## 六、选型结论（2026-10-21 业务模式确认后）

**已确认业务模式**：供应商直发 / 以销定采，不做 30 分钟达。结论：**选 B 的轻量版（B-lite）**，不是纯 A，也不是完整 B，更不是 C。

### 6.1 为什么不选 A / B / C

| 方案 | 为什么不适配 |
|------|--------------|
| 纯 A（库存默认 999 的"假库存"） | 数字会被下单持续扣减、退款回补，逐渐漂移；库存总量/预警/生命周期等统计口径失真；运营仍要维护一个没有业务意义的数字。把一个虚假库存固化成业务数据，后续清洗成本更高。 |
| 完整 B（日清 + 库存管理页 + 流水） | 日清、盘点、补货解决的是"自营有货"场景；以销定采没有每日实物库存，这套流程用不上，属于过度设计。 |
| C（门店/前置仓库存） | 不做 30 分钟达就不需要仓级库存与按地址可售，直接排除。 |

### 6.2 B-lite 的范围

核心判断：以销定采要的不是"数量"，而是**能不能接单**。因此只给库存加一个业务语义开关，不引入数量管理。

1. **数据**：`goods_sku` 增加 `stock_mode`（0=有限库存，1=不限库存），存量默认 0 保持现状；新增商品默认 1（不限库存）。SPU 不加字段，库存汇总只统计有限库存 SKU。按规范提供 `db/boot` 与 `db/cloud` 双份增量 SQL，并重新生成 `aryn_boot_full.sql` 校验。
2. **建品**：库存策略单选（默认「不限库存」），选「有限库存」才显示并必填数量；多规格同一 SPU 共用一种策略（第一版不做逐 SKU 混合，UI 更简单）。
3. **下单链路**：不限库存 SKU 跳过库存校验与扣减；取消/退款**不回补**（否则库存越退越多）。秒杀商品走自己的 Redis 库存池，不受影响，但下单时要跳过对商品库存的二次扣减。
4. **加购/结算/再购/赠品**：不限库存一律视为有货（购物车加购、快捷加购、再来一单预览、买赠赠品校验都要按模式分支）。
5. **C 端展示**：不再展示精确库存。不限库存显示「现货/可售」，有限库存显示「有货/仅剩少量」，数量为 0 显示「售罄/补货中」。
6. **管理端**：商品列表库存列对不限库存显示「不限」；提供批量「暂停接单 / 恢复接单」，运营不用再进编辑页改数字。
7. **统计与预警**：不限库存商品不参与低库存预警和库存总量口径，避免全部命中 `stock < 10`。

### 6.3 改动点清单

| 域 | 入口 | 改动 |
|----|------|------|
| DB | `db/boot`、`db/cloud` 增量脚本 + `build-full-sql.mjs` | 加 `stock_mode` 列、索引按需；双模式各一份 |
| 商品域 | `GoodsSku` 实体/DTO/VO；`GoodsSkuServiceImpl.reduceStock/rollbackStock`；`GoodsSpuServiceImpl` 库存汇总；`QuickCartServiceImpl`；`ProductStatisticsMapper.xml` | 模式读写、扣减跳过、汇总/预警过滤、快捷加购放行 |
| 订单域 | `OrderPriceComputeService.orderStockHandler`；`OrderInfoServiceImpl`（建单/取消/再购预览）；`ShoppingCartServiceImpl` 加购校验；赠品校验 | 不限库存跳过校验/扣减/回补；视为有货 |
| 管理端 | `product/goods-spu/form.vue`、`components/sku/sku-table/index.vue`、商品列表 | 策略单选、数量联动、库存列「不限」、暂停接单入口 |
| C 端 | `GoodsInfo.vue`、商品列表/瀑布流/收藏/足迹、`vk-data-goods-sku-popup`、快捷加购 | 状态化文案，去精确数字；不限库存视为有货 |

### 6.4 风险与后续

- **放弃超卖保护**：不限库存模式下，能否履约靠采购/供应商确认兜底。系统需要在"下单后采购"环节能识别缺货并走退款/通知，否则用户会为买不到的商品付款。
- **下单后采购是缺口**：供应商直发/以销定采还缺采购单、供应商确认、缺货通知/退款这条链路，建议作为下一期需求单独立项，本次库存改造不夹带。
- **限量需求**：若后续需要"每日/每航次限量"，在 `stock_mode` 基础上加 `daily_limit` 字段即可，不要退回用库存数字表达。
- **Excel 导入/秒杀/拼团**：导入商品默认按有限库存创建；秒杀/拼团库存与商品库存解耦，需要回归验证。

### 6.5 工作量

约 **2.5–3 天**：后端 1.5 天（含双模式 SQL）、管理端 0.5 天、C 端 0.5 天、测试与回归 0.5 天。建议顺序：SQL → 商品域 → 订单域 → 管理端 → C 端 → 回归（`mvn test -pl aryn-boot -am`、`pnpm check:type && pnpm test:unit && pnpm lint`、`pnpm type-check`）。

## 七、待确认

1. 是否接受 C 端不展示精确库存（会影响现有商详/列表 UI 与部分运营习惯）。
2. 称重商品是否纳入本期（涉及 `stock` 改小数/按 kg 与订单称重差异处理）。
3. 暂停接单第一版是否允许"商品仍在 C 端可见但显示售罄"，还是直接下架（后者零成本，前者需要 C 端售罄态支持）。
