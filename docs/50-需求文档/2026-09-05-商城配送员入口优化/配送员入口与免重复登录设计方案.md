# 商城配送员入口与免重复登录设计方案

## 1. 文档信息

- 设计日期：2026-09-05
- 适用端：`aryn-mall-uniapp` 商城端
- 关联能力：商城个人中心、配送员工作台、TOC/TOB 身份认证、配送权限
- 设计状态：待评审
- 现状参考：个人中心设计稿及当前移动端实现

## 2. 背景与问题

当前商城个人中心无条件展示“配送员入口”。普通消费者也能看到该入口，点击后进入配送员手机号和密码登录页面，造成以下问题：

1. 普通用户无法理解入口用途，个人中心信息噪音较大。
2. “配送员入口”容易被理解为配送员招募入口，实际功能只是工作人员登录。
3. 商城用户已经登录时仍需再次输入配送员账号密码，操作链路重复。
4. 商城用户身份和配送员员工身份不同，不能直接把商城 token 当作配送 token 使用。

当前系统已经具备独立配送员 token、配送员权限和配送路由拦截能力。现有配送员登录会校验员工账号、账号状态及 `delivery:execute` 权限，工作台接口使用独立 `deliveryToken`。

## 3. 设计目标

### 3.1 产品目标

- 只有已登录且具备有效配送资格的用户看到配送工作台入口。
- 已登录的配送员点击入口后可以免重复输入密码进入工作台。
- 入口名称和说明准确表达“工作人员工作台”，不制造招募误解。
- 配送员被停用、解绑或权限回收后，入口和工作台访问及时失效。

### 3.2 技术目标

- 商城 TOC token 与配送员 TOB token 始终隔离。
- 通过服务端完成配送资格判断和身份换取，客户端不自行判权。
- Boot 单体模式和 Cloud 微服务模式使用同一套业务语义和认证规则。
- 不接受客户端提交的 `userId`、`phone` 或 `staffId` 作为授权依据。

## 4. 非目标

- 本期不实现配送员招募、申请入驻或资格审核流程。
- 本期不支持配送员抢单、自动派单或路线规划。
- 本期不把商城用户直接改造成系统员工账号。
- 本期不取消现有独立配送员账号密码登录方式，作为无商城登录态或异常场景的兜底入口。

## 5. 核心身份模型

商城用户和配送员是两个不同的身份域：

```text
商城用户登录
  -> TOC token
  -> 浏览商品、下单、查看自己的订单

配送员身份换取
  -> 校验当前商城用户与配送员员工账号的绑定关系
  -> 校验租户、账号状态、配送员状态和配送权限
  -> 签发独立 deliveryToken
  -> 配送员 TOB token
  -> 访问配送工作台和本人配送任务
```

配送接口仍然只信任配送员身份。商城 token 只能用于资格查询和身份换取，不能直接操作配送任务。

## 6. 入口展示规则

| 用户状态 | 入口展示 | 点击行为 |
|---|---|---|
| 未登录 | 不展示 | 无 |
| 已登录，无配送员绑定 | 不展示 | 无 |
| 已登录，绑定存在但权限未开通 | 不展示 | 无 |
| 已登录，配送资格正常 | 展示“配送工作台” | 换取或复用 `deliveryToken` 后进入 |
| 已登录，配送员账号停用 | 可展示灰色状态，也可不展示 | 提示“配送权限已暂停” |
| 已有有效 `deliveryToken` | 展示入口和待处理数量 | 直接进入工作台 |
| 商城登录态过期 | 不展示或清除入口状态 | 引导商城登录 |

默认采用“无资格不占位”的方案。只有已经绑定配送员身份但被停用时，才建议保留灰色提示卡，帮助工作人员发现权限问题。

## 7. 个人中心交互设计

### 7.1 入口位置

入口放在“我的服务”区域之后、“猜你喜欢”之前，作为独立横向卡片。该位置符合工作人员从个人中心进入工作台的预期，也不会干扰订单主流程。

### 7.2 推荐视觉层级

- 标题：`配送工作台`
- 正常副标题：`已为你开通配送权限`
- 有待处理任务：`3 项任务待处理`
- 权限暂停：`配送权限已暂停`
- 图标：配送车辆或工作台图标，使用品牌主色
- 右侧：箭头；有任务时显示待处理数量
- 不显示员工手机号、账号、租户信息等敏感数据
- 卡片高度建议约 `136rpx`，与个人中心其他服务卡片保持统一圆角和间距

不使用“配送员入口”作为标题。若未来需要招募配送员，应新增“申请成为配送员”功能，不能复用本入口。

### 7.3 页面加载状态

个人中心加载时，配送资格区域使用以下策略之一：

1. 推荐：资格请求完成前暂不渲染入口，避免先显示后隐藏造成跳动。
2. 资格请求超时或失败时默认不展示入口，并记录可观测日志。
3. 已有本地有效资格缓存时先展示轻量占位，再用服务端结果校正。

资格缓存只能改善显示体验，不能作为授权依据。

### 7.4 点击流程

```text
点击配送工作台
  -> 已有 deliveryToken 且未过期：进入工作台
  -> 没有 deliveryToken：调用身份换取接口
  -> 换取成功：保存 deliveryToken 和配送员资料，进入工作台
  -> 返回 401：刷新商城登录态后自动重试一次
  -> 返回 403：清理配送状态，提示权限已暂停或失效
  -> 网络错误：留在个人中心，提示稍后重试
```

按钮在请求期间进入 loading 状态，防止连续点击造成重复换取。

## 8. 后端接口设计

### 8.1 查询配送资格

```text
GET /auth/delivery/eligibility
认证：商城 TOC token
```

响应示例：

```json
{
  "eligible": true,
  "status": "ACTIVE",
  "staffName": "张三",
  "pendingTaskCount": 3
}
```

字段说明：

- `eligible`：是否允许展示入口。
- `status`：`ACTIVE`、`DISABLED`、`UNBOUND`。
- `staffName`：可选，仅用于展示，不作为授权依据。
- `pendingTaskCount`：可选，用于入口角标；应按当前配送员身份查询。

接口不返回完整权限列表，不接受用户 ID、手机号或配送员 ID 参数。

### 8.2 换取配送员身份

```text
POST /auth/delivery/exchange
认证：商城 TOC token
请求体：空
```

服务端处理步骤：

1. 从商城 token 获取当前用户和租户。
2. 查询当前商城用户对应的配送员绑定关系。
3. 校验 `sys_user` 属于当前租户且账号状态正常。
4. 校验配送员记录未逻辑删除且状态可用。
5. 校验员工权限包含 `delivery:execute` 或管理员通配权限。
6. 以员工账号主体签发独立 `deliveryToken`。
7. 返回 token 信息和最小配送员资料。

响应示例：

```json
{
  "tokenValue": "...",
  "expiresIn": 7200,
  "staff": {
    "id": "delivery-staff-id",
    "staffName": "张三"
  }
}
```

### 8.3 既有密码登录

保留现有配送员手机号和密码登录接口，供以下场景使用：

- 用户未登录商城。
- 用户无法完成商城账号绑定。
- 独立配送端继续使用账号密码登录。
- 身份换取服务暂时不可用时的运维兜底。

密码登录和身份换取最终都必须签发同类型、同权限边界的 `deliveryToken`。

## 9. 账号绑定设计

### 9.1 推荐模型

建立商城用户与系统员工账号之间的明确关联：

| 字段 | 含义 |
|---|---|
| `mall_user_id` | 商城用户 ID |
| `sys_user_id` | 系统员工账号 ID |
| `delivery_staff_id` | 配送员资料 ID |
| `tenant_id` | 租户 ID |
| `status` | 绑定状态 |
| `bind_time` | 绑定时间 |
| `unbind_time` | 解绑时间 |

现有 `delivery_staff.user_id` 继续表示 `sys_user` 员工账号，不改变字段语义。

### 9.2 绑定规则

- 绑定和解绑由租户管理员完成。
- 两个账号必须属于同一租户。
- 手机号只能用于管理员搜索或首次辅助匹配，不能作为长期授权主键。
- 手机号变更不得自动转移配送资格。
- 一个商城用户在同一租户内最多绑定一个有效配送员身份。
- 一个配送员员工账号原则上只绑定一个商城用户，重复绑定时必须明确提示管理员。
- 解绑后立即禁止新的身份换取，已有配送 token 在服务端短期失效窗口后也必须拒绝配送接口访问。

### 9.3 过渡方案

如果本期暂不新增绑定表，至少由服务端完成一次明确绑定，并保存绑定结果。禁止前端每次使用手机号直接判断配送资格，也禁止前端提交配送员 ID 进行换取。

## 10. 前端实现要求

### 10.1 个人中心

- 仅在商城 `authStore.isLoggedIn` 为真时发起资格查询。
- 资格接口返回 `eligible = true` 时渲染入口。
- 资格查询失败默认隐藏入口，不影响商城个人中心其他功能。
- 进入页面时刷新资格，避免权限回收后继续展示旧入口。
- 点击入口时优先检查本地 `deliveryToken`，再调用身份换取。
- 成功后保存 `deliveryToken` 和 `deliveryStaffInfo`。
- 不在页面中硬编码 `VITE_OPEN_BOOT`、`/boot` 或手工拼接模式路径。

### 10.2 token 存储和清理

- 商城 token 保存在现有商城认证存储中。
- 配送 token 继续使用独立的 `deliveryToken`。
- 退出商城登录时同时清除 `deliveryToken` 和配送员资料。
- 退出配送工作台时只清除 `deliveryToken`，保留商城登录状态。
- 配送接口返回认证失效时清除配送 token，并跳转配送登录或返回个人中心。

### 10.3 路由

- `/pages/delivery/**` 继续由配送员 token 保护。
- 个人中心入口只负责导航和身份换取，不直接放宽配送路由权限。
- 已有有效配送 token 时进入 `delivery-index`。
- 无 token 且身份换取失败时进入现有 `delivery-login` 或返回个人中心，具体由错误码决定。

## 11. 后端安全要求

- 资格判断必须在服务端完成，前端隐藏入口不属于安全控制。
- 身份换取必须从认证上下文获取商城用户，不接受客户端传入当前身份参数。
- 必须校验租户隔离、逻辑删除、员工账号状态、配送员状态和权限标识。
- 配送接口继续要求配送员 TOB 身份，并校验任务归属。
- 改派、解绑、停用后，原配送员必须失去对应任务的读取和写入权限。
- 记录身份换取、绑定、解绑、权限拒绝等审计日志，日志中不得记录明文 token。
- 不把完整员工权限集合返回给商城端。
- 身份换取接口应具备幂等性，重复调用可以返回当前有效配送 token 或签发新 token，但不能创建重复绑定关系。

## 12. Boot/Cloud 双模式适配

### 12.1 请求路径

- 源码中的 API 路径首段必须是有效服务域，例如 `/auth/delivery/eligibility`。
- Boot 模式通过统一 `rewriteBootUrl` 改写为 `/boot/auth/delivery/...`。
- Cloud 模式由 Gateway 路由到认证服务。
- 前端统一使用 `parseOpenBoot(import.meta.env.VITE_OPEN_BOOT)` 和 `rewriteBootUrl`。

### 12.2 后端部署

- Boot 模式必须能在 `aryn-boot` 中注入并执行身份换取逻辑。
- Cloud 模式认证服务、UPMS 和订单配送域之间通过既有 API/Dubbo 契约通信。
- 不允许业务 biz 模块相互直接 import。
- 新增配置必须同时提供 Boot 配置和 Cloud/Nacos 配置。

### 12.3 数据库

若新增账号绑定表：

- 同时提供 `aryn-mall-java/db/boot/` 和 `aryn-mall-java/db/cloud/` 增量 SQL。
- SQL 必须可重复执行，不得 `DROP` 或 `TRUNCATE` 存量数据。
- 将 Boot 脚本登记到 `build-full-sql.mjs` 的 `sections`。
- 重新生成并校验 `aryn_boot_full.sql`。
- 核对租户表白名单和 Cloud 基线脚本一致性。

## 13. 错误与边界状态

| 场景 | 用户反馈 | 客户端动作 |
|---|---|---|
| 商城 token 过期 | 请先登录商城 | 清理商城态并跳转商城登录 |
| 未绑定配送员 | 当前账号未开通配送权限 | 隐藏入口或返回个人中心 |
| 权限被暂停 | 配送权限已暂停，请联系管理员 | 清除配送 token |
| 配送员账号停用 | 配送账号已停用 | 清除配送 token，禁止进入 |
| 租户不一致 | 当前账号无配送权限 | 不泄露具体绑定信息 |
| 身份换取超时 | 暂时无法进入配送工作台，请稍后重试 | 保留商城页面 |
| 配送 token 过期 | 配送登录已过期 | 清除配送 token，可重新换取一次 |
| 连续点击 | 无额外提示 | 按钮 loading 并忽略重复操作 |

错误提示不应暴露“某手机号绑定了哪个员工”或其他租户信息。

## 14. 验收标准

### 14.1 产品验收

- 未登录用户看不到配送工作台入口。
- 无配送资格用户看不到配送工作台入口。
- 有效配送员能在个人中心看到入口和待处理数量。
- 已登录配送员首次点击无需再次输入手机号和密码。
- 入口标题为“配送工作台”，副标题能说明权限范围。
- 权限暂停、账号停用和解绑状态有明确反馈。

### 14.2 安全验收

- 商城 token 不能直接调用配送任务接口。
- 身份换取不接受客户端提交的用户或配送员身份参数。
- 换取过程校验租户、绑定、员工状态、配送员状态和 `delivery:execute`。
- 停用或解绑后不能继续读取或操作配送任务。
- 配送 token 与商城 token 使用不同存储键和请求认证范围。

### 14.3 工程验收

- Boot 和 Cloud 模式下资格查询路径均正确。
- Boot 和 Cloud 模式下身份换取路径均正确。
- `aryn-boot` 可编译通过。
- 新增数据库变更时，Boot/Cloud 增量 SQL 均存在且可重复执行。
- 前端通过类型检查和单元测试。
- 至少覆盖未登录、无资格、有资格、换取失败、token 过期五类场景。

## 15. 推荐实施顺序

1. 确认商城用户与 `sys_user` 的绑定来源，决定是否新增绑定表。
2. 增加服务端配送资格查询接口。
3. 增加商城 token 换取配送 token 接口。
4. 修改个人中心入口展示、文案和 loading 状态。
5. 接入 `deliveryToken` 保存、清理和错误处理。
6. 补齐 Boot/Cloud 路径、配置和数据库适配。
7. 增加认证、权限、租户和前端交互测试。
8. 完成 H5 与微信小程序手工回归后再灰度发布。

## 16. 待确认事项

- 商城用户和系统员工账号当前是否已有稳定的关联字段或管理流程。
- 配送员是否允许同时作为普通消费者下单并查看商城订单。
- 权限被暂停时，个人中心采用“隐藏入口”还是“灰色提示卡”。
- 身份换取成功后是否需要设置比普通配送登录更短的 token 有效期。
- 独立配送员小程序上线后，商城个人中心入口是否保留为兼容入口。

## 17. Web 管理端是否需要修改

需要修改。当前管理端已经有配送员列表和新增/编辑弹窗，但表单只关联 `sys_user` 后台用户：

- `delivery_staff.user_id` 关联后台员工账号。
- 当前表单可以从后台用户列表中选择账号。
- 当前表单没有选择或绑定商城 `user_info` 用户的能力。
- 当前列表没有展示“商城账号绑定状态”和“配送权限状态”。

因此，当前 Web 页面可以派单，但不能支撑“商城用户登录后自动识别配送员并免重复登录”。必须补充账号绑定和权限状态管理。

## 18. 推荐的后台角色模型

### 18.1 三个对象的关系

```text
sys_user
  系统员工账号，负责登录 TOB 配送端
      |
      | delivery_staff.user_id
      v
delivery_staff
  配送员资料、接单状态、车辆信息
      ^
      |
      | delivery_account_binding
      |
user_info
  商城用户账号，负责登录 TOC 商城
```

移动端身份换取成功后，签发的 `deliveryToken` 主体仍然是 `sys_user.id`。这样可以直接复用当前移动端配送接口：配送端通过 TOB 身份的用户 ID 查询 `delivery_staff.user_id`，无需修改任务归属逻辑。

### 18.2 权限和状态分离

后台需要明确区分以下三个概念：

| 概念 | 来源 | 作用 |
|---|---|---|
| 账号状态 | `sys_user.status` | 是否允许员工登录 |
| 配送权限 | 角色菜单中的 `delivery:execute` | 是否允许执行配送任务 |
| 接单状态 | `delivery_staff.status` | 当前是否参与派单，在线/忙碌/离线 |

“离线”不应等同于账号停用。离线配送员仍可以查看自己的历史任务或进入工作台，但不能出现在默认派单候选中。移动端入口资格建议要求账号正常、具备配送权限、存在有效绑定和有效配送员资料，不强制要求接单状态为在线。

## 19. Web 端信息架构

### 19.1 配送管理菜单

建议保留现有“配送管理”菜单，并调整为以下结构：

```text
配送管理
├── 配送任务
├── 配送员管理
├── 配送范围
└── 配送配置
```

“配送员管理”负责账号、绑定和接单状态；“配送任务”负责派单和任务生命周期；两者不混合创建账号，避免管理员在派单弹窗里临时修改身份配置。

### 19.2 配送员列表改造

现有列表建议增加以下列：

| 列 | 展示内容 |

| 权限状态 | 已开通、未开通、已停用 |
| 接单状态 | 在线、忙碌、离线 |
| 当前任务 | 进行中任务数量 |
| 最近登录 | 最近配送端登录时间 |
| 操作 | 查看、编辑、绑定、停用、解绑 |

列表筛选增加：员工账号、商城手机号、绑定状态、权限状态、接单状态。手机号默认脱敏显示，例如 `138****1234`。

列表顶部增加两个统计：

- 已开通配送员数量。
- 待绑定商城账号数量。

### 19.3 派单候选展示

现有派单弹窗只展示配送员名称或 ID，建议改为：

```text
张三    在线    进行中 2 单    电动车

```

默认只查询：当前租户、账号正常、权限有效、配送员资料未删除且接单状态为在线的配送员。管理员可以通过“显示忙碌配送员”开关扩大候选范围，但后端仍需最终校验。

## 20. 新增配送员的推荐交互

不建议继续使用当前“关联后台用户 + 手填姓名手机号”的单层弹窗。推荐改为“新增配送员”向导，分为三个步骤。

### 20.1 第一步：员工账号

标题：`选择配送员员工账号`

提供两个选项：

1. `选择已有员工账号`
2. `创建新的配送员账号`

选择已有账号时：

- 只展示当前租户内账号正常的员工。
- 默认优先展示已经拥有 `delivery:execute` 的账号。
- 没有配送权限时显示“未开通配送权限”，允许管理员点击“开通配送权限”。
- 已经关联其他有效配送员资料的账号不可重复选择。

创建新账号时，表单只填写员工必要信息：姓名、手机号、登录用户名、初始密码、部门。系统自动分配“配送员”角色；该角色默认包含 `delivery:execute`，不授予订单管理、用户管理等后台管理权限。

### 20.2 第二步：绑定商城账号

标题：`绑定商城登录账号`

管理员可通过手机号、商城用户 ID 或昵称搜索商城用户。结果行展示：

```text
张三    138****1234    普通会员    未绑定配送员
```

绑定前展示确认提示：

```text
商城登录账号：张三（138****1234）
配送员工账号：张三（员工手机号 138****1234）
绑定后，该商城账号登录个人中心时会显示配送工作台入口。
```

交互规则：

- 默认只搜索当前租户的商城用户。
- 已绑定其他配送员的商城账号不可直接覆盖。
- 手机号不一致时允许绑定，但必须二次确认并记录审计日志。
- 不建议以手机号自动绑定，手机号只用于搜索和辅助校验。
- 支持“暂不绑定，稍后处理”，但该配送员在移动商城端不会出现入口。

### 20.3 第三步：配送资料

标题：`完善配送资料`

字段：

- 配送员姓名：默认取员工账号昵称，可修改。
- 联系手机号：默认取员工账号手机号；修改时提示是否同步员工账号手机号。
- 车辆信息：可选。
- 接单状态：默认离线，管理员确认后可切换在线。

提交前显示完整摘要：

```text
员工账号：张三
商城账号：张三（138****1234）
配送权限：已开通
接单状态：离线
```

点击“创建并开通”后，后端在一个事务内完成账号角色、配送资料和绑定关系处理。任一步失败都不能留下半成品配送员。

## 21. 已有配送员的绑定和权限操作

### 21.1 详情抽屉

点击列表“查看”打开详情抽屉，分为四个区域：

1. **身份信息**：员工账号、商城账号、脱敏手机号、租户。
2. **配送资格**：账号状态、配送权限、配送资料状态、绑定时间。
3. **履约状态**：接单状态、当前任务数、今日完成数、最近登录时间。
4. **操作记录**：绑定、解绑、停用、权限变更和身份换取记录。

### 21.2 绑定操作

“绑定商城账号”按钮打开搜索弹窗，复用新增向导第二步的搜索组件。绑定成功后提示：

```text
绑定成功。该商城账号下次进入个人中心时会显示配送工作台。
```

### 21.3 解绑操作

解绑前明确提示影响：

```text
解绑后，该商城账号将不再显示配送工作台入口；配送员员工账号和历史配送任务不受影响。
```

解绑不删除 `delivery_staff`，也不删除员工账号。已有配送任务仍保留原配送员归属，是否改派由管理员单独处理。

### 21.4 停用操作

停用分为两种：

- `停用接单`：接单状态切换为离线，不能被新任务派单，但可以登录查看已有任务。
- `停用配送资格`：回收 `delivery:execute` 或停用员工账号，移动端入口不再显示，配送接口拒绝访问。

两种操作必须使用不同按钮和不同确认文案，不能继续使用模糊的“切换状态”。

## 22. Web 与移动端的匹配流程

### 22.1 配置流程

```text
管理员进入配送员管理
  -> 选择或创建 sys_user 员工账号
  -> 分配配送员角色（含 delivery:execute）
  -> 创建 delivery_staff，保存 user_id = sys_user.id
  -> 搜索并绑定商城 user_info
  -> 账号状态正常、权限有效、资料未删除
```

### 22.2 移动端进入流程

```text
商城用户登录
  -> 请求 /auth/delivery/eligibility
  -> 服务端按当前商城用户 + 当前租户查询绑定关系
  -> 找到 sys_user 和 delivery_staff
  -> 校验员工账号、配送权限和配送资料
  -> 返回 eligible = true
  -> 个人中心展示“配送工作台”
  -> 点击后调用 /auth/delivery/exchange
  -> 签发以 sys_user.id 为主体的 deliveryToken
  -> 移动端进入 delivery-index
```

### 22.3 与当前移动端代码的兼容点

- 当前移动端配送请求已经单独使用 `deliveryToken`，继续保留。
- 当前配送员资料接口根据 TOB token 的用户 ID 查询 `delivery_staff.user_id`，继续保留。
- 当前 `/pages/delivery/**` 路由要求 `deliveryToken`，继续保留。
- 只新增商城身份换取入口，不改变配送任务的归属字段和状态机。
- 现有手机号+密码配送员登录继续作为独立端和异常场景的兜底方式。

## 25. 数据库和事务要求

### 25.1 绑定表

如果当前没有稳定的商城用户到员工账号关联，新增 `delivery_account_binding` 表。建议约束：

- `(tenant_id, mall_user_id)` 唯一，只允许一个有效配送身份。
- `(tenant_id, sys_user_id)` 唯一，避免同一员工被多个商城账号绑定。
- `delivery_staff_id` 建立索引。
- 使用 `del_flag` 逻辑删除，不物理删除历史绑定。
- 记录 `bind_by`、`bind_time`、`unbind_by`、`unbind_time`。

### 25.2 创建事务

“创建并开通”必须在服务端事务中完成：

```text
创建或选择 sys_user
  -> 分配配送员角色
  -> 创建 delivery_staff
  -> 创建商城账号绑定
  -> 写入操作日志
```

若员工账号已存在但没有配送权限，应由后端明确补充角色或返回待处理状态，不能只创建 `delivery_staff` 记录后让移动端无法登录。

### 25.3 Boot/Cloud SQL

新增绑定表或字段时：

- Boot 和 Cloud 各提供一份编号递增的增量 SQL。
- SQL 可重复执行，不使用 `DROP` 或 `TRUNCATE`。
- 更新 Boot 全量 SQL 构建器和校验结果。
- 核对租户表白名单、唯一索引和 Cloud 基线脚本。

## 27. 验收补充

### 27.1 Web 端验收

- 可以从一个向导完成员工账号、配送权限、配送资料和商城账号绑定。
- 已有关联配送资料的员工不能重复创建。
- 已绑定其他配送员的商城账号不能被无提示覆盖。
- 列表能区分账号状态、配送权限和接单状态。
- 派单候选只显示当前租户且具备有效配送资格的配送员。
- 停用接单不会误删配送权限或历史任务。
- 解绑商城账号不会删除员工账号和配送员历史数据。

### 27.2 Web 到移动端联调验收

- 管理员创建并绑定账号后，商城用户重新进入个人中心可以看到“配送工作台”。
- 无绑定、权限缺失、员工停用、配送资料删除时，商城端不显示入口。
- 点击入口后可以换取 `deliveryToken`，无需再次输入密码。
- 换取后的 token 主体对应 `sys_user.id`，移动端 `/app/delivery/staff/me` 能返回同一条 `delivery_staff` 资料。
- Web 派单给该配送员后，移动端工作台能看到对应任务。
- Web 解绑或停用资格后，移动端下一次资格刷新不再显示入口，配送接口拒绝旧身份继续操作。

### 27.3 双模式验收

- `VITE_OPEN_BOOT=true`：Web 和移动端请求都能正确改写到 `/boot/...`。
- `VITE_OPEN_BOOT=false`：请求首段仍为有效微服务域，Gateway 能路由到认证、用户和订单服务。
- Boot 编译、Cloud API 契约和前端类型检查均通过。
- Boot/Cloud 绑定表 SQL 内容、索引和租户字段一致。

## 28. 推荐实施顺序（Web 优先）

1. 先确认商城用户、员工账号和配送员资料的绑定模型。
2. 增加绑定表及 Boot/Cloud 增量 SQL，补充租户配置。
3. 后端实现向导式创建、绑定、解绑、资格和接单状态接口。
4. 修改 Web 配送员列表，展示绑定/权限/接单三类状态。
5. 将新增配送员改造成三步向导，避免手填重复身份信息。
6. 实现商城资格查询和配送 token 换取接口。
7. 修改移动端个人中心按资格显示入口，并接入免重复登录。
8. 联调“Web 配置 -> 商城个人中心 -> 配送工作台 -> Web 派单”完整链路。
9. 完成停用、解绑、改派、token 过期和 Boot/Cloud 双模式回归。
