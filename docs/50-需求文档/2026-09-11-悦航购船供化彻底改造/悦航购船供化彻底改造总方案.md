# 悦航购船供化彻底改造总方案

> 日期：2026-09-11  
> 状态：竞品调研结合公司业务后的产品与系统总方案  
> 适用项目：`aryn-mall-java`、`aryn-mall-ui`、`aryn-mall-uniapp`  
> 参考材料：`docs/50-需求文档/2026-09-11-船供商城竞品调研/竞品全景.html`、`海员个人与船供配送改造方案.md`

## 1. 最终判断

悦航购不应继续按“普通商城增加几个船供字段”的方式演进，而应改造成：

> **面向海员的船供交易入口 + 面向公司内部的船供履约作业系统。**

它不是开放式综合电商，也不是纯船供 ERP，更不是第三方物流平台。最适合公司的定位是：

~~~text
海员个人购买 / 船员共同采购
              ↓
        悦航购小程序
              ↓
商品主数据 + IMPA/ISSA + 共享购物车
              ↓
订单合并 + 船舶/靠港计划 + 支付
              ↓
仓库配货 + 扫码拣货 + 拍照留证
              ↓
公司自有司机港口/船舶配送
~~~

核心差异化不是商品数量，也不是低价，而是把“海员下单、整船合并、按靠港时间送达、司机交付留证”做成一条闭环。竞品调研显示，B 端船供 ERP 已经很多，但“B 端船供运营 + C 端海员入口 + 自有港口配送”仍有明显空位。

## 2. 调研结论如何转化为公司策略

### 2.1 竞品信息中可确认的事实

竞品全景材料盘点了国际船供 SaaS、B2B 船供平台、海员 C 端入口和国内区域配送项目，得出的有效结论是：

1. 直接面向海员下单并送到船的产品数量少，且大多处于早期、单港或区域化阶段。
2. Seaborn、Tidal、嘉软 MTS、多麦德 MSP 等 B 端产品覆盖报价、采购、库存、财务，但普遍没有海员 C 端下单入口。
3. 长江汇验证了“船员个人需求汇总为整船订单”的需求，但其趸船、无人机和内河服务区模式不宜直接照搬。
4. Sailor's Cart、Seafarer.Global 等验证了共享购物车、合并订单和船上交付的价值。
5. IMPA/ISSA 目录、RFQ 解析、扫码拣货、拍照留证、到港预约是行业能力方向，不应全部在第一天做完，但必须在架构上预留。
6. ShipServ、MarineOnline 更适合作为后续外部获客渠道，不应成为当前订单主链路的前置依赖。

竞品中的用户数、GMV、覆盖港口和匹配准确率多为厂商自称，不能直接作为财务预测或技术容量依据。本方案只吸收被多家产品重复验证的流程，不照搬宣传数字。

### 2.2 对公司真正有价值的能力

| 能力 | 是否采用 | 公司化改造方式 |
|---|---|---|
| 海员个人购买 | 必做 | 保留简单零售体验，但配送目标改为港口/船舶 |
| 船员共享购物车 | 必做 | 同一船舶下多个海员分别加购，授权人员统一确认 |
| 整船订单合并 | 必做 | 按船舶和靠港计划合并，减少司机和仓库作业次数 |
| 三步极简下单 | 必做 | 选择船舶/靠港计划、选商品、确认配送并支付 |
| IMPA/ISSA 编码 | 必做 | 先建内部物料编码映射，逐步补全公开目录 |
| 到港预约 | 必做 | 以 ETA/ETD、泊位、时间窗驱动调度 |
| 扫码拣货和拍照 | 重要 | 先服务公司仓库和司机，不做复杂 WMS |
| AI RFQ/PDF/Excel 解析 | 二期 | 先人工导入结构化模板，积累数据后上线 AI |
| 多币种和对账 | 二期/三期 | 有国际 B 端客户和外币结算后再做 |
| ShipServ/MarineOnline 入驻 | 获客选项 | 作为外部询价入口，不改变内部订单模型 |
| 无人机/配送船 | 暂不做 | 公司已有司机和港口配送能力，重资产投入不匹配 |
| 开放供应商 marketplace | 暂不做 | 先把自营商品和履约跑稳，避免引入供应商结算复杂度 |
| 企业账期/授信/发票 | 暂不做 | 未确认付款主体前不把企业采购模型前置 |

## 3. 产品定位和边界

### 3.1 三类用户

| 用户 | 核心任务 | 主要端 |
|---|---|---|
| 海员个人 | 买生活用品、食品和个人用品，查看配送 | UniApp 小程序 |
| 船员采购发起人/船长授权人员 | 发起整船采购、收集成员需求、确认订单 | UniApp 小程序 + 管理端 |
| 公司运营、仓库和司机 | 管商品、接订单、配货、派车、交付和留证 | Web 管理端 + 同一小程序的司机模式 |

第一阶段不单独建立船东企业账户、供应商账户和复杂审批体系。海员仍然是下单用户，船舶是采购和配送上下文；后续确认商业模式后再增加企业付款主体。

### 3.2 两种购买场景

~~~text
purchase_scene = 1  海员个人购买
purchase_scene = 2  船供采购
~~~

商品允许同时被两种场景使用；订单必须保存场景快照。个人购买和船供采购都使用公司内部司机送到港口或船舶，不出现普通快递作为船供租户的主流程。

### 3.3 不做“两个系统”

个人商城和船供采购应共用：商品、SKU、库存、支付、订单、售后、司机和配送任务。差异只通过场景策略表达：

- 可见字段不同。
- 数量单位和起订量不同。
- 购物车分组不同。
- 配送上下文校验不同。
- 管理端筛选和报表维度不同。

禁止为个人购买、船供采购复制两套商品表、订单表和司机任务表。

## 4. 目标业务闭环

### 4.1 个人购买

~~~text
登录
→ 选择当前船舶/靠港计划
→ 进入个人购买
→ 选商品和规格
→ 加入购物车或立即购买
→ 确认港口/泊位/送达时间窗
→ 在线支付
→ 自动生成内部配送任务
→ 公司配货、派司机
→ 司机送达并拍照/签收
→ 海员查看配送进度并确认收货
~~~

### 4.2 船供采购

~~~text
登录
→ 选择船舶和靠港计划
→ 进入船供采购
→ 搜索 IMPA/ISSA/中文/英文/条码
→ 从常购清单或历史订单批量加购
→ 多名船员共享购物车并填写备注
→ 授权人员统一确认数量和价格
→ 选择时间窗并支付/确认
→ 仓库生成拣货波次
→ 扫码拣货、复核、拍照留证
→ 司机按港口和船期配送
→ 船上人员签收
~~~

### 4.3 内部运营闭环

~~~text
商品建档 → 上架检查 → 订单接收 → 库存锁定 → 配货/拣货
→ 交接司机 → 出车 → 到港 → 交付 → 签收 → 售后/短装处理
~~~

每个关键节点必须有可追踪的操作人、时间、原值/新值和证据，不把事实寄托在前端通知或聊天记录上。

## 5. 目标系统架构

### 5.1 总体结构

```text
┌──────────────────────────────┐  ┌──────────────────────────────┐
│ UniApp 微信小程序             │  │ 管理后台 Web                  │
│ 海员模式：个人/船供下单       │  │ 商品/物料/船舶/订单/仓库/调度 │
│ 司机模式：拣货/出车/签收      │  │ 运营/异常处理/报表            │
└───────────────┬──────────────┘  └───────────────┬──────────────┘
                └─────────────────┼────────────────┘
                           Gateway / Auth
                                   │
         ┌─────────────────────────┼─────────────────────────┐
         │                         │                         │
  商品与物料域              船舶与靠港域               交易与履约域
  商品 SPU/SKU               船舶/成员/靠港计划         购物车/订单/支付
  IMPA/ISSA/单位              港口/泊位/时间窗           库存/拣货/配送
         │                         │                         │
         └─────────────────────────┼─────────────────────────┘
                                   │
              MySQL + Redis + 对象存储 + 异步任务/消息
```

### 5.2 采用模块化单体优先、微服务可拆分

当前项目已经支持 Boot 单体和 Cloud 微服务双模式，建议：

1. 先在现有模块边界内实现“模块化单体”，减少跨服务调试成本。
2. API、DTO、事件和表边界按照领域拆开，Cloud 模式通过 API/Dubbo 通信。
3. 不因为竞品宣传中的“平台化”提前拆成十几个服务。
4. 当商品、订单、履约或 AI 任务有独立扩缩容需求时再拆服务。

推荐领域归属：

| 领域 | 当前模块/新增模块 | 主要职责 |
|---|---|---|
| 商品与物料 | `aryn-product` | SPU/SKU、船供资料、编码、单位、价格库存 |
| 船舶上下文 | 新增 `aryn-vessel-api/biz` | 船舶、成员、港口、靠港计划 |
| 交易 | `aryn-order` | 购物车、共享购物车、结算、订单、售后 |
| 支付 | `aryn-pay` | 支付、退款、回调幂等、支付快照 |
| 履约 | `aryn-order` 或独立 fulfillment 边界 | 锁库存、波次、拣货、短装、交接 |
| 配送 | 现有 delivery 能力 | 司机、出车、任务、到港、签收证据 |
| 集成 | 后续新增 integration 边界 | RFQ、外部 B2B 平台、船期数据 |

## 6. 商品主数据重做

### 6.1 商品销售范围

`ship_goods_profile` 增加显式销售范围，避免 `is_ship_supply` 无法表达“个人和船供均可”：

~~~text
sale_scope = 1  仅个人购买
sale_scope = 2  仅船供采购
sale_scope = 3  个人购买和船供采购
~~~

### 6.3 SKU/包装资料


### 6.4 编码匹配模型

不要把 IMPA 直接硬编码成商品表唯一字段。建议增加 `product_code_mapping`：

~~~text
id
tenant_id
spu_id
sku_id
code_type       IMPA / ISSA / BARCODE / INTERNAL / SUPPLIER
code_value
match_source    MANUAL / IMPORT / AI / EXTERNAL
confidence
status
~~~

这样一个 SKU 可以对应多个编码，AI 匹配也可以保留置信度并等待人工确认；商品名称变化不会破坏历史订单。

### 6.5 商品发布检查

个人商品至少要求名称、主图、类目、价格和库存；船供商品还要求 IMPA 或内部物料编码、采购单位、箱规、MOQ 和 step_qty。资料不完整的商品可以保存草稿，但不能进入船供目录。

## 7. 共享购物车与整船订单

这是竞品中最适合公司的核心能力，应高于 AI RFQ 排期。

### 7.1 共享购物车模型

~~~text
shared_cart
- vessel_id
- vessel_call_id
- owner_user_id
- status
- expires_at

shared_cart_member
- cart_id
- user_id
- role
- can_edit
- can_confirm

shared_cart_item
- cart_id
- user_id
- sku_id
- requested_quantity
- approved_quantity
- member_remark
~~~

普通个人购物车继续保留；船供模式下允许采购发起人创建共享购物车，通过小程序邀请同船成员加入。授权人员确认后生成一个订单，订单明细保留成员来源和备注。

### 7.2 第一阶段的简化权限

第一阶段不做复杂审批链，只支持：

- 发起人：创建、邀请、修改和提交共享购物车。
- 成员：添加自己的商品和备注，只能修改自己的明细。
- 确认人：统一调整数量、确认价格和提交订单。
- 管理员：可在后台纠正未配货订单，并记录审计日志。

## 8. Web 管理端彻底改造

### 8.1 从“商品 CRUD”改成“船供运营工作台”

管理端一级导航建议调整为：

~~~text
运营工作台
  ├── 今日待处理
  ├── 靠港日历
  └── 异常中心

商品与物料
  ├── 商品中心
  ├── IMPA/ISSA 编码
  ├── 批量导入任务
  ├── 常购清单
  └── 价格/库存变更记录

船舶与客户
  ├── 船舶档案
  ├── 船员绑定
  ├── 靠港计划
  └── 船舶采购历史

订单与履约
  ├── 个人订单
  ├── 船供订单
  ├── 共享购物车
  ├── 待配货/拣货波次
  └── 短装和售后

配送调度
  ├── 待派单
  ├── 港口配送看板
  ├── 出车单
  └── 签收凭证
~~~

### 8.2 商品中心必做

当前商品页 `aryn-mall-ui/apps/web-ele/src/views/product/goods-spu/index.vue` 只有基础筛选和批量上下架，必须改为：

- 按销售范围、IMPA、英文名、条码、库存预警、资料完整度筛选。
- 商品行显示中文名、英文名、编码、单位/箱规、MOQ、库存、售价和完整度。
- 批量导入采用上传、解析、预览、确认四步。
- 支持复制商品、批量补资料、批量改销售范围、批量上下架和导出。
- 支持查看 SKU、价格库存记录和变更审计。
- 大量商品时使用服务端分页、远程品牌搜索和列配置，不一次性加载所有 SKU。

当前 `goods-spu/form.vue` 要拆成“基础资料、船供资料、SKU/包装、交易规则、详情、发布检查”六个分组。多 SKU 录入支持复制上一行、按列粘贴、单位批量填充和 MOQ/step_qty 校验。

### 8.3 订单与履约工作台

订单列表增加购买场景、船舶、港口、ETA、时间窗、司机和短装状态。履约看板以“靠港时间窗”排序，而不是单纯按订单创建时间排序。一个订单从支付到交付要能看到：

~~~text
订单 → 库存锁定 → 拣货波次 → 复核 → 交接司机 → 出车 → 到港 → 签收
~~~

### 8.4 扫码拣货和照片留证

司机模式放在同一个 UniApp 小程序中，通过登录身份或服务端角色返回司机入口；不另建一套司机小程序。司机工作台增加：

- 按波次和船舶展示拣货单。
- 扫码校验 SKU、数量和箱/托盘。
- 缺货、短装、替代品必须选择原因。
- 配货和装车环节拍照留证。
- 司机交接时记录件数、异常和照片。

第一阶段不做完整仓储管理系统，不引入库位、波次策略和复杂补货算法；先解决“拿对货、送对船、留证据”。

司机和海员共用一个小程序代码包，但路由、权限和首页完全分开：

~~~text
海员角色 → 海员首页、商品、购物车、订单、配送进度
司机角色 → 今日任务、扫码拣货、出车、到港、签收、异常
~~~

司机只能看到分配给自己的任务，不能访问海员商城和其他司机任务。若司机数量很少，第一期可以先由 Web 响应式页面完成任务确认，但扫码、拍照、定位和离线重试最终应收敛到小程序司机模式。

## 9. 小程序彻底重做

### 9.1 新底部导航

```text
首页 | 商品 | 购物车 | 订单 | 我的
```

“分类”并入商品页，首页从营销首页改为船舶工作台。海员角色首屏显示当前船舶、下一靠港、待配送订单和常购入口；司机角色使用完全不同的任务首页，而不是默认热搜和通用瀑布流。

### 9.1.1 两个端的职责边界

本项目上线只建设两个端：

| 端 | 面向用户 | 主要职责 | 不承担的职责 |
|---|---|---|---|
| 微信小程序 | 海员、船供采购人、公司司机 | 下单、共享购物车、配送查看、扫码、定位、拍照、签收 | 大批量商品维护、复杂报表、批量导入 |
| Web 管理端 | 运营、商品、仓库、调度、管理员 | 商品主数据、批量导入、订单处理、拣货波次、司机派单、靠港看板、异常和报表 | 面向海员的移动下单体验 |

不再单独建设“司机端 Web”“司机 App”或第三个小程序。司机是同一个小程序中的受控角色，管理端只负责配置和派单。

### 9.2 首页船舶工作台

~~~text
当前船舶：XXX 轮（切换）
下一靠港：港口 / ETA / 泊位
待处理：共享购物车待确认、配送中订单

[船供采购] [个人购买] [再来一单] [查看配送]

常购商品 | 最近购买 | 我的清单 | 港口公告
~~~

新增 `shipContextStore`，保存当前用户的 `purchaseScene`、`vesselId`、`vesselCallId`、港口、泊位、时间窗和收货人。这个上下文贯穿商品列表、购物车、结算和订单详情；切换船舶时必须防止购物车串船。

### 9.3 船供采购页

船供采购页必须允许“不进详情直接批量下单”：

1. 支持 IMPA、ISSA、中文、英文、条码和内部编码搜索。
2. 支持常购、最近购买、我的清单、按类目、按储存条件和按库存筛选。
3. 列表直接显示采购单位、箱规、MOQ、step_qty、库存和当前船舶。
4. 每行直接填写数量，数量不符合规则时就地提示并给出建议值。
5. 支持扫码加入、批量勾选和从历史订单复制。
6. 支持共享购物车，成员能看到自己的明细，确认人统一提交。

### 9.4 个人购买页

个人购买页保持简单：商品图、零售价、库存、规格、评价和收藏。它与船供页共用商品数据，但不强行展示 IMPA、箱规和船供字段。结算仍然必须选择港口/船舶配送，不显示普通快递。

### 9.5 购物车和结算

购物车按“当前船舶 → 购买场景”分组。船供商品按采购单位和箱规展示；个人商品按零售单位展示。结算顺序改为：

~~~text
购买场景 → 船舶 → 靠港计划 → 港口/泊位 → 时间窗 → 收货人 → 备注 → 支付
~~~

当前 `src/sub-pages/order/order-confirm/index.vue` 默认获取地址并将配送方式设为普通快递，必须改成内部港口/船舶配送。地址簿可以为其他零售租户保留，但本租户不作为结算首屏。

### 9.6 订单和配送进度

订单详情改为内部配送时间线：

~~~text
已支付 → 仓库配货 → 已派司机 → 司机取货 → 前往港口 → 已到港 → 已交付 → 已签收
~~~

隐藏快递公司、快递单号和第三方物流轨迹，显示船舶、港口、司机、预计到达、异常和签收照片。船供订单提供“复制商品清单/再来一单”，但必须重新确认船舶、靠港计划、库存和价格。

## 11. AI、RFQ 和外部平台的演进顺序

### 11.1 不直接从 AI 开始

竞品把 AI RFQ 解析作为卖点，但公司当前最重要的问题是商品主数据、订单合并和内部履约。如果没有稳定的 IMPA/ISSA、单位、SKU、价格和库存数据，AI 只能把脏数据更快地写入系统。

推荐顺序：

~~~text
Excel 模板导入
→ 编码映射和人工校验
→ 邮件/PDF/Excel RFQ 结构化解析
→ AI 匹配候选商品和数量
→ 人工确认后生成共享购物车/报价草稿
~~~

AI 输出必须保留原文、候选匹配、置信度和人工确认结果，不能直接生成可支付订单。

### 11.2 外部 B2B 平台

ShipServ 和 MarineOnline 可以作为后续获客渠道。接入时单独建设外部询价适配器，将外部 RFQ 转换为内部 `rfq_draft`，不要让第三方订单直接绕过库存、支付和配送校验。

## 12. 分阶段实施路线

### 阶段 0：业务确认和数据治理

目标：先统一业务规则，不写页面假设。

- 确认首批港口、泊位、时间窗和司机配送范围。
- 整理现有商品、SKU、单位、包装、IMPA/内部编码和库存。
- 确认个人订单是否都必须绑定船舶，确认个人收货人规则。
- 确认船供订单支付、取消、短装、替代品和售后规则。
- 确认共享购物车的发起人、确认人和成员权限。

交付物：字段字典、状态机、首批商品清单、港口/船舶清单、验收样例。

### 阶段 1：核心交易和内部配送闭环

目标：跑通一个港口、一个仓库、一个司机组的真实闭环。

- 商品销售范围和船供资料。
- 船舶、成员和靠港计划。
- 内部配送 `delivery_way=4`。
- 个人购买和船供采购结算。
- Web 商品列表和订单/配送筛选。
- 小程序首页、双场景目录、购物车、结算和配送时间线。
- 同一小程序的司机模式：今日任务、到港、签收和照片留证。
- 支付回调幂等、配送任务和签收快照。

暂不加入共享购物车和 AI，先验证最小可用闭环。

### 阶段 2：船供效率和仓库履约

目标：让大单、多人采购和仓库作业效率达到可用。

- 共享购物车和整船订单。
- 常购清单、历史订单复制和批量加购。
- IMPA/ISSA/条码映射。
- Excel 批量导入和错误报告。
- 拣货波次、扫码拣货、短装和照片留证。
- 靠港日历、港口配送看板和司机交接。

### 阶段 3：智能化和外部获客

目标：提高运营规模和外部订单处理能力。

- AI 邮件/PDF/Excel RFQ 解析和候选匹配。
- 多币种和外部 B 端对账。
- ShipServ/MarineOnline RFQ 适配器。
- 船期数据接口和 ETA 变更自动提醒。
- 库存预测和替代品推荐。

### 阶段 4：平台化扩展

仅在业务验证后考虑：

- 船东/船管企业账户。
- 企业预算、审批、账期、发票。
- 供应商入驻和多供应商比价。
- 福利金/eWallet。
- 跨港口仓配网络和第三方运力。

## 13. 架构决策记录

### ADR-001：自研扩展，不采购通用商城 SaaS

**决策**：基于现有悦航购改造成船供交易和履约系统。

**原因**：公司已经拥有 Spring Boot、Vue、UniApp、订单、支付、库存和配送基础；通用商城或纯 B 端 ERP 都无法同时满足海员入口和自有司机配送。

**代价**：需要自行建设船舶、共享购物车、编码主数据和仓库履约能力。

### ADR-002：模块化单体优先，保留 Cloud 拆分能力

**决策**：先在现有 Boot 聚合模式中完成闭环，接口和 API 仍按 Cloud 可拆分方式设计。

**替代方案**：一开始拆成商品、船舶、交易、履约、AI 多个微服务。拒绝原因是当前业务规模和团队运维能力不足以抵消分布式复杂度。

### ADR-003：共享购物车优先于 AI RFQ

**决策**：阶段 2 先做同船多海员的共享购物车和整船订单，再做 AI 解析。

**原因**：共享购物车直接减少沟通和重复下单，是公司现有客户马上能使用的效率能力；AI 必须建立在干净编码和价格库存数据上。

### ADR-004：自有司机是履约事实来源

**决策**：以 delivery_task、delivery_trip、delivery_evidence 和司机操作记录为准，消息和地图只做辅助。

**原因**：公司实际配送到港口/船舶，不存在快递单号和第三方轨迹，必须围绕交接和签收证据设计。

### ADR-005：订单级场景，商品级销售范围

**决策**：订单使用 `purchase_scene`，商品使用 `sale_scope`，两者不混用。

**原因**：同一商品可能个人和船供都可买；同一租户也同时存在两种订单。

## 14. 非功能要求

### 性能

- 商品列表和搜索接口 p95 小于 500ms，详情和结算接口 p95 小于 800ms。
- 批量导入 1 万行以内可异步完成，并提供进度和错误文件。
- 结算必须服务端重新校验库存、价格和配送上下文。

### 可靠性

- 支付回调、订单创建和配送任务创建必须幂等。
- 订单和配送关键状态变更写操作日志。
- 备份订单、库存、配送证据和导入任务；建议 RPO 不超过 1 小时、RTO 不超过 4 小时。

### 安全

- 船员只能访问自己所属船舶、自己的订单和被授权共享购物车。
- 司机只能访问分配给自己的出车单和配送任务。
- IMPA、价格、成本价、手机号和签收照片按角色控制。
- 上传的 Excel、PDF、图片进行类型、大小和病毒扫描，禁止把文件内容直接拼接进 SQL 或命令。

### 可维护性

- Boot/Cloud 同步实现和 SQL。
- API DTO 与 biz 实现分离。
- 新业务状态使用枚举和字典，不在页面散落魔法值。
- 共享购物车、库存锁定、配送任务和签收证据补充单元测试、接口测试和关键链路测试。

## 15. 关键指标

### 用户和交易

- 海员登录后首次下单完成率。
- 船供订单平均下单时长。
- 共享购物车参与人数和合并订单比例。
- 历史订单再购比例。
- 船供商品搜索命中率和 IMPA 匹配人工修正率。

### 履约

- 配货准确率和扫码覆盖率。
- 短装率、替代品率和异常关闭时长。
- 司机准时到港率。
- 从支付到交接司机的平均时长。
- 签收照片和签收人完整率。

### 经营

- 每个靠港计划的订单合并数。
- 每次港口出车的订单数、件数和配送成本。
- 个人购买与船供采购的客单价和复购率。
- 商品资料完整度和库存预警处理时长。

## 16. 最终落地原则

1. 产品第一身份是船供交易和履约系统，不是通用商城。
2. 海员个人购买和船供采购共用底层能力，但使用不同的商品展示、数量规则和下单路径。
3. 公司自有司机、港口、船舶和靠港计划是核心业务事实。
4. 商品主数据、IMPA/ISSA、单位和包装先治理，再上 AI。
5. 共享购物车、整船合并订单和到港预约优先于复杂营销。
6. 扫码拣货、照片留证和异常处理要早于无人机、开放平台和复杂供应商体系。
7. ShipServ、MarineOnline 是后续获客渠道，不替代内部订单和履约模型。
8. 所有新能力同时适配 Boot 与 Cloud，所有数据库变更同时提供两套增量 SQL。
9. 先用一个港口、一个仓库和一组司机做真实试点，再扩展港口和商品规模。

## 17. 营销活动扩展设计

### 17.1 结论：可以扩展，但要先拆开营销和交易

当前项目已经有优惠券、限时折扣、秒杀、拼团、分销和页面装修等营销基础能力，相关代码主要位于 `aryn-promotion`，订单价格计算位于 `aryn-order/.../OrderPriceComputeService`。因此不是从零开始。

但现状偏普通零售：订单价格计算直接依赖优惠券、折扣和秒杀远程服务，船供数量规则、购买场景、船舶和靠港计划尚未成为营销条件。如果后续每增加一个活动就修改订单创建和结算代码，活动越多越容易出现价格不一致、优惠叠加错误和退款无法还原。

推荐将营销能力抽象为：

~~~text
营销活动配置
      ↓
活动规则匹配
      ↓
结算优惠试算
      ↓
下单时锁定优惠
      ↓
支付确认 / 取消释放 / 售后分摊
~~~

订单服务只负责调用营销引擎并保存结果，不直接知道“满减、折扣、买赠、阶梯价”的具体实现。

### 17.2 营销和订单之间的边界

订单必须保存营销快照，至少包括：

~~~text
promotion_snapshot
- activity_id
- activity_type
- promotion_name
- rule_snapshot
- discount_amount
- gift_items
- applied_item_ids
- purchase_scene
- price_before
- price_after
~~~

历史订单不能重新读取当前活动配置来计算金额。营销活动结束、暂停或商品变价，都不能改变已支付订单的成交价。

### 17.3 统一营销上下文

每次结算向营销引擎传入统一上下文：

~~~text
tenant_id
user_id
purchase_scene       个人购买 / 船供采购
vessel_id
vessel_call_id
sku_items             SKU、数量、单位、原价
cart_type             普通购物车 / 共享购物车
member_level
activity_time
port_code
~~~

这样新增活动时可以直接配置适用条件，不需要在订单服务中增加大量 `if/else`。

### 17.4 适合公司业务的营销类型

#### 个人购买一期可做

- 新用户首单优惠。
- 指定生活用品/食品满减。
- 个人购买优惠券。
- 船员会员等级折扣。
- 复购券和历史订单再购优惠。
- 指定港口或指定靠港时间窗的短期活动。

#### 船供采购优先做

- 按 SKU 数量或金额的阶梯价。
- 同船合并订单达到金额后的整单优惠。
- 指定船供目录的采购价。
- 常购清单专属价。
- 指定船舶或指定船员群组的活动价。
- 买指定箱数赠送或搭配赠品。

#### 不建议直接照搬普通电商

- “包邮”不适合公司内部司机配送，应改成港口配送优惠或整单配送成本策略。
- 复杂拼团不应阻塞船供采购，船供本身更适合共享购物车和整船合并。
- 秒杀要谨慎用于食品和船供刚需，避免低库存造成无法配货。
- 分销佣金不是当前核心，除非未来发展外部代理或船员推广。

### 17.5 活动适用范围模型

活动配置至少支持：

~~~text
activity_type
1 优惠券
2 满减
3 折扣
4 阶梯价
5 买赠
6 首单/复购
7 船供整船优惠

scope_type
1 全场
2 指定 SPU/SKU
3 指定类目
4 指定销售场景
5 指定船舶/船员群组
6 指定港口/靠港时间窗
~~~

规则还要包含开始结束时间、优先级、是否可叠加、适用端、用户领取限制、总库存/名额和活动预算。活动状态统一由后端判定，前端只展示可用结果。

### 17.6 优惠叠加和价格计算

必须先定义固定规则，再增加活动类型：

1. 商品阶梯价先确定 SKU 成交基价。
2. 活动折扣和会员折扣按优先级选择，默认不叠加。
3. 满减或优惠券在可用商品金额上计算。
4. 买赠商品单独生成赠品明细，不混入付费数量。
5. 船供整船优惠只对同一 `vessel_id + vessel_call_id` 的订单计算。
6. 共享购物车确认前可以试算，支付前必须重新试算并锁定。

第一期建议使用“同类优惠取最优 + 跨类型按固定顺序”的简单规则，不做任意叠加。所有优惠明细返回前端，避免用户看到的金额和订单金额不一致。

### 17.7 交易时序

营销活动必须支持预览、锁定、确认、释放四个动作：

~~~text
结算：previewPromotion
创建订单：reservePromotion
支付成功：confirmPromotion
取消/超时：releasePromotion
退款：按订单明细释放或扣减优惠
~~~

优惠券已有 reserve/release 能力，可以继续复用；阶梯价和整船优惠需要新增活动锁定记录。每个锁定动作使用订单号和活动 ID 幂等，避免支付重试重复占用名额。

### 17.8 Web 管理端营销中心

Web 端新增“营销中心”，但不把活动入口混入商品 CRUD：

~~~text
营销中心
  ├── 活动列表
  ├── 优惠券
  ├── 满减/折扣
  ├── 船供阶梯价
  ├── 船供整船优惠
  ├── 买赠活动
  ├── 活动商品
  ├── 规则冲突检查
  └── 活动效果
~~~

活动创建采用“基本信息 → 适用范围 → 规则 → 商品/场景 → 预览 → 发布”的步骤。发布前检查时间冲突、商品销售范围、价格底线、库存和是否允许叠加；发布后不能直接修改已影响订单的核心规则，只能暂停或新建版本。

### 17.9 小程序营销展示

营销不应破坏船供采购的效率：

- 商品列表展示“船供阶梯价”“满额优惠”“常购价”等简短标签。
- 船供批量加购时实时显示当前数量距离下一阶价格还差多少。
- 共享购物车确认页展示整船订单优惠，不要求每个船员分别领券。
- 个人购买保留优惠券入口、首单和复购优惠。
- 结算页展示优惠来源、优惠金额和不可用原因。
- 活动详情页不应成为下单必经页面。

### 17.10 实施优先级

第一阶段：

- 保留并适配现有优惠券和限时折扣。
- 增加 `purchase_scene`、船供商品范围和单位数量校验。
- 结算统一返回优惠明细和最终价格。
- 保存订单营销快照。

第二阶段：

- 船供阶梯价。
- 共享购物车整船优惠。
- 买赠和常购清单专属价。
- 活动锁定/释放和规则冲突检查。

第三阶段：

- 会员成长和复购自动化。
- 个性化推荐和活动人群。
- 外部渠道优惠映射。
- 活动效果、毛利和配送成本联动分析。

### 17.11 营销扩展验收标准

- 新增一种活动类型时，不修改订单状态机和配送任务创建逻辑。
- 个人购买和船供采购可以配置不同活动，互不串用。
- 共享购物车确认、支付重试、取消和退款不会重复计算或重复释放优惠。
- 订单历史金额不受活动修改影响。
- 结算页、订单详情、后台订单和退款金额使用同一份营销快照。
- Boot 和 Cloud 模式下营销规则、价格计算、优惠锁定和 SQL 配置一致。

## 18. 小程序登录与身份模式改造

### 18.1 当前登录现状

当前小程序已经支持微信登录、手机号验证码登录、密码登录，并在 `authStore` 中维护商城 TOC token。同时配送员还有独立的 `deliveryToken`，并且认证服务已经提供：

~~~text
GET  /auth/delivery/eligibility
POST /auth/delivery/exchange
~~~

这套能力可以复用，不需要推翻现有认证服务，也不建议让海员和司机重新注册两套账号。

### 18.2 推荐登录模式

上线只保留一个小程序，登录后按角色进入不同模式：

~~~text
普通海员：微信快速登录 → 加载用户资料和船舶 → 海员首页
有司机资格：微信快速登录 → 查询配送资格 → 换取司机 token → 司机工作台
无司机资格：只能进入海员模式
~~~

微信快速登录作为海员主入口，手机号验证码和密码登录作为兜底。司机不再要求用户在同一个小程序内重复输入一套配送员密码；已登录商城且具备资格时，使用现有 exchange 接口换取短期司机 token。

### 18.3 登录后会话初始化

登录成功后统一执行以下步骤：

1. 保存商城 TOC token。
2. 获取当前用户信息和租户能力。
3. 获取用户所属船舶和默认靠港计划。
4. 查询配送工作台资格。
5. 有资格时换取独立司机 token，但保持司机 token 与商城 token 隔离。
6. 根据 `mode`、角色和能力跳转海员首页或司机首页。

一期可以复用现有用户信息、`getDeliveryEligibility` 和船舶接口分步调用；只有当首屏请求过多时才增加 `/auth/app/bootstrap` 聚合接口。

### 18.4 安全和路由规则

- 司机 token 过期只退出司机模式，不强制退出海员商城。
- 退出登录必须同时清理商城 token、司机 token、司机资料、船舶上下文、共享购物车缓存和跳转路径。
- 司机页面必须由路由守卫和后端接口双重鉴权，不能只依赖本地 storage 中的 `deliveryToken`。
- 用户首次登录且没有船舶成员关系时进入选择/绑定流程；绑定必须通过后台邀请、邀请码或管理员授权，不能任意搜索绑定船舶。
- `/pages/delivery/login` 保留兼容入口：未登录时回普通登录页，已登录且有资格时直接换取司机身份；确认无调用后再下线旧的独立配送员密码登录。
- 路由白名单只放行公开浏览页面，购物车、个人中心、订单和船舶页面必须经过商城登录校验。

### 18.5 登录改造验收

- 微信登录成功后可以进入海员首页并加载船舶上下文。
- 有配送资格的用户无需二次输入密码即可进入司机模式。
- 没有配送资格的海员无法访问司机路由和司机接口。
- 司机 token 失效不会清除商城登录状态。
- 退出登录后两套身份、船舶上下文和购物车缓存均被清理。
- Boot 和 Cloud 模式下认证、配送资格、船舶和订单请求路径均正确。
