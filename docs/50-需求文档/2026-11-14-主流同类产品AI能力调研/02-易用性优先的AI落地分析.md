# 易用性优先的 AI 落地分析（船供 / 海员个人 / 工厂餐厅）

> 日期：2026-11-14
> 关联：
>
> [主流同类产品 AI 能力调研](./README.md)
> 前提：
> 管理端优先「方便生产营销活动」
> 移动端优先「易用性」
> 三类采购场景：船供采购、海员个人采购、工厂餐厅采购
> **每单采购量较大**
>
> （船供单笔 1 万～十几万、几十到上百 SKU；工厂餐厅周期性大单；海员个人为上船前自购囤货）
> **当前处于开发阶段，尚无大量真实交易数据**
>
> （2026-11-14 补充：海员个人为自购、送到船，并与整船补给单合并配送）



***

## 0. 一句话结论

三类场景的本质不是「逛商城」，而是 \*\*「把一份采购清单变成一张不出错的订单」\*\*。

所以移动端 AI 的价值排序应该是：



1. **少输**：清单识别、单位换算、商品匹配、常购复用

2. **少错**：异常前置、MOQ / 步长 / 库存校验、审批摘要

3. **少想**：航次 / 菜单用量测算、缺货替代推荐

4. **少点**：批量改数量、按人分组、一键复购

管理端 AI 的价值排序应该是：



1. **少填**：输入活动目标，自动生成活动方案和配置草稿

2. **少试**：规则冲突、价格倒挂、库存不足在发布前校验

3. **少做图**：文案、海报、活动页骨架生成

4. **少导表**：活动复盘用自然语言问数

**关键判断：AI 不是入口，是「填表器 + 校验器 + 摘要器」。**

如果底层没有批量录入、单位、模板、复用这些结构，AI 只会让错误发生得更快。

## 0.1 冷启动约束：没有数据时，AI 该做什么、不该做什么

> 2026-11-14 补充：当前仍在开发阶段，尚无大量真实订单 / 行为 / 消耗数据；海员个人为自购，收货地址是船，且与整船补给单合并配送。

### 能用的 AI（不依赖历史数据）



| 类型    | 具体能力                                    | 为什么现在能用              |
| ----- | --------------------------------------- | -------------------- |
| 解析类   | Excel / 图片 / PDF / 文字 / 语音清单 → 结构化行     | 只依赖输入内容和商品目录，不需要历史交易 |
| 匹配类   | 品名 / 别名 / 规格 / 单位 / 编码的语义匹配             | 只依赖商品主数据，不需要用户行为     |
| 生成类   | 活动方案、活动页文案、Banner、推送文案                  | 只依赖活动规则和当前库存         |
| 规则测算类 | 船型 / 航次天数 / 人数 / 餐次 → 补给量；菜单 / 人数 → 采购量 | 用专家系数表和模板，不用模型预测     |
| 摘要类   | 审批摘要、订单摘要、异常解释                          | 只依赖当前单据内容            |

### 暂时不能用的 AI（没有数据就无法验证）



| 类型  | 具体能力                | 为什么先不做           |
| --- | ------------------- | ---------------- |
| 预测类 | 销量预测、自动补货、库存优化      | 没有历史销量，模型学不出可靠曲线 |
| 推荐类 | 个性化推荐、「猜你喜欢」、千人千面   | 没有行为数据，推荐结果不可信   |
| 定价类 | 价格弹性、最优折扣、优惠力度优化    | 没有成交数据，无法判断敏感度   |
| 分层类 | 客户生命周期、流失预测、高价值客户识别 | 没有足够样本，标签不准      |
| 归因类 | 活动归因、转化归因、渠道归因      | 没有对照组和历史基线，归因不成立 |

### 冷启动期的替代策略

**用「规则 + 模板 + 人工确认」代替「模型预测」：**



* 航次补给：先做「船型 / 航次天数 / 人数 / 餐次 × 品类系数」的专家表，输出建议清单，人工调整。

* 菜单采购：先做「菜单 × 用餐人数 × 人均用量」的模板，输出建议采购量。

* 活动选品：先用「库存高 / 动销慢 / 毛利够 / 应季」的规则筛选，不做个性化推荐。

* 活动力度：先用「历史同类活动」或「运营经验值」做默认，不做价格弹性模型。

* 经营分析：先做「固定指标 + 同比 / 环比」，不做 AI 归因。

**同时从现在开始采集冷启动数据（见 §7.1），为后续模型做准备。**

## 1. 三类场景的差异



| 维度     | 船供采购                                     | 海员个人采购                              | 工厂餐厅采购                   |
| ------ | ---------------------------------------- | ----------------------------------- | ------------------------ |
| 采购主体   | 船舶（采购确认人 / 船员）                           | 海员个人（自购）                            | 工厂 / 餐厅采购员               |
| 触发方式   | 靠港 / 航次驱动                                | 随时、高频                               | 日 / 周 / 月菜单驱动            |
| 单笔金额   | 1 万～十几万                                  | 中大额（上船前自购囤货）                        | 中大额、周期性                  |
| SKU 数  | 几十到上百                                    | 几个到几十                               | 几十到上百，但相对稳定              |
| 决策依据   | 航次天数、船员人数、餐次、库存、上次采购                     | 个人偏好、价格、船上收货                        | 菜单、用餐人数、库存、合同价           |
| 关键约束   | 靠港时间窗、MOQ / 步长、IMPA/ISSA、内部配送、共享购物车、按人拆行 | 船舶绑定、**送到船**、**与船供补给单合并配送**、靠港配送、弱网 | 供应商、合同价、账期、分批收货、对账       |
| 已有能力   | Excel 导入、接龙粘贴、共享购物车、靠港申报、履约波次、按人拆行       | 个人购物车、船舶上下文、常购                      | 导入清单、采购主体、地址配送           |
| 最大痛点   | 清单来源杂、单位错配、商品匹配靠猜、核对累                    | 找货、重复买、凑单、船上收货地址                    | 每周重复算量、报价对比、拆单、对账        |
| AI 切入点 | 清单结构化、单位换算、航次测算、商品匹配、审批摘要                | 自然语言搜索、常购复购、送到船默认、场景组合              | 菜单→用量、周期模板、报价对比、替代品、对账问答 |

**一句话概括：**



* 船供是「复杂大单」，AI 要解决**准确性和核对成本**。

* 工厂餐厅是「重复大单」，AI 要解决**算量和复用**。

* 海员个人是「高频自购」，AI 要解决**找货、复购和「送到船」的体验**。

> **海员个人不是 B2B 采购**
>
> ：不需要审批、预算、按人归属、共享购物车；重点是「默认送到当前船舶 / 靠港、按靠港批次履约、常购一键复购」。

## 2. 大单场景的 5 个易用性瓶颈

### 2.1 输入瓶颈：清单来源不结构化



| 项          | 内容                                                          |
| ---------- | ----------------------------------------------------------- |
| 现状         | 清单来源有 Excel、微信群接龙、口头报货、图片、手写纸条；接入点分散                        |
| 已有         | Excel 导入（支持 2000 行）、接龙粘贴、报告页逐行处置                            |
| 缺口         | 图片 / PDF / 语音清单不能直接进；多来源不能合并；重复粘贴会数量翻倍；跨天收集会过期              |
| AI 能做什么    | OCR / 语音转文字 / 文本解析 → 结构化行；识别「人名 / 品名 / 数量 / 单位」；规则解析回退；标置信度 |
| 非 AI 必须做什么 | 批次模型（一次粘贴 / 上传 = 一个批次）、替换上一份、来源标记、跨天恢复、入口显性化                |
| 优先级        | **P0**                                                      |

**判断：** 你们接龙改造方案里已经识别出「重复粘贴翻倍、24h 过期、确认人权限、二次核定」四个结构性问题。这四个不是 AI 能解决的，必须先把批次模型做对，AI 解析才有意义。

### 2.2 匹配瓶颈：名称 / 规格 / 单位不统一



| 项          | 内容                                                                                                    |
| ---------- | ----------------------------------------------------------------------------------------------------- |
| 现状         | 商品名里写规格（「国产香蕉 约 1kg / 把」「猪五花肉片 300g / 盒」）；SKU 没有「销售单位」字段；「香蕉 3 斤」命中「约 1kg / 把」后按 **3 把** 下单，报告显示「已匹配」 |
| 已有         | fuzzy / 向量匹配、候选 chips、人工补选                                                                            |
| 缺口         | 单位校验、别名、IMPA/ISSA 编码匹配、匹配置信度、规格数字比较                                                                   |
| AI 能做什么    | 语义匹配（「五花肉」→「猪五花肉片」）、别名扩展、单位换算建议（3 斤 ≈ 1.5 把 → 按步长取 2 把）、候选排序与理由                                       |
| 非 AI 必须做什么 | `goods_sku` 增加 `sales_unit`（销售单位）、`unit_weight_kg`（单件净重）、`unit_spec_text`（展示规格）；目录回填；导入 / 接龙 / 详情统一展示 |
| 优先级        | **P0（数据治理先行）**                                                                                        |

**判断：** 单位错配是大单场景最危险的错误，因为它**不报错、不拦截、直接下单**。AI 只能给建议，必须「任何情况下不自动改数量，最终由人确认」。

### 2.3 数量瓶颈：MOQ / 步长 / 包装 / 人数天数换算



| 项          | 内容                                                                         |
| ---------- | -------------------------------------------------------------------------- |
| 现状         | 用户自己算箱 / 袋 / 桶；阶梯价按整单总量判档；整箱与散买混在一起                                        |
| 缺口         | 按人数 × 天数 × 餐次的用量测算；按包装向上取整；「再买 X 件降一档」提示；批量改数量                             |
| AI 能做什么    | 航次补给测算（船供，规则系数表）、菜单用量测算（工厂餐厅，规则系数表）、取整建议、阶梯价优化建议。**冷启动阶段用专家系数和模板，不做销量预测。** |
| 非 AI 必须做什么 | 数量输入 +/−、整箱切换、批量修改、MOQ / 步长校验、阶梯价实时提示                                      |
| 优先级        | **P0（基础交互）/ P1（测算）**                                                       |

### 2.4 核对瓶颈：几十上百行，异常淹没在正常行里



| 项          | 内容                                                  |
| ---------- | --------------------------------------------------- |
| 现状         | 报告页按商品平铺；每行一个人名输入框；异常行和正常行混在一起；同一批数据报告页核一次、提交弹窗再核一次 |
| 缺口         | 按人分组、异常优先、折叠正常行、摘要、批量确认                             |
| AI 能做什么    | 异常解释（为什么没匹配、单位为什么可疑）、匹配理由、审批摘要、风险提示                 |
| 非 AI 必须做什么 | 按人分组、仅看待处理、批量操作、状态保持、一次核对                           |
| 优先级        | **P0**                                              |

**判断：** 大单核对的关键不是「AI 帮你核」，而是**把 80% 的正常行折叠掉，只把 20% 的异常推到人面前**。AI 负责解释异常，人负责拍板。

### 2.5 决策瓶颈：审批 / 预算 / 替代品 / 交付窗口



| 项          | 内容                                 |
| ---------- | ---------------------------------- |
| 现状         | 大额订单需要审批；缺货时人工找替代；靠港时间窗紧           |
| 缺口         | 审批摘要、预算对比、缺货替代、交付风险提示              |
| AI 能做什么    | 生成审批摘要（金额、品类、关键项、异常项）、替代品推荐、交付风险提示 |
| 非 AI 必须做什么 | 审批流、预算字段、库存锁定、交付日历                 |
| 优先级        | **P1**                             |

**判断：** 海员个人不涉及审批 / 预算 / 按人归属，这一节只适用于船供和工厂餐厅。

**移动端首页建议：**

三类用户打开小程序的第一屏不应该都是「商品流」，而应该是「任务流」：



```
船供：待确认清单 / 上次航次清单 / 航次补给测算 / 靠港日历 / 待审批 / 待收货
海员个人：常购清单 / 上船囤货清单 / 船上收货（默认） / 优惠 / 订单
工厂餐厅：本周菜单测算 / 周期采购单 / 待审批 / 报价对比 / 待收货 / 对账
```

AI 不占首页 C 位，而是嵌在「清单导入、核对、测算、复购」四个动作里。

## 4. 管理端：营销活动生产工作台

### 4.1 现状痛点



| 痛点    | 具体表现                                         |
| ----- | -------------------------------------------- |
| 活动类型多 | 秒杀、满减、拼团、优惠券、会员价、阶梯价、整船优惠、满额包邮、新人专享、低价捡漏     |
| 配置字段多 | 时间、商品 / 分类 / 品牌、人群、门槛、折扣、库存、限购、渠道、叠加规则、页面、文案 |
| 选品靠经验 | 不知道选哪些商品、定多大折扣、备多少库存                         |
| 素材靠设计 | 活动页、Banner、商品图、推送文案都要人做                      |
| 校验靠试错 | 价格倒挂、规则叠加冲突、库存不足，往往发布后才发现                    |
| 复盘靠导表 | 活动结束导 Excel，人工算 ROI                          |

### 4.2 目标形态：一个「活动工作台」，三步出活动



```
Step 1  输入意图（3 个必填）
        目标：清库存 / 拉新 / 复购 / 节日 / 船供靠港旺季 / 会员激活
        预算：优惠总预算 + 库存预算
        时间：开始~结束

Step 2  AI 生成「活动包」
        ├─ 活动组合建议：主活动 + 辅助活动 + 钩子
        ├─ 选品清单：按库存/毛利/价格带/应季/靠港日历（有数据后再加销量/复购）
        ├─ 优惠规则：阶梯价 / 整船优惠 / 满减 / 券 / 包邮 / 会员价
        ├─ 人群与渠道：全部 / 会员等级 / 新人 / 船供 / 采购主体
        ├─ 页面骨架与文案：装修器楼层 + Banner + 推送文案
        ├─ 预算与库存测算
        └─ 互斥与冲突检查

Step 3  运营审核 → 写入现有营销引擎 → 预览 → 发布
```

### 4.3 AI 在 6 个环节具体做什么



| 环节   | AI 输出                                                | 人工确认点       | 落到哪个现有模块   |
| ---- | ---------------------------------------------------- | ----------- | ---------- |
| 活动策划 | 活动类型组合、节奏、力度、门槛                                      | 选哪个方案       | 营销中心       |
| 选品   | 候选商品清单 + 推荐理由 + 建议折扣 + 建议库存                          | 增删商品、改折扣    | 商品库 + 营销中心 |
| 规则配置 | 满减 / 阶梯 / 整船 / 券 / 包邮的结构化草稿                          | 改门槛、改时间、改限购 | 营销引擎       |
| 素材   | 活动页文案、Banner、商品主图、推送 / 站内信文案                         | 审核文案与图片     | 装修器 + 素材库  |
| 校验   | 价格倒挂、叠加冲突、库存不足、时间冲突、限购冲突                             | 逐条确认或修改     | 发布前校验      |
| 复盘   | 固定指标（曝光 / 点击 / 转化 / GMV/ROI）+ 对比 + 下次建议；冷启动期不做 AI 归因 | 采纳建议        | 数据看板       |

### 4.4 三类场景的活动重点不同



| 场景   | 优先活动类型                      | 不建议               |
| ---- | --------------------------- | ----------------- |
| 船供采购 | 阶梯价、整船优惠、满额包邮、靠港档期价、船队客户专属价 | 秒杀、拼团（大单不敏感，容易破价） |
| 海员个人 | 新人专享、满减、优惠券、会员价、凑单包邮        | 整船优惠（用不上）         |
| 工厂餐厅 | 阶梯价、合约价、周期性满减、账期客户专属        | 秒杀、拼团             |

**判断：** 管理端 AI 不应该默认生成「秒杀」，而应该**按场景选择活动类型**。大单客户对「单价降 2%」的敏感度，远高于「限时抢购」。

### 4.5 关键原则



1. **AI 只出草稿，发布必须人工确认。**

2. **所有规则落到现有营销引擎，不新建一套「AI 规则」。**

3. **选品必须带约束**：库存、毛利、价格倒挂、活动互斥、限购。

4. **活动必须可归因**：每个活动有独立编码，能算曝光、点击、转化、GMV、ROI。

5. **先做「复用」再做「生成」**：历史活动一键复制、改时间 / 商品 / 折扣，比从零生成更可靠。

## 8. 结论



1. **冷启动阶段，AI 的价值不在「预测」，而在「理解、生成、校验」**：清单解析、商品匹配、活动草稿、审批摘要、异常解释，这些不依赖历史数据，现在就能用。

2. **三类场景的共性远大于差异**：都是「清单→订单」，都怕单位错、匹配错、核对漏。所以 P0 应该做共用能力，而不是先做三个场景的定制功能。

3. **船供是复杂度最高、差异化最大的场景**：航次补给测算、靠港时间窗、按人归属，是主流竞品没有的；但测算先用规则系数，不做模型。

4. **工厂餐厅是 ROI 最清晰的场景**：菜单→用量→周期采购→对账，链路固定，先用模板跑通，再谈优化。

5. **海员个人是频次最高的场景，也是唯一的 C 端自购场景**：不需要审批 / 预算 / 按人归属；个人订单与整船补给单合并配送、但订单 / 支付独立；把「送到船」做成默认、把「常购复购」做顺，比任何推荐算法都有效。

6. **管理端营销活动的易用性，核心不是「AI 写文案」，而是「AI 把活动配置填成草稿 + 发布前校验」**。这决定了运营愿不愿意用。

7. **顺序不能反**：先治理单位 / 规格数据，再做 AI 匹配；先做批次模型，再做 AI 解析；先做活动复用，再做活动生成；先采数据，再做预测。

### 9.1 Q1：海员个人「送到船」送到哪、是否合并配送

**结论&#x20;**`【已确认】`**：主场景是送到靠港船舶；个人订单与这艘船的整船补给单合并为同一个配送批次一起送。**

**设计结论：合并履约，不合并订单；合并配送，不合并支付。**

#### 设计落点



| 层   | 做法             | 关键字段 / 动作                                                                            |
| --- | -------------- | ------------------------------------------------------------------------------------ |
| 订单层 | 个人订单保持独立       | `buyer_type=个人`、`delivery_way=船`、`vessel_id`、`vessel_call_id`                        |
| 履约层 | 与船供订单合并为一个配送批次 | `delivery_batch_key = vessel_id + vessel_call_id + delivery_window`；个人订单、船供订单都挂到同一批次 |
| 支付层 | 独立支付 / 结算      | 个人订单个人在线支付；船供订单按合同 / 账期；不混算、不合并发票                                                    |
| 分拣层 | 同波次分拣，按人打标签    | `contributor_name`、个人订单号标签；整船收货后能按人分发                                                |
| 收货层 | 统一收货 + 个人明细    | 船供由采购确认人整批收货；个人订单可由个人确认，也可由同一收货人代确认                                                  |
| 截单层 | 跟随补给单截单        | 晚于截单时间提示「本次补给已截单，将随下一批次配送」                                                           |
| 售后层 | 独立售后           | 个人订单退换货不影响整批补给；售后单独立                                                                 |

#### 页面必须说清楚的三句话



1. **送到哪**：「随本次补给单一起送到 **XX 轮**（**XX 港**）」。

2. **什么时候**：「预计 **XX 月 XX 日** 随补给单送达；实际时间以补给单为准」。

3. **怎么改**：「如需送岸上地址，请切换配送方式（当前仅支持船 / 岸上两种）」。

#### 不建议



* **不要把个人订单和船供订单合成一张订单**：支付主体、结算主体、售后主体都不同，合并后对账会乱。

* **不要取消个人订单的独立售后**：整批补给退换货流程长，个人商品等不起。

* **不要默认让个人订单独立配送**：那会丢掉「随整船补给一起送」这个最大的履约成本优势。

* **岸上地址不建议 P0 做多地址**：先做「船」一个默认目标，岸上地址作为 P1 例外场景。

#### 风险

个人订单的时效从此绑定补给单：补给单延误，个人订单也延误。必须在结算页明示，并在补给单延误时主动通知个人订单用户。

### 9.2 Q2：工厂餐厅是否已上线、走导入清单还是周期采购单、有没有合同价 / 报价

**结论&#x20;**`【公开资料】+【判断】`**：工厂餐厅 / 团餐采购的行业标准链路不是「一次性导入清单」，而是「周期申购 → 合同价 / 折扣率 → 分批收货 → 按月对账」。合同价 / 报价体系是行业标配，不是可选项。**

#### 公开资料给出的标准链路



```
周期申购（按食堂/部门/周期）
  → 询价/合同价（市场价/政府指导价/批发市场网上价 + 固定折扣率或下浮率；或供应商协议价）
  → 审核 → 一键下单
  → 分批收货（送货单 + 验收单，至少两人验收）
  → 按月对账（送货单 + 验收单 + 发票，次月 10 日前核对）
  → 付款/供应商考核
```

#### 判断与切法



1. **如果工厂餐厅目前只做了「导入清单」**：说明只覆盖了「下单」这一小段，缺「定价、报价对比、收货、对账」四段。大单客户一定会要求合同价和月结，否则每单都要重新询价，运营成本极高。

2. **如果已经上线「周期采购单」**：P0 可以直接复用，重点补「合同价 / 折扣率」字段和「历史申购模板」。

3. **MVP 切法**：



| 阶段 | 做什么                                                              | 不做什么             |
| -- | ---------------------------------------------------------------- | ---------------- |
| P0 | 复用现有导入清单 / 下单链路；如果工厂餐厅还没上线，P0 不新增专属功能，先把共用能力（单位、匹配、常购、活动工作台）做顺   | 不做完整 SRM、不做供应商门户 |
| P1 | 周期采购单（按食堂 / 部门 / 周期）+ 历史申购模板 + 合同价 / 折扣率字段（`supplier_sku_price`） | 不做自动询价、不做供应商考核   |
| P2 | 多供应商报价对比 + 验收单 / 送货单 / 对账单三单匹配 + 供应商考核 / 食安证照 / 菜谱 BOM           | 不做中央厨房 / 多组织全链路  |



1. **合同价的最小数据结构**：`supplier_sku_price`（供应商、SKU、协议价或折扣率、生效期、报价周期、最小起订量、含税 / 不含税）。没有这张表，「合同价」只能写在合同附件里，系统算不出结算金额。

**一句话：工厂餐厅不是「又一个船供」，它的核心是「重复 + 对账」，不是「航次」。**

### 9.4 Q4：船供航次补给，是否已有经验系数

**结论&#x20;**`【公开资料】`**：已有可用的公开基线，可以直接做一版专家表；但没有「一套数字打天下」的系数，必须按船型、航线、航次天数、船员国籍 / 宗教、舱容、本船历史消耗修正。**

#### 先分清四种口径（不能混用）



| 口径     | 来源                                                         | 数字                                                       | 用途         | 注意                                                 |
| ------ | ---------------------------------------------------------- | -------------------------------------------------------- | ---------- | -------------------------------------------------- |
| 设计定额   | 中国船舶行业标准 CB/T 3649—2011《海船食品、饮水、淡水及人员和行李重量计算定额》            | 食品 **3 kg**、饮水 **30 kg**、淡水 **100 kg** / 人 / 天           | 船舶设计容量     | 适用于 1000 GT 及以上民用海洋船舶设计；饮水 / 淡水含烹饪、洗涤，**不等于瓶装饮用水** |
| 船供规划基线 | Baltona Shipchandlers；ShipCalculators                      | 全口径 **5-8 kg**/ 人 / 天                                    | 采购订单检查     | 含三餐、零食、饮料、清洁等非食品；必须用本船历史消耗修正；不是法规口粮                |
| 仓储估算   | Wärtsilä 百科                                                | 干货 **1.5** + 冷藏 **1.4** + 冷冻 **1.1** = **4.0 kg**/ 人 / 天 | 冷库 / 干货库容量 | 用于仓储，不是采购                                          |
| 法定口粮   | 葡萄牙 1978 法令、图瓦卢《Shipping (Rations) Regulations》、法国 1986 法令 | 见下方明细                                                    | 菜单 / 营养校验  | 国别差异大，不能直接套用                                       |
| 法律要求   | MLC 2006 Standard A3.2；交通运输部《海员船上工作和生活条件管理办法》              | 数量、质量、营养价值、多样性满足实际需要；WHO 建议饮用水中位数 **2 L**/ 人 / 天         | 合规底线       | 不是具体采购量                                            |

#### 品类系数表（规划起点，`【公开资料】`综合）



| 品类                 | 建议起点（kg 或 L / 人 / 天） | 说明                                |
| ------------------ | -------------------- | --------------------------------- |
| 肉类 / 禽类 / 鱼虾       | 0.4-0.6 kg           | 含冷冻 / 冷藏；长航次提高冷冻比例                |
| 新鲜蔬菜 / 水果          | 0.5-0.8 kg           | 短航次多鲜品；长航次用耐储根茎 / 柑橘 / 苹果         |
| 干货（米 / 面 / 豆 / 意面） | 0.3-0.5 kg           | 干重；按主食结构调                         |
| 乳制品 / 蛋            | 0.3-0.4 kg           | 冷藏；长航次用 UHT / 蛋粉                  |
| 油脂 / 调味 / 罐头 / 烘焙  | 0.1-0.2 kg           | 含糖、盐、酱料、罐头                        |
| 饮料（果汁 / 软饮 / 茶咖啡）  | 1-2 L                | 按箱折算；高温航线取上限                      |
| 瓶装饮用水              | 2-3 L                | 有造水机只算瓶装饮用；无造水机按 10-20 L 含烹饪 / 洗涤 |
| 日用品 / 清洁           | 0.1-0.2 kg           | 非食品；按人数 / 航次                      |

#### 修正规则（直接写进测算逻辑）



1. **航次 > 30 天**：鲜品比例下降，冷冻 / 干货 / UHT 上升；叶菜 / 浆果减少，根茎 / 柑橘 / 苹果增加。

2. **高温 / 高湿航线**：饮用水 +20-30%，饮料取上限；同时校核冷库容量。

3. **宗教 / 国籍 / 特殊饮食**：按船员名单调整；猪肉 / 牛肉 / 清真 / 素食分开。

4. **安全库存**：7-14 天（ShipCalculators 口径）；锚地 / 拥堵 / 改航风险高的航线取上限。

5. **舱容校核**：冷冻 / 冷藏 / 干货三库分开；不能只看总吨位。

6. **历史消耗修正**：用本船过去 3-6 个航次的领料 / 盘库数据修正；新船用基线。

7. **短航次 / 车客渡船**：可按航行时间酌减（CB/T 3649—2011 注）。

#### 示例：22 人 × 30 天（660 人・天）



| 品类               | 计算         | 数量                     |
| ---------------- | ---------- | ---------------------- |
| 肉类 / 禽 / 鱼       | 0.5 × 660  | 330 kg                 |
| 蔬果               | 0.65 × 660 | 429 kg                 |
| 干货               | 0.4 × 660  | 264 kg                 |
| 乳蛋               | 0.35 × 660 | 231 kg                 |
| 油脂 / 调味 / 罐头     | 0.15 × 660 | 99 kg                  |
| 食品合计             | —          | **≈ 1,353 kg（1.35 t）** |
| 按 CB/T 3 kg 食品   | 3 × 660    | **1,980 kg（1.98 t）**   |
| 按国际全口径 5-8 kg    | 5-8 × 660  | **3.3-5.3 t**          |
| 饮料               | 1.5 × 660  | 990 L                  |
| 瓶装水（无造水机按 2.5 L） | 2.5 × 660  | 1,650 L                |
| 日用品              | 0.15 × 660 | 99 kg                  |

**怎么用这组数字：**



* **食品采购预算**：按 **2.5-3.5 kg / 人 / 天（含损耗 / 备货）**，22 人 30 天约 **1.65-2.31 t**；CB/T 的 3 kg = 1.98 t 正好在区间内，可做下限校核。

* **全口径预算（含饮料 / 水 / 非食品 / 包装）**：按 **4-6 kg / 人 / 天**，22 人 30 天约 **2.64-3.96 t**；ShipCalculators 的 5-8 kg 是上限参考。

* **水**：有造水机只算瓶装饮用 2-3 L / 人 / 天；无造水机按 10-20 L / 人 / 天含烹饪 / 洗涤（Baltona 口径）。CB/T 的 30 kg 饮水 + 100 kg 淡水是设计容量，不要直接当采购量。

* **安全库存**：按 7-14 天另加。

#### 法定口粮明细（用于菜单 / 营养校验，不直接当采购量）



* **葡萄牙 1978（Portaria 491/78）**：肉 300 g、鱼 250 g、鳕鱼 60 g、牛奶 0.5 L、奶酪 40 g、蛋 60 g、面粉 250 g、豆 50 g、土豆 400 g、米 70 g、糖 60 g、蔬菜 300 g、水果 300 g、黄油 / 人造黄油 30 g、油 50 g、酒 0.8 L、茶 / 咖啡 20 g。

* **图瓦卢（Shipping (Rations) Regulations）**：米 / 饼干 / 西米 1 lb，或面粉 / 面包 1.5 lb；罐头肉 / 鱼 3/4 lb；糖 4 oz；盐 1/2 oz；脂肪 2 oz；饮用水 3 quarts ≈ 2.8 L；每周茶叶 2 oz、肥皂半块。

* **法国 1986**：普通船舶约 3,200 kcal / 人 / 天；远洋渔业约 4,200 kcal / 人 / 天。

* **MLC 2006 / 交通运输部办法**：食品和饮用水在数量、质量、营养价值、多样性上满足海员人数与航程；配员 10 人及以上应配船上厨师；应成立膳食委员会并定期公示膳食费用、食品饮用水采购、膳食安排计划。

### 9.5 Q5：三类场景的单量占比和 Top 痛点排序

**结论&#x20;**`【判断/假设】`**：没有公开数据能回答「你们三类场景各占多少」，只能基于业务模式给一版假设，并用上线后 4 周真实数据校准。**

#### 假设矩阵



| 维度         | 船供            | 海员个人      | 工厂餐厅         |
| ---------- | ------------- | --------- | ------------ |
| GMV 占比（假设） | **60-70%**    | 10-15%    | 20-30%       |
| 订单频次       | 低（按航次）        | **高（随时）** | 中（日 / 周 / 月） |
| 单笔金额       | **最高**        | 中         | 中高           |
| SKU 行数     | **最高（几十到上百）** | 低（几个到几十）  | 中高（几十，但稳定）   |
| 痛点强度       | **最高**        | 中         | 高            |
| P0 顺序      | **1**         | **2**     | **3**        |

#### Top 痛点排序（`【判断】`）



| 场景   | Top 痛点（从高到低）                    | 对应能力                   |
| ---- | ------------------------------- | ---------------------- |
| 船供   | 单位错配 > 商品匹配 > 清单来源杂 > 核对累 > 审批慢 | 单位治理、匹配、清单解析、异常优先、审批摘要 |
| 工厂餐厅 | 重复算量 > 报价对比 > 拆单 / 对账 > 菜单变化    | 周期模板、合同价、三单匹配、菜单 BOM   |
| 海员个人 | 找货 > 重复买 > 送到船地址 > 凑单 / 包邮      | 自然语言搜索、常购复用、送到船默认、包邮提示 |

#### 为什么这么排



* **船供 GMV 最大、复杂度最高**：单笔 1 万～十几万、几十上百 SKU，错一单代价最高，所以 P0 先解决「不出错」。

* **海员个人频次最高、改动最小**：它不需要审批 / 预算 / 合同价，只需要「送到船默认 + 常购复用」，投入小、体验提升直接，所以排第 2。

* **工厂餐厅 ROI 清晰但工作量大**：需要合同价、报价对比、按月对账，属于「第二个产品」，所以排第 3；如果它已经上线且单量大，可以提到 P1 最前面。

#### 怎么验证（上线后 4 周）

统计三组数：



1. 三类场景的订单数、GMV、SKU 行数、单笔金额分布。

2. 清单导入行数、人工改行数、匹配补选率、单位 MISMATCH 率。

3. 下单时长、活动配置时长、审批退回率。

用真实占比替换上表假设，再决定 P1 资源往哪类场景倾斜。

### 9.6 Q6：是否接受「规则 + 模板 + 人工确认」，3-6 个月后再上预测模型

**结论&#x20;**`【判断】`**：接受，而且这不是妥协，是行业常规做法。但建议把「3-6 个月」改成「3-6 个月校准 + 12 个月后再谈季节性预测」。**

| 阶段      | 做什么                                           | 不做什么                 |
| ------- | --------------------------------------------- | -------------------- |
| 0-3 个月  | 规则 + 模板 + 人工确认；全量埋点（见 §7.1）                   | 不做销量预测、自动补货、个性化推荐    |
| 3-6 个月  | 用真实数据校准系数、匹配阈值、活动模板；做「规则 + 轻量模型」混合（匹配排序、异常检测） | 不做端到端预测              |
| 6-12 个月 | 评估自动补货、个性化推荐；先离线回测，再灰度                        | 不直接全量上线              |
| 12 个月以后 | 评估季节性预测（春节、休渔期、航线季节）                          | 3-6 个月数据覆盖不了一个完整年度周期 |

#### 公开实践支持



* 船供指南明确说：优先用本船历史人均消耗率；厨房记录、盘库、上次请购、菜单周期比通用系数更可靠（[Baltona](https://www.baltona-ship.com/blog/ship-provisioning-checklist-for-long-voyages/)）。

* 团餐系统明确说：支持调用历史申购记录微调，而不是让模型从零预测（[餐链・正大案例](https://www.mealcome.com/customers/6001547)）。

* 团餐规范要求：下达采购计划时对就餐人员预估、考虑人员变动（SB/T 10856—202X 征求意见稿）。

* 这些做法都是「历史 + 规则 + 人工确认」，不是机器学习。说明**规则先行是行业常态，不是冷启动的降级方案**。

#### 数据门槛（建议写进验收）



| 能力     | 最低数据门槛                                   |
| ------ | ---------------------------------------- |
| 商品匹配模型 | 1,000+ 行清洗后的清单、300+ 张订单、人工改选记录           |
| 用量测算校准 | 每个场景 3-6 个月；船供至少 3-6 个航次；工厂餐厅 12-24 个周周期 |
| 活动优化   | 20+ 场完整活动（曝光 / 点击 / 转化 / GMV/ROI 齐全）     |
| 季节性预测  | 12 个月以上，覆盖春节 / 休渔期 / 航线旺季                |
