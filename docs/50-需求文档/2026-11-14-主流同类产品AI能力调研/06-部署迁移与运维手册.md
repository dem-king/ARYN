## 1. 部署前置与配置

Boot使用 `aryn-boot/src/main/resources/application.yml`；Cloud使用upms/order/product/promotion各biz配置及Nacos对应dataId。应用配置必须与本次增量SQL同版；先备份结构/菜单/Nacos配置，确认回退应用能容忍新增字段/表。有效Secret只通过部署Secret注入，禁止放SQL、截图、审计和提交记录。

| 配置 | 实际位置 / 变量 | 含义 |
|---|---|---|
| 主密钥ID | `aryn.ai.key-id` / `AI_MASTER_KEY_ID`，默认primary | 只决定新凭证的封装Key；密文自带旧keyId |
| 主密钥 | `aryn.ai.keys.primary` / `AI_MASTER_KEY_PRIMARY` | Base64编码的32字节AES256密钥；空值时不能保存/解密凭证 |
| 旧主密钥 | `aryn.ai.keys.<历史keyId>` | 需另由Secret配置整个map；没有名为AI_PREVIOUS_KEYS的自动解析器 |
| 内网端点准入 | `aryn.ai.allowed-private-hosts` / `AI_ALLOWED_PRIVATE_HOSTS` | 默认HTTPS、拒内网与重定向；精确允许确需的私有host。不能关闭整体验证 |
| 内部RPC签名 | `aryn.ai.runtime-tokens.order/product/promotion` / `AI_RUNTIME_TOKEN_ORDER/PRODUCT/PROMOTION` | 各服务独立长随机Secret；upms验证侧与相应调用侧一致；Boot同样配置 |
| 预算 | `AI_DAILY_TOKEN_LIMIT`，默认1000000；`AI_MAX_CONCURRENT`4；`AI_MAX_TASK_CALLS`100 | 按租户和用途锁定入场；token未知按预留上限，不宣称实耗 |
| 采购worker | `PROCUREMENT_SCAN_MS`5000、`PROCUREMENT_MAX_ROWS`2000 | 线程池/队列有界，租约短事务，外呼不持有事务 |
| 营销worker | `CAMPAIGN_SCAN_MS`5000 | 失败/取消/租约fencing，与人工草稿修订隔离 |
| 索引扫描 | `aryn.ai.index-scan-ms`，代码默认30000 | 固定2线程/16等待队列，每租户1在途、轮换扫描；不是任意大线程池 |
| 检索 | `AI_EMBEDDING_TOP_K`6 / `AI_EMBEDDING_SCORE_THRESHOLD`0.55 | 候选ID排序后重取实时事实；阈值需业务标注校准 |
| 前端模式 | `import.meta.env.VITE_OPEN_BOOT` | 使用公共parse/rewrite；true→`/boot/...`，false保留服务首段 |

`AI_ENABLED`、`AI_ALIAS_RECALL_ENABLED`、`AI_EMBEDDING_ENABLED`等旧开关仍在配置，但不代表已有有效的数据库active配置。旧 `AI_API_KEY/BASE_URL/MODEL/TIMEOUT_MS`、`AI_EMBEDDING_*` 只能通过平台页显式导入草稿；没有自动激活或失败后换备用供应商。

密钥轮换：先将新旧keyId全部加入解密map→各实例验证可读旧配置→切新keyId→在后台显式替换供应商Key并测试/启用新版本→保留旧版本/旧索引与在途任务所需Key。旧Key只有在配置、索引、在途任务与回滚窗口全部退役后才可移除。没有自动全库重加密任务。

运行节点必须校时；签名包含action/tenant/usage/task/call/version/provider/epoch和60秒窗口。Key替换不要覆盖同一密文版本。JDK HttpClient的逐次DNS检查不能保证绑定校验IP，生产必须同时用出站代理/防火墙限制目标，防DNS重绑定和非预期内网访问。

|---|---|---|

| 248 / 1001 | 成套向量generation/item/state | product +Nacos |
| 249 / 1002 | SKU度量9字段、审核编码/别名 | product |
| 250 / 1003 | 采购draft/batch/row/contribution | order |
| 251 / 1004 | 合送组/link/operation、仓库归属字段 | order +Nacos |
| 252 / 1005 | 合送管理菜单 | upms |
| 253 / 1006 | B2B命令修订 | promotion |
| 254 / 1007 | 无副作用模拟记录 | promotion |
| 255 / 1008 | 活动包/持久生成任务、配置及权限 | promotion/upms +Nacos |
| 256 / 1009 | 显式协议政策草稿分支 | promotion |
| 257 / 1010 | 关联装修修订/摘要 | promotion |
| 258 / 1011 | 持久人工发布operation | promotion +Nacos |
| 259 / 1012 | 营销工作台菜单/4类权限 | upms |

对应文件名以 `db/boot/<编号>*.sql` 和 `db/cloud/<编号>*.sql` 唯一文件为准。所有增量具备幂等守卫、没有有效Key、不物理删业务数据；Cloud完整基线已同步。执行前须确认既有B2B236—246等前置已经到位；不能把本表当作从任意老版本升级的全套方案。

部署步骤：

1. 在独立副本演练增量两遍，核对tenant_id非空、唯一键、存量UNKNOWN默认、Nacos内容与MD5、菜单及角色权限；备份可恢复后再安排正式停写窗口。
2. 执行本模式增量。Boot执行247→259；Cloud执行1000→1012，分别核对脚本内USE。跨库DDL不是一个原子事务，每文件保留结果和失败点，修正后按幂等脚本续跑。
3. 兼容部署common-ai/API契约、upms权威配置、product/order/promotion与Boot入口；Cloud核对Dubbo接口版本、RPC token及Nacos生效内容，不能只更新一个biz。旧版本执行中的worker先排空/停止。
4. 平台管理员进入「AI 配置 → 业务配置 → 接入文本模型」。DeepSeek 官方已填 API 基础地址，其他 OpenAI 兼容服务需填写供应商名称和基础地址。填 API Key 和供应商提供的模型 ID，选择场景，依次「保存并继续 → 测试业务模型 → 启用配置」。同一模型绑定多个场景时只测试一次。测试结果按版本保留 24 小时，刷新或换有启用权限的管理员审批时可以继续。测试使用固定样本，会产生真实供应商用量。
5. 按租户准备向量索引：平台管理员先在现有全局租户切换器选择目标租户，再打开“目录索引”；该面板操作的是当前有效租户上下文。建立generation、等待READY/覆盖完成，再以expectedRevision人工切换。新旧模型同维也不能共用空间。
6. 未建立可用索引时使用字面路径；无AI配置时文字/Excel规则与人工核对仍可工作。商品审核度量/编码逐步治理，不从标题自动认定精确重量。
7. 为指定租户和角色开放采购、合送及营销入口。工作台SQL继承已有ship-supply租户可见性，但**不自动授予任何角色**生成/模拟/发布权限；配置AI的平台权限不等于发布营销的业务权限。
8. 分别验证两种前端模式的真实请求、Cloud分服务RPC、真实角色菜单，以及下面的恢复流程。只有完成这些现场项目才能将整体验收结项。

Boot全量维护命令（仅生成与静态检查）：

```bash
node db/boot/build-full-sql.mjs
node db/boot/verify-full-sql.mjs
```

## 3. 权限与业务操作

- 平台配置：`upms:ai-config:query/edit/test/activate`，同时要求用户级platformAdmin+TOB身份。调用记录显式选租户，不向普通租户泄露平台凭证。
- 「业务配置」上方显示当前生效模型，草稿中可改用已有模型。供应商换密钥和模型参数调整分别在「供应商」「模型」处理。导入旧部署配置、历史回滚和全局紧急停用在「版本与运维」中。商品语义匹配的索引需在目标租户下构建并切换。
- 采购：TOC当前用户+场景+企业/船/靠港/目标车权限，恢复不信任客户端缓存。换身份/主体会清理本地待同步数据；服务端按最新成员与商品度量重验。
- 营销工作台：`promotion:campaign:edit/generate/simulate/publish`分开。发布同时要求模拟、装修发布以及主活动或协议政策发布权限；有券还需券模板添加权限。
- 一个活动包只有一个主活动（4/5/7/12）或显式核定的协议政策；定向券是可选辅规则。10/11专区仍走既有标签治理，采购档期独立维护，停运零售类型禁止复活。
- 先保存→固定主体/件数/时间试算→核对成本/库存/预算/未知事实→生成装修→原装修器审阅→刷新受保护预览→明确风险确认→人工发布。任何事实/修订变化要求重算；服务端始终重验有效期。
- 成本未知/低于成本等须明确确认；STOCK_SHORT、GIFT_STOCK_UNPROVEN不允许靠勾选绕过。`POLICY_BUDGET_NOT_ENFORCED`表示协议价没有订单侧硬预算消耗控制，必须业务核定，不能解释为预算保险。
- 定向券仅创建停用、未发行模板；核对企业/个人目标后走原授权激活与发放流程。不添加领券中心、自动发券或群发通知。
- 指标只读PAGE_VIEW/COMPONENT_CLICK/RENDER_ERROR和可证明的活动已消耗预算。归因订单/利润缺事实时为空，不输出模拟ROI。

## 4. 故障恢复与回滚

| 症状 | 核查与操作 |
|---|---|
| 配置误填 | 草稿保存不影响active；修正草稿后重测。紧急时停用全部或单供应商，保留审计 |
| 回滚文本配置 | 平台版本页选旧版，重新确认测试时效/凭证可解密后按expectedRevision回滚；在途任务仍固定原版，紧停可阻断其后续外呼 |
| 向量模型变更 | 不改旧generation；新模型建新generation，READY后人工切。回退时选仍保留、可解析旧配置的完整generation |
| 采购离页/响应丢失 | 用服务器draft/batch/rows恢复，本地仅保请求信封和未同步编辑；同requestId重试。FAILED按原配置版本续跑；CANCELLED或MATERIAL_EXPIRED需重新提交来源 |
| revision冲突 | 刷新权威记录，核对别人修改后再操作；不能不断换requestId绕过CAS |
| 来源替换冲突 | 原来源贡献已被手改/消费、版本或成员变化时拒绝安全替换。保留LEGACY/手工量，不按旧汇总值猜测扣量 |
| 合送故障 | 查看delivery_group_operation；按单固定事件ID重放outbox。取消/移组只处理当前订单，不撤销别人的签收/退款 |
| 发布超时 | 先读publication列表。PUBLISHED表示事务已提交，重放同requestId返回相同记录；不要新建活动规避超时 |
| 发布FAILED_RECOVERABLE/VALIDATING | 按保存的operation执行人工重试，重验原确认、事实/修订/有效期。事实过期则重新模拟并建立新确认；不自动接受新风险 |
| 页面已被独立修改 | 重新审阅页面并生成当前digest；旧operation不覆盖别人后续编辑。已发布回滚走各资源既有权限/版本命令 |

发布资源全部位于promotion库，同一真实本地事务包含活动/协议启用、停用券模板、装修版本/指针、活动包与operation；页面最后启用。同库异常整体回滚，没有伪造跨Dubbo事务，也没有需要部署的跨服务发布补偿Job。operation在事务外预登记，所以进程崩溃后仍可人工恢复。

应用回滚先关闭新增入口与worker，再根据兼容矩阵回退应用；保留新表/列和审计，数据库用增量向前修复。不要用DROP新表或恢复整库作为默认回滚，否则会破坏新采购贡献与已发布资源。

## 5. 数据保留与清理

新增可执行工具：[`db/maintenance/ai-retention.py`](../../../aryn-mall-java/db/maintenance/ai-retention.py)。Python3 +mysql CLI，无新增依赖。默认只预览并ROLLBACK；真正apply前要求 `--writers-stopped`，应停止业务入口、相关worker、回调/重试并排空在途调用，避免依赖检查后出现新引用。工具不会替代实际停写，标志是运维的窗口声明。

保留窗口由业务/合规核定，本工具拒绝少于90天的截止日期。按租户、小批、明确ID执行，先在副本验证，再在维护窗口按预览结果执行；建议将原件/调用记录清理纳入受控的每日维护流程，索引/配置/凭证退役逐ID人工审阅；本轮没有安装自动cron。Cloud四域必须位于同一MySQL实例才能做完整依赖检查，分服务器部署需另提供受审阅的一致离线依赖清单，禁止只连接upms猜测引用为空。

| kind | 行为 / 保留边界 |
|---|---|
| sources | 清除过期batch原文/BLOB/文件名，以及行原文/品名/规格/编码/归属姓名/候选与自由处置文案；未确认的旧来源转CANCELLED并标MATERIAL_EXPIRED，撤销租约/重试。保留SKU/销售量/来源位置/revision/确认结果/贡献；不改历史订单或当前贡献量 |
| calls | 只处理过期已终态调用，检查采购/营销/索引依赖；逻辑删除、脱敏taskId，保留计量元数据。不清在途RUNNING，不改当天预算 |
| index | 必须明确generation ID，无当前state引用、过留存期、非构建中；先RETIRING禁用，每次最多500item清向量/品名并逻辑删除，重复运行至generation RETIRED。正在保留的回滚候选不要选入 |
| config | 必须明确版本ID；检查全租户索引、未终结采购/营销、有效调用租约和active/draft；无引用才逻辑删除并清document。退役后该版本不能再回滚 |
| credential | 必须明确ID；所有未退役配置的provider引用均消失后，才清sealed_value并逻辑删除；不能只按“不是当前active”删除旧Key |

每次成功写入平台 `ai_config_operation` 的RETENTION_*元数据审计：runId、所选ID、处理数量、操作者；不存原文、向量或Secret。sources会脱敏历史原文，正式执行前应确认留存期及审计需求，清空字段不支持靠取消逻辑删除恢复。备份、导出、浏览器本地缓存也须按同一策略过期；恢复旧备份后重新脱敏再开放业务。

默认预览示例（在aryn-mall-java目录；所有大写值均需替换为现场值）：

```bash
python3 db/maintenance/ai-retention.py \
  --kind sources --upms UPMS_SCHEMA --order ORDER_SCHEMA \
  --product PRODUCT_SCHEMA --promotion PROMOTION_SCHEMA \
  --tenant TENANT_ID --platform-tenant PLATFORM_TENANT_ID \
  --before 2026-08-01 --actor OPS_ACCOUNT --limit 20 \
  --defaults-extra-file /secure/mysql-maintenance.cnf
```

Boot四个schema参数都填aryn_boot。`mysql-maintenance.cnf`权限应为0600，密码不能放命令行；也可由Secret注入MYSQL_PWD。预览只输出kind/runId/数量。正式执行增加 `--apply --writers-stopped`；index/config/credential另提供明确 `--id`。返回非0表示事务失败、修改与审计一起回滚，禁止加mysql `--force`忽略错误。

仓库内复验工具为 `db/maintenance/verify-ai-retention.py`：设置 `ARYN_AI_RETENTION_TEST_SCHEMAS` 为仅含boot/cloud两个 `aryn_ai_verify_*` schema的JSON，连接参数放受保护的 `ARYN_AI_RETENTION_TEST_DEFAULTS`，再执行脚本。未配置时明确SKIPPED；只有全程通过才算留存行为验证。它在隔离库写合成fixture并保留审计，不执行物理删除。

LEGACY贡献没有可证明的批次来源，继续只读保留，不参与旧来源自动撤销；历史已确认报告兼容只读，未确认旧同步任务重新导入新管道。协议/发布审计及贡献没有自动销毁策略，后续档案保留期限须单独核定。过期RUNNING计量行也不会被本工具猜测改成成功，需调查实际调用后另作审计处理。
