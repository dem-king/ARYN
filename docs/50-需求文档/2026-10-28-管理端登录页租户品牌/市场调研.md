# 多租户 SaaS 管理后台登录页：租户识别与品牌归属调研

> 调研日期与访问日期：2026-10-28。范围：多租户 SaaS 管理后台在登录前如何识别租户、登录页展示谁的品牌，以及对应的套餐边界与安全边界。本文只做调研，不涉及代码改动。

## 摘要

1. 主流默认不是“登录页显示租户品牌”，而是“平台品牌的中性登录页 + 登录后或识别身份后解析租户”。Shopify、Stripe、Notion、Slack、有赞、微盟、淘宝、京东、SHOPLINE、BigCommerce 都是这一结构；登录页首先承担的是平台信任与防钓鱼锚点，而不是租户广告牌。
2. 租户品牌主要出现在四个位置：识别身份之后（Microsoft 输入邮箱后显示租户 branding）、租户专属主机（Salesforce My Domain、Atlassian 自定义域、Slack 工作区域名）、企业专属或白标部署（钉钉专属、Auth0/WorkOS 自定义域）、面向客户的前台（Shopify 店铺域、Zendesk 帮助中心）。管理后台整体白标反而是少数。
3. 登录前识别租户的规模化做法是子域名；企业 SSO 场景是邮箱域发现/HRD；专属或私有化场景是组织代码/数据库选择器；邀请或 SSO 深链只做辅助入口，不作为主登录入口。
4. tenantId 出现在 URL 并不天然是漏洞。主流产品普遍把 tenant/org 标识放在路径或参数里，但只把它当“选择器”，由服务端校验成员关系。真正的风险是未授权访问、租户枚举和品牌钓鱼，而不是标识本身。
5. 对本项目的建议：短期保持共享中性登录（平台品牌）+ 登录后租户品牌，这是现在最像主流的选择；若“登录页必须出现租户品牌”是硬需求，做“用户名→租户→密码”的两步 identifier-first；长期正解是租户子域名，可再扩展自定义域名。不建议把裸 tenantId 专属链接作为主入口。

## 1. 方法与证据边界

- 证据优先级：官方文档、官方帮助中心、官方产品页、官方 API/开发者文档高于二手文章；关键结论尽量给到原文链接。产品登录页实测只用于确认入口形态和页面品牌，不用于推断内部实现。
- 访问日期：2026-10-28。产品文档与套餐会随版本变化，本文以访问日为准。
- 实测范围：检查了 `shopify.com/login`、`dashboard.stripe.com/login`、`slack.com/signin`、`id.atlassian.com/login`、`login.salesforce.com`、`www.feishu.cn/admin`、`oa.dingtalk.com`、`work.weixin.qq.com`、`account.youzan.com/login`、`account.weimob.com`、`admin.myshopline.com`、`myseller.taobao.com`、`shop.jd.com` 等入口的跳转与页面标题。
- 限制：Shopify、BigCommerce 等帮助中心对自动抓取返回 403 或 JS 壳，部分结论依据官方页面在搜索结果中的摘要，已在表中标注“官方摘要”。有赞/微盟的后台白标套餐边界、企业微信/淘宝/京东的后台白标能力未核实。未做厂商访谈或定量抽样，因此“主流分布”是定性判断，不是统计比例。

## 2. 识别方式分类与对比

| 识别方式 | 代表产品 | 登录页品牌 | 租户可见性/泄漏面 | 部署与运维成本 | 适用阶段 |
|---|---|---|---|---|---|
| 共享中性登录页，登录后解析租户 | Shopify、Stripe、Notion、Slack、有赞、微盟、淘宝、京东、SHOPLINE、BigCommerce | 平台品牌 | 登录前不暴露租户；登录后由账号/邮箱/用户名反推；枚举面小 | 最低，单套登录 | PLG、自助 SMB、marketplace |
| 子域名（每租户一个 host） | Slack、Atlassian、Salesforce My Domain、Zendesk、Okta、BigCommerce | 多为平台品牌，租户主机可叠加租户名称/Logo | 租户名出现在 DNS/URL，可被枚举；需防子域接管 | 中高，需泛解析、证书、Host 路由 | 规模化 B2B、企业客户 |
| 自定义域名（租户自有域名） | Atlassian（Premium）、Zendesk（仅帮助中心）、Auth0、WorkOS、Okta、Shopify/SHOPLINE/BigCommerce（仅店铺前台） | 可全白标，或仅前台白标 | 域名本身是公开信息；需 DNS 校验、证书、域名唯一性 | 高，DNS/证书/客服/合规 | Enterprise、white-label、客户前台 |
| 邮箱域发现 / Home Realm Discovery | Microsoft Entra、Auth0 Organizations、WorkOS AuthKit、Notion（多 IdP 选择）、Salesforce Login Discovery | 先平台品牌，识别后切租户/IdP 品牌 | 需要已验证邮箱域；错误信息可能泄露账号/组织存在性 | 中，需域名验证与 IdP 集成 | 企业 SSO、B2B SaaS |
| 租户/组织编码输入 | 钉钉专属（组织代码）、Slack（工作区 URL）、Salesforce（Custom Domain 输入）、Odoo（数据库选择器）、飞书（SSO 企业域名输入） | 平台品牌为主；专属版可定制 | 编码/库名可被枚举；登录页可被仿冒 | 中，需编码体系与校验 | 专属部署、私有化、多数据库 |
| 带 tenant/org 参数的专属链接或邀请链接 | Auth0 邀请、WorkOS 邀请 | 平台品牌或邀请页品牌 | 链接泄漏、转发、日志/Referer 泄露；需签名与过期 | 低到中，需令牌与撤销机制 | 新客入驻、企业 SSO 接入 |
| SSO / IdP-initiated + 组织选择器 | Microsoft My Apps、Okta、WorkOS Admin Portal、Auth0 Organization Picker | IdP/平台品牌；组织选择器可显示组织名 | 组织列表只应展示已授权组织；IdP 断言是信任边界 | 中高，需 SAML/OIDC、SCIM、JIT | Enterprise、渠道/多组织用户 |

共享中性登录页是“默认解”：用户只记住平台地址，租户由账号归属在登录后解析。第一步留在平台域名下，运营成本最低，最适合自助注册与 marketplace。代价是登录前没有租户品牌，用户名/邮箱必须全平台唯一。

子域名是“规模化 B2B 的标准解”：host 即租户标识，可在首屏渲染租户品牌，也方便收藏。代价是 DNS、通配证书、Host 路由、Cookie 作用域与租户生命周期管理；可被外部解析的子域名还可能被枚举，必须防子域接管。Salesforce My Domain、Atlassian 站点域、Slack 工作区域名都属于这一类，但登录页往往仍保留平台品牌。

自定义域名是“企业/白标解”，且常被误解为“管理后台白标”。Zendesk 的 host mapping 只改帮助中心，不改 Agent 登录页；Shopify 店铺可绑自定义域名，但后台登录仍用 `myshopify.com`；Microsoft 的自定义域主要改用户名后缀，不改登录主机。真正把后台整体搬到租户域名的，多为专属部署或身份层白标产品。

邮箱域发现/HRD 是“企业 SSO 解”：用户先输邮箱，系统按已验证域名路由到租户或企业 IdP。它天然带来“邮箱是否存在/属于哪个组织”的枚举面，需要收敛错误与限流。

租户编码输入是“专属/私有化解”：钉钉专属要求组织代码，Odoo 登录时可选数据库。它显式、可控，但摩擦大，编码/库名也可被枚举，只适合客户有限、部署边界清晰的场景。

邀请/专属链接是“增长/接入解”，不是主登录入口。它解决“新用户不知道去哪登录”或“企业 SSO 接入”；一旦成为日常入口，就会遇到链接泄漏、转发、书签失效和钓鱼仿冒。

### 3.1 海外产品

|---|---|---|---|---|---|
| Shopify | `shopify.com/login` 跳转到 `admin.shopify.com`；登录后进入 `/store/{handle}` | Shopify | 不要求先选店；登录后由账号关联解析店铺（多店选择细节未核实） | 店铺前台可绑定自定义域名，但后台登录仍使用 `myshopify.com`；未核实后台白标 | [26][27][28] |
| Stripe | `dashboard.stripe.com/login` | Stripe | 邮箱账号；同一邮箱可有多个 Stripe 账号，登录后在左上角切换 | 无租户品牌；Dashboard 是 Stripe 品牌 | [29][30] |

| Zendesk | `{subdomain}.zendesk.com`；Agent 登录在默认 Zendesk 域 | Zendesk | 子域名即租户；Agent 由账号进入对应子域 | Host mapping 可把帮助中心改为 `support.yourdomain.com`，但明确不影响登录页和 Agent 界面；官方文档标注所有 Suite 均支持 | [21] |

| WorkOS | AuthKit Hosted UI；默认 WorkOS 域 | 应用品牌可配置 | SSO 按已验证邮箱域路由；多组织时让用户选择；邀请绑定组织 | Custom Domains 生产可用，$99/月起；SSO 按连接计费 | [9][10][11][12][13] |
| BigCommerce | `login.bigcommerce.com/login`；控制面板为 `store-{hash}.mybigcommerce.com` | BigCommerce | 账号登录后进入店铺；控制面板地址含 store hash | 店铺前台可绑定自定义域名；控制面板仍是 BigCommerce 域；未核实后台白标 | [31][32] |
| Notion | `notion.com/login` | Notion | 邮箱/验证码或密码；登录后进入工作区；多 SSO 提供商时让用户选择 | SAML SSO 需 Business/Enterprise；未核实管理后台自定义域名 | [33] |
| Odoo | `/web/login` + 数据库选择器；`dbfilter` 可按 host 映射数据库 | Odoo | 登录时选择数据库；或由 `dbfilter` 按子域名映射 | 自托管/Odoo.sh；生产建议关闭数据库列表 | [34] |

Microsoft 是“共享中性登录 + 识别后品牌”的最清晰样本：在 SaaS/多租户应用（如 `myapps.microsoft.com`、Outlook）上，租户定制登录页只在用户输入邮箱或手机号并点 Next 之后出现；如果希望首屏就显示租户品牌，必须在自定义 URL 中带 `whr=contoso.com` 这类已验证域名提示，而不是任意 tenantId。这直接说明：**登录前品牌不是不能做，而是要用“域名”这种可验证信号来做**。[1][2]

Salesforce 则说明“共享页 + 租户域名输入”可以共存：`login.salesforce.com` 首屏是 Salesforce 品牌，但提供 “Use Custom Domain” 输入，用户输入 My Domain 后进入租户登录页；直接访问 `{domain}.my.salesforce.com` 也能到同一租户页。租户品牌出现在租户主机/租户页，而不是共享首屏。[23][25]

### 3.3 关键观察

第一，管理后台的平台品牌是常态。Shopify、Zendesk、BigCommerce、SHOPLINE、有赞、微盟、淘宝、京东、飞书、钉钉、企业微信的商家入口都先展示平台品牌；租户品牌出现在登录后界面、店铺前台、帮助中心或企业专属版本。把“登录页显示平台品牌”直接判定为设计错误，缺乏市场依据。

第二，子域名很常见，但“子域名 = 租户品牌登录页”不成立。Slack、Atlassian、Salesforce 的租户域名主要解决“去哪登录/进哪个租户”，登录页仍以平台账号体系为主。

第三，“自定义域名”多数不是管理后台白标。Zendesk 只改帮助中心，Shopify/SHOPLINE/BigCommerce 只改店铺前台，Microsoft 只改邮箱后缀；把自定义域名当后台白标会低估 DNS、证书、客服和域名冲突成本。

第四，邮箱域发现是 SSO 能力，不是 SMB 登录能力。Microsoft、Auth0、WorkOS、Notion 的邮箱发现都建立在“已验证域名 + 企业 IdP”之上。

第五，租户编码输入的体验最差，但在专属/私有化场景合理。钉钉专属的组织代码、Odoo 的数据库选择器要求用户先知道一个“内部标识”，不适合自助增长。

## 4. 品牌归属与商业模式/套餐边界

| 模式 | 代表产品 | 可验证的套餐/文档边界 | 品牌归属与商业逻辑 |
|---|---|---|---|
| 平台品牌 + 登录后租户 | Shopify、Stripe、Notion、Slack、有赞、微盟、淘宝、京东、SHOPLINE、BigCommerce | 登录页/后台入口为平台品牌；租户上下文在登录后解析 | PLG、自助 SMB、marketplace 的默认：平台信任、防钓鱼、低支持成本、跨租户升级 |
| 识别后条件品牌 | Microsoft Entra、Salesforce My Domain、Notion SSO | Company branding 需 P1/P2 等；My Domain 登录页可换 Logo；Notion SAML 需 Business/Enterprise | 企业客户在“识别身份后”看到自己的品牌，兼顾平台信任与租户体验 |
| 租户专属主机 | Atlassian、Zendesk、Okta、Auth0、WorkOS、飞书、钉钉专属 | Atlassian 自定义域需 Premium/JSM Standard；Zendesk host mapping 所有 Suite 均支持但仅作用于帮助中心；Auth0 多自定义域/自管证书为 Enterprise；WorkOS Custom Domain $99/月；Okta 最多 3 个自定义域 | Enterprise/white-label：品牌控制、SSO、专属域名，供应商可对 DNS/证书/支持收费 |
| 专属部署 | 钉钉专属；飞书仅核实到企业域名/SSO 文档 | 钉钉专属支持登录页/欢迎页/UI 自定义、专属组织代码、专属 SSO；飞书套餐边界未核实 | 大客户/金融级隔离：品牌 + 数据/部署隔离，ACV 高，交付重 |
| 前台白标 | Shopify、SHOPLINE、BigCommerce、微盟 ShopExpress、Zendesk 帮助中心 | 店铺/帮助中心可绑定客户域名；管理后台不随之白标 | 面向消费者的品牌呈现；后台仍由平台控制，兼顾信任与滥用治理 |

按客群看：PLG/自助 SMB/marketplace 坚持平台品牌；Enterprise/white-label/专属域名/SSO 才做租户品牌。套餐边界的规律是：**平台品牌负责“信任与获客”，租户品牌负责“企业身份与品牌控制”，前者是默认，后者是付费/企业能力。** Microsoft 把 company branding 放在 P1/P2、M365 Business Standard 或 SharePoint Plan 1 之后；Atlassian 把自定义域放在 Jira/Confluence Premium 或 JSM Standard；Zendesk 的 host mapping 虽然所有 Suite 都支持，但只作用于帮助中心、不改登录页；WorkOS 把 Custom Domain 作为 $99/月的独立能力；Auth0 把多自定义域和自管证书放在 Enterprise。这些都不是“所有套餐默认白标”的证据。[1][6][7][12][13][20][21]

反过来，PLG/SMB/marketplace 产品坚持平台品牌也有明确商业理由：登录页是品牌资产和信任锚点，统一域名便于防钓鱼、客服、滥用治理和跨租户升级；如果每个 SMB 都要求独立登录域名，供应商的 DNS/证书/支持成本会迅速超过客单价。Shopify 即使允许店铺绑定自定义域名，仍要求用 `myshopify.com` 登录后台；Zendesk 即使允许帮助中心 host mapping，Agent 登录仍在 Zendesk 域；这就是“前台白标、后台不白标”的典型边界。[21][27]

## 5. 安全边界与泄漏面

### 5.1 tenantId 出现在 URL、页面、公开接口，算安全问题吗？

不算“天然漏洞”，算“攻击面”。Microsoft 把租户标识放在 `/{tenant}/` 路径，Salesforce 把 My Domain 放在 URL，Slack 把工作区域名放在 host，Auth0 把 `organization` 放在授权参数；这些都是主流实现。OWASP 的判断标准不是“标识是否出现”，而是“服务端是否把标识当授权依据”：

> “Treat client-supplied tenant identifiers as selectors only. Verify that the authenticated principal is authorized to act in the selected tenant.”  
> “Opaque, random identifiers can reduce enumeration, but they are not authorization controls.” [45]

OWASP A01:2021 也明确把“修改 URL 参数、强制浏览”列为访问控制失效的典型方式，并强调访问控制只能在可信的服务端代码中生效。[46] 因此：

- URL/页面出现 tenantId 可以接受，但每次请求都必须用“已认证主体 + 租户成员关系/服务授权”做服务端校验；不能因为请求头带了 `tenant-id` 就信任它。
- 公开接口只应返回“公开展示所需的最小字段”。租户名称/Logo 属于低敏感信息；地址、电话、官网、业务模式、内部主键属于更高暴露面。若接口还返回内部 `id`，且 ID 是连续数字，枚举成本极低。
- 若要做登录前品牌，优先用 host/slug 这类“公开、稳定、可验证”的键，而不是裸数字 tenantId；或者先完成身份识别，再返回品牌。
- 不要把 tenantId 放进未签名、可篡改的“专属登录链接”；如果必须携带，用短时效签名令牌，并绑定邮箱/组织。

### 5.2 品牌伪装与钓鱼风险

平台品牌登录页其实是一种防钓鱼设计：用户被训练成“只在这个平台域名输入账号密码”。租户品牌登录页越多，可被仿冒的目标越多；如果租户可以自定义 CSS/文案/Logo，攻击者更容易做出高度可信的假页面。Microsoft 的做法很能说明问题：对使用 auto-acceleration 或 smart links 的组织，登录 UI 会出现“域名确认对话框”，要求用户确认自己要登录的租户域名；同时，Microsoft 以“phishing resistance”为由，正在退役自定义 CSS 的布局/定位属性，并最终完全退役自定义 CSS。[1][2]

可落地的缓解措施：

- 子域名：由平台统一持有泛解析，校验 Host 必须在租户注册表中；禁止租户把子域名 CNAME 到不受控的第三方；监控悬空 DNS，防子域接管；全站 HTTPS/HSTS。
- 自定义域名：DNS TXT/CNAME 所有权验证；一个域名只能绑定一个租户（Microsoft 明确“一个域名只能在一个目录验证”，WorkOS 明确“一个自定义域只能由一个团队配置”）；证书自动续期与到期告警；域名回收/离职流程。[4][12]
- 登录页：不允许任意 CSS/JS 注入；限制 Logo/背景图来源；加安全响应头；对“租户品牌页”保留平台信任标识（如“由悦航购提供”）；监控近似域名/仿冒页面。
- 邀请链接：绑定邮箱与组织、签名、短时效、可撤销；不要把裸 org_id 放在链接里；链接泄漏后可立即失效。[8][11]
- 邮件域：配置 SPF/DKIM/DMARC，降低品牌邮件被仿冒的概率。

### 5.3 租户枚举风险

租户枚举有三个常见入口：登录/注册错误信息、邮箱域发现、公开品牌接口。OWASP WSTG 对账号枚举的修复建议是“对无效账号、密码或其他凭据返回一致的通用错误信息”；这条同样适用于“租户是否存在”。[47]

- 登录：不要返回“用户不存在/租户不存在/密码错误”的差异信息；统一为“账号或密码错误”；对未知用户名也走相似的验证码/延迟路径。
- 邮箱发现：只对“已验证域名”做自动路由；同一域名对应多个组织时让用户选择，而不是直接报错；无匹配时给通用提示；对同一 IP/邮箱/设备做限流与 Bot 检测。Auth0 明确其 Organization Domain Discovery 只基于 verified domains，且“不会限制谁可以注册或登录”；WorkOS 也只按已验证域名路由。[5][9][10]
- 组织选择器：只展示当前已认证用户所属的组织，不要展示全量租户；Auth0 的组织选择器只显示用户加入的组织（默认前 20 个）。[5]
- 公开品牌接口：不要用“存在/不存在”的不同状态码或不同响应时间；不要返回内部 ID/地址/电话；按 slug/host 查询；加缓存和速率限制；对异常枚举做告警。
- 限流：Auth0 对注册/登录攻击的建议包括 Bot Detection 和 Suspicious IP Throttling；本项目登录已有验证码，但仍建议在“用户名→租户”这类新接口上单独限流。[48]

### 5.4 邀请链接与专属链接

邀请链接的正确做法是“把组织上下文放进一个受控令牌”，而不是“把 tenantId 拼进 URL”。Auth0 的组织邀请链接会带组织上下文（文档明确 `organization_name` 会出现在邀请链接中），WorkOS 的邀请是“发给特定邮箱、加入特定组织”，接受后自动成为该组织成员。[8][11] 这说明主流实现并不是反对链接带组织信息，而是要求：链接绑定收件人、可验证、可撤销、可过期。

如果要做“专属登录链接”，至少满足：签名（不可篡改）、绑定邮箱或一次性令牌、短时效、可撤销、登录后再次校验成员关系；并且登录页仍保留平台信任标识。裸 `?tenantId=123` 不满足这些条件，不应作为主入口。

### 5.5 SSO / IdP-initiated

SSO 是“租户品牌登录页”最合理的落地场景：企业客户有自己的 IdP、自己的域名、自己的品牌，平台把认证委托出去。此时安全边界在 IdP 断言：校验 issuer/audience/signature、校验域名归属、JIT provisioning 时再次确认租户成员关系；不能仅凭 URL 里的 tenant 参数就信任。Microsoft HRD、Auth0 Enterprise Connections、WorkOS SSO 都是这个模型。[2][5][9]

## 6. 对本项目的选型建议

### 6.1 本项目约束（来自任务背景，不作为市场证据）

单套管理后台，所有租户共用 `/auth/login`；登录表单只有用户名+密码；用户名在 `sys_user` 全局唯一（`selectUserByName` 显式忽略租户拦截），登录后由用户记录反推 tenantId；登录后的布局已按租户显示名称/Logo（`resolveAdminBrand` + 公开接口 `/upms/app/tenant/shop-info`，按 `tenant-id` 请求头返回名称、Logo、地址、官网、电话、businessMode）；`sys_tenant` 只有 name/logo/address/site/phone 等字段，没有租户编码/域名；C 端 UniApp 每租户独立构建，`VITE_TENANT_ID` 在构建期写死；登录页目前硬编码平台品牌“悦航购”。

这些约束决定了三件事：A/B 不需要改表；B 依赖“用户名全局唯一”这一现状；C 需要新增租户编码/域名并配套双模式 SQL，但可以顺带解除“用户名必须全局唯一”的长期约束。

### 6.2 三条可落地路径

| 路径 | 做法 | 成本 | 体验 | 风险 | 适用前提 | 判断 |
|---|---|---|---|---|---|---|
| A. 共享中性登录 + 登录后租户品牌 | 保持 `/auth/login` 单页；登录页明确写“悦航购 · 商家工作台”，不冒充租户；登录后沿用现有租户品牌 | 低，主要是文案/i18n 与视觉 | 最好，一步登录 | 低；登录前无租户品牌 | SMB/自助、无白标合同 | 现在最像主流做法 |
| B. 两步 identifier-first | 第一步只输用户名（平台品牌）；服务端按全局唯一用户名解析租户；第二步显示租户 Logo/名称 + 密码；返回品牌 + 短时效签名 loginTicket，不返回 tenantId；未知用户走通用回退；限流+验证码 | 中，新增预登录接口、签名票据、前端两步、测试 | 中，多一步，但登录前能看到租户品牌 | 中；用户名/租户枚举、品牌接口滥用 | 用户名全局唯一、租户品牌数据质量可控 | 企业 IdP 主流；SMB 非默认 |
| C. 租户子域名 | `{code}.admin.example.com`；`sys_tenant` 增加不可变 `code` 与 `admin_host`/`custom_domain`；泛解析 + 通配证书；按 Host 解析租户；登录页首屏租户品牌；Cookie 按 host 隔离；boot/cloud 双份配置 + 增量 SQL；C 端 `VITE_TENANT_ID` 映射同一 `code` | 高，DNS/证书/路由/迁移/客服 | 最好，可收藏、可品牌化 | 中；子域接管、钓鱼、DNS/证书运维、租户枚举 | 企业/白标客户达到一定数量，有运维能力 | 长期正解 |
| D. 自定义域名（C 的扩展） | 在 C 基础上允许租户绑定自有域名；DNS 验证、证书、域名唯一性、回收流程 | 很高 | 最佳品牌一致性 | 中高；钓鱼、域名冲突、证书/客服 | 头部 Enterprise/white-label | 长期正解的高端扩展，不建议先做 |
| E. 签名邀请/SSO 深链 | 邀请链接或 IdP-initiated 链接携带签名组织上下文；绑定邮箱、短时效、可撤销；仅用于入驻/SSO | 低到中 | 对受邀用户好，对日常登录一般 | 链接泄漏、转发 | 有邀请制/企业 SSO | 辅助入口，不做主入口 |

### 6.3 推荐结论

**现在最像主流做法的是 A。** 不是因为它“高级”，而是因为它是 Shopify、Stripe、Notion、Slack、有赞、微盟、淘宝、京东、SHOPLINE、BigCommerce 的共同结构：平台品牌的中性登录页，登录后解析租户。把登录页的“悦航购”改成“悦航购 · 商家工作台”，并在文案上明确“登录后进入您的企业工作台”，就能消除“平台品牌冒充租户品牌”的观感，同时保留最低成本、最低风险和最好的登录体验。

**如果“登录页必须在密码之前显示租户品牌”是硬需求，选 B。** 我们的用户名全局唯一，这是 B 的天然前提；不需要改 `sys_tenant`。但 B 的关键不是“多一步”，而是“不要泄露 tenantId”：预登录接口只返回 `{brandName, logoUrl, loginTicket}`，`loginTicket` 短时效、签名、绑定用户名+租户+nonce；未知用户名返回平台默认品牌，不返回“租户不存在”；接口单独限流，登录页保留验证码。这个模式与 Microsoft 的“先输入邮箱、再显示租户 branding”同源，属于企业 IdP 的主流做法；但它不是 SMB SaaS 的默认，因为多一步会损失转化。

**长期正解是 C。** 当客户进入 Enterprise/白标/SSO 阶段，子域名是规模化 B2B 的标准解：Salesforce My Domain、Atlassian 站点域、Slack 工作区域名、Okta org 都是这个思路。C 的落地要点：`code` 必须不可变、URL-safe、全局唯一，不能用租户显示名；`admin_host` 与 C 端 `VITE_TENANT_ID` 共用同一 `code`；泛解析 + 通配证书 + Host 白名单；Cookie 按 host 隔离；租户停用/删除时回收域名；boot/cloud 双模式配置与增量 SQL 同步。C 还可以把“用户名全局唯一”降级为“租户内唯一”，这是共享登录模式做不到的。D 只在头部客户明确要求自有域名时再做，且必须配 DNS 验证、证书生命周期和域名冲突处理。

**“带 tenantId 的专属登录链接”不是主流主入口。** 它只适合邀请/SSO 深链，而且必须签名、绑定邮箱、短时效、可撤销。更主流的替代是：子域名（日常书签）、邮箱域发现（企业 SSO）、签名邀请/SSO 深链（新客/企业接入）。如果现在就把 `?tenantId=` 作为主入口，会同时得到“链接泄漏 + 租户枚举 + 品牌钓鱼 + 书签失效”四个问题，收益只是省掉一次租户解析。

### 6.4 决策规则

- SMB/自助/无白标合同：A，平台品牌，登录后租户品牌。
- 客户明确要求“登录页看到我们公司”：B，先做 identifier-first，不改表；登录前品牌接口不要复用按 `tenant-id` 头取数的 `/shop-info`，应新建按用户名/宿主解析、只返回名称与 Logo 的接口。
- 进入 Enterprise/白标/SSO：C，子域名；D 作为头部客户扩展；E 用于邀请/SSO 接入。
- 任何情况下：不要用裸 tenantId 链接作为主入口；不要让公开品牌接口返回内部 ID/地址/电话；不要在未验证域名的情况下做租户品牌登录页。
