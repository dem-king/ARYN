微信小程序的折叠屏适配，
到底做到什么程度？

覆盖竖折 / 横折 / 阔折 / 三折 / iOS 折叠五种形态，从平台机制、厂商兜底、商家布局三层拆解。

中等偏下能跑，但不好用

小程序在折叠屏上不会崩，但也几乎不会变好：展开后留白、整体放大、图片拉伸是常态，真正针对大屏重排版式的属于极少数。
根因不是技术做不到，而是盘子太小（渗透率 3.52%） + 微信没把折叠屏列为独立适配场景 + 形态碎片化让等比缩放失效。

01不同形态，适配差距很大

评级口径：A 优秀 / B 良好 / C 可用但未利用大屏 / D 明显影响使用。下图为本次调研的评估打分（非行业统计）。

各折叠形态下微信小程序的可用程度（0–100）

03三层拆解：卡在哪一层

折叠屏体验不是「商家一个人的事」，平台、系统、商家三层各有一道坎。

L1 平台层

微信客户端 / 基础库

《大屏适配指南》只分手机、平板、PC 三类，折叠屏没有独立章节。社区提问「双屏留白」，官方回复「符合预期」。rpx 基准在冷启动大屏时可能算错且不重算（社区多例反馈）。

B− 能跑但无专项支持
L2 系统层

厂商分栏兜底

华为「平行视界」和荣耀大屏模式对小程序默认全屏、不参与分栏，两家官方都写明「设计如此」，用户需手动点右上角「在…中显示」才能分屏。

C 有兜底但用不上
L3 商家层

小程序自身布局

绝大多数只做一套 750 宽的竖屏稿，靠 rpx 等比放大。展开后留白、元素变大、图片拉伸，宽出来的面积基本浪费。

D+ 几乎未做展开态

04八类典型翻车现场

按「现象 → 技术根因」排列，可直接对照自查。

展开后大片留白、页面「压扁」

微信默认不全屏 + 容器宽度写死 → 宽度翻倍但内容不跟着铺开。

字号、卡片整体变大

rpx 基准按冷启动 windowWidth 计算，折叠切换后不重算（社区多例）；开 resizable 时双屏更明显。

图片拉伸、主体跑位被遮挡

全屏底图用 mode="widthFix" 按宽算高，与 fixed 前景错位。

大屏断点永远不触发

窗口化 / 兼容模式下 windowWidth 停在 4xx，@media 600px 分支不命中。

横屏白屏、方向锁失效

resizable:true + pageOrientation:landscape，单屏进入时渲染异常。

宽屏没有分栏

平行视界 / 大屏模式不作用于小程序，默认全屏拉伸。

内容压在折痕上

未为折痕预留安全边距，也未监听折叠状态变化。

新形态直接黑边

微信客户端未适配（iPhone Duo），只能等平台更新。

份额上，2026Q3 中国折叠屏华为约 74%——「折叠屏适配」在中国市场实质上就是「华为横折 + 阔折适配」。

06给悦航购的行动建议

不做「折叠屏专属设计」，但必须做「展开不翻车」。这是投入产出比最高的区间，也是相对同行的差异点。

P0 必做
  • 全屏背景改 aspectFill + 容器 100vw/100vh；禁止 widthFix 做全屏底图
  • 宽度一律 100% / flex / grid，容器不写死 px；关键按钮热区 ≥ 44px
  • 用 match-media 或 createMediaQueryObserver 处理 ≥600px 分支，onResize 里重取 windowWidth

约 0.5–1 人日 · 主要防现网事故

P1 值得做
  • 商详页展开态两栏：左商品图 / 右价格、规格、加购
  • 列表页左列表 + 右详情（或左侧筛选栏），把宽度换成效率
  • 底部 TabBar 宽屏居中限宽或侧边栏，避免图标被拉成一条线
  • 横向布局中间预留 24px 折痕安全区

约 1–2 人日 · 差异化体验

P2 观察
  • 外屏卡片、半折悬停态、三折专属版式：暂不投入
  • 按机型出多套设计稿：不推荐，宽度段会无限细分（420/440/460/480…）
