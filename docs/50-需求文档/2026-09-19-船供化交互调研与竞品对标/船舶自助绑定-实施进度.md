## 一、本轮实际做完的事

### 1.1 部署（原本最大的阻塞）

vessel 服务此前跑的是旧 jar，所有新接口 404。重建时踩到两个坑：

1. **`docker compose build` 报 `error getting credentials`**（macOS keychain 弹出被取消）。
   绕开方式：直接用 `DOCKER_BUILDKIT=0 docker build -t aryn-mall-java-aryn-vessel-biz:latest .`
   构建，再 `docker compose up -d --no-deps --force-recreate aryn-vessel-biz`。
   注意：`restart-service.sh` 用 `| tail` 收尾会**吞掉失败退出码**，看日志容易误判成成功。

2. **Nacos 租户白名单缺失导致崩溃循环**（重启 9 次仍在涨）。
   `TenantSchemaValidator` 双向严格校验：库里有 `tenant_id` 的表必须在 `hx.tenant.tables` 里登记，
   否则启动即抛 `IllegalStateException: 多租户 schema 校验失败` → 无限重启。

   关键细节：**直改 Nacos 的 MySQL `config_info` 表对运行中的 Nacos 无效**（配置有缓存），
   必须走 API 发布：

   ```bash
   AT=$(curl -s -X POST "http://localhost:8848/nacos/v1/auth/login" \
        -d "username=nacos&password=nacos" \
        | python3 -c "import json,sys;print(json.load(sys.stdin)['accessToken'])")
   curl -X POST "http://localhost:8848/nacos/v1/cs/configs?accessToken=${AT}" \
        --data-urlencode "dataId=aryn-vessel-biz-dev.yml" \
        --data-urlencode "group=DEFAULT_GROUP" \
        --data-urlencode "content@/tmp/vessel_cfg.yml"
   ```

   改完 `docker restart` 验证：重启计数归 0、日志无 schema 报错。

### 1.2 端到端验证（都实跑过，不是纸面推演）

新增 `dev-tools/smoke-vessel-bind.sh`，**21 条断言全绿**，覆盖：

- 权限收敛：普通船员(2) 加人 / 生成邀请码 / 检索候选**三处都被拒**；采购确认人(3) 三处都能做
- 重复绑定拦截：已是成员时提交申请、兑换邀请码都被拒
- 邀请码：6 位且不含 `0/O/1/I`、大小写与空格不敏感、用完限次即失效、非生成人不能撤销
- 隐私：成员列表与候选列表手机号均脱敏（`138****1234`）
- 端侧权限边界：C 端 token 访问管理端审核接口被拒

脚本会自行写入 Redis 短信码用于登录、结束时清理自己创建的邀请码，可重复执行。

除脚本外，手工跑通了脚本覆盖不到的**冷启动全链路**（需要管理端 token）：

```
未绑定用户提交认领申请（applyRole=4）
  → 运营在管理端看到待审（申请人昵称/手机号已脱敏）
  → 直接通过（船名匹配不到）→ 返回可执行报错，要求指定已有船或填新船名
  → 改「新建船舶后绑定」→ 系统建船 + 写入成员(role=4) + 申请单置为已通过并回填船舶ID
  → 业务员登录后能看到这条新船
  → 业务员按手机号添加船员成功（手机号经 Dubbo 解析为用户ID）
  → 生成邀请码 → 第三个用户兑换加入成功 → 用完次数后再兑换被拒
  → 驳回无理由被拦、有理由通过、已处理申请不能重复审核
```

验证用临时数据已清理；`seed-acceptance-data.sh` 里留了一条**待审核申请**供验收直接测审核。

## 二、已确认的设计（本次最重要的业务产出）

原方案被推翻过一次。最初按「船员自助获客」设计（邀请码 + 申请审核），
但实际业务是**销售业务员地推**——业务员跑船跑港、当面推销、现场用 App 下单。重新确认后的口径：

| 问题 | 确认结论 |
|---|---|
| 谁下单 | **两种都有**：首次拜访业务员代下单，后续船员自己复购 |
| 业务员身份 | **就用现有 C 端账号**，不新增登录身份 |
| 授权依据 | **船舶成员关系**——是这条船的成员就能操作这条船 |
| 谁可以拉人 | **限特定角色**：发起人(1) / 采购确认人(3) / 业务员(4)；普通船员(2) 不行 |
| 业务员怎么上船 | **申请认领 + 运营审核**（覆盖「船还没录入系统」的情况） |

由此形成三条通道，都已可用：

1. **业务员认领船舶**（冷启动）——提交申请，运营审核通过后成为该船成员
2. **成员现场拉人**（日常主路径）——业务员在船上，掏出手机把船员加进来
3. **邀请码自助加入**（补充）——业务员不在场时，船员之间互相拉人

## 四、已知问题与风险

| 风险 | 级别 | 说明 |
|---|---|---|
| **业务员角色可自封** | 🔴 高 | 任何人可提交 `applyRole=4` 自称业务员。若运营审核不严，会出现非公司人员获得「添加成员、代下单」权限。**建议**：审核时要求填写工号并核对，或后续接入员工体系校验 |
| **成员互相拉人无上限** | 🟡 中 | 业务员可无限添加成员。当前无数量限制与异常告警 |
| **邀请码可外传** | 🟡 中 | 6 位码若被截图外传，外部人员可加入。已有缓解：24 小时有效期、可撤销、可限次。**建议**：默认限次而非不限（当前 `maxUses=0` 表示不限，前端默认不传即不限） |
| **代下单归属未定** | 🟡 中 | 影响对账与售后责任划分，需要业务侧拍板 |
