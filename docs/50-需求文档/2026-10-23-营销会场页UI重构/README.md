## 〇、一页结论

| 项 | 结论 |
|----|------|
| **第一轮为什么还是不好看** | 不是因为"没对齐规格"，而是因为**第三轮把 AI 示意稿当成了验收基准**（该轮 §14 明确"全面向原型靠拢"）。AI 示意稿本身带着一批廉价特征：实心色**描边卡**、方块 CTA、"秒/折"**文字当图标**、并列**灰色小胶囊标签**。这些被逐像素复刻进了代码，于是"看着脏"的部分被固化下来 |
| **真正的六类根因** | ① 版头结构重复且吃掉 1/3 屏（秒杀：导航空题 + 版头大标题 + Tab 一行 + 倒计时一行，四处重复同一件事）；② 促销强度三级**没有拉开**（折扣页主色面积反而比秒杀页更大）；③ 单卡信息过载（秒杀卡 4 个促销元素抢同一行、拼团卡一行 3 个灰胶囊、折扣网格卡 336rpx 塞 5 个元素）；④ 页面没有节奏（无吸顶、无分区、无收尾）；⑤ 图形语言贫弱（图标是"文字方块"、空态用 🤝 emoji、无进度轨道）；⑥ 状态与边界不完整（未开始场次商品仍像可抢、拼团详情非进行中时底部 CTA 整条消失、空态无操作入口） |
| **方案主线** | 不追示意稿，改为**按竞品真实范式重排信息架构 + 用一张反模式清单做删除**：把"加元素表达促销"换成"删元素 + 把主色面积当稀缺资源分配"。四页共用一套版头语言、一套字号阶梯、一套三态组件 |
| **强证据的 4 条硬约束**（来自本轮竞品调研，非推测） | ① 已结束场次**不渲染**，未开始**置灰到点亮**；② 会场页用"**高矮版头动态切换**"（滚动后压缩为吸顶窄条）取代多段吸顶堆叠；③ 促销词的消费者端表达在弱化（抖音已弃用"秒杀"字样）；④ 拼团详情的底部按钮是**随关系/玩法变化的状态矩阵**，不是固定双按钮 |
| **不做** | 不伪造无字段的社会证明（在抢人数/回购数/好评数）；不改下单动线；不改后端；不做暗色模式 |
| **工作量** | P0 结构与规格重排（纯前端样式+模板）≈3 人日；P1 增强（吸顶压缩条/悬浮回顶/玩法说明/图标与插画素材）≈2 人日。**零后端、零 DB、零新增接口** |
| **交付物** | 本文档 + 可视化对照稿（4 页目标形态，可在对话内直接预览） |

## 三、竞品范式与硬约束（本轮调研）

> 方法：Web 检索公开设计规范与改版复盘，标 `[实]`（有公开来源）/`[知]`（行业通识）。竞品截图级结论沿用前置文档（盒马/小象/拼多多/叮咚）。

### 3.1 秒杀会场的头部与场次轴

| 主流做法 | 来源 |
|---------|------|
| 场次是**带状态的横滑 pill**，不是等宽下划线 Tab；京东秒杀按流量峰切场（10–12／14–16／20 点），**已过场次直接隐藏**，只留"进行中 + 未开始" | [京东秒杀玩法解析](https://mtt.m.jd.com/article/articleView/d7ae7b43-9490-48fd-b35a-fd389c16f2ad.action?from=recommand)、[秒杀玩法拆解](https://www.woshipm.com/operate/2464427.html) |
| 未开始的硬规矩：**按钮置灰、到点自动点亮**；预热期显示"距开始"，进行中显示"距结束" | [秒杀系统设计](https://docs.feishu.cn/article/wiki/DS9xwYn3UiipvokNwcHcT71NnMe)、[秒杀 PRD](https://www.woshipm.com/pd/4245568.html) |
| 倒计时分三层，**滚动后压缩成吸顶窄条**（淘宝把"固定版头"改成"高矮版头动态切换"） | [淘宝会场改版复盘](https://www.uxbaike.com/post/20187/20211) |
| 粒度：秒固定两位 + `tabular-nums`；**天单独一格**，不与时分秒同宽 | 同上（行业通识部分） |

**可迁移**：横滑 pill 三态（进行中=实心主色+白字 700；未开始=浅底+主色字；已结束不渲染）；头部大倒计时"天块 + 时:分:秒";滚动 120rpx 后切 88rpx 吸顶窄条。

### 3.2 商品卡的信息优先级

- **会场页用左图右文横排**：图文列表"可展示更多促销信息、增删标签对版面影响最小、对比速度快"；双列网格适合"以图片对比为决策"的品类，但单卡容不下"立省+进度+CTA"三件套（[商品展示列表选型](https://www.woshipm.com/pd/1539370.html)）。
- **进度要"轨道 + 文案"双出**，且当前进度与总进度强对比、轨道不带色（[Arco Progress](https://arco.design/docs/spec/progress)）；秒杀卡字段标配 = 图 / 品名 / 秒杀价 / 原价 / **秒杀进度** / 立即秒杀（[秒杀 PRD](https://www.woshipm.com/pd/4245568.html)）。
- 淘宝秒杀改版方向 = "以品为中心 + 价差直给"，并明确**删减"写了没错但不写也行"的信息**（[淘宝秒杀复盘](https://www.uisdc.com/taobao-2)、[大促会场改版](https://www.uxbaike.com/post/20187/20211)）。

### 3.3 拼团的社交化表达

- 拼多多人拼团底部是**状态矩阵**而非固定双按钮：好友分享进入＝【继续参与 TA 的拼单】；陌生人＝【单独购买】+【发起拼单】；另有万人团等促销态（[拼团产品逻辑](https://www.opp2.com/302821.html)、[拼多多体验报告](https://www.woshipm.com/evaluating/2385517.html)）。
- 空态应有"图标/插画 + 说明 + 操作"三件套；分享入口固定在导航右上 + 底部 CTA 左侧（[Arco Empty](https://arco.design/docs/spec/empty)、[飞书空状态](https://open.feishu.cn/document/design-specification/component---data-display/empty?lang=zh-CN)）。
- 双价靠**颜色权重**拉开，明确引导发起拼团；价格写进按钮内形成同屏比价（同上）。

### 3.4 折扣会场的组织方式

- 大促会场三阶段：**收敛**（严格控制信息密度、删装饰）→ **统一**（模块组件化、统一标题与标签布局）→ **提效**（顶部+底部双导航收敛为统一顶部导航，用高矮版头兼顾氛围与效率）（[淘宝大促设计改版](https://www.uxbaike.com/post/20187/20211)）。
- 多活动并列时以"活动 Tab"/价格带分档组织，而不是把多个活动的商品串成一条长列表（[京东特价入口改版](https://www.cbndata.com/information/293536)）。

### 3.5 四条硬约束（建议直接写进本期验收）

1. 已结束场次**不渲染**；未开始 CTA 置灰、到点自动点亮。
2. 会场页用**高矮版头动态切换**（滚动后压缩吸顶），不做多段吸顶堆叠、不在会场页保留底部 Tab。
3. 促销表达**克制**：不堆同义促销元素；"秒杀/疯抢"这类硬词不加重、不叠感叹号（抖音已把消费者端"限时秒杀"更名为"限时抢购"）([抖音电商说明](https://school.jinritemai.com/doudian/web/article/108102))。
4. 拼团详情底部是**状态矩阵**（未参团/我发起/我参与/待支付/未开始/已结束），不是固定"单独购买 + 发起拼团"两个按钮。

### 15.2 顺带修掉的结构缺陷（重要）

`seckill.vue` / `discount.vue` 的页面容器是 `min-height: 100vh` + `scroll-view { flex: 1 }`：
`min-height` 不会限制高度，内容一多就把整页撑高，**scroll-view 形同虚设**（实际是页面在滚）——
后果是 `refresher-enabled` 下拉刷新与 `@scroll` 都不触发（P0 之前就存在，只是没做交互所以没暴露）。
改为 `height: 100vh; overflow: hidden` + 滚动区 `min-height: 0; flex: 1`（与 `sub-pages/message/chat` 同款写法）后，
内部滚动、下拉刷新、吸顶与回顶才真正生效。

## 十七、P2 数据能力落地（2026-10-23 第四批）

### 17.1 秒杀「N 人在抢」= 购物车去重人数

| 项 | 内容 |
|----|------|
| 口径 | 租户内、未删除、加购时间 ≥ 场次开始时刻的**去重 user_id 数**。不是加购件数、不是下单数；购物车里当前还放着的才算"在抢"，买完行被清掉后自然减一 |
| 链路 | `RemoteShoppingCartService.countDistinctSkuUsersSince`（order-api）→ `shopping_cart` 聚合查询（order-biz，XML `countDistinctSkuUsersSince`）→ `SeckillActivityServiceImpl.countCartUsers` 回填 `AppSeckillVO.cartUserCount`（promotion-biz，每场次 1 次 RPC，不按商品 N+1） |
| 降级 | 远程失败/未注入/无数据 → `null`，C 端整行不渲染；统计不参与库存与下单任何判定 |
| 展示 | 秒杀信息条副标下一行「N 人在抢」（20rpx/600 白字），与「整点开抢 · 限量特价」同列，不占卡片空间（避免每卡多一个促销数字） |
| 安全 | 租户/时间窗全部显式传参，不依赖 Dubbo 调用链路的线程上下文 |

### 17.2 折扣「仅剩 N 件」= 商品级真限量 + 超卖拦截

**数据模型**（`153discount_goods_stock_incremental.sql`，boot/cloud 各一份，可重复执行）

| 对象 | 变更 |
|------|------|
| `discount_goods` | `stock int NULL`（限量，NULL=不限量，存量行保持 NULL → 行为不变）、`sold_count int NOT NULL DEFAULT 0` |
| `discount_stock_lock`（新表） | `tenant_id, activity_id, sku_id, order_id, quantity, status(1占用/0释放), release_reason`；唯一键 `(tenant_id, order_id, sku_id)` 保证幂等与并发安全 |

**占用/释放**

| 时机 | 行为 |
|------|------|
| 下单（`OrderPriceComputeService.reservePromotion`） | 逐 SKU：未配置 stock → 跳过；已有占用明细 → 幂等跳过；否则先写明细（唯一键挡重复）再 `UPDATE ... WHERE sold_count + qty <= stock` 原子扣减；扣减失败整单回滚并抛「折扣商品库存不足」 |
| 取消/超时/退款（`releasePromotion`） | 按订单查占用明细 → `sold_count = GREATEST(sold_count - qty, 0)` 回补 → 明细置 `status=0` 并记原因；释放失败只告警，不阻塞取消 |
| 支付确认 | 无需处理：库存在**下单时**已占用（与秒杀预扣同思路，避免未支付订单不占库存导致超卖） |

**关键取舍**

1. 远程返回 `DiscountStockReserveResultDTO` 而不是抛异常：Dubbo 会把跨进程异常包成 `RpcException`，下单侧只认 `ArynBusinessException` 时会把"库存不足"当成"服务不可用"而放行，拦截就失效了。
2. 不用 Redis：折扣是长周期活动、并发远低于秒杀，行级锁 `UPDATE ... WHERE sold_count + qty <= stock` 足够，少一层缓存一致性。
3. 编辑活动不清零已售：`updateWithGoods` 是"删光重建"商品行，重建前先把各 SKU 的 `sold_count` 抄回来，并校验「限量不能小于已售」。

**管理端**：折扣活动编辑页商品表格新增「限量库存」列（留空 = 不限量），随表单一起提交。

**C 端**：折扣商品卡在省额旁显示——剩余 ≤10 件「仅剩 N 件」、剩余 0「已售罄」，其余不展示（避免每张卡都挂一个数字）。
