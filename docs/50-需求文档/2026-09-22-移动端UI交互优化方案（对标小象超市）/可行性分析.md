## 2. P0 设计 Token：可行，但有三个必须先解决的前置

### 2.1 现状：主题源有 5 处、且互相冲突

| 载体 | 当前值 | 影响面 |
|------|--------|--------|
| `src/App.ku.vue` `themeVars` | `#FF2237` / 辅色 `#FF6B7A` / 底色 `#FFF0F0` | 运行时 `--wot-color-theme-*`，覆盖 wot-design-uni 组件 |
| `src/uni.scss` | `$uni-color-primary: #007aff`（uni-app 默认蓝） | 编译期注入每个 scss 块；**但当前源码里 `$uni-*` 变量使用数为 0**，属"死配置" |

| `pages.config.ts` + `src/pages.json` | tabBar `selectedColor: #FF2237` | 原生 tabBar，编译期写死 |
| 页面内硬编码 | 见 2.3 | 逐页样式 |

### 2.2 前置一：品牌色未拍板（方案自己写了"需产品确认"）

原型里已经用了「深海航海蓝 `#0B63E5` + 活力橙 `#F2741D`」这套。这条不拍板，后面所有产出（tabBar 图标 PNG、登录页 logo、空态插画、原型走查）都要返工。**建议把它作为 Phase 1 的第一个决策点，而不是"边做边定"。**

### 2.3 前置二：Token 覆盖不到原生容器与运营配置

- **覆盖得到**：页面/组件的 scoped 样式、wot-design-uni 组件（`wd-*` 出现 72 个文件、`wd-text` 93 处）。
- **覆盖不到（必须走编译期静态值）**：原生 tabBar（`pages.config.ts`）、原生导航栏（`@navBgColor` 等 `globalStyle` 变量）、`theme.json`。这三个只能改成新品牌色后重新编译，不能靠 CSS 变量动态换肤。
- **覆盖不到（属运营数据）**：首页装修 JSON 里运营配置的颜色。`db/boot/74home_banner_images.sql` 整块 `UPDATE page_design.page_content`，其中含 24 处 `rgba(...)`（价格红 `rgba(255,0,0,1)`、购买按钮色等），`page_design_version` 快照同理。
  → 若要求"散落色值清零"，**必须同时出一份装修数据迁移 SQL（boot+cloud 双份）把运营色改成 Token 默认值，或明确约定"运营配置色允许覆盖 Token"**。否则页面改完仍是红的。

### 2.4 前置三：工作量的真实量级（可量化）

- 全仓 `src` 内 hex 色值：**687 处 / 169 个唯一值 / 90 个文件**。
- 去掉近似灰度后：**非中性色 234 处 / 98 个唯一值**（中性色 453 处，可批量走中性 Token）。
- 颜色大户：`pages/user/shopping-cart/index.vue`(38)、`vk-data-goods-sku-popup`(34)、`sub-pages/message/notice`(29)、`user/distribution`(26)、`promotion/seckill`(23)、`promotion/discount`(21)。

结论：**Token 落地是"机械活 + 代码评审"，不是难点**；用 `rg '#[0-9a-fA-F]{3,8}'` 做守门 + 分批迁移即可，2~3 天可完成主体，剩余长尾随各 Phase 顺手清理。

## 4. 四个「看着是前端活，实际要动后端」的项

### 4.1 场景化"一键买齐组合" —— 无组合商品模型

全仓无套装/组合/BOM 概念。要做真组合购，需要：组合表（组合主表 + 明细 SKU）→ C 端组合详情/加购接口（拆单到购物车或直接生成多行）→ 管理端组合编辑页 → 优惠与库存口径（不够库存怎么算）→ 双模式 SQL。**这是 Phase 1 里唯一的"新领域能力"**，建议整体挪到 Phase 3 或直接降级为"场景货架"。

### 4.2 搜索联想与容错词表

后端 `AppGoodsSpuController#search` 已支持关键词跨"编码组/名称组"匹配，且 `product_code_mapping`（43 号脚本）可作别名/编码映射来源；但**不存在 suggestion 接口与词表维护入口**。若要求"输入『苹』联想『苹果/苹果醋/苹果汁』"并可控运营，需要：suggestion 接口 + 词表表（或复用别名） + 管理端维护 + 双模式 SQL + 前端防抖。

### 4.3 会员等级进度

`MemberLevel` 有 `conditionType(1累计消费/2累计积分)` 与 `conditionValue`，但 `getPointsInfo` 不返回当前累计值/差额，因此"再消费 ¥160 升 Lv.4"算不出来。要么补 `PointsInfo`（或新增 level-progress 接口），要么降级为"当前等级 + 查看权益"。

### 4.4 船供专属履约节点（靠港 / 装卸 / 交接确认）

现有节点全部来自 `delivery_task.status` 的 **6 个通用状态**（1 待派单、2 待取货、3 配货中、4 待送达、5 已送达、6 已签收，另有 7 取消/8 异常/9 退回）。项目里**没有拣货工单、打包、装卸、交接确认这些领域对象**。要加"靠港计划/装卸货/交接确认"必须：新增任务状态或独立节点表 + 配送工作台（`pages/delivery/*`）新增动作 + 权限/SQL 双模式 + 状态机联动订单。**成本与风险都是 P2 里最高的一项，建议单独立项。**

## 6. 性能基线的优先级需要重排

### 6.1 主包体积：`static/logo.png` 单文件 1.5MB 在主包内（最该先做）

- 微信构建产物 `dist/build/mp-weixin`：按文件字节合计约 3.5MB，其中 **非 sub-pages 部分约 2.98MB**，`sub-pages` 约 0.5MB。
- `src/static` 合计 1.6MB：`logo.png` **1.5MB**（1190×1190 RGBA PNG，仅 `pages/login/index.vue` 使用）、tabbar 8 张共 56KB。
- 微信小程序主流限制为主包 2MB：当前静态资源几乎占满主包预算。**压缩/替换 logo（<100KB，或改为 CDN 图）是"秒开"收益最高、成本最低的一步**，比虚拟列表优先级更高。
- 另：`manifest.config.ts` 已开 `optimization.subPackages`，但 `pages.json` 无 `preloadRule`，建议补分包预加载。

### 6.2 瀑布流不适合虚拟列表

`diy-goods-waterfall` 用 CSS `column-count` 双列（`waterfall-columns`），`z-paging` 的 `useVirtualList` 依赖固定/可估算 cell 高度，二者冲突（瀑布流高度天然不齐）。建议：

- 列表页/搜索结果页（等高行）→ 可上虚拟列表；
- 首页瀑布流 → 用"分页 + 首屏 N 条 + 图片 `lazy-load` + 骨架卡"，不做虚拟列表；
- 图片走 CDN 尺寸参数：当前 `spu_urls` 为原图直链（`db/assets` 回填的是本地文件），无缩略图/详情图分级，属真实缺口。

### 10.3 两种落地路径（建议选 B1）

| 路径 | 做法 | 成本 | 风险 |
|------|------|------|------|
| **B1（推荐）「补给单 = 共享购物车的产品化外壳」** | 复用 `shared_cart` 全套能力；首页"今日补给单"卡 = 当前船舶/靠港下 `status=2收集中` 的共享购物车；"按单加购" = 把 `shared_cart_item` 的待确认项写进个人购物车；"我的补给单" = 复用 `shared-cart/list.vue`；"去核对" = 复用 `shared-cart/detail.vue` | **前端为主**（首页卡片 + 金刚区入口 + 底部操作条）+ 2 个新接口（见下） | 低。不动状态机、不动订单链路 |
| **B2 新建「补给单」领域** | 新表 + 新状态机 + 新页面 + 与管理端对齐 | 高（估 10~15 天，含双模式 SQL） | 与 `shared_cart` 功能重叠，长期维护两套协作采购模型 |

**B1 需要的两个新接口**（都属"小改"，因为底层数据已存在）：

1. `GET /order/app/shared-cart/current?scene=replenish` —— 按当前 `vesselId + vesselCallId` 返回进行中的共享购物车 + 汇总（项数/已确认数/合计金额/还差明细），供首页卡片一次取数；
2. `POST /order/app/shopping-cart/batch` —— 入参 `[{skuId, quantity}]`，服务端逐条校验 MOQ/步长/库存后批量落库，返回成功/失败清单（**免掉 N 次往返与多规格弹层阻塞**）。

**"清单还差"（目标量）的两种口径**（必须产品拍板）：

- **口径 1（零后端改动）**：不做"目标量"，卡片改为展示"待确认 4 项 / 已确认 8 项"，进度条 = 已确认项数占比。原型文案需相应调整。
