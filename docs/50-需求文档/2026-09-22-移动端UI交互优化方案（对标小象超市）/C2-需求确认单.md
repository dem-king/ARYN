## 1. 七项决策（默认口径已冻结）

| # | 问题 | 结论（默认口径） |
|---|------|------------------|
| 1 | 匹配列 | 单列「商品编码」自动识别类型，优先级 IMPA > ISSA > 内部编码 > 条码 > 供应商编码；同值命中多个 SKU 时进「未匹配」并给出候选，不自动入单 |
| 2 | 谁能导入 | 确认人/发起人（与 C1 排计划同权限，服务端 `requireConfirmer`）；普通成员无导入入口 |
| 3 | 重复 SKU | 与补给单已有明细合并数量（同 SKU 汇总后累加），不新增重复行；被逻辑移除的行**复活**并写入新数量 |
| 4 | 导入行归属 | 记在导入操作者名下（`shared_cart_item.user_id` = 操作者，与 C3 历史复用口径一致） |
| 5 | 未处理行 | 确认时跳过未处置行并如实统计（`skipped_rows`），不整体驳回 |
| 6 | 单位与库存 | `conversion_rate` 不参与换算，库存按 `sku.stock` 与数量直比；单位/规格不一致只提示、不拦截 |
| 7 | 平台范围 | v1 支持微信小程序（`chooseMessageFile`）+ H5（`chooseFile`）；App 端延后 |

## 2. 模板列（与解析共用同一份列定义）

| 列 | 必填 | 说明 |
|----|:----:|------|
| 分类 | 否 | 目录模板写入的一级/二级分类（如「乳品烘焙/鲜奶」），仅展示，不参与解析 |
| 商品编码 | 否 | 优先匹配；为空时走品名+规格兜底 |
| 品名 | 是 | 编码未命中时的兜底匹配依据 |
| 规格 | 否 | 参与兜底匹配与「规格变更」判定 |
| 数量 | 是 | 正整数；与补给单同口径，不做单位换算 |
| 单位 | 否 | 仅展示与提示 |
| 备注 | 否 | 写入 `member_remark` |
| 库存 / 起订量 / 步长 / 售价 | 否 | 只读参考列，服务端现状快照，**不参与解析**（客户改了不算数） |

### 2.1 模板形态（2026-09-28 变更）

原「下载标准模板」只给一行示例，客户要自己把编码、品名、规格一条条敲进去，商品一多就极易：
编码抄错 → 整行未匹配；品名用自己的叫法 → 命中不了；规格写法与商品资料不一致 → 被报「规格变更」。

现改为**按分类铺满在售商品**的采购目录：模板打开即按分类列出全部在售商品，
客户只需在要采购的行填「数量」，其余行留空。列仍与解析共用同一份定义
（`ReplenishImportExcel.COLUMNS`），参考列不参与解析。

- 商品范围：SKU 与 SPU **均在售**（下架商品列进去只会在报告里被标「已下架」）。
- 编码列：按 IMPA > ISSA > 内部编码 > 条码 > 供应商编码挑一个**匹配链路能识别**的值；
  取值同时覆盖 `product_code_mapping`（SKU 级）与 `ship_goods_profile`（SPU 级，运营在管理端维护）。
- 行数上限 2000（与单文件导入上限一致）；超出时截断并在响应头 `X-Catalog-Truncated` 回传真实总数。
- 排序：一级 sort → 一级名 → 二级 sort → 二级名 → 品名。
  只按 sort 不够：不同类目树的 sort 会撞车（实测「蔬菜」与「家用电器」同为 sort=1），
  撞车时相邻类目的行会交错，模板就没法按分类阅读。

### 2.2 「未填数量」是正常状态（NOT_FILLED）

目录模板铺满在售商品，客户只填要买的几行，**绝大多数行天然没填数量**。
原口径把「数量为空」归入 INVALID_QTY，会导致 273 行的模板只填 5 行时
报告显示 268 行「数量异常」，真正的错误（编码抄错、库存不足）被彻底淹没。

因此新增独立结果类型 `NOT_FILLED`（未填数量 = 本次不采购）：

- **判定优先级最高**：先于「未匹配」与「已下架」——客户没打算买的行，商品下架与否都与它无关；
- 报告单独计数 `not_filled_rows`，不计入 `invalid_rows`；
- 不进「待处置」列表，确认并入时**不计入 `skipped_rows`**（那不是处理失败）；
- 填了但解析不出数字（如「十份」）仍是 INVALID_QTY，两者语义分离。

## 3. 结果分类（报告口径）

| 类型 | 判定 | 报告动作 |
|------|------|----------|
| 匹配成功 OK | 唯一命中且数量合法、库存充足 | 直接入单 |
| 未填数量 NOT_FILLED | 数量列为空/空白（客户本次不采购） | 略过，不报错、不计入跳过 |
| 未匹配 UNMATCHED | 编码/品名均未命中，或多规格歧义 | 「补选」→ 商品搜索选择 SKU |
| 规格变更 SPEC_CHANGED | 编码命中但规格文本与当前 SKU 不一致 | 「确认新规格」后入单 |
| 超库存 OVER_STOCK | 数量 > 当前库存 | 「调减数量」（默认建议值 = 库存向下取步长，且不低于 MOQ） |
| 数量异常 INVALID_QTY | 数量非正/低于 MOQ/非步长整数倍/填写内容解析不出数字 | 调整数量 |
| 已下架 OFF_SHELF | 编码命中但 SKU/SPU 已下架 | 不计入「未匹配」；仅提示不可导入 |


## 4. 边界与约束

- 单文件 ≤ 5MB，数据行 ≤ 2000 行（超出直接拒绝并提示）。
- 仅接受 `.xlsx` / `.xls`：扩展名 + 魔数（xlsx `PK\x03\x04`、xls `D0 CF 11 E0`）双重校验。
- 解析与匹配**全部在服务端完成**，客户端只回传「行号 → 处置动作」，不信任客户端回传的行内容（沿用 `ProductImportServiceImpl` 的范式）。
- 确认并入幂等：同一任务重复确认返回首次结果，不重复累加数量。
- 导入不锁价、不校验库存占用、不触发下单；库存仅作为「超库存」提示口径。
- 导入行 `planned_quantity = Excel 数量`、`fulfilled_quantity = 0`，C1 进度条自然生效。

## 5. 明确不做（二期）

- 名称/规格模糊匹配打分（v1 只做编码精确 + 品名+规格精确/包含）。
- 异步解析与真实进度百分比（v1 单请求 + 不确定态 loading，不画假进度条）。
- App 端文件选择；导入历史记录页；供应商报价比对。
