### 1.1 后端

- `POST /mall-order/app/shopping-cart/batch` —— 批量加购
  - **部分成功语义**：逐项复用单条加购校验，单项失败只记录原因、不回滚已成功项。
  - **刻意不加 `@Transactional`**：否则任一项失败回滚整批，用户只能反复试错找出不可买的那一项。契约测试专门守这条。
  - 补 MOQ/步长校验，口径与共享购物车提交时的 `validateQuantityRules` 一致。
  - 包装资料远程失败时降级放行，不因装饰性规则打挂整批。
- `GET /mall-order/app/shared-cart/active-summary` —— 首页卡片聚合
  - 一次返回进行中购物车 + 项数 + 人数 + 估算合计 + 明细预览（最多 3 条 + 截断标记）。
  - 无进行中购物车返回零值（`cart = null`）而非抛异常，首页可渲染空态。
  - 商品域不可用时降级：仍返回项数与人数，只是缺商品名。

### 1.2 前端

- 新增装修组件 `replenish-card`（`src/components/diy/diy-replenish-card/`）
  - 可见性与船舶工作台同口径：未登录 / 无船 / 纯零售租户均不渲染。
  - 点击进共享购物车详情；「按单加购」进选货页（不直接下单式加购，避免绕过 MOQ 确认）。
- 四处注册同步：后端 `PageDesignComponentTypes`（含单例集合）、管理端 registry + 预览/设置面板 + fixtures、UniApp registry + `diy/index.vue` 静态分支 + 类型。
- 修正单例重复报错文案：原先硬编码「船舶工作台」，新增第二个单例组件后会误导运营，改为按类型映射（并补 2 例测试，含船舶工作台回归）。

### 1.3 当时刻意没做的事（**已经被 C1 推翻，见下**）

第一批时 `SharedCartSummaryVO` **不含** `plannedQuantity`，组件也不展示「已采 N 项 / 还差 X 件 / 进度条」。

原因：`approved_quantity` 与 `ITEM_CONFIRMED` 只在「确认人提交整船订单」这一次事务里写入（`SharedCartServiceImpl#applyApprovedQuantities`），收集阶段全部是 `ITEM_PENDING`，**没有"目标量 − 已采量"可算**。编一个只会是假的 0 或假进度条。

> **现状（2026-09-22 17:40 更新）**：该缺口已由提交 `4342b1b` 补齐 ——
> 77 号双模式脚本给 `shared_cart_item` 加了 `planned_quantity` /
> `fulfilled_quantity`，进度口径收敛到 `ReplenishProgressCalculator`，
> `active-summary` 已返回 `progress`，并新增 `PUT .../items/plan` 接口。
> 原契约测试 `replenish-contract.test.ts` 固化的旧约束已改写为新约束
> （进度必须来自真实计划量列、未设计划不得回落需求量）。
> **前端接入**已于同日完成：卡片展示真实进度条与「已采 N 项 · 还差 M 项」，
> 详情页支持确认人排计划/回填已采量，两处共用
> `aryn-mall-uniapp/src/utils/replenish-progress.ts` 的同一套口径。
> 剩余项（组件默认出现在首页、C2/C3/C4）见 [会话交接](会话交接.md) §3。
