# 积分抵扣商品范围竞品调研

> 调研问题：**「哪些商品可以使用积分抵现」应该在哪一层配置？**——现网（2026-10-24）悦航购没有商品级（SPU/SKU）「允许积分」设置，积分可用性由全局开关 + 订单场景 + 营销活动反向排除三层决定。本调研回答：同类竞品是怎么做的、现网设计是否不合理、若要补商品级控制该怎么做。
>
> 调研日期（访问日期）：**2026-10-24**
> 前置文档：[2026-10-23-营销优惠叠加规则调研/02-竞品规则调研.md](../2026-10-23-营销优惠叠加规则调研/02-竞品规则调研.md)（已覆盖「活动 × 券 × 积分」叠加矩阵，本文只聚焦**商品范围**维度，引用其结论时标注"10-23 调研"）
>
> 环境限制：本次会话 WebSearch/WebFetch 不可用；采用 DuckDuckGo HTML SERP + r.jina.ai 抓正文 + grep.app 公共代码索引。DDG 中途限流，mall4j / lilishop 未取得官方文档正文（见 §7 缺口）。

## 0. 结论先行（TL;DR）

1. **积分抵现的配置三件套（开关 + 兑换比例 + 单笔上限）在所有被调研系统中都是全局的**，没有任何一家头部 SaaS 或平台电商提供商品级「该商品可用积分」的正向开关。
2. 商品级控制只以三种形态真实存在：
   - **活动反向排除**（有赞/微盟/悦航购现网同款）：秒杀/新人价等活动把商品拉出积分基数；
   - **兑换选品**（有赞积分商城、CRMEB 积分商品、芋道 PointActivity）：商家选品做「纯积分/积分+差价」兑换，是独立购买路径而非抵扣；
   - **平台报名制**（淘宝淘金币，仅 D 级经验帖）：商家按商品报名、活动商品可屏蔽金币——未找到官方原文。
3. **「商品单独设置积分抵扣上限」在 CRMEB 是 2026-06 商家功能建议、至今仍在投票中未实现**（官方社区帖）——证明这是真实商家痛点（引流品薄利怕亏），但也说明头部开源同样没做。**悦航购现网口径（全局 + 活动排除 + 20% 上限）不落后于同类系统**，且活动级叠加开关比 CRMEB 更细。
4. 一个易混淆的对照：**发放侧（送积分）反而常见商品级**——CRMEB 商品编辑的营销设置里已有按商品的「赠送积分」字段；社区建议正是把「抵扣上限」也放到它旁边。即行业把「商品级」留给发放，把「抵扣范围」留给全局 + 活动。
5. 若悦航购要补：推荐**商品级三态字段（跟随全局 / 可用 / 不可用，默认跟随全局）**，在积分 eligible 判定链上加一层商品级否决与活动级 AND 组合；默认值必须「跟随全局」保证存量行为不变（见 §5）。

## 3. 竞品证据

### 3.1 有赞（A 级，2026-10-23 已核官方原文，本次复核引用）

- 积分抵现 = **全局插件配置**：`积分运营 → 修改积分消耗规则 → 积分抵现`，可设抵扣比例与**抵扣金额上限**（"每笔订单最多可使用积分抵扣金额"）。10-23 调研 §2.7。
- **官方文档与互斥表均未见「积分抵现商品范围 / 指定商品可用」配置项**；反向证据（官方 FAQ）甚至"会员折扣商品不叠加积分抵现"都无开关（10-23 调研 §2.7 反向证据条目）。
- 商品级控制的唯一出口：
  1. **活动反向排除**——互斥表中秒杀 × 积分抵现 = ❌（强制），拼团/限时折扣/满减送等 × 积分抵现 = 可配（活动级开关）；10-23 调研 §2.1；
  2. **积分商城（积分兑换）**——商家**选品**组成兑换商品，与积分抵现互斥（❌），是"另一条购买路径"；10-23 调研 §2.1 矩阵「积分商城」行。
- 结论：**有赞无商品级抵扣开关；商品维度 = 活动排除 + 兑换选品**。

### 3.2 微盟（A 级，2026-10-23 已核官方原文，本次复核引用）

- 积分被抽象为「下单可抵扣方式」（积分/余额/储值卡），开关挂在**券模板**（勾选才可与券同享）和**会员卡-商品折扣**（"叠加优惠 + 下单可抵扣方式"）上；10-23 调研 §3.1/§3.2。
- **券级/折扣级可配 ≠ 商品级**：配置对象是"这张券、这组商品折扣"，不是"这个商品可用积分"。官方帮助中心未见商品级积分开关（10-23 调研 §3.3 说明微盟无叠加总表，更未见商品范围条款）。
- 结论：微盟与有赞同构，**抵扣范围控制在"优惠对象"侧，不在商品侧**。

### 3.3 CRMEB（A 级官方文档 + A 级官方社区帖，本次新抓正文）

官方文档《积分配置》（doc.crmeb.com/pro_s/pro_v3_2/18341，访问 2026-10-24）配置项全文：

> **积分抵用开关**：开启/关闭，开启后下单时可以使用积分抵用订单余额；
> **积分抵用**：需设置积分抵用比例，即 1 积分可抵扣多少元；
> **积分抵扣上限**：最多抵扣积分（每笔订单可抵扣的积分上限）；最高抵扣比例（一笔订单最高可抵扣订单实付金额的百分比 0-100%）；
> **下单赠送积分**：按照订单的实际支付金额赠送积分；
> **积分有效期**：默认关闭，可按年/季/月清理。

——全部为**系统级全局配置，针对商城所有商品**，无商品范围项。

官方社区功能建议帖（crmeb.com/ask/thread/75617，发布 2026-06-04，状态"投票中"，访问 2026-10-24）原话：

> "积分抵扣上限的设置……**是针对商城所有商品的，无法做到精细化运营，像一些利润薄的引流品，用这里的规则抵扣积分就容易产生亏损**，有些利润高点的商品想让用户多用点积分却也无法做到，所以这里提个建议就是增加【商品单独设置积分抵扣上限】的功能……1、位置直接在添加商品中的营销设置里，**放在的赠送积分下面** 2、打开默认选择的是【使用系统积分抵扣规则】……"

三条关键信息：
1. CRMEB 抵扣口径与悦航购现网同构（全局开关 + 比例 + 双上限），**无商品级**；
2. 商家对「引流品被积分击穿毛利」的抱怨与本次需求动机完全一致——痛点真实但**至今未实现**（仍在投票）；
3. 帖子上下文证明 CRMEB 商品编辑页**已有按商品的「赠送积分」字段**（发放是商品级，抵扣是全局）——行业把商品级留给发放侧的又一例证。

### 3.4 芋道 ruoyi-vue-pro（B 级，公共代码索引命中官方仓库源码，本次新抓）

- 抵扣配置挂**会员域全局配置**：`MemberConfigRespDTO` 含 `pointTradeDeductEnable`（"启用积分折扣"）、`pointTradeDeductUnitPrice`（"1 积分抵扣多少金额（单位分）"）；交易侧由全局计价器 `TradePointUsePriceCalculator` 消费（源码：`yudao-module-mall/yudao-module-trade/src/test/.../TradePointUsePriceCalculatorTest.java`，经 grep.app 命中 master 分支源码片段）。
- 积分商品化走**积分商城活动选品**：promotion 模块 `PointActivityDO` + `PointProductDO` + `PointProductSaveReqVO`（活动 + 按商品设置积分价/差价，源码命中 `PointActivityServiceImpl` 引用链）。
- 商品 SPU 实体无「是否支持积分抵扣」字段。
- 结论：**与悦航购现网完全同构**（全局抵扣配置 + 兑换选品活动，无商品级开关）。

### 3.5 其他开源实现（C 级，grep.app 代码命中，本次新抓）

## 5. 共性规律与对悦航购的评估

### 5.1 规律（5 条）

1. **抵扣范围配置的行业标准 = 全局三件套（开关/比例/单笔上限），没有主流系统做商品级正向开关**；例外只有淘金币报名制（未证实）。
2. **商品级控制只存在于两条侧线**：活动反向排除（把商品拉出基数）与兑换选品（独立购买路径）——前者悦航购已有，后者悦航购没有（也无紧迫性）。
3. **发放与抵扣的配置粒度不对称**：发放（送积分）常见商品级（CRMEB 赠送积分字段），抵扣几乎都是全局——因为抵扣直接吃毛利、影响计价与分摊链路，行业选择用"上限 + 活动排除"控风险，而不是逐商品开关。
4. **"商品级抵扣上限"是被记录的真实需求但未被满足**（CRMEB 投票帖，2026-06 至今）：引流品/薄利品怕积分击穿毛利。悦航购用「活动排除 + 20% 上限」已部分覆盖同一风险。
5. 平台电商用**下单页试算兜底**解释商品例外（京东"以提交订单时是否可选择使用为准"）——不配置、以试算结果为准，值得在 C 端文案上对齐。

### 5.2 现网设计评价

**「找不到商品级积分设置」不是漏做，而是与行业主流一致的合理默认。**有赞/微盟/CRMEB/芋道四家（覆盖头部 SaaS 与头部开源）均无商品级抵扣开关；悦航购的活动级叠加开关（2026-10-24 刚落地的 `pointsStackable` 体系）甚至比 CRMEB 更细。若产品诉求升级为"按商品精细化控制积分"，则属于增强需求而非缺陷修复。

### 5.3 若要增强：三个方案（按投入递增，均为建议非决定）

| 方案 | 内容 | 依据 | 成本要点 |
|---|---|---|---|
| **A. 维持现状 + 透明化** | 不加商品级配置；把「本单商品不支持积分抵现」的 `pointsStackReason` 在 C 端确认页/商品行持续明示，客服口径引用活动规则 | 行业主流即如此；京东"试算兜底"文案惯例 | 零后端改动 |
| **B. 商品级三态开关（推荐）** | goods_spu（或 sku）加 `point_deduct_mode`：0=跟随全局 / 1=可用 / 2=不可用，默认 0；`orderPointsDeductHandler` 的 `pointsEligibleItems` 过滤链上叠加商品级否决（与 `plan.pointsStackable` 取 AND）；管理端放商品编辑「营销设置」；C 端原因文案复用 `pointsStackReason` | CRMEB 社区建议帖的同款位置与默认值设计（"使用系统积分抵扣规则"）；默认 0 保证存量订单行为零变化；双模式增量 SQL（boot/cloud 各一份 + 全量重生成） | 改动集中在计价过滤一处 + 商品表单一处；注意手写 XML 列清单同步（防静默漏列）；确认页 `pointsDeductMax` 随基数收敛的既有机制天然兼容 |
| **C. 商品级抵扣上限（二期可选）** | 在 B 之上支持按商品覆盖抵扣上限（比例或金额），替代全局 20% | CRMEB 商家原话诉求（引流品单独收紧、高毛利品放宽） | 计价上限取值需按明细聚合重算，复杂度显著高于 B；建议有真实运营案例后再做 |

不建议的方向：**白名单制（默认全部不可用、勾选才可用）**——无竞品先例，且存量在售商品会静默失去积分资格，引发客诉；默认值必须「跟随全局」。
