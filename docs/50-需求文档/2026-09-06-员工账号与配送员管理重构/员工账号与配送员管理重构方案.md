# 员工账号与配送员管理重构实施方案

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** 明确员工账号、配送员资料、配送资格和商城账号的边界，消除通用用户弹窗中直接分配配送员角色造成的歧义和半成品数据。

**Architecture:** 保留 `sys_user` 作为 ToB 员工登录账号，保留 `delivery_staff` 作为配送业务资料，保留 `user_info` 作为商城 ToC 账号。配送资格由配送员管理域统一授予和回收，商城账号绑定作为可选的免重复登录能力；第一阶段通过页面导航和后端保护完成职责收敛，避免新增跨服务分布式创建事务。

**Tech Stack:** Vue 3 + TypeScript + Element Plus + Vben UI；Spring Boot 3 + Spring Cloud Alibaba + Dubbo + MyBatis-Plus + Sa-Token；MySQL；Boot 单体和 Cloud 微服务双模式。

## 3. 核心产品结论

### 3.1 “配送员”不应继续出现在通用用户角色选择中

结论：不合理，应从通用用户新增/编辑弹窗中隐藏并由后端禁止普通角色接口直接修改。

原因：

1. 选择角色只会产生 `sys_user_role`，不会自动产生 `delivery_staff` 资料。
2. 员工可能拥有配送权限但没有配送资料，无法正常进入配送工作台。
3. 通用用户管理员不一定理解“配送资格”和“配送员资料”的区别。
4. 配送资格开通、停用、解绑、删除和配送会话撤销已经由配送员管理域负责，重复放在用户管理会产生两个事实来源。
5. 当前截图出现两个同名“配送员”，还暴露出角色数据重复或跨租户展示未正确收敛的问题。

通用用户弹窗只负责后台员工的基础角色；配送员角色 `delivery_staff` 由配送员管理的“开通配送资格”操作维护。

### 3.2 “员工管理”在当前系统中就是“系统设置 > 用户管理”

当前没有独立的员工管理模块。`/system/user` 页面管理的就是租户内 `sys_user` 员工账号，而商城消费者在用户业务域管理，两者不是同一类用户。

本期不新增第三套员工账号页面，统一将现有菜单和文案明确为“员工账号”：

```text
系统设置
├── 员工账号（原用户管理，路由保持 /system/user）
├── 部门管理
└── 角色管理
```

### 3.3 创建配送员的推荐流程

第一阶段采用两页衔接的流程：

```text
系统设置 > 员工账号
  -> 创建员工账号（不选择 delivery_staff）
  -> 返回配送管理

配送管理 > 配送员管理 > 新增配送员
  -> 选择员工账号
  -> 填写配送资料
  -> 开通配送资格
  -> 可选：绑定商城账号
```

商城账号绑定不是创建配送员资料的必要条件：

- 只使用独立配送端账号密码登录时，可以暂不绑定商城账号。
- 需要商城个人中心显示“配送工作台”并免重复登录时，必须绑定商城账号。

## 4. 目标权限模型

### 4.1 角色分类

| 分类 | 示例 | 管理位置 | 是否允许通用用户弹窗修改 |
|---|---|---|---|
| 平台/后台角色 | `ROLE_ADMIN`、运营角色、基础员工角色 | 系统设置 | 是，但受权限范围限制 |
| 配送资格角色 | `delivery_staff` | 配送员管理 | 否 |
| 菜单按钮权限 | `delivery:staff:qualification`、`delivery:staff:bind` | 角色管理/配送员管理 | 仅由授权管理员配置 |

`delivery_staff` 是系统管理的保护角色，不是普通后台角色。它至少包含 `delivery:execute`，用于配送端身份校验。

### 4.2 最低权限员工角色

当前用户新增接口要求至少选择一个角色。若某租户没有可用的最低权限员工角色，管理员容易被迫选择“超级管理员”或“配送员”，这是阻断问题。

方案要求：

1. 优先复用租户已有的最低权限员工角色。
2. 如果不存在，新增幂等角色“普通员工”，编码建议为 `ROLE_STAFF`，默认不授予管理菜单。
3. “普通员工”角色只用于满足员工账号的基础角色要求，不自动包含配送权限。
4. 不允许使用 `ROLE_ADMIN` 作为配送员员工账号的默认角色。

### 4.3 受保护角色的后端规则

UPMS 普通用户新增/编辑接口必须增加服务端保护：

- 新增请求包含 `delivery_staff` 角色时直接拒绝，并提示“请在配送员管理中开通配送资格”。
- 编辑请求不允许通过角色列表授予或回收 `delivery_staff`。
- 编辑普通字段时必须保留已有的受保护配送角色，不能因为前端隐藏复选框而被整体删除。
- 只有配送员资格接口和配送员向导可以调用 `changeRoleByCode(..., "delivery_staff", ...)`。
- `ROLE_ADMIN` 的全权限语义保持不变，但不能把它作为配送员的替代角色。

## 5. 目标业务流程

### 5.1 新员工且需要成为配送员

```text
管理员进入 系统设置 > 员工账号
  -> 新增员工
  -> 填写昵称、手机号、用户名、密码、部门、状态
  -> 选择“普通员工”或其他最低权限后台角色
  -> 保存

管理员进入 配送管理 > 配送员管理
  -> 新增配送员
  -> 第一步搜索并选择员工账号
  -> 第二步选择商城账号，或勾选“暂不绑定”
  -> 第三步填写配送资料
  -> 默认勾选“开通配送资格”
  -> 提交
```

结果：

- `sys_user`：员工账号存在且状态正常。
- `delivery_staff`：配送资料存在，`user_id` 指向员工账号。
- `sys_user_role`：由配送员向导异步授予 `delivery_staff`。
- `delivery_account_binding`：仅在选择商城账号时产生有效绑定。

### 5.2 已有员工转为配送员

```text
配送员管理 > 新增配送员
  -> 搜索员工账号
  -> 选择未关联配送资料的账号
  -> 填写配送资料
  -> 开通配送资格
```

如果员工已经拥有 `delivery_staff` 资格，向导显示“已开通配送权限”；如果已有配送资料，禁止重复选择。

### 5.3 绑定商城账号

绑定操作必须显式选择商城用户，不能以手机号自动授权：

```text
配送员资料 + sys_user
        |
        | 可选绑定
        v
商城 user_info
```

约束：

- 一个租户内一个商城用户最多一个有效配送员绑定。
- 一个员工账号原则上最多一个有效商城绑定。
- 已绑定其他配送员的商城账号不可覆盖绑定。
- 手机号不一致可以允许管理员确认后绑定，但必须记录审计日志。
- 解绑不删除员工账号、配送员资料和历史配送任务。

### 5.4 停用和删除

必须区分以下操作：

| 操作 | 影响 |
|---|---|
| 停用接单 | 不出现在默认派单候选中，可继续登录查看已有任务 |
| 停用配送资格 | 回收 `delivery_staff`，配送端入口和接口失效 |
| 解绑商城账号 | 商城个人中心不再显示配送工作台，员工和历史任务保留 |
| 删除配送员资料 | 解绑商城账号、回收资格、撤销配送会话，历史任务保留归属 |
| 停用员工账号 | 员工账号不可登录，配送守卫动态拒绝访问 |
| 删除员工账号 | 若仍有关联配送资料，必须先在配送员管理完成清理 |

## 7. 后端改造

### 7.1 UPMS 用户接口

保留现有路径，新增角色保护和员工删除检查：

| 方法 | 路径 | 改造 |
|---|---|---|
| GET | `/upms/user/page` | 返回员工账号摘要，可增加配送资格只读字段 |
| GET | `/upms/user/{id}` | 返回可编辑角色和受保护角色摘要 |
| POST | `/upms/user` | 拒绝客户端直接授予 `delivery_staff` |
| PUT | `/upms/user` | 保留受保护配送角色，不允许通用接口回收或授予 |
| DELETE | `/upms/user/{id}` | 有配送资料关联时拒绝删除 |

角色保护应放在服务端，不依赖前端过滤。`SysUserServiceImpl.updateUser` 不能继续采用“删除全部角色后按前端列表重建”的无保护逻辑；应将受保护角色从现有关联中取出并合并保存。

### 7.2 配送员接口

保留已有配送接口，并明确职责：

| 方法 | 路径 | 责任 |
|---|---|---|
| GET | `/mall-order/delivery/staff/onboard-sys-user-search` | 搜索可用员工账号 |
| POST | `/mall-order/delivery/staff/onboard` | 创建配送资料，可选绑定商城账号和开通资格 |
| PUT | `/mall-order/delivery/staff/{id}` | 仅编辑配送资料白名单字段 |
| PUT | `/mall-order/delivery/staff/{id}/binding` | 绑定商城账号 |
| DELETE | `/mall-order/delivery/staff/{id}/binding` | 解绑商城账号 |
| PUT | `/mall-order/delivery/staff/{id}/qualification` | 授予或回收配送资格 |
| PUT | `/mall-order/delivery/staff/{id}/availability` | 修改接单状态 |
| DELETE | `/mall-order/delivery/staff/{id}` | 联动清理配送员身份并逻辑删除资料 |

新增向导请求继续使用：

```json
{
  "userId": "sys-user-id",
  "staffName": "张三",
  "staffPhone": "13800000000",
  "vehicleInfo": "电动车",
  "mallUserId": "mall-user-id",
  "status": "3",
  "grantQualification": true
}
```

禁止新增客户端传入 `tenantId`、配送员身份主体或用于授权的手机号。

### 7.3 配送资格一致性

开通、停用、解绑、删除均必须继续使用现有可靠化机制：

- 本地资料变更和 outbox 写入在本地事务内完成。
- 资格授予/回收在提交后执行。
- 失败返回 `PROCESSING` 或进入补偿重试，不伪造成功。
- 资格变化推进 Redis 版本号，失效各实例缓存。
- 停用或解绑立即撤销存量配送会话。
- 配送访问守卫继续动态检查租户、员工状态、配送资料和 `delivery:execute`。

### 7.4 员工删除跨服务方案

推荐新增订单域远程检查契约，不让 UPMS 依赖 order-biz：

```java
public interface RemoteDeliveryAccountService {

    boolean hasActiveDeliveryStaff(String sysUserId);

}
```

UPMS 删除员工账号前调用该契约：

- Cloud：Dubbo 调用订单服务。
- Boot：本地 Bean 注入，仍走同一接口语义。
- 订单服务不可用时删除采用 fail-closed，返回“无法确认配送关联，请稍后重试”。

如果本期不实现远程删除检查，必须至少在管理端隐藏删除按钮并在发布说明中标记为上线阻断项，不能只依赖前端提示。

## 8. 数据库和初始化脚本

### 8.1 角色保护迁移

新增递增脚本，Boot 和 Cloud 各一份，例如：

```text
aryn-mall-java/db/boot/37employee_role_scope.sql
aryn-mall-java/db/cloud/37employee_role_scope.sql
```

脚本要求：

1. 幂等创建每个租户的 `ROLE_STAFF`“普通员工”角色，默认不绑定管理菜单。
2. 为 `delivery_staff` 角色补齐唯一的角色编码约束或一致性检查。
3. 不物理删除历史角色和用户角色关联。
4. 对同一租户重复的 `delivery_staff` 角色先输出预检查结果。
5. 由管理员确认后，保留稳定角色 ID，其他重复角色及其菜单/用户关联做逻辑迁移和逻辑删除。
6. 迁移过程必须记录受影响租户、角色和员工账号数量。

禁止在迁移脚本中直接 `DROP`、`TRUNCATE` 或无条件物理删除存量数据。

### 8.2 Boot/Cloud 同步

涉及数据库脚本时必须同时完成：

- Boot 增量 SQL。
- Cloud 增量 SQL。
- Boot `build-full-sql.mjs` 的 `sections` 登记。
- 重新生成 `aryn_boot_full.sql`。
- Cloud 如修改租户表、角色菜单或 Nacos 配置，补齐对应基线和摘要。

如果本期只调整页面和服务端校验、不增加表结构，则仍需确认已有 `delivery_staff`、`delivery_account_binding`、`delivery_qualification_operation` 在 Boot/Cloud 的租户配置一致。

## 9. API 和模式兼容要求

### 9.1 管理端路径

管理端现有配送 API 使用 `/mall-order/delivery/**`，员工账号 API 使用 `/upms/user/**`。新增或修改请求必须继续遵循：

- Cloud 模式首段为有效微服务域。
- Boot 模式通过统一 `rewriteBootUrl` 改写，不在页面硬编码 `/boot`。
- 不读取 `VITE_OPEN_BOOT` 后自行拼接路径。
- 用户管理跳转只改变前端菜单文案和路由，不改变后端服务域。

### 9.2 Boot/Cloud 行为一致性

两种模式必须具有相同业务结果：

| 场景 | Boot | Cloud |
|---|---|---|
| 创建员工账号 | 本地 UPMS | UPMS 服务 |
| 搜索员工账号 | 本地订单/UPMS 调用 | Dubbo 调用 UPMS |
| 创建配送资料 | 本地订单服务 | 订单微服务 |
| 授予配送资格 | 本地 outbox + UPMS | 订单 outbox + Dubbo UPMS |
| 删除员工保护 | 本地远程接口实现 | Dubbo 远程接口 |
| 商城账号绑定 | 本地用户服务 | Dubbo 用户服务 |

## 10. 分阶段实施任务

### Phase 0：数据和权限盘点

1. 查询每个租户的角色清单，确认是否存在“普通员工”角色。
2. 查询 `role_code = delivery_staff` 的重复角色。
3. 查询 `sys_user_role` 中拥有配送角色但没有 `delivery_staff` 资料的账号。
4. 查询有 `delivery_staff` 资料但没有有效配送资格的账号。
5. 查询员工账号和商城账号的重复有效绑定。
6. 形成迁移预检报告，人工确认后再执行角色清理。

验收：所有异常数量可追溯，未执行破坏性清理。

### Phase 1：通用用户管理收口

1. 新增或确认最低权限“普通员工”角色。
2. 前端角色列表过滤 `delivery_staff`。
3. 后端新增/编辑接口拒绝直接修改 `delivery_staff`。
4. 编辑用户时保留受保护配送角色。
5. 用户列表增加配送资格只读摘要。
6. 员工账号删除增加配送关联检查。
7. 菜单标题、页面标题、字段文案统一为“员工账号”。

验收：用户管理不能新授予或误回收配送资格；普通员工可以安全创建。

### Phase 2：配送员向导和导航修正

1. 修正“员工管理”错误文案。
2. 增加“去创建员工账号”入口。
3. 返回向导后重新加载员工账号。
4. 明确商城账号绑定为可选步骤。
5. 保持资格开通、解绑、停用、删除的独立操作。
6. 列表和详情增加员工账号、商城账号、资格状态的清晰展示。

验收：管理员不查文档也能理解从哪里创建员工账号、哪里开通配送资格、何时绑定商城账号。

### Phase 3：数据修复和兼容验证

1. 执行角色重复预检。
2. 迁移重复角色关联，保留历史审计信息。
3. 修复只有配送角色没有配送资料的历史账号。
4. 修复配送资料和商城绑定不一致的数据。
5. 重新生成 Boot 全量 SQL。
6. 验证 Cloud Nacos 租户配置和摘要。

验收：历史账号不会因前端隐藏角色而失去合法配送资格；异常数据均有处理记录。

### Phase 4：可选的向导内创建员工账号

本期不作为上线前置功能。后续如需减少页面跳转，再单独设计：

- 向导第一步增加“创建配送员员工账号”。
- 账号创建仍由 UPMS 负责，订单域通过 API 调用，不直接 import UPMS 实现。
- Cloud 模式不能假设 UPMS 和订单数据库共享本地事务。
- 账号创建成功后再创建配送资料；失败时使用补偿任务或明确的待完善状态。
- 不在一个未定义的分布式事务中同时声称“账号、资格、绑定全部成功”。

## 13. 风险与回滚

| 风险 | 处理 |
|---|---|
| 隐藏角色导致编辑时误删配送资格 | 后端合并受保护角色；前端只做展示过滤 |
| 没有最低权限员工角色 | 先补齐 `ROLE_STAFF`，禁止用超级管理员替代 |
| 角色重复导致重复显示或权限漂移 | 先预检，再逻辑迁移，不直接物理删除 |
| Cloud 跨服务删除检查失败 | fail-closed，禁止删除，不返回“删除成功” |
| 员工账号删除后配送资料孤儿化 | UPMS 删除前远程检查，配送域负责最终清理 |
| 资格授予远程失败 | 使用现有 outbox 和补偿任务，状态展示 `PROCESSING` |
| Boot/Cloud SQL 不一致 | 双脚本、Boot 全量重建、Cloud 基线和摘要同步 |
| 管理员误把商城账号当员工账号 | 文案统一使用“商城账号”和“员工账号”，表单分域展示 |

回滚原则：

- 页面文案和角色过滤可独立回滚。
- 后端保护上线前必须先完成历史异常盘点。
- 数据迁移脚本只允许幂等和可审计的逻辑操作，不提供无条件回滚删除。
- 任何资格回收失败都保留 outbox 记录，不通过回滚掩盖失败。

## 14. 最终操作说明

上线后的管理员操作应当是：

```text
新员工要做配送员：
1. 系统设置 > 员工账号 > 新增员工账号
2. 选择普通员工/最低权限角色
3. 配送管理 > 配送员管理 > 新增配送员
4. 选择该员工账号并填写配送资料
5. 开通配送资格
6. 按需绑定商城账号
```

一句话规则：

> 用户管理创建“人和登录账号”，配送员管理创建“配送身份和资格”，商城账号绑定决定是否能从商城个人中心进入配送工作台。
