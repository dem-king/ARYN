# 02 身份与资格模型

## 1. 三种购买场景

系统已有 `PurchaseSceneEnum`，直接沿用，不新增枚举：

| code | 含义 | 订单入口 | 配送方式 |
| --- | --- | --- | --- |
| 1 | 海员个人购买 | 普通商详/购物车/结算 | 快递、自提、岸上地址 |
| 2 | 船供采购 | 船舶上下文、船供共享车 | `deliveryWay=4` 公司配送到船 |
| 3 | 企业采购 | 岸上企业共享车（`cart_type=2`） | `deliveryWay=3` 公司配送岸上 |

说明：

- 场景是**订单属性**，不是账号属性；同一账号可以下三种单。
- 商品级 `sale_scope` 与订单级 `purchase_scene` 独立；一个 SKU 可以同时支持个人和船供。
- 普通岸上地址下单，服务端会归一为 `purchaseScene=1`；只有岸上共享车导入才会落 3。
- 企业采购不要在 C 端做「手动切换场景」，避免个人用户随便选企业场景；入口固定在岸上共享车。

## 2. 三种主体键

| 场景 | 主体 | 主体键 | 资格查询 |
| --- | --- | --- | --- |
| 个人 | 用户 | `tenant_id + user_id` | 本租户内 `purchase_scene=1` 的已支付订单数 = 0，且注册在 30 天内 |
| 船供 | 船舶 | `tenant_id + vessel_id` | 本租户内该 `vessel_id` 的 `purchase_scene=2` 已支付订单数 = 0 |
| 企业 | 采购主体 | `tenant_id + buyer_org_id` | 本租户内该 `buyer_org_id` 的 `purchase_scene=3` 已支付订单数 = 0，且主体审核通过 |

三个主体键互不影响：

- 采购员下了船供单，不消耗他的个人新人资格（个人只看 scene=1）。
- 采购员个人下单，不消耗船/工厂首单资格。
- 一个业务员帮 A 船、B 船下单，两船各自算首单，不按业务员账号串。
- 一个采购员管 A 厂、B 厂，两厂各自算首单。

## 3. 船舶身份（现有，需补两块）

### 现有

- `VesselMember`：`vesselId`、`userId`、`memberRole`、`canEdit`、`canConfirm`、`status`、`bindSource`。
- 角色：1 发起人/船长授权、2 普通船员、3 采购确认人、4 业务员。
- `RemoteVesselService.isVesselMember(tenant, vesselId, userId)` 和 `getVesselMemberRole` 已可用。
- `DeliveryContextValidator` 已校验「在船成员 + 靠港有效 + 靠港与船匹配」。

### 要补

1. **`/vessel/app/my-vessels` 返回角色和权限**：现在返回 `VesselInfo`，没有 `memberRole/canEdit/canConfirm`，前端只能知道「是成员」，不能区分船长/采购确认人/普通船员。
   - 建议新增 `VesselMembershipVO`（船舶字段 + `memberRole` + `canEdit` + `canConfirm` + `status`），只加字段，不改原结构。
2. **船供提交权限**：
   - `DeliveryContextValidator.validate` 增加 `purchaseScene` 入参；当 `scene=2` 时，除 `isVesselMember` 外还要 `canConfirm=1`。
   - `canConfirm` 以 `vessel_member.can_confirm` 列为唯一权威（`RemoteVesselService.canConfirmSupply`），不按角色硬编码：发起人(1)/采购确认人(3)/业务员(4) 默认置 1（与共享车 `VESSEL_MANAGER_ROLES`、成员管理 `MEMBER_ADMIN_ROLES` 同口径），普通船员(2)为 0。历史行由 233/248 脚本回填。
   - 个人到船订单（`scene=1` + `deliveryWay=4`）仍只校验在船成员，普通船员可以给自己买。
3. **职责**：
   - 船长/发起人：建车、邀请成员、指定确认人。
   - 采购确认人：核定数量、提交整船订单。
   - 普通船员：个人自购、参与共享车加购，不单独提交船供单。
   - 业务员：可代船员建车/提交，但资格仍挂船。

## 4. 企业/工厂身份（新增，自助绑定）

> **2026-11-14 调整**：绑定全流程免平台审核，创建主体不采集营业执照与信用代码。
> 创建即 `audit_status=1`；搜索加入即成为采购员（`can_confirm=0`）。
> `audit_status=0` 仅存量数据保留，新流程不再产生。

### 4.1 入口

小程序「我的」→「我的工厂/企业」，和「我的船舶」并列；岸上共享车创建时，如果当前用户没有绑定工厂，也给出「去绑定工厂」入口。

### 4.2 三条绑定通道

```text
用户进入「我的工厂」
├─ 搜索工厂（仅按名称）
│   ├─ 已存在 → 直接加入 → 成为采购员（can_confirm=0）
│   └─ 不存在 → 创建工厂 → 填名称、类型、地址、联系人 → 立即通过 → 成为厂长
├─ 扫同事邀请码 / 分享卡 → 加入（免审）
└─ 已绑定 → 切换当前工厂、管理成员、发起岸上企业车
```

### 4.3 状态机

**工厂主体 `buyer_org.audit_status`**

| 状态 | 含义 | 可做什么 |
| --- | --- | --- |
| 0 待审核 | 用户已提交创建 | 可查看、可下企业单，但不享首单 |
| 1 已通过 | 运营审核通过 | 可享首单、可邀请成员、可建岸上车 |
| 2 已驳回 | 资料不合格 | 可修改重新提交；不享首单 |
| 3 已停用 | 运营停用/工厂注销 | 不可新建岸上车；历史订单保留 |

**成员 `buyer_org_member.status`**

| 状态 | 含义 |
| --- | --- |
| 1 正常 | 在厂/在职，可按角色操作 |
| 0 已移除 | 离职/解绑；历史订单快照不变 |

**申请 `buyer_org_apply.status`**

| 状态 | 含义 |
| --- | --- |
| 1 待审核 | 已提交创建或加入申请 |
| 2 已通过 | 已建主体或已入成员 |
| 3 已驳回 | 资料不符/重复主体 |
| 4 已取消 | 申请人撤回 |

### 4.4 角色与权限

| 角色 | code | 建车 | 加购/改数 | 确认提交 | 邀请成员 | 维护地址 | 查看订单 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 厂长/管理员 | 1 | 是 | 是 | 是 | 是 | 是 | 是 |
| 采购员 | 2 | 是 | 是 | 看 `canConfirm` | 否 | 否 | 是 |
| 业务员 | 3 | 是 | 是 | 看 `canConfirm` | 是 | 否 | 是 |
| 查看者 | 4 | 否 | 否 | 否 | 否 | 否 | 是 |

落地时不要只看角色，统一看 `canEdit` / `canConfirm`，和船舶成员保持同一套判断。

### 4.5 防伪造（2026-11-14 免审核后口径）

- 不再采集 `credit_code` 与营业执照；`credit_code` 唯一索引保留，但只在填了才生效（NULL 不冲突）。
- 判重改为「名称归一化 + 地址 + 手机号」模糊命中时提示「可能已存在，去申请加入」，不硬拦。
- 一个用户最多创建 3 个工厂主体，防止批量造壳。
- 搜索加入默认采购员且 `can_confirm=0`：能加购改数、不能提交整单；确认权由厂长单独授予。
- 邀请码设有效期和最大使用次数；成员加入留 `bind_source`、`apply_id`。
- 首单权益不再与 `audit_status` 绑定，改由运营发放（见 `2026-11-14-采购主体自助化`）。

## 5. 首单资格规则

### 5.1 个人

- 条件：`tenant + userId`，`purchase_scene=1` 已支付订单数 = 0，注册在 `registerWithinDays` 天内。
- 现有 `checkNewbieEligibility` 只按用户全量订单，需改成按场景过滤；否则采购员下过船供单会丢掉个人新人资格。
- 返回原因：`ELIGIBLE`、`ALREADY_PAID`、`REGISTER_TIMEOUT`、`PARAM_INVALID`、`ERROR`。

### 5.2 船供

- 条件：`tenant + vesselId`，`purchase_scene=2` 已支付订单数 = 0；下单人 `canConfirm=1`；船在营；靠港有效。
- 返回原因：`ELIGIBLE`、`ALREADY_ORDERED`、`NOT_MEMBER`、`NO_PERMISSION`、`NO_VESSEL`、`NO_CALL`、`ERROR`。
- 首单权益：订单级满减/免运，按船一次；实际档位满 1000 减 100、满 3000 减 400、满 5000 减 800，单笔封顶 800（228/240 种子，可配置）。
- 新船礼包（P2）：固定组合（米/油/蛋/奶/纸品）整包一口价，按船一次，和满减二选一。

### 5.3 企业

- 条件：`tenant + buyerOrgId`，`purchase_scene=3` 且**下单时主体已审核通过**（`buyer_org_audit_status=1` 快照）的已支付订单数 = 0；`buyer_org.audit_status=1`；下单人是该主体成员且有 `canConfirm`。
- 返回原因：`ELIGIBLE`、`ALREADY_ORDERED`、`ORG_NOT_VERIFIED`、`ORG_REJECTED`、`NOT_MEMBER`、`NO_PERMISSION`、`ERROR`。
- 首单权益：订单级满减/免运，按工厂一次；档位同船供（228/240 种子，可配置）。
- 工厂多餐厅：按工厂算一次；餐厅作为主体下的收货点/部门，不单独算首单。
- **待审核期间下的单不消耗首单**：下单时服务端把主体审核状态快照进 `order_info.buyer_org_audit_status`，首单统计只算快照=1 的已支付单。否则「待审核可下单」与「审核通过后享首单」互相打架——工厂待审核时付了一单，审核通过反而失去首单。

### 5.4 已支付口径

- 只统计 `pay_status=1` 的订单；**付过款即消耗资格（含后续退款）**，`pay_status` 是由支付回调/确认收款推进的单向状态，退款不回退。未支付、已取消、超时关闭不计。
- 全额退款**不恢复**首单资格，防「下单-退款-再领」。
- 部分退款不恢复。
- 企业单另要求下单时主体审核状态快照=1（见 5.3）；历史无主体订单不参与。
- 货到付款订单在「确认收货/收款」后算已支付；具体以订单状态为准。

## 6. 权益与锁

### 6.1 权益形式

- 个人：保留 type 9 新人价，`purchase_scene=1`。
- 船供/企业：复用 type 7 `TYPE_SHIP_WHOLE_DISCOUNT`，`rules.tiers` 配订单级满减；`purchase_scene=2/3`。
- type 7 现有活动 503 已配过 500/30、1000/80、2000/200，说明订单级链路可用。
- 首单活动加规则：

```json
{
  "firstOrderOnly": true,
  "subjectType": "1",
  "tiers": [
    { "minAmount": 1000, "discountAmount": 100 },
    { "minAmount": 3000, "discountAmount": 400 },
    { "minAmount": 5000, "discountAmount": 800 }
  ],
  "monthlyBudget": 50000,
  "maxDiscountAmount": 800
}
```

企业侧 `subjectType` 用 `"2"`（1=船，2=采购主体），月预算 10 万。实际种子以 228/240 为准。

### 6.2 锁

- 现在 `PromotionLockUsage.countUserLocks` 按 `userId`，不能用于按船/按工厂。
- `PromotionLock` 增加 `subjectType`、`subjectId`（vesselId 或 buyerOrgId），并加索引：

```text
(tenant_id, activity_id, subject_type, subject_id, status)
```

- 资格查询 + 下单锁定两层：
  - 试算前按主体查已支付订单数，不满足直接不参与活动；
  - 下单时按主体加 Redis 锁/DB 锁，防并发两个首单同时通过。
- 锁记录随订单取消/关闭释放；已支付不释放。

## 7. 页面分流规则

新人专享页顶部用三段式 tab，不按账号写死类型：

| 用户能力 | 默认 tab | 可见 tab |
| --- | --- | --- |
| 普通个人，无船无厂 | 个人自购 | 个人 |
| 在船成员，`canConfirm=1` | 船上采购 | 个人、船上采购 |
| 在船普通船员 | 个人自购 | 个人；船上采购置灰/引导绑定 |
| 工厂成员，审核通过 | 企业采购 | 个人、企业采购 |
| 工厂成员，待审核 | 企业采购 | 个人、企业采购（首单卡显示审核中） |
| 同时有船有厂 | 最近一次下单场景 | 三段全显示，可手动切 |

页面文案：

- 个人 tab：现价、`省¥X · 限 N 件`、`每款首件享新人价，超出按销售价`。
- 船供 tab：`新船首单 · 满 ¥1000 减 ¥100 起`、`按船限一次`、`去发起船上采购`（档位从活动 tiers 读取，不硬编码）。
- 企业 tab：`企业首单 · 满 ¥1000 减 ¥100 起`、`按工厂限一次`、`去合并采购`（档位从活动 tiers 读取，不硬编码）。
- B2B tab 不出现「限 1 件」的鸡蛋；避免让采购员误以为只能买 1 件。

## 8. 与账号标签的关系

可以给用户展示一个「当前身份」标签，但只作为 UI 默认值：

- 标签由能力实时计算，不落库为唯一账号类型。
- 用户换船、离职、换工厂，标签自动变。
- 权限判断永远回到 `purchaseScene + deliveryWay + vesselId/buyerOrgId + 成员权限`，不看标签。
