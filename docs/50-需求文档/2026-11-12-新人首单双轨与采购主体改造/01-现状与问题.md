## 2. 为什么「每人每款限 1 件」不适合船供/企业

### 错位一：限购与批量采购冲突

船上补给是「鸡蛋 10 盒、米 20 袋、土豆 50 斤」的批量采购。现在第 1 件新人价、第 2 件起恢复售价，会出现：

- 采购员对账要拆行，同一 SKU 两个单价；
- 整单让利很小，16 款各买 1 件也就省七八十元，对几百上千的补给没感知；
- 后端发布校验把 `limitPerUser` 固定为 1，想按船供放开到 5 件/10 件，规则层不支持。

### 错位二：「新人」的颗粒度不对

- 现在资格按 `userId`：未成功支付过订单 + 注册 30 天内。
- 船供真实主体是船：换采购员、一个公司多条船账号，会出现「老船算新人」「新船不算新人」。
- 企业真实主体是工厂/餐厅：采购员换人、一个采购员管多个工厂，按账号算都会失真。
- 开小号可以重复领，B 端反而更难防。

### 错位三：首单考核点不对

船供/企业首单看的是：

- 首单金额、首单品类结构；
- 30/60/90 天复购；
- 配送时效、靠港窗口匹配；
- 账期、发票、对公付款。

单品一口价解决不了这些，反而让采购员把注意力放在「怎么拆单凑 1 件」。

## 3. 租户不是企业买家

这是本轮讨论最容易混淆的点：

- `tenant_id` 是 SaaS 商城/运营方，所有表都带，MyBatis 自动隔离；它回答「这单在哪个商城下的」。
- 一个租户下面可以有海员个人、船、工厂餐厅三类买家。
- 企业/工厂餐厅是租户下的**采购主体**，不是租户本身。
- 按租户算企业首单，等于把全平台所有工厂当成一家：第一家下过单，其他家全部失去资格。

所以正式做法是：

```text
租户 tenant_id（哪个商城）
├─ 个人 userId
├─ 船供 vessel_id
└─ 企业 buyer_org_id（工厂/餐厅）
```

首单键：

| 场景 | 主体键 |
| --- | --- |
| 个人 | `tenant_id + user_id + purchase_scene=1` |
| 船供 | `tenant_id + vessel_id + purchase_scene=2` |
| 企业 | `tenant_id + buyer_org_id + purchase_scene=3` |

## 4. 现有代码能力与缺口

### 已经有的能力

| 能力 | 现状 | 可复用点 |
| --- | --- | --- |
| 购买场景 | `PurchaseSceneEnum`：1 个人 / 2 船供 / 3 企业；`OrderInfo`、`ShoppingCart`、`OrderItem`、`DeliveryTask`、`PromotionContextDTO` 都带 `purchaseScene` | 场景分流、活动过滤、订单快照 |
| 船供配送校验 | `DeliveryContextValidator` 在 `deliveryWay=4` 时校验船舶必填、靠港计划有效、用户是在船成员 | 船供身份校验基础 |
| 船舶成员 | `VesselMember`：1 发起人/船长授权、2 普通船员、3 采购确认人、4 业务员；带 `canEdit` / `canConfirm` | 工厂成员角色照此设计 |
| 船舶自助绑定 | `VesselBindApply`、`VesselInviteCode`、`bindSource`、审核状态 | 工厂自助绑定照此设计 |
| 岸上企业车 | `SharedCart.CART_TYPE_SHORE=2`：绑发起人地址、`deliveryWay=3`、提交生成 `purchaseScene=3` | 企业采购唯一入口 |
| 订单级满减 | `PromotionActivity.TYPE_SHIP_WHOLE_DISCOUNT=7`，`rules.tiers[{minAmount,discountAmount}]`；已有活动 503 配过 500/30、1000/80、2000/200 | 船供/企业首单可直接复用 |
| 新人资格 | `RemoteBuyerProfileService.checkNewbieEligibility(tenant,userId,days)` | 个人资格保留，新增船/企业资格 |
| 营销锁 | `PromotionLock` 按 `tenant + user + activity` 计数 | 需要扩船/企业主体维度 |

### 必须补的缺口

| 缺口 | 现状 | 影响 |
| --- | --- | --- |
| 新人活动未限定场景 | 活动 `purchase_scene` 为空，引擎不按场景过滤 | 个人新人价可能漏到船供/企业订单，P0 先修 |
| 新人资格只按用户 | `checkNewbieEligibility` 只看 `userId` | 船供/企业无法按船/工厂判定 |
| 企业无主体字段 | `shared_cart` 只有 `ownerUserId + 地址`；`order_info` 只有 `tenantId + scene=3` | 工厂无法识别，首单无法按工厂算 |
| 岸上车去重按发起人 | `uk_shared_cart_shore_active` 用 `shore_active_owner` | 一个采购员管两个工厂时只能开一张车 |
| `my-vessels` 不带角色 | 接口返回 `VesselInfo`，没有 `memberRole/canEdit/canConfirm` | 前端无法区分船长/采购确认人/普通船员 |
| 船供提交只校验在船 | `DeliveryContextValidator` 只 `isVesselMember`，不看 `canConfirm` | 普通船员理论上可提交船供单 |
| 首单锁按用户 | `PromotionLockUsage.countUserLocks` 按 `userId` | 业务员代下单会把多条船的首单串在一起 |
| 企业车 UI 无主体 | 创建弹层只选地址 | 采购员无法选择工厂 |
