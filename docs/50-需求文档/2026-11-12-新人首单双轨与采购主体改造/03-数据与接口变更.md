## 2. 现有表变更

### 2.1 `shared_cart`

新增：

```sql
ALTER TABLE `shared_cart`
  ADD COLUMN `buyer_org_id` varchar(32) NULL COMMENT '采购主体ID（岸上企业车必填；船供车为空）',
  ADD COLUMN `buyer_org_name` varchar(200) NULL COMMENT '采购主体名称快照';
```

去重键调整（关键）：

当前：

```text
shore_active_owner = CASE WHEN cart_type='2' AND status='2' AND del_flag='0'
                          THEN owner_user_id ELSE NULL END
UNIQUE uk_shared_cart_shore_active (tenant_id, shore_active_owner)
```

问题：一个采购员管两个工厂时，第二家工厂开不了收集中车。改为：

```sql
-- 1) 先加列
ALTER TABLE `shared_cart`
  ADD COLUMN `buyer_org_id` varchar(32) NULL,
  ADD COLUMN `buyer_org_name` varchar(200) NULL;

-- 2) 去掉旧索引和旧生成列
ALTER TABLE `shared_cart` DROP INDEX `uk_shared_cart_shore_active`;
ALTER TABLE `shared_cart` DROP COLUMN `shore_active_owner`;

-- 3) 新生成列：岸上 + 收集中 + 未删除时，按“发起人 + 采购主体”去重
ALTER TABLE `shared_cart`
  ADD COLUMN `shore_active_scope` varchar(80)
  GENERATED ALWAYS AS (
    CASE WHEN `cart_type` = '2' AND `status` = '2' AND `del_flag` = '0'
         THEN CONCAT(`owner_user_id`, ':', COALESCE(`buyer_org_id`, ''))
         ELSE NULL END
  ) STORED;

-- 4) 新唯一索引
ALTER TABLE `shared_cart`
  ADD UNIQUE KEY `uk_shared_cart_shore_scope` (`tenant_id`, `shore_active_scope`);
```

兼容：

- 历史岸上车 `buyer_org_id` 为 NULL，生成键为 `owner_user_id:`，仍是一人一张，不阻塞历史数据。
- 新建岸上车必须带 `buyer_org_id`，同一发起人可在不同工厂各开一张收集中车。
- 回滚：删新索引/新列，恢复 `shore_active_owner` 与旧索引（见 05 文档）。

### 2.2 `order_info`

新增：

```sql
ALTER TABLE `order_info`
  ADD COLUMN `buyer_org_id` varchar(32) NULL COMMENT '采购主体ID（企业采购快照）',
  ADD COLUMN `buyer_org_name` varchar(200) NULL COMMENT '采购主体名称快照',
  ADD COLUMN `buyer_org_credit_code` varchar(32) NULL COMMENT '统一社会信用代码快照',
  ADD COLUMN `buyer_org_audit_status` char(1) NULL COMMENT '下单时主体审核状态快照（233/248 追加）；首单消耗只统计=1';

CREATE INDEX `idx_order_buyer_org`
  ON `order_info` (`tenant_id`, `buyer_org_id`, `purchase_scene`, `pay_status`);
```

说明：

- `order_info` 已有 `tenant_id`、`purchase_scene`、`vessel_id`、`vessel_name`、`vessel_call_id`。
- `buyer_org_audit_status` 由服务端在下单时按主体档案写入（客户端不可传）；企业首单统计只算快照=1 的已支付单，待审核期间支付不烧首单。
- `order_item`、`PromotionSnapshot` 不需要主体字段；订单级快照足够。
- `purchase_scene` 注释补 3（企业采购），现有 `PurchaseSceneEnum` 已支持。

### 2.3 `promotion_lock`

新增：

```sql
ALTER TABLE `promotion_lock`
  ADD COLUMN `subject_type` varchar(16) NULL COMMENT '首单主体：vessel / buyerOrg；普通锁为空',
  ADD COLUMN `subject_id` varchar(32) NULL COMMENT '船舶ID或采购主体ID';

CREATE INDEX `idx_promotion_lock_subject`
  ON `promotion_lock` (`tenant_id`, `activity_id`, `subject_type`, `subject_id`, `status`);
```

用途：

- 现有 `countUserLocks` 仍按 `userId`，个人新人价不变。
- 首单活动用 `countSubjectLocks(tenant, activityId, subjectType, subjectId)`。
- 下单时按主体加锁，防并发两单都过首单校验。

### 2.4 `promotion_activity`

不改表结构，改数据。**分两步，不能合并到 P0 一次执行**：

**P0（脚本 227）：只修个人新人活动场景**

```sql
-- 个人新人价只作用于个人场景（当前为空，会漏到船供/企业）
UPDATE `promotion_activity`
SET `purchase_scene` = '1', `update_time` = NOW()
WHERE `id` = '3170000000000000501';
```

**P1（脚本 228，已实施）：`firstOrderOnly` 引擎上线后插入首单活动**

```sql
-- 船供首单礼（type=7 整船优惠；purchase_scene=2）
-- 企业首单礼（type=7 整船优惠；purchase_scene=3）
```

`rules` 示例：

```json
{
  "firstOrderOnly": true,
  "subjectType": "1",
  "tiers": [
    { "minAmount": 1000, "discountAmount": 100 },
    { "minAmount": 3000, "discountAmount": 400 },
    { "minAmount": 5000, "discountAmount": 800 }
  ],
  "monthlyBudget": 50000,
  "maxDiscountAmount": 800
}
```

企业侧 `subjectType` 改为 `"2"`，月预算 10 万。实际种子以 `228/240` 为准；早期文档里的 300/500 档位未采用。

> 重要：P0 阶段促销引擎不认识 `firstOrderOnly`，提前插入会把 type 7 当成普通整船满减。P1 引擎已上线，228 已在 boot 库执行两遍；cloud 240 需在 237/145/157/185 之后执行。
>
> 2026-11-13 起种子默认**草稿**（`status=1`、`publish_time=NULL`）：全租户直接发布有预算风险，由运营按租户确认档位/预算后手动发布。`INSERT IGNORE` 只插不更，重复执行不覆盖运营调整；已按旧版脚本发布的环境保持原状态，脚本不回改。

## 5. 促销引擎改造

### 5.1 上下文

`PromotionContextDTO` 增加：

```java
@Schema(description = "采购主体ID（企业采购）")
private String buyerOrgId;
```

`purchaseScene` 注释改为 1 个人 / 2 船供 / 3 企业。

### 5.2 活动过滤

在 `PromotionEngineServiceImpl.calculate` 前，对 type 7 活动增加：

```text
rules.firstOrderOnly == true
  → 按 subjectType 调资格接口
  → 不满足则跳过该活动
```

缓存粒度：

- `tenant + subjectType + subjectId` 在单次试算内缓存；
- 资格异常按不满足处理（fail-closed），不阻断下单，只是不享受首单。

### 5.3 锁

`PromotionLockUsage` 增加：

```java
long countSubjectLocks(String tenantId, String activityId, String subjectType, String subjectId);
```

`PromotionReservationServiceImpl` 下单锁：

- 首单活动按 `subjectType + subjectId` 加锁；
- 非首单活动仍按 `userId`；
- 订单取消/关闭释放，已支付保留。

### 5.4 兼容

- `firstOrderOnly` 默认 false；存量 type 7 活动行为不变。
- `subjectType` 为空时按用户锁，保持旧行为。
- 现有活动 503（500/30、1000/80、2000/200）只作为配置参考，不复活；新建长期首单活动。

| 历史岸上车 `buyer_org_id` 为空 | 保留可查看/可提交；订单主体为空；不参与首单；页面显示「历史主体未绑定」 |
| 历史企业订单无主体 | 不回溯；首单统计只统计 `buyer_org_id` 非空的订单 |
| 待审核期间下的企业单 | 快照 `buyer_org_audit_status=0`，支付后也不消耗首单；审核通过后首单仍可享 |
| 233 上线前的窗口期企业单 | 快照为 NULL，不消耗首单（宁宽勿烧；窗口仅存在于未升级环境） |
| 历史个人订单 `purchase_scene` 为空 | 保持；新订单归一为 1；资格查询按 `purchase_scene=1` 或空值兼容 |
| 历史船供订单 | 已有 `vessel_id`，首单统计可直接用 |
| 旧客户端不传 `buyerOrgId` | 岸上车创建报错；引导升级/绑定工厂；船供车不受影响 |
| `my-vessels` 新字段 | 只加字段，旧客户端忽略 |

## 8. 关键 SQL 校验

```sql
-- 个人新人活动必须只作用于个人
SELECT id, purchase_scene FROM promotion_activity
WHERE id = '3170000000000000501';  -- 期望 1

SELECT INDEX_NAME, COLUMN_NAME
FROM information_schema.STATISTICS
WHERE TABLE_SCHEMA = DATABASE() AND TABLE_NAME = 'shared_cart'
  AND INDEX_NAME IN ('uk_shared_cart_shore_scope', 'uk_shared_cart_shore_active');

-- 订单主体索引
SELECT INDEX_NAME FROM information_schema.STATISTICS
WHERE TABLE_SCHEMA = DATABASE() AND TABLE_NAME = 'order_info'
  AND INDEX_NAME = 'idx_order_buyer_org';

-- 订单主体审核状态快照列（233/248）
SELECT COLUMN_NAME FROM information_schema.COLUMNS
WHERE TABLE_SCHEMA = DATABASE() AND TABLE_NAME = 'order_info'
  AND COLUMN_NAME = 'buyer_org_audit_status';

WHERE member_role IN ('1','4') AND (can_confirm IS NULL OR can_confirm <> '1');
```
