# 业务流程与状态

> 证据：2026-07-28 已确认需求与状态设计；复核于 2026-08-31；置信度：已验证（设计基线），当前代码未完成运行态验收。

## 统一术语

| 术语 | 定义 |
|---|---|
| 商城配送 | 订单配送方式 `deliveryWay = 3`，由租户自己的配送员履约 |
| 配送任务 | 一张商城配送订单唯一对应的履约记录 |
| 配送尝试 | 一次从派单到送达、异常或退回的尝试，由 `attempt_no` 标识 |
| 已送达 | 配送员上传有效凭证后形成的配送事实 |
| 订单完成 | 客户确认收货或系统超时确认后的交易事实 |
| 待退回 | 已取货订单进入退款流程后，等待管理员确认商品返回仓库 |

## 主流程

```text
客户选择商城配送
  -> 结算校验配送范围并按现有规则计算运费
  -> 创建订单时再次校验范围
  -> 支付成功，订单进入待发货
  -> 幂等创建待派单任务和配货明细
  -> 管理员指定配送员
  -> 任务消息落库，在线推送并尝试发送微信订阅消息
  -> 配送员开始配货并逐项勾选
  -> 全部勾选后确认取货
  -> 任务进入配送中，订单进入待收货
  -> 配送员上传 1 至 6 张图片并提交已送达
  -> 任务进入已送达，订单仍为待收货
  -> 客户确认或从 delivered_at 起超时
  -> 订单完成并发送现有订单完成事件
```

## 配送任务状态机

| 状态 | 含义 | 主要允许操作 |
|---|---|---|
| `WAITING_ASSIGNMENT` | 支付成功，尚未指定配送员 | 管理员派单、订单取消/全额退款关闭 |
| `ASSIGNED` | 已指定配送员，尚未开始配货 | 配送员开始配货、上报异常；管理员改派 |
| `PICKING` | 配送员逐项核对商品 | 勾选/取消勾选、确认取货、上报异常 |
| `DELIVERING` | 商品已取走，正在配送 | 提交送达、上报异常、进入待退回 |
| `DELIVERED` | 已提交有效现场凭证 | 只读等待客户确认或自动确认 |
| `EXCEPTION` | 当前尝试无法继续 | 管理员重新派送、改派或关闭 |
| `RETURN_PENDING` | 已取货后退款，等待商品退回 | 管理员确认退回并关闭任务 |
| `CLOSED` | 取消、退款退回完成或管理员终止 | 只读 |

合法流转：

```text
WAITING_ASSIGNMENT -> ASSIGNED
ASSIGNED -> PICKING | EXCEPTION
PICKING -> DELIVERING | EXCEPTION
DELIVERING -> DELIVERED | EXCEPTION | RETURN_PENDING
EXCEPTION -> ASSIGNED | CLOSED | RETURN_PENDING
RETURN_PENDING -> CLOSED
WAITING_ASSIGNMENT | ASSIGNED | PICKING -> CLOSED
```

不允许从 `DELIVERED` 回到进行中状态。纠纷和售后进入退款域处理，不篡改已形成的送达事实。

## 订单状态联动

| 业务时点 | 订单状态 | 配送任务状态 |
|---|---|---|
| 支付成功 | `WAITING_FOR_DELIVERY` | `WAITING_ASSIGNMENT` |
| 派单/配货 | `WAITING_FOR_DELIVERY` | `ASSIGNED/PICKING` |
| 确认取货 | `WAITING_FOR_RECEIPT` | `DELIVERING` |
| 提交送达 | `WAITING_FOR_RECEIPT` | `DELIVERED` |
| 客户/系统确认 | `COMPLETED` | `DELIVERED` |
| 全部退款完成 | `CANCELED` | `CLOSED` |

订单主状态不增加“待派单、配货中、配送异常”等值，这些状态只属于配送任务。

## 派单与改派

- 候选配送员必须属于当前租户、账号启用并拥有 `order:delivery:execute` 权限。
- 派单请求携带任务 `version`；服务端以 `id + tenant_id + status + version` 条件更新。
- 进行中任务改派必须填写原因。
- 重新派送或改派使 `attempt_no` 加一，并重置当前配货勾选状态；历史操作、异常和凭证保留。
- 已送达、待退回和已关闭任务不能改派。
- 配送员停用不会静默转移任务；后台必须突出显示并由管理员显式改派。

## 配货与取货

- 任务创建时按订单项生成配货明细，订单项保存商品交易快照，配送明细只保存核对状态。
- 配送员可重复勾选/取消勾选当前尝试的商品。
- 确认取货前服务端重新检查所有有效订单项均已勾选。
- 确认取货事务同时更新任务为 `DELIVERING`、订单为 `WAITING_FOR_RECEIPT`、订单项为 `SHIPPED` 并记录 `deliver_time`。
- 任一步条件更新失败时整个事务回滚。

## 送达与自动确认

- 配送员只能为当前指派给自己的 `DELIVERING` 任务提交送达。
- 必须关联 1 至 6 个本人、本租户上传且未被其他任务占用的 JPEG/PNG 素材。
- 送达事务保存凭证、日志并设置 `delivered_at`；事务后才发送客户可见的进度通知。
- 商城配送自动确认以 `delivery_task.delivered_at` 为起点；现有快递订单继续以 `order_info.deliver_time` 为起点。
- 重复提交使用客户端幂等号、唯一索引和状态条件更新，不重复写凭证或日志。

## 异常与再次配送

- 异常原因至少包括：客户不在、无法联系、地址错误、客户拒收、商品问题、车辆/人员问题和其他。
- 异常说明必填；异常图片可选，但若上传仍需满足本人和租户归属校验。
- 管理员处理异常时可以重新指派原配送员、改派其他配送员或关闭任务。
- 每次处理生成新 `attempt_no`，历史异常、图片和操作记录不可覆盖。

## 退款与退回

- 未确认取货时，退款审批可以按现有流程执行；订单全部退款后关闭配送任务。
- 确认取货后，只要客户提交任一退款申请，整张配送任务即进入 `RETURN_PENDING`，禁止继续提交送达；第一期不处理“部分商品退回后继续配送其余商品”的拆单履约。
- 管理员必须在配送任务中确认商品已经退回仓库；退款审批服务以该事实作为放款前置条件。
- 退回确认需要操作人、时间、备注和可选凭证，不能只依赖前端按钮状态。
- 管理员确认整单商品退回后，任务转为 `CLOSED`；随后才允许现有退款审批逐项完成。

## 并发和幂等

关键状态更新统一采用条件更新：

```sql
UPDATE order_delivery_task
SET status = ?, version = version + 1, update_time = NOW()
WHERE id = ?
  AND tenant_id = ?
  AND assignee_id = ?
  AND status = ?
  AND version = ?
  AND del_flag = '0';
```

影响行数为零表示任务已变化、重复操作或无权操作。接口返回稳定业务错误，不再无条件覆盖最新状态。
