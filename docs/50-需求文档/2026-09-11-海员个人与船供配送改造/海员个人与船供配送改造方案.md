# 海员个人与船供配送改造方案

> 日期：2026-09-11  
> 状态：方案基线，待业务确认后排期  
> 适用项目：aryn-mall-java、aryn-mall-ui、aryn-mall-uniapp

## 1. 文档说明

本方案基于以下业务事实编制：

- 主要客户是海员，不以外部散客为主要客群。
- 海员既可以购买个人用品，也可以发起船供采购。
- 个人购买和船供采购都由公司自有司机送到港口或船舶。
- 不接入普通快递，不使用第三方快递单号。
- 船舶、港口、泊位和靠港时间窗是配送上下文，不替代海员用户身份。

本文件覆盖业务边界、领域模型、后端、管理端、UniApp、数据库、双模式适配、实施阶段和验收标准。

## 2. 总体结论

系统不是纯 B2C 商城，也不是企业采购系统，而是“海员用户商城 + 船供采购 + 自有车队港口配送”的混合模式。

同一租户内同时支持两类订单：

~~~text
海员账号
  ├── 个人购买订单
  │     ├── 个人用品、食品、生活用品
  │     ├── 海员个人下单
  │     └── 公司司机送至港口/船舶
  │
  └── 船供采购订单
        ├── 海员或船上人员发起
        ├── 为船舶或全体船员采购
        ├── 支持批量、单位、箱规和采购备注
        └── 公司司机按船期送至港口/船舶
~~~

核心设计：

1. 租户经营模式和订单购买场景分离。
2. 海员 user_info 仍是客户主体，船舶只是业务和配送上下文。
3. 两种订单共用商品、支付、订单和内部配送基础设施。
4. 订单状态尽量复用现有状态，不新建一套企业采购状态机。
5. 船供报价、企业账期、审批和发票全部作为后续可插拔能力，不进入第一阶段主链路。

## 3. 现状与改造依据

### 3.1 当前可复用能力

当前后端已经具备：

- user_info 海员/商城用户账号体系。
- 商品 SPU/SKU、购物车、订单、支付、售后基础能力。
- delivery_staff、delivery_task、delivery_trip、delivery_evidence 等自有配送能力。
- UniApp 配送员工作台，包括任务、出车、异常和凭证页面。
- 管理端配送任务、配送员、出车单和仓库配置页面。
- Boot 单体和 Gateway + Nacos + Dubbo Cloud 双模式。

当前订单创建对普通快递和商城配送要求用户地址，内部代码位于 OrderInfoServiceImpl.createOrder；当前支付成功事件会针对商城配送创建 delivery_task，相关代码位于 ArynOrderPayEventListener 和 DeliveryTaskServiceImpl.createTaskOnPay。

### 3.2 不能直接复用的部分

- 普通快递地址和第三方物流链路不适用于港口配送。
- delivery_task 当前没有船舶、泊位、港口和交货窗口字段。
- 商品当前没有 IMPA、采购单位、箱规和船供英文资料。
- 订单当前没有“个人购买/船供采购”场景字段。
- 当前 UniApp 结算页默认普通快递，并依赖用户地址。
- 当前管理端订单列表没有按船舶、靠港时间窗和船供场景筛选。

## 4. 业务边界

### 4.1 纳入范围

- 海员账号登录、资料和船舶绑定。
- 个人购买商品。
- 船供采购商品。
- 港口、泊位、锚地和船边配送。
- 公司司机任务、出车、配货、送达和签收。
- 船舶、靠港计划和交货时间窗。
- IMPA 编码、单位、箱规和中英文商品资料。
- 按船舶、靠港计划、司机和配送状态查询订单。

### 4.2 第一阶段明确不做

- 外部散客获客和独立公共商城运营。
- 企业客户主档、船东/船管公司账户。
- 复杂报价中心和多级审批。
- 授信、月结、发票和多币种。
- 普通快递和第三方物流。
- 多仓库存、供应商采购和报关系统直连。
- AI 采购助手和复杂自动补货。

这些能力保留扩展点，但不能成为当前订单或配送链路的前置依赖。

## 5. 架构决策记录

### ADR-001：订单级购买场景

决策：增加 order_info.purchase_scene，不使用租户级开关区分个人购买和船供采购。

~~~text
1 = 海员个人购买
2 = 船供采购
~~~

原因：同一租户同时存在两种订单，租户级模式无法表达实际业务。

### ADR-002：海员是客户，船舶是上下文

决策：继续使用 user_info 作为购买人；船舶通过 vessel_member 与用户建立关系。

原因：当前没有明确企业付款主体，不能提前引入 customer_info、授信和企业账号模型。

### ADR-003：统一使用自有车队港口配送

决策：个人购买和船供采购都使用公司内部司机配送；新增港口/船舶配送类型，不接入快递。

~~~text
1 = 普通快递，仅保留给其他零售租户
2 = 上门自提，兼容现有能力
3 = 现有商城配送，保持兼容
4 = 港口/船舶内部配送，船供租户默认使用
~~~

### ADR-004：订单状态优先复用

决策：个人和船供订单继续使用现有支付和订单状态；配送事实由 delivery_task 表达。

~~~text
待付款 → 待收货/待送达 → 已完成
~~~

只增加船供字段和配送状态，不在第一阶段创建“待报价、待审批、待对账、待结算”主状态机。

### ADR-005：先扩展商品资料，不污染零售模型

决策：采用 ship_goods_profile、ship_sku_profile 扩展表保存船供字段。

原因：船供字段只对部分商品和租户生效，避免在通用 SPU/SKU 上堆积大量空字段。

### ADR-006：保留 Boot/Cloud 双模式

决策：所有新接口、新模块、新表和菜单同时适配 Boot 与 Cloud。

## 6. 领域模型

### 6.1 租户经营模式

sys_tenant.business_mode 用于控制租户整体运营方式：

~~~text
1 = 普通零售
2 = 船供运营
~~~

该字段只控制可用菜单、默认配送方式和商品入口，不代替订单的 purchase_scene。

船供租户默认：

- 默认配送方式为 4 港口/船舶内部配送。
- 隐藏普通快递入口。
- 个人购买和船供采购都进入统一配送工作台。
- 是否显示优惠券、会员、营销由租户菜单和配置决定。

## 7. 配送模型

### 7.1 任务创建

个人购买和船供采购只要使用 delivery_way=4，支付成功后都创建内部配送任务。

任务创建必须满足：

- 订单支付成功或业务确认通过。
- 订单配送方式为内部配送。
- 船舶、港口和时间窗完整。
- 订单明细存在。
- 同一订单只创建一个有效配送任务。

使用订单号和任务唯一键保证支付回调、消息重试和手工补偿不会重复建任务。

### 7.2 delivery_task 扩展字段

~~~text
vessel_id
vessel_call_id
delivery_way
delivery_place_type
port_code
port_name
berth
delivery_window_start
delivery_window_end
need_crane
agent_name
agent_phone
recipient_name
recipient_phone
purchase_scene
~~~

### 7.3 任务状态

继续复用现有状态：

~~~text
待派单 → 待取货 → 配货中 → 待送达 → 已送达 → 已签收
                                      └→ 异常/待退回
~~~

提醒、WebSocket 和订阅消息只作为通知，不作为配送状态事实来源。

### 7.4 个人订单与船供订单的配送差异

| 项目 | 个人购买 | 船供采购 |
|---|---|---|
| 购买人 | 单个海员 | 海员或船上人员 |
| 商品数量 | 通常较少 | 通常较多 |
| 是否需要船舶 | 建议需要 | 必须需要 |
| 是否需要靠港计划 | 配送时需要 | 必须需要 |
| 是否内部配送 | 是 | 是 |
| 是否允许批量清单 | 可选 | 必须支持 |
| 是否第一阶段审批 | 否 | 否 |

## 13. 实施计划

### 阶段 0：业务冻结，3～5 个工作日

确认：

- 个人订单是否必须绑定船舶。
- 靠港计划由后台维护还是海员提交。
- 司机是否允许同一出车单配送多个订单。
- 送船是否必须填写泊位，还是允许只填写港口。
- 是否需要锚地和舷吊字段。
- 船供订单是否第一阶段全部在线支付。
- 船供订单是否允许海员查看同船其他订单。

默认建议：

- 内部配送订单必须有船舶、港口和时间窗。
- 第一阶段全部在线支付。
- 一订单一配送任务。
- 订单先分组展示，暂不物理合并。

### 阶段 1：个人购买和船供配送闭环，5～6 周

完成：

- 购买场景。
- 船舶、成员和靠港计划。
- 港口/船舶配送字段。
- 个人购买和船供采购入口。
- 在线支付。
- 支付后幂等创建配送任务。
- 管理端派单。
- 司机端配货、出发、送达和签收。
- 订单和配送凭证联动。
- Boot/Cloud 双模式。

### 阶段 2：船供运营提效，4～5 周

完成：

- IMPA 编码。
- 单位和箱规。
- 英文商品资料。
- 批量导入商品。
- 常购清单和再来一单。
- 按船、按靠港窗口聚合订单。
- 拣货单和送货单。
- ETA 变更提醒。
- 缺货、短装和补送。
- 港口配送看板。

### 阶段 3：按实际需求扩展

可选能力：

- 报价单和协议价。
- 船长审批。
- 企业客户和船东账户。
- 授信和账期。
- 对账和发票。
- 多币种。
- 批次、保质期和损耗。
- 供应商采购和库存预测。

## 14. 一致性和安全要求

### 14.1 订单幂等

- 客户端请求号保持现有 request_id 机制。
- 支付回调按支付单号和订单号幂等。
- 创建配送任务按租户和订单唯一。
- 签收按当前状态条件更新。
- 司机重复提交送达凭证不能重复推进状态。

### 14.2 权限和数据隔离

- 海员只能查询自己的订单。
- 船员只有在有效 vessel_member 关系下才能下船供订单。
- 司机只能查询已派给自己的配送任务。
- 管理员只能操作当前租户数据。
- 船舶、订单、配送任务和凭证均必须经过租户隔离。

### 14.3 ETA 变更

ETA 修改必须：

- 记录旧值和新值。
- 记录操作人和操作时间。
- 通知相关订单和司机。
- 对未送达任务重新检查时间窗。
- 对已出车任务进入人工确认流程，不自动覆盖司机事实。

→ 自动生成内部配送任务
→ 管理员派司机
→ 司机送至港口/船舶
→ 海员签收
→ 订单完成
~~~

船供采购：

~~~text
海员进入船供采购
→ 选择船舶
→ 批量选择商品
→ 设置数量、单位和备注
→ 选择送达时间窗
→ 在线支付/确认
→ 仓库配货
→ 司机按船配送
→ 船上人员签收
~~~

技术验收：

- 个人订单和船供订单可以正确区分。
- 船供租户不出现普通快递选项。
- 内部配送订单不要求用户地址。
- 支付重复回调不会重复创建任务。
- 一个订单只有一个有效配送任务。
- 司机无法访问其他司机任务。
- 司机无法访问其他租户任务。
- 签收和订单完成状态保持一致。
- ETA 改动有审计记录。
- Boot 和 Cloud 请求路径均正确。
- Boot/Cloud SQL 和租户表配置一致。
- 现有普通零售租户的快递、商城配送和订单流程不受影响。

## 16. 关键指标

试点阶段建议跟踪：

- 个人订单下单完成率。
- 船供订单平均下单耗时。
- 每单商品数量。
- 配货差错率。
- 司机准时送达率。
- 港口等待时长。
- 签收凭证完整率。
- ETA 变更后的任务调整时长。
- 缺货和短装比例。
- 订单取消率和售后率。

## 17. 最终落地原则

1. 海员是客户，船舶是配送和采购上下文。
2. 个人购买和船供采购是两种订单场景，不是两套系统。
3. 两种订单统一由公司司机完成港口/船舶配送。
4. 普通快递不进入船供租户主流程。
5. 先跑通个人购买和船供配送闭环，再增加报价、审批、账期和发票。
6. 所有新增能力必须同时适配 Boot 和 Cloud。
7. 所有订单金额、商品信息、配送目标和签收证据必须保存快照。

## 18. 商品多时的 Web 商品中心优化

### 18.1 当前实现的主要问题

当前管理端商品列表主要展示商品名称、类目、品牌、价格、状态、规格、销量和总库存，筛选条件也只有名称、类目、品牌、规格和上下架状态。当前录入页按单个 SPU/SKU 逐项填写，缺少 IMPA、英文名称、采购单位、包装规格、起订量、步进量、储存条件和船供销售范围等字段。

当前只支持批量上下架，不支持批量导入、批量补资料、批量调价、批量调整船供属性或快速复制商品。商品数量较多时，继续使用现有页面会导致录入慢、查找慢、船供商品资料不完整，并且容易把“可零售商品”和“可船供商品”混在一起。

### 18.2 推荐的商品模型

在 `ship_goods_profile` 中明确商品销售范围，不要只用 `is_ship_supply` 表示是否船供：

~~~text
sale_scope = 1 仅海员个人购买
sale_scope = 2 仅船供采购
sale_scope = 3 个人购买和船供采购
~~~

建议补充以下字段：

~~~text
spu_id
sale_scope
impa_code
barcode
name_en
search_aliases
storage_type
shelf_life_days
ship_supply_remark
publish_completeness
~~~

在 `ship_sku_profile` 中维护：

~~~text
sku_id
base_unit
purchase_unit
conversion_rate
package_spec
package_spec_en
moq
step_qty
gross_weight
volume
~~~

这样同一商品可以同时服务个人购买和船供采购，订单只保存购买场景，商品资料不需要复制两份。

### 18.3 Web 商品列表改造

商品中心建议改为“高密度列表 + 快速操作”，保留现有分页，不建议一次性加载全部商品：

1. 增加顶部场景筛选：全部、个人商品、船供商品、两者可用、资料不完整、库存预警、已上架、已下架。
2. 增加搜索字段：商品名称、英文名称、IMPA、条码、搜索别名、SKU 编码。
3. 增加筛选字段：一级/二级类目、品牌、储存条件、供应范围、库存区间、创建时间和更新时间。
4. 商品行显示主图、中文名、英文名、IMPA、销售范围、采购单位/箱规、最低起订量、总库存、最低售价、资料完整度和状态。
5. 固定左侧选择列和右侧操作列，支持列显示配置；不要把所有字段永久堆在表格中。
6. 行内提供编辑、复制、新建相似商品、查看 SKU、补齐资料、上下架；删除继续使用逻辑删除并要求二次确认。
7. 支持批量上下架、批量设置销售范围、批量设置类目/品牌、批量补充储存条件和批量导出。

### 18.4 批量导入和批量维护

这是商品数量较多时的必做能力，优先级高于复杂的价格体系：

1. 提供 Excel 模板下载，分为商品主表、SKU 表和图片/附件说明。
2. 导入采用“上传 -> 解析 -> 校验预览 -> 确认导入”四步，不允许上传后直接写库。
3. 校验 IMPA、条码、SKU 编码、规格组合、价格、库存、起订量和步进量；错误行提供可下载的错误报告。
4. 对大文件使用异步任务，展示处理进度、成功数、失败数和导入批次号；小文件可同步处理。
5. 支持按 SKU 编码或 IMPA 更新已有商品，禁止用商品名称作为唯一匹配键。
6. 导入和批量修改记录操作人、时间、原值、新值和批次号，价格、库存和上下架变更均可追溯。

### 18.5 商品编辑页改造

将现有“基本信息/规格信息/商品详情”扩展为以下分组，并保留草稿保存：

~~~text
基础资料：中文名、英文名、别名、主图、详情图、品牌、类目
船供资料：销售范围、IMPA、条码、储存条件、保质期、船供说明
SKU/包装：规格、销售单位、采购单位、换算关系、箱规、重量、体积
交易规则：售价、原价、成本价、起订量、步进量、库存预警线
配送属性：是否允许港口/船舶配送、特殊装卸要求
发布检查：资料完整度、缺失项、重复编码和价格库存异常
~~~

多 SKU 表格应支持复制上一行、批量填充、按列粘贴、批量修改单位/箱规/起订量，并在保存前校验 SKU 组合唯一性。船供商品未完成 IMPA、采购单位、起订量和步进量时，不允许发布到船供目录，但可以保存草稿。

### 18.6 后端和性能要求

1. 商品列表接口只返回列表摘要，不返回完整详情、富文本和全部 SKU；详情页再按 ID 获取完整数据。
2. 商品列表接口一次返回 `saleScope`、船供摘要和资料完整度，避免前端逐商品请求扩展表造成 N+1 查询。
3. 在 `tenant_id`、`status`、`category_second_id`、`brand_id`、`impa_code`、`barcode`、`update_time` 上建立组合或单列索引，具体以查询计划确认。
4. 中文名、英文名、IMPA 和条码搜索都必须服务端分页；首期使用数据库索引和规范化前缀/精确查询，不因商品数量增加就立即引入搜索集群。
5. 类目、品牌、规格字典按租户缓存；品牌很多时使用远程搜索，不一次性加载全部品牌。
6. 批量接口必须限制单批数量、校验租户权限，并使用事务或可重试批次，避免半批写入无法追踪。
7. Boot 和 Cloud 的商品 API、菜单权限、增量 SQL、全量 SQL 必须同步维护。

## 19. 小程序端页面和交互优化

### 19.1 总体导航

小程序不能继续只有一套普通商城路径。建议在首页、分类页、搜索页和购物车顶部保持统一的场景切换：

~~~text
个人购买 | 船供采购
~~~

场景切换只改变商品入口、字段展示、数量规则和结算信息，不改变登录身份。用户最近一次选择可以记忆，但进入订单确认页必须再次展示当前场景，避免误下单。

### 19.2 首页和分类页

1. 首页增加两个明确入口：个人购买、船供采购；船供入口展示“按船舶/港口配送”。
2. 分类页在船供场景下显示 IMPA、船用品类、常购清单和按储存条件筛选；个人场景保留简洁类目。
3. 分类和品牌数据按需加载，商品多时不要把所有商品预加载到首页。
4. 船供目录增加“常购商品、最近购买、我的船舶常用清单、缺货替代”四类快捷入口。

### 19.3 搜索和商品列表页

当前搜索以中文名称、销量排行和热搜榜为主，需扩展为：

1. 支持中文名、英文名、IMPA、条码、别名和 SKU 编码搜索。
2. 输入时提供联想结果，明确标注“中文名/英文名/IMPA/品牌”。
3. 船供列表显示采购单位、箱规、起订量、步进量、可用库存和配送温区。
4. 船供列表每行支持直接输入数量或步进加减，支持勾选后批量加入船供购物车。
5. 个人列表保留零售价格、评价和常规购买数量，不显示不必要的船供字段。
6. 筛选条件至少包括类目、品牌、库存状态、储存条件和是否常购；排序支持常购、销量、价格和更新时间。
7. 保留分页/上拉加载，避免一次返回全部商品；搜索无结果时提供相近名称和常购商品。

### 19.4 商品详情页

现有详情页包含普通运费、地址和价格展示，需要根据场景切换：

个人购买：显示零售价、个人购买单位、库存、优惠信息和港口/船舶配送说明。

船供采购：显示 IMPA、中文/英文名称、采购单位、箱规、起订量、步进量、库存、储存条件和船供备注；价格按当前购买场景返回，不能只显示个人零售价。

两种场景都要支持规格选择、加入购物车、立即购买、收藏和再次购买。详情页不应把普通快递作为默认文案；配送信息应改为“公司司机送至港口/船舶”。

### 19.5 购物车页

购物车必须按“购买场景 + 船舶”分组，至少支持：

1. 个人商品和船供商品分组显示，不能混成一张普通购物车。
2. 船供商品按采购单位显示数量，展示换算后的箱数/件数。
3. 校验 MOQ 和 step_qty；数量不符合时给出可操作的修正值。
4. 支持按船舶切换购物车上下文，防止把同一批货送错船。
5. 显示库存不足、商品下架、价格变化和资料变更，并允许移除或重新选择。
6. 提供“再来一单/从历史订单复制到购物车”，这是船供高频采购的核心效率功能。

### 19.6 订单确认页

当前页面初始化默认地址并将 `deliveryWay` 设为普通快递，需要改为场景化确认：

~~~text
购买场景：个人购买 / 船供采购
配送方式：公司司机港口/船舶配送
配送目标：船舶、港口、泊位/锚地
靠港计划：ETA、ETD、送达时间窗
收货人：姓名、电话、船上岗位或代理联系方式
订单备注：装卸要求、联系要求、温区和特殊说明
~~~

个人购买和船供采购均可送货，因此地址组件不应作为主入口；港口/船舶配送信息必须优先展示。`deliveryWay=4` 时隐藏普通快递和第三方物流选项，船舶和靠港计划校验通过后才允许支付。个人订单仍可少填船供资料，但配送目标和时间窗不能省略。

### 19.7 订单列表、详情和配送进度

1. 订单列表增加个人购买/船供采购标签，支持按船舶、港口、订单状态和配送状态筛选。
2. 订单详情展示商品场景、船舶、港口、靠港计划、司机、出车状态、预计送达时间和签收凭证。
3. 配送进度使用公司内部司机节点：待配货、待派车、已派车、司机取货、前往港口、已到港、已交付、已签收；不要展示快递单号和第三方物流轨迹。
4. 增加“再来一单”，船供订单按原船舶和商品清单复制，但必须重新确认靠港计划和库存价格。

### 19.8 一期和后置范围

一期必须完成：

- Web 商品场景筛选、船供字段、批量导入、资料完整度和 SKU 批量维护。
- 小程序双场景入口、IMPA/英文搜索、船供数量规则、分组购物车、船舶/港口结算和配送进度。
- 商品列表摘要接口、扩展字段一次返回、库存/价格变化校验。

可以后置：

- 智能推荐、替代品推荐、搜索集群、复杂阶梯价和供应商协同。
- 图片 OCR、自动翻译、自动生成英文描述和高级 BI 分析。

商品数量多并不意味着一期就要引入复杂搜索中台；先把商品主数据、批量维护和船供场景结算做正确，收益最高且风险可控。

## 20. 小程序处于初级阶段时的大胆重构方案

### 20.1 结论：直接重做核心信息架构

当前小程序仍然是“首页/分类/购物车/我的”的普通零售骨架，商品详情和订单确认页也围绕普通快递地址设计。既然当前用户量和历史交互包袱都不大，不建议继续围绕现有页面做局部兼容，而应直接重做以下三条主线：

~~~text
船舶上下文 -> 船供目录 -> 批量购物车 -> 靠港配送下单 -> 配送进度
个人购买 -> 个人商品 -> 简化购物车 -> 港口/船舶配送下单 -> 配送进度
历史订单 -> 再来一单 -> 重新确认船舶和靠港计划
~~~

保留现有商品、收藏、评价等可复用组件和 API 封装，但可以重做页面、路由、状态管理和结算交互，不需要迁就当前默认快递、默认地址和促销导向的页面结构。

### 20.2 推荐的新底部导航

底部导航建议调整为：

~~~text
首页 | 商品 | 购物车 | 订单 | 我的
~~~

“分类”不再作为独立的主导航入口，而是收进“商品”页；“首页”负责展示当前船舶和靠港任务，“订单”负责个人订单、船供订单和配送进度。促销、秒杀和推荐商品可以保留为首页模块，但不能占据首屏主任务。

### 20.3 首页重做为船舶工作台

登录后的首页首屏应优先显示当前配送上下文，而不是广告或通用商品瀑布流：

~~~text
当前船舶：XXX 轮（可切换）
下一靠港：上海港 · ETA 09月18日 08:00
配送状态：暂无待送货 / 有 2 个订单待确认

[船供采购] [个人购买] [再来一单] [查看配送]

常购商品 | 最近购买 | 待补货清单 | 港口公告
~~~

如果用户尚未绑定船舶，首页只要求完成一次“选择/绑定船舶”，不再引导用户先维护普通收货地址。个人购买也沿用同一个船舶和港口配送上下文，避免个人订单走一套、船供订单走另一套。

### 20.4 新增全局船舶上下文

新增 `shipContextStore`，统一保存当前用户的：

~~~text
purchaseScene       购买场景：个人/船供
vesselId             当前船舶
vesselCallId         当前靠港计划
portCode             港口
berthOrAnchorage     泊位或锚地
deliveryWindow       送达时间窗
consignee            收货人和联系电话
~~~

该上下文贯穿商品列表、详情、购物车、结算和订单详情。切换船舶时必须提示购物车是否需要一起切换，禁止把属于 A 船的购物车直接提交给 B 船。场景、船舶和靠港计划必须在订单提交前再次确认，并写入订单快照。

### 20.5 商品页直接拆为两个入口

#### 船供采购页

这是高频主流程，页面应围绕效率设计：

1. 顶部固定 IMPA/英文/中文/条码搜索框。
2. 下方提供常购、最近购买、我的清单、按类目、按温区和按库存筛选。
3. 列表直接显示采购单位、箱规、起订量、步进量、库存和当前船舶。
4. 每行直接输入数量，符合步进量后加入购物车；不强制逐个进入商品详情。
5. 支持多选、批量改数量、批量加入购物车和“从上次订单复制”。
6. 支持扫描 IMPA/条码快速加入商品；扫描不到时允许手动搜索。

#### 个人购买页

保持相对简单：

1. 展示零售价、图片、评价、库存和个人购买单位。
2. 支持类目、品牌、销量和价格筛选。
3. 保留商品详情、规格选择、收藏和立即购买。
4. 结算仍选择港口/船舶配送，不出现普通快递。

两个入口共享商品接口和商品详情组件，但不要用一套页面塞满两类用户都不需要的字段。

### 20.6 购物车和结算页直接重做

购物车按以下层级展示：

~~~text
当前船舶
  ├── 船供采购
  │    ├── 商品 A：采购单位、箱规、数量、起订量校验
  │    └── 商品 B：库存不足或价格变更提示
  └── 个人购买
       └── 商品 C：零售单位和数量
~~~

结算页不再加载默认收货地址作为首要数据，而是先确认：

~~~text
购买场景 -> 船舶 -> 靠港计划 -> 港口/泊位 -> 送达时间窗 -> 收货人 -> 备注
~~~

支付前显示“公司司机送至港口/船舶”，配送方式固定为内部配送。地址簿可以保留用于兼容其他租户，但在本租户主流程中隐藏，避免用户误以为会走快递。

### 20.7 订单和配送页重做为时间线

订单首页按“待确认、待配货、配送中、已完成、售后”分组，同时显示个人/船供标签和船舶名称。订单详情采用时间线：

~~~text
已支付 -> 仓库配货 -> 已派司机 -> 司机取货 -> 前往港口 -> 已到港 -> 已交付 -> 已签收
~~~

用户可查看司机姓名/电话、预计到港时间、港口和靠泊信息；不展示快递公司、快递单号和第三方物流轨迹。船供订单详情增加“再来一单”和“复制商品清单”，个人订单保留“再次购买”。

### 20.8 可直接删除或隐藏的旧页面

在本租户中可以直接从主流程移除：

- 普通快递配送选择。
- 默认收货地址作为结算首屏。
- 第三方物流轨迹页。
- 以热搜、秒杀和通用促销为主的首页首屏。
- 只支持单个商品进入详情后购买的船供采购路径。

普通零售租户仍需兼容的页面不要物理删除，按租户 `business_mode` 或能力开关隐藏，避免破坏系统的双模式和多租户兼容。

### 20.9 直接重构的技术边界

小程序建议新增或重构以下模块：

~~~text
src/store/shipContextStore.ts       船舶、靠港计划和配送上下文
src/store/purchaseCartStore.ts      按场景/船舶组织购物车
src/composables/usePurchaseScene.ts 场景切换和字段权限
src/pages/home/                     船舶工作台首页
src/pages/catalog/                  双场景商品目录
src/pages/cart/                     分组购物车
src/pages/order/                    场景化结算、订单和配送时间线
src/api/vessel.ts                   船舶和靠港计划
src/api/product/ship-supply.ts     船供搜索、清单和批量加购
~~~

页面可以重写，`src/api/` 仍需遵守现有分层和 Boot/Cloud URL 改写规则；所有新请求路径首段使用有效微服务域，不在页面直接拼接 `/boot`。后端接口应优先提供“列表摘要 + 批量加购 + 结算校验 + 再来一单”能力，避免小程序自行拼装业务规则。

### 20.10 重构后的验收主链路

~~~text
登录
→ 选择当前船舶和靠港计划
→ 进入船供采购
→ 搜索 IMPA 或选择常购清单
→ 批量填写数量
→ 系统校验起订量、步进量和库存
→ 确认港口/泊位/时间窗
→ 支付
→ 仓库配货
→ 公司司机配送
→ 用户查看时间线并签收
~~~

同时验证：

- 切换到个人购买仍可购买并使用同一内部配送链路。
- 用户无法把 A 船购物车提交给 B 船。
- 商品下架、库存变化、价格变化和靠港计划变更均有明确提示。
- 船供采购不需要进入商品详情逐件购买。
- Boot 和 Cloud 模式下商品、船舶、订单和配送请求路径均正确。
