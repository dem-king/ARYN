## 1. 原始请求

> 新人专享的产品需要支持单独调价吗，调研一下小象超市等这类产品的业务逻辑是怎么处理新人专享产品的。

附带截图：移动端首页存在一个「新人专享 / 快手好菜 美味即享」楼层，三张商品卡（越南巴沙鱼片 ￥19.90、海天金标生抽 ￥19.90、海南高山香蕉 ￥9.90），每张卡片有「抢」按钮。

补充确认（用户口径）：

> 新人专享就是给没有下过单的用户。

## 2. 结论摘要

1. **需要单独定价**，但行业做法是「同一 SKU + 一层人群定向活动价」，**不是**给商品加第三个价格字段、也不是复制一套新人版商品。
2. **悦航购当前完全没有这个能力**：截图里的「新人专享」只是装修组件的手填标题，价格就是普通售价，新老用户看到的价格完全一致。
3. 判定口径已明确为「本租户内无已支付订单」，落库为 `order_info` 的 `pay_status = '1'`，有现成索引可用。
4. 落地存在一条架构约束：促销模块判断新人需要读订单数据，而 `promotion-biz` 与 `order-biz` **禁止直接依赖**，必须新增 Dubbo 远程接口。

## 3. 竞品业务逻辑

### 3.1 各平台做法

| 平台 | 机制 | 关键规则 |
|---|---|---|
| 小象超市（原美团买菜） | 新人 1 分购 / 新人专享楼层 | 资格按账号（微信/手机号）维度；规则强调「以 App 内展示为准」 |
| 叮咚买菜 | 新人特价任选 1 件 + 首单免邮 + 88 元新人券包 | 引流款限购 1 件防薅；券包含品类满减券、0 元尝鲜券 |
| 美团优选 | 新人全额返红包 | 规则从「首单实付」金额计算 |
| 美团系 / 多多买菜通用 | 商家侧「限购 1 份、第二份恢复原价」 | 结算环节判定资格；不满足则恢复原价；与其它优惠互斥 |

### 3.2 归纳出的五条通用规则

1. **新人价是活动价**：运营选品 → 配新人价 → 配限购 → 配资格规则。商品原价不动，活动下线后商品照常按原价销售。
2. **浏览时浅判、结算时硬判**：列表/详情页对疑似新人展示新人价 + 角标 + 划线原价；下单/支付前再校验一次资格，不合格恢复原价。
3. **资格口径为账号维度「从未下单」**，以已支付订单为准；防刷靠限购 + 库存 + 风控。
4. **展示必须带价格锚点**：新人价 + 划线原价 + 新人角标，这是转化率的来源。
5. **与秒杀/折扣互斥**，取其一，避免价格击穿。

> 证据来源为公开报道与平台规则说明（见文末参考来源），非官方规则原文；具体细则以各 App 内展示为准。

## 4. 悦航购现状盘点

### 4.1 「新人专享」当前的真实形态

截图中的楼层是装修组件 `goods-group` 的实例：

- 标题「新人专享」是运营在后台手填的 `title` 字段（`aryn-mall-ui/apps/web-ele/src/views/promotion/page-design/components/goods-group/setting.vue:49-50` 的「区块标题」表单项，`maxlength=20`）。
- 数据源是「手动选择商品 ID」或「按分类 + 销量排序」。
- C 端渲染时价格直接取后端下发的字段：`￥{{ item.price.toFixed(2) }}`（`aryn-mall-uniapp/src/components/diy/diy-goods-group/index.vue`）。

**结论：该楼层没有任何资格判定或价格改写，「专享」目前只是一句文案。老用户看到的价格与新人完全相同。**

### 4.2 现有可复用能力

| 能力 | 位置 | 可复用点 |
|---|---|---|
| 活动 → 商品 → 活动价 + 限购 模型 | `SeckillGoods.seckillPrice` / `limitPerUser` | 新人活动模型几乎可照抄秒杀 |
| 固定价定价类型 | `DiscountActivity.discountType`（1打折 2减价 3固定价） | 已支持「固定价」语义 |
| 下单改价挂点 | `OrderPriceComputeService` + `PromotionEngineServiceImpl` | 校验与改价可直接挂在这条链上 |
| 优惠快照 | `PromotionSnapshot`（priceBefore / priceAfter / ruleSnapshot） | 新人价成交可留痕 |
| 活动锁定与确认 | `PromotionLock` + `PromotionReservationService`（reserve/confirm/release） | 幂等与并发控制可复用 |
| 装修楼层组件模式 | `PageDesignComponentTypes` 中 `SECKILL` / `DISCOUNT` 楼层（挂活动/场次 ID） | 新增「新人专享楼层」有现成先例 |

### 4.3 能力缺口

| 缺口 | 证据 |
|---|---|
| 商品无人群价字段 | `GoodsSku` 仅有 `salesPrice` / `originalPrice` / `costPrice`（`aryn-product-api/.../GoodsSku.java:42-52`）。**建议保持现状**，新人价不应落到商品表 |
| 活动无人群维度 | 秒杀/折扣/拼团均不区分人群 |
| 无新客判定逻辑 | `order-biz` 与 `promotion-biz` 中不存在任何「已支付订单数 / 首单」判定 |
| 券无人群条件 | `CouponInfo` 有满减/折扣/限领次数，无「仅新人可领」 |
| 促销模块无法读订单 | `promotion-biz/src/main` 无任何 `com.aryn.cloud.order` 引用；`aryn-order-api` 的 `remote/` 下仅有 `RemoteDeliveryAccountService`、`RemoteSharedCartService` |

## 5. 判定规则设计（已确认口径）

### 5.1 判定条件

```sql
-- 本租户内该用户是否已支付过订单
SELECT COUNT(1) FROM order_info
WHERE tenant_id = ? AND user_id = ? AND pay_status = '1';
```

`pay_status`：`0.未支付；1.已支付`（建表脚本注释）。`order_info` 有唯一索引 `uk_order_request (tenant_id, user_id, request_id)`，`tenant_id` 打头，按租户 + 用户查询可走索引。

### 5.2 「下过单」的三种口径与取舍

| 口径 | SQL 条件 | 后果 |
|---|---|---|
| 只要下过单（含未支付/已取消） | `COUNT(*) > 0` | 下一单不付款即永久失去新人价，**不可取** |
| **付过款就算（含退款）** | `pay_status = '1'` | 退款用户不再恢复新人身份。**建议采用** |
| 付过款且未退款 | `pay_status = '1' AND status != '11'` | 退款后可重新当新人，存在「下单→退款→再享新人价」的薅法 |

**建议采用第二种**，理由：

- 天然防「退款刷新人价」这一最常见薅法。
- `pay_status` 是单向状态：支付回调更新带 `.eq(payStatus, NO)` 乐观条件并做幂等处理（`ArynOrderPayEventListener.java:75-84`），判定稳定。
- 退款流程**只改** `order_info.status`（→ 已取消）与订单项状态，**不回写** `pay_status`（`OrderRefundServiceImpl.java:100-213`、`ArynRefundListener.java:99-124`），因此「付过款又退款」的用户会被判为非新人 —— 这是可接受的代价：真实用户极少首单即退款。

### 5.3 边界规则

| 边界 | 规则 |
|---|---|
| 未支付订单是否占位 | 新人价**只做身份校验，不预占库存/额度**。避免「下单不付款」恶意锁库存 |
| 「每人限购」计量 | 按**已支付订单**的累计件数计算，与身份判定同源 |
| 多账号 | 第一版按 `user_id` 判定（`UserInfo` 主体为 openid/手机号，`UserInfo.java:82`）。手机号维度留给风控，不首期实现 |
| 跨租户 | 判定天然按租户隔离（`tenant_id` 已在条件中），A 租户的老客在 B 租户仍是新人 —— 符合租户隔离语义 |

## 6. 技术可行性核对

### 6.1 跨模块查询必须走 Dubbo（强制约束）

依据 AGENTS.md 分层规则，`promotion-biz` 不得直接 import `order-biz`。需在 `aryn-order-api` 新增远程接口，例如：

```java
// aryn-order-api：供 promotion 模块判定新客
public interface RemoteOrderQueryService {
    /** 本租户内该用户是否已支付过订单 */
    boolean hasPaidOrder(String tenantId, String userId);
}
```

boot 模式走 injvm、cloud 模式走 Dubbo，同一份代码双模式可用。

> 注意：`OrderInfo` 等 DTO 若走 Dubbo 序列化，必须 `implements Serializable`（strict 模式），新增 remote 签名时需检查。

### 6.2 字段陷阱：`UserInfo.totalConsume` 不可作为判定依据

`user_info.total_consume`（「累计消费金额」）看似是现成判据，但：

- 其唯一的写入点是 `MemberOrderGrowthServiceImpl.processOrderComplete`，经 `UserInfoMapper.increaseTotalConsume`（`aryn-user-biz/.../MemberOrderGrowthServiceImpl.java:53`）。
- 触发时机是 **订单完成（确认收货）**，由 `OrderInfoServiceImpl:561` 发布 `OrderCompleteEvent`，走 RocketMQ 异步消费。
- 因此：订单已支付但未确认收货的用户，`totalConsume` 仍为 0。

**用它判「是否消费过」会漏判（把已付款未收货的用户当成新人），且依赖 MQ 到达时序，不可作为资格判据。**

### 6.3 C 端价格改写挂点

装修楼层的商品数据由 `aryn-mall-uniapp/src/components/diy/retail-data.ts` 中的 `loadGoodsGroup` / `loadGoodsGroupPage` 加载（走 `@/api/product/spu` 的 `getByIds` / `getPage`）。按用户身份出价需要在这条链路上叠加一层价格改写，或由服务端在接口内直接出价。

**风险提示**：若该楼层走免登白名单接口，服务端拿不到用户身份，无法按人出价。登录态与免登态的出价路径需分别处理（与既有「C 端免登接口白名单」问题同源，漏配后端白名单会伪装成「登录已过期」）。

## 7. 建议方案

### 方案 A · 完整新人价（对标小象超市）

新增「新人专享活动」：活动 → 商品 → 活动价 + 每人限购，叠加资格规则（本租户内已支付订单数 = 0）。装修楼层新增组件类型挂活动 ID（参照 `seckill` / `discount` 楼层模式）。结算时硬校验 + 落 `PromotionSnapshot`。

工作量：活动 CRUD、C 端列表/详情**按身份出价**的价格合并、结算校验、新客判定远程接口（boot/cloud 双模式）、双模式增量 SQL。

### 方案 B · 券包先行（对标叮咚轻量版）

给 `CouponInfo` 增加「仅新人可领」的人群条件，配新人券包。改动小得多，但楼层展示仍是原价，转化效果弱一档。

> 叮咚实际是「新人特价 + 券包」组合使用；纯券是退路而非终态。
