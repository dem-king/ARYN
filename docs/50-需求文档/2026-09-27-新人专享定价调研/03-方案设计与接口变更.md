# 03 · 方案设计与接口变更

> 前置阅读：[README](README.md)（调研结论与判定口径）。本文是方案 A 的落地方案。
> 状态：**设计完成，未实施**。

## 0. 已确认的决策（2026-09-27）

| 决策项 | 结论 |
|---|---|
| 方案 | **方案 A：完整新人价**（浏览浅判 + 结算硬判，非纯券包） |
| 限购 | **每人每 SKU 限购 1 件**（单订单内该 SKU 数量必须 = 1，超量拦截） |
| 适用范围 | **租户维度**，与船绑定无关（绑没绑船、绑哪条船都不影响资格） |
| 时效 | **要加**：注册 N 天内有效，N 为活动级配置项，**默认 30 天** |

## 1. 架构选型：复用 `promotion_activity` 通用引擎，不建新表

调研深挖后发现仓库里已有一条完整的「人群定向改价」链路，新人价应该挂进去，而不是照抄秒杀新建独立表组：

| 已有能力 | 位置 | 对新人价的意义 |
|---|---|---|
| 通用活动表 `promotion_activity`（rules 存 JSON，scopeType 8 种） | `PromotionActivity.java` | 新人活动 = 一种新的 `activityType`，**无需新表** |
| 用户维度资格判定先例 | `PromotionEngineServiceImpl.matchesScope` 的 `scopeType="8"`（常购专属价，`matchesFrequentScope`，fail-closed） | 新人资格判定照此模式加入引擎 |
| 回调式跨模块服务 | `RemoteBuyerProfileService` 定义在 promotion-api、**实现在 order-biz**（`aryn-order-biz/.../dubbo/RemoteBuyerProfileServiceImpl.java`） | 新人判定远程接口照此模式，不用新建服务类 |
| 试算→改价 | 引擎 `preview` 产出 `UnitPriceOverride(skuId, unitPrice)` → 订单侧 `applyPromotionLadder` 写回 `item.salesPrice` | 新人价改价走同一通道 |
| 锁定/确认/释放 | `PromotionReservationServiceImpl` + `PromotionLock`（reserve/confirm/release 幂等） | 「在途新人价订单唯一」约束挂这里 |
| `PromotionContextDTO.userId` | `PromotionContextDTO.java:32` | 引擎内可直接拿到当前用户 |

不选「照抄秒杀新建 newbie_activity 表组」的原因：秒杀的场次、库存、Redis 槽位机制对新人价全部多余（限购 1 件由资格本身保证），工作量翻倍且多一套状态机要维护。

### 1.1 活动模型

```text
promotion_activity（复用，不建新表）
├── activityType = "9"（新增 TYPE_NEWBIE_PRICE；现有 4=阶梯价 5=赠品 7=整船折扣，
│                     取 9 避开存量取值，实施前 grep 字典与种子数据复核）
├── scopeType    = "2"（指定商品，scopeValue = SKU ID 逗号分隔，复用 matchesScope 现成逻辑）
├── startTime / endTime / status(1草稿 2已发布 3暂停 4结束) / priority / stackable
└── rules（JSON，扩展 schema）：
    {
      "registerWithinDays": 30,          // 注册 N 天内有效，默认 30
      "limitPerUser": 1,                 // 固定 1，发布校验强制
      "skus": [                          // 每个 SKU 的新人价（价格各不相同）
        { "skuId": "...", "price": 19.90 },
        { "skuId": "...", "price": 9.90 }
      ]
    }
```

发布校验：`rules.skus` 与 `scopeValue` 的 SKU 集合必须一致；`price` 必须 ≥ 0 且 < 对应 SKU 售价；`limitPerUser` 必须为 1。校验挂在活动发布接口（与管理端编辑保存两侧）。

### 1.2 资格判定（新增一个远程方法，实现在 order-biz）

```java
// promotion-api：扩展既有 RemoteBuyerProfileService（回调模式：接口在 promotion-api，实现挂 order-biz）
NewbieEligibilityVO checkNewbieEligibility(@Param("tenantId") String tenantId,
                                           @Param("userId") String userId,
                                           @Param("registerWithinDays") Integer registerWithinDays);

// 返回：eligible（是否新人）、reason（未登录/已下过单/注册超时/参数异常）
```

order-biz 实现内部：

1. `order_info` 存在性查询：`tenant_id + user_id + pay_status='1'` 有记录 → 已下过单（走 `uk_order_request` 索引前缀）。
2. 注册时效：经 `RemoteMallUserService`（order-biz 已在引用，`OrderInfoServiceImpl.java:58`）取 `user_info.create_time`，`createTime + registerWithinDays 天 >= now`。
3. **fail-closed**：任何远程/数据异常按「非新人」返回并告警，不阻断下单主流程（与常购专属价同策略）。
4. 引擎侧对同一 `context.userId` 的判定结果做请求内缓存（试算与下单各调一次 preview，避免重复查库）。

> 口径提醒：`user_info.total_consume` 不可用（订单**完成**才累加且走 MQ 异步，见 README 6.2）；判定只认 `pay_status='1'` + `create_time`。

### 1.3 下单链接入点（order 侧改动最小化）

现状顺序（2026-09-27 核对，秒杀随购物车结算改造后；下单 `OrderInfoServiceImpl.java:405-413` 与结算 `:724-732` 两入口一致）：

```text
generateOrderItems
→ applyPromotionLadder（引擎改基价：阶梯价/整船折扣/赠品 + 新人价将挂这里）
→ orderPromotionPriceHandler（秒杀 > 限时折扣 > 原价；已提前到会员/券之前）
→ 会员折扣 → 优惠券 → 整船分摊
→ reservePromotion（写 PromotionLock）→ ArynOrderCreateBeforeEvent（秒杀预扣，失败阻断整单）
```

问题：`orderPromotionPriceHandler` 的折扣分支会**无条件覆盖** `salesPrice`，会把引擎给的新人价冲掉。改动：

1. `applyPromotionLadder` 返回的 `PromotionCalculationVO` 中提取命中新人价的 SKU 集合，传入 `orderPromotionPriceHandler`。
2. handler 内优先级定为 **秒杀 > 新人价 > 限时折扣 > 原价**：秒杀命中照旧覆盖（平台爆款优先）；折扣分支对新人价 SKU **跳过**（不再覆盖）。
3. 数量拦截：新人价 SKU 在该订单内 `buyQuantity > 1` 时抛业务异常「新人专享商品每人限购 1 件」（与秒杀限购同风格，秒杀侧 2026-09-27 已升级为 Redis 预扣 + 失败阻断）。
4. 在途唯一：`promotion_lock` 增加 `user_id` 列（增量 SQL，历史行不回填）。`reserve` 时若该用户已存在 **LOCKED 状态且活动类型为新人价**的锁 → 拒绝：「已有新人专享订单待支付」。防「同时下两单都锁新人价、先后支付两单都享价」。
5. 快照：新人价作为 engine `details` 之一，随既有 `PromotionSnapshot`（priceBefore/priceAfter/ruleSnapshot）落库，无需新表。

> ⚠️ **同日并行改造警示**：本需求动的是 `orderPromotionPriceHandler` 这条热点链，而 2026-09-27
> 「秒杀商品随购物车结算」改造（见需求记录）刚把该 handler 的调用点提前到会员/券之前、
> 激活了秒杀预扣（`ArynOrderCreateBeforeEvent`）并改了预扣幂等键。**Phase 2 动手前必须基于
> 改造后的最新代码重新核对调用顺序与既有用例**，不得按本文引用的行号直接改。

### 1.4 互斥与叠加总结

| 场景 | 行为 |
|---|---|
| 新人价 SKU 同时在秒杀 | 秒杀生效（秒杀优先，通常更低且平台级活动优先保护） |
| 新人价 SKU 同时在限时折扣 | 新人价生效，折扣跳过 |
| 新人价 + 会员折扣/优惠券 | 照常叠加（新人价是「改基价」，与会员/券分属不同层级，与现状阶梯价一致） |
| 新人价 + 整船折扣 | 照常（整船折扣按可折金额分摊，不冲突） |

## 2. C 端（UniApp）

### 2.1 新装修组件 `newbie-floor`（三端注册）

| 注册点 | 改动 |
|---|---|
| 服务端契约 | `PageDesignComponentTypes` 新增 `NEWBIE_FLOOR = "newbie-floor"`，加入 `KNOWN_TYPES` + `DATA_DRIVEN_TYPES` |
| 管理端 | `component-registry.ts` 注册 + 属性面板（标题默认「新人专享」、数据源=自动取当前进行中的新人价活动，无需运营手配活动 ID） |
| 移动端 | `src/components/diy/diy-newbie-floor/`（参照 `diy-discount` 的「楼层读活动」模式），`registry.ts` 注册 |

展示规则（对应行业「浏览时浅判」）：

- 楼层对**所有人**可见（营销吸引），每张卡片展示：新人价（大字）+ 划线原价（`shouldShowOriginalPrice` 口径复用 `price-display.ts`）+「新人」角标。
- 已登录新人：正常展示，可加购/抢购。
- 未登录：展示新人价，点「抢」触发登录拦截（既有 `useQuickCart` 的登录拦截模式）。
- 已登录非新人：展示新人价但按钮置灰为「已错过」？——**不采用**（泄露判定逻辑且体验差）。采用：照常展示新人价，结算页判定后按原价并提示「新人专享价仅限首单」。（与美团/多多现行做法一致）
- **缓存**：该楼层禁用 `withDataSourceCache` 的匿名缓存或以 `userId` 为缓存键，防止 A 用户的新人价被 B 用户命中。

### 2.2 新增 App 接口（promotion 域）

```text
GET /promotion/app/newbie/current
→ 当前进行中的新人价活动 + SKU 列表
  { activityId, activityName, registerWithinDays,
    goods: [{ skuId, spuId, name, imageUrl, newbiePrice, originalPrice(salesPrice), limitPerUser }] }
```

- 返回价格策略：**接口固定返回新人价**（楼层展示用），资格判定在结算链路做——不在此接口做按人出价，避免用户维度缓存与免登态复杂性。
- **必须登录态**：该接口**不进** C 端免登白名单（`skipToken` 与后端白名单双端核对，避免「登录已过期」误报坑）；未登录前端本地渲染原价兜底。
- 路径首段 `/promotion` 为微服务域，boot 模式经 `rewriteBootUrl` 改写为 `/boot/app/newbie/current`，双模式自洽。

## 6. 风险与开放点

1. **秒杀/折扣/新人价三链叠加的回归**：`orderPromotionPriceHandler` 是热点路径，改动需重点回归「秒杀单、折扣单、阶梯价单」既有用例（`OrderPriceComputeServiceTest` 扩展）。
2. **promotion_lock 加列的存量兼容**：`user_id` 为 NULL 的历史锁在「在途唯一」查询中自然被排除（`user_id IS NULL` 不等于当前用户），无需数据迁移。
3. **楼层对非新人展示新人价**的合规观感：结算页必须给出明确的原价提示文案；若运营侧不接受，可配置「楼层仅新人可见」（二期开关，MVP 不做）。
4. ** Dubbo 序列化**：新增返回体 `NewbieEligibilityVO` 必须 `implements Serializable`（strict 模式）。
5. **activityType="9" 取值**：实施前 grep `db/` 与 `promotion_activity` 存量数据确认无冲突。
