# 商城装修完整性与竞品调研

日期：2026-09-05  
范围：`aryn-mall-java`、`aryn-mall-ui`、`aryn-mall-uniapp`，以及 Shopify、Shoplazza、有赞、微盟公开的一手产品/开发者资料。  
结论性质：源码静态审查 + 官方公开资料对照；未连接生产租户，也未把未执行的 E2E、真实数据库迁移和 H5/微信构建当作通过。

## 一、结论

当前商城装修属于“核心链路已成型、发布质量未闭环”，建议按 **可用但不宜宣称完整** 处理。按电商 SaaS 装修的六个维度估算：

| 维度 | 当前判断 | 依据 |
|---|---|---|
| 页面编辑 | 较完整 | 统一三栏设计器、组件库、页面大纲、属性面板、拖拽/复制/撤销重做、页面设置 |
| 组件与数据 | 基本完整 | 管理端与 UniApp 共有 17 个组件；商品、分组、排行榜、活动、优惠券、店铺信息等有真实数据源 |
| 草稿与发布 | 较完整 | 草稿修订号、预览令牌、发布/下线、版本快照、回滚、发布前校验 |
| 模板与复用 | 已具备 | 系统/租户模板实体、模板 CRUD、模板应用时重建组件 ID |
| 多端与双模式 | 设计完整、运行验证不足 | v2 schema、移动端 typed registry、Boot/Cloud 路径规则；H5/微信构建仍受既有工具链阻断 |
| 运营级质量 | 不完整 | 仓库计划明确 Gate 3 未关闭；无既有 E2E 约定、无 MySQL/Docker 迁移演练、项目级质量门禁仍有基线问题 |

综合判断：产品能力约 **70%~80%**，工程交付完整度约 **60%~70%**。后一个数字更关键：装修页面可以被编辑和发布，但还缺少上线前可证明的跨端一致性、迁移回滚和回归保障。

## 二、现有实现盘点

### 1. 管理端

- 旧首页装修入口仍存在：`views/promotion/home-decoration`；它面向首页的简化编辑体验。
- 新统一入口为 `views/promotion/page-design` + `views/promotion/page-designer`，页面类型区分首页和微页面。
- 组件注册表 `page-designer/registry/component-registry.ts` 目前包含 11 个基础组件和 6 个零售组件，共 17 个：分类导航、优惠券、留白、手选商品、图片广告、公告、富文本、搜索框、轮播、标签导航、标题文本、商品分组、商品排行、限时活动、倒计时、营销入口、店铺信息。
- 设计文档模型为 schema v2：`document.page` 保存导航、背景、下拉刷新和分享设置；组件以 `id/type/version/props` 保存，支持 v1 迁移。
- 编辑器已有命令历史、草稿自动保存、脏状态、版本冲突、预览弹窗、发布弹窗和模板弹窗。

### 2. 后端与数据

`PageDesignController` 提供：分页查询、详情、新建、更新、草稿更新、编辑器数据、预览 token、复制、发布、下线、版本列表、版本回滚、删除以及首页兼容接口。`PageDesignTemplateController` 提供模板列表、新增、修改、删除。

`AppPageDesignController` 提供已发布页面、按 ID 查询和预览 token 读取。`page_design_version` 保存不可变版本快照，`page_design_template` 保存系统/租户模板；Boot 与 Cloud 均有 `10page_design_alter.sql`、`11page_design_publish.sql`，Boot full SQL 也已登记。

### 3. 移动端

UniApp 使用 `components/diy/registry.ts` 的 typed registry，与管理端 17 个组件类型对齐；未知组件有兜底组件。商品、活动、店铺信息等组件有 loading/empty/error/invalid 策略，链接通过统一 resolver 处理。

### 4. 当前明确缺口

1. **发布门禁缺少真实运行证明**：计划状态明确写着 Gate 3 open，未完成 E2E、迁移演练和 H5/微信构建闭环。
2. **旧首页编辑器与新设计器并存**：用户体验、权限、能力边界和后续维护成本容易分叉，应定义迁移/下线策略。
3. **组件仍以固定注册表为主**：适合当前自营商城，但还没有面向租户的组件开关、行业组件包、组件版本生命周期和灰度发布能力。
4. **数据驱动组件的运营控制较弱**：已有商品/活动数据源，但未见统一的筛选器、排序器、缓存策略、失效提示和埋点配置模型。
5. **发布治理不足**：已有版本和回滚，但报告、审批、定时发布、分环境发布、发布后监控和一键恢复尚未形成完整产品流程。
6. **质量指标缺失**：没有装修页面级的渲染成功率、组件接口失败率、首屏性能、点击/转化埋点和异常页面告警闭环。

## 三、同类产品能力对照

| 产品 | 官方资料体现的装修模型 | 对本项目的启示 |
|---|---|---|
| Shopify Online Store 2.0 | 主题由 templates、sections、blocks 组成；商家在 theme editor 中按页面模板添加、删除、重排 section/block，模板可复用，且通过 JSON template 保存页面结构。来源：[Theme architecture](https://shopify.dev/docs/storefronts/themes/architecture)、[Sections](https://shopify.dev/docs/storefronts/themes/architecture/sections)、[Templates](https://shopify.dev/docs/storefronts/themes/architecture/templates) | 把“页面结构”和“组件属性”作为稳定 schema；组件支持嵌套、可配置上限和模板级复用；不要把页面内容散落在组件私有字段中。 |
| Shoplazza | 官方帮助中心以主题、页面编辑器、section/自定义模块、预览和发布为核心；其产品定位强调无需代码的拖拽式店铺搭建。来源：[Shoplazza Help Center](https://help.shoplazza.com/hc/en-us)、[Shoplazza](https://www.shoplazza.com/) | 需要把“装修”做成店铺运营工作台：主题/模板、预览、发布、移动端适配和非技术用户引导应在同一流程内。 |
| 有赞 | 官方产品定位覆盖微商城、店铺页面和营销经营；公开帮助入口长期围绕店铺装修、页面/素材和营销组件组织。来源：[有赞帮助中心](https://help.youzan.com/)、[有赞官网](https://www.youzan.com/) | 中国 SaaS 用户通常期待营销组件与装修直接联动，商品、优惠券、活动、会员权益和客服入口应是一级能力，而不是只提供图片/文本排版。 |
| 微盟 | 官方产品体系强调智慧商业、营销活动和多渠道经营；装修通常与商城、营销、会员和内容模块共同交付。来源：[微盟官网](https://www.weimob.com/) | 装修能力不能只看“页面好不好看”，还要能承载渠道、会员、活动和门店经营场景，并支持不同终端的内容差异。 |

竞品共同基线不是组件数量，而是五件事：**结构化 schema、模板复用、实时预览、可控发布、业务数据组件**。Shopify 更强在 schema 与主题生态；有赞/微盟更强在营销经营联动。ARYN 当前已覆盖这五项的基础形态，但在生态、治理、观测和发布可靠性上仍明显落后。

## 四、建议方案

### P0：先达到“可放心发布”

1. **关闭 Gate 3**：建立一个最小 Playwright 主链路，覆盖新建微页面、添加/排序/复制组件、保存草稿、预览、发布、App 读取、回滚和跨租户拒绝。
2. **做一次真实迁移演练**：在临时 MySQL 上执行 Boot/Cloud 增量 SQL，验证 v1 页面迁移、v2 保存发布、回滚、重复执行和孤儿版本；把结果记录进需求归档。
3. **统一入口**：新建“商城装修”工作台，旧首页编辑器只保留兼容跳转；所有页面最终进入同一个 schema、权限和发布流程。
4. **发布前检查清单**：组件 schema、链接目标、素材可访问性、活动有效期、租户边界、移动端兼容、未发布变更、页面体积。
5. **双端构建恢复**：解决 H5/微信构建工具链问题；在 CI 固定 Node/pnpm/构建器版本，保存最小可运行 fixture 的产物检查。

### P1：补齐竞品可感知差距

1. **模板中心**：系统模板、租户模板、行业模板三层；支持缩略图、标签、搜索、复制、覆盖预览和模板版本。
2. **数据组件增强**：统一数据源协议，支持手选/分类/标签/排序/分页/库存过滤；组件显示数据更新时间和失效原因。
3. **发布治理**：发布说明、操作人、审批状态、定时发布、定时下线、灰度租户、变更 diff 和一键恢复。
4. **主题能力**：抽出全局色板、字体、圆角、间距、按钮和商品卡片 token；页面级只覆盖必要变量，减少逐组件调色。
5. **运营闭环**：为组件和链接增加曝光、点击、加购、领券、转化事件；提供页面级性能和错误指标。

### P2：形成平台能力

1. **组件 SDK/契约**：组件元数据包含版本、终端、权限、数据依赖、配置 schema、迁移器和降级策略；允许按租户启用组件包。
2. **多渠道页面**：H5、微信小程序、App/原生容器共享 schema，同时允许终端覆盖配置并在发布前比较差异。
3. **实验与个性化**：按渠道、会员、地域、时间段做 A/B 页面版本；与营销活动日历和人群包联动。
4. **性能预算**：页面组件数、图片体积、接口数、首屏时间和 CLS 设硬门槛，发布时阻断超预算页面。

## 五、建议的验收指标

- 主链路 E2E：发布成功率 100%，跨租户读取拒绝 100%，回滚后线上版本与目标快照一致。
- 兼容性：17 个组件在管理端预览、H5、微信小程序 fixture 中类型和关键 props 一致；未知组件不白屏。
- 稳定性：草稿保存无并发覆盖，版本号冲突可提示并恢复；发布/下线/回滚均有审计记录。
- 性能：默认首页首屏接口数、页面 JSON 大小、图片总字节和首屏时间设基线，超限不能直接发布。
- 运营：页面曝光、组件点击、商品/优惠券/活动转化事件可查询，能定位到页面版本和租户。
