## 3. 关键口径（已实现，代码即文档）

1. **绑定分流**（`SalesCustomerBindFacade`，按 `ISalesCustomerBindFacade` 接口注入）：邀请人为在职销售 → 无归属客户直接绑定（SHARE/QRCODE）；客户已是分销员下级 → 只写待转交认领、不改归属；已归属其他销售 → 不改；自点忽略；**非销售邀请人：客户未归属销售时走原分销 `register`，客户已正式归属销售时直接忽略，不再建立新的分销上级关系**（需求 §4.2）。销售会员账号不会被写成客户的分销上级。
2. **订单快照**：`createOrder` 调 `RemoteSalesAttributionService.resolve(tenantId, userId)`（已绑在职销售 → 未过期认领中的在职销售 → 无），写入 `order_info.sales_staff_id/name`；Dubbo 失败仅告警（实现不再吞异常，由调用方兜底）。历史订单不随换绑变化。
3. **提成基数**：本仓库 `payment_price`/`actual_pay_price` 含运费 → 在线 `max(0, paymentPrice-freightPrice)`；货到付款 `max(0, actualPayPrice-freightPrice)`，为空回退在线口径；2 位小数 `RoundingMode.DOWN`；基数 0 不建单。
4. **首单转交**：以订单上的销售快照为准。客户尚无归属时，支付即同一事务完成「改归属(CLAIM)+换绑日志+认领置已转交+分销员一次性奖励（首单实付不含运费×`referral_reward_rate`）」；即使下单后认领被改到另一位销售或已过期，仍按快照完成转交（被替换的待认领统一作废），避免"原销售拿提成但客户未转交、奖励丢失"。奖励落库 `status=0 待结算` 并计入原分销员 `pending_commission`（INCOME 流水备注「客户转交奖励」），由分销结算任务按 `distribution_config.settle_cycle_days` 释放为可提现佣金（先抵 `commission_debt`）；首单全额退款时自动扣回（pending→available→`commission_debt` 三态处理、EXPENSE 流水、按 `biz_order_id` 幂等，客户归属不回退）。按唯一键双击幂等。
5. **互斥**：`DistributionPayHandler` 遇 `salesStaffId` 非空直接跳过；`DistributionSettlementServiceImpl.settleOrder` 在买家已归属在职销售时跳过（防转交后旧关系继续计佣）。
6. **退款**：按 `refundBase/commission_base` 比例扣回、累不超提成额；`可发放`（支付创建即为该状态）直接冲减（全额→已全额退款）；`已发放` 生成负数 `sales_payout_adjustment` 结转到下月台账；按 `refundNo` 幂等；退款早于支付时记录待重放（支付时补应用 + 任务重放兜底；延迟超过 7 天被放弃的记录会在业绩单生成后自动重开补应用）。业绩单已进入**待确认**台账时，退款成功后自动重算台账金额（详见第 7 条）；全额退款联动扣回转交奖励（第 4 条）。
7. **发放台账**：业绩单支付创建即为「可发放」，`settle_at` 只作为退款风险观察期标记，不再是放行门槛。每月到 `sales_config.monthly_cutoff_day`（默认 1 日）生成上月台账（仅生成日生成；漏跑时若存在未入批的上月业绩单则幂等补跑），聚合与入批均按 `pay_time < 台账月次月 1 日 0 点` 过滤（历史未入批单顺延，台账月之后的订单绝不纳入）；**只有退款负数结转、没有业绩单的销售（含离职）也会生成负实发台账**，保证扣回落地；台账「待确认」期间发生退款会按批次内业绩单重算应发/实发金额，财务确认前还会再重算一次并校验批次单数一致（避免按旧金额发放）；生成入批后按实际入批订单再重算一次，台账金额与批次明细一致；扣减待结转负数后唯一键幂等，财务确认后台账「已发放」、业绩单同步「已发放」（批量更新同步推进 `version`）。
8. **券兑换**：单事务「校验券包/库存/可用佣金 → 行锁用户扣 `available_commission`（`total_commission` 不变）+ EXPENSE 佣金流水 → 按券模板发券（`coupon_user` 唯一键幂等 + 券库存原子扣减）→ 写兑换记录」；任一步失败整体回滚。提现接口返回明确下线错误。
9. **推广码**：`scene=sid=<memberUserId>`、页面 `pages/home/index`；仅在职销售本人可生成；data URI 返回，前端可直接展示/保存。
10. **双模式**：order→promotion、user→promotion 全部走 `*-api` Dubbo 接口，无跨 biz 直接 import；Controller 路径首段为微服务域（前端 `/promotion/...`、`/mall-order/...`、`/mall-user/...`），boot 模式由既有 `rewriteBootUrl` 改写，未硬编码 `/boot`；销售业务配置入库（`sales_config`），新增的推广码版本配置 `wx.miniapp.env-version` 按双模式规则同时提供 boot `application.yml` 与 cloud Nacos 增量脚本（`db/cloud/209sales_qrcode_nacos_config.sql`）。

## 6. 已知限制 / 业务待定

1. **已发放业绩单全额退款**：同时置「已全额退款」并生成负数结转（双重保障：不再参与发放 + 下月扣回），与需求文档「只生成负数调整」表述略有差异，按更安全口径实现。
2. **非销售订单退款记录**：`sales_refund_record` 也会为无销售归属的订单落一条待应用记录，7 天无业绩单自动置已应用，避免队列无限增长；分销域同类记录属存量行为未改。
3. **转交奖励释放依赖分销结算任务**：奖励先入 `pending_commission`，由 `distributionSettleJobHandler` 按 `distribution_config.settle_cycle_days` 释放为可提现佣金；任务停用或延迟时奖励会暂时停留在待结算，任务恢复后自动释放（不丢金额）。
4. **首单转交异常数据兜底**：客户无正式归属且无任何分销关系时（异常数据），仍按订单快照完成归属但按规则不发奖励，仅记录告警日志。
5. **离职销售无法扣回**：已发放批次退款产生的负数调整结转到下月台账，由财务在台账中处理；若销售已离职无法扣回，按需求 §7 记欠款/线下处理，系统不自动追缴。
6. **小程序「我的客户」**：昵称/头像原样返回由前端展示，未做服务端脱敏（该页面只有销售本人可见）。
7. **推广码缓存**：`data URI` 响应体积较大（约 10–20KB），已 Redis 缓存 7 天；微信接口失败短缓存 5 分钟避免打爆，前端需做好失败兜底（已实现错误提示）。
8. **报表口径**：业绩报表/趋势按 `sales_order` 聚合（成交额=提成基数-已退基数、提成=提成-已扣回），与发放台账同源；不含未归销售订单。
9. **退款与确认并发**：待确认台账的退款重算在同一事务内完成，确认前还会再重算一次，并校验批次单数一致（fail-closed，数据异常时提示刷新重试）；跨事务并发窗口已通过 `version` 推进 + `FOR UPDATE` 锁定读收敛，联调时建议按「退款 → 确认」顺序回归一次。
10. **转交奖励待结算不足**：极端数据下原分销员 `pending_commission` 小于奖励金额时，释放任务会保守跳过并告警（余额/状态不动，等待下个周期），不自动作废或跨扣。
11. **锁定读前提**：奖励释放/扣回的 `FOR UPDATE` 依赖单库单事务；若后续拆分读写分离或多数据源，需要复核该实现。

### 8.3 独立复核加固（第二轮，2026-11-05）

第二轮独立复核针对并发/金额边界提出若干缺陷，已全部修复并回归：

| # | 复核问题 | 修复 |
|---|---|---|

| # | 复核问题 | 修复 |
