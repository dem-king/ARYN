# 销售业绩归属与提成

## 1. 需求来源

公司有大量外勤销售。销售跑成的客户在小程序下单后，订单要记到这个销售名下：订单管理里显示销售人员，并据此计算业绩和提成。

2026-11-05 已确认的口径：

| # | 口径 |
|---|---|
| 1 | 提成按**实付金额**计算，**不含运费** |
| 2 | 客户与销售绑定；**销售离职时可以换绑**给其他销售 |
| 3 | 现有普通分销功能**保留**；销售不算本人自购业绩 |
| 4 | 公司销售的提成**不能在小程序提现**，随基本工资一起发放 |
| 5 | 分销员绑定的客户可以被销售接手：分销员拿一笔**一次性推荐奖励（或首单奖励）**，此后该客户的订单归销售 |
| 6 | **普通分销员的佣金也不能提现**，改为兑换大额优惠券 |
| 7 | 离职销售尚未发放的提成照常进入台账，由财务决定是否发放 |

## 2. 现状与差距

现有分销模块位于 `aryn-promotion`，以下能力可以复用：

- 分享链接带 `shareUserId`，客户登录后自动绑定：`aryn-mall-uniapp/src/composables/useDistributionShare.ts`
- 支付成功事件触发计佣，结算幂等：`DistributionPayHandler`、`DistributionSettlementServiceImpl.settleOrder`
- 待结算 → 到期释放的定时任务：`DistributionSettleJobHandler`
- 按退款基数比例回退佣金；佣金已提走时记为欠款：`DistributionSettlementServiceImpl.refundDistributionOrder`

不能直接拿来承载公司销售的原因：

| 差距 | 现状 |
|---|---|
| 订单不记录销售 | `order_info` 没有推广人/销售字段；归属在支付时按买家**当前**的邀请人现查，订单本身无快照 |
| 身份不是员工 | 分销员只能是 C 端会员，与 `sys_user`、部门无关联；任何 C 端用户都能自助注册成分销员 |
| 比例单一 | 全局只能启用一套配置，所有人一个比例 |
| 不能换绑 | `bindInviterIfAbsent` 只在未绑定时生效，没有换绑和交接 |
| 可在小程序提现 | 佣金走“小程序申请提现 → 审核 → 打款”，与员工提成随工资发放的流程冲突（本次一并改为兑换优惠券） |
| 无报表 | 没有按销售、部门、月份统计的业绩报表和导出 |
| 无地推码 | 只能分享商品页链接，没有个人推广小程序码；后端没有小程序码生成能力 |

结论：**新建独立的“销售业绩”账本**，复用分销的绑定入口、支付/退款事件和结算机制；不把公司销售混进 `distribution_user`，否则个人比例、员工身份、按工资发放都无法落地。同时把普通分销的提现改成优惠券兑换。

## 3. 目标与非目标

**目标**

- 后台登记公司销售（关联员工账号、部门和销售本人的小程序会员账号），只有登记过的销售才产生销售业绩
- 客户通过销售的分享链接或推广码进入并登录后，自动绑定该销售
- 下单时把归属销售快照写入订单；订单列表、详情和导出都显示“归属销售”
- 支付后按销售个人提成比例生成业绩单；退款按比例扣回；按自然月汇总随工资发放
- 后台生成月度发放台账，财务确认发放；小程序不提供提现入口
- 分销员的佣金取消提现，改为兑换大额优惠券；后台提供券包配置和兑换记录管理
- 客户可以从分销员转给销售，分销员获得一次性推荐奖励，之后该客户的订单归销售
- 销售离职时把名下客户批量转给其他销售，全程留痕；历史订单归属不变

**非目标**

- 不做销售团队的上下级分成（团队长抽成）
- 不改变普通分销的绑定规则和佣金比例，只把提现改成兑换优惠券
- 不接入工资系统，发放只做台账和导出

## 4. 方案

### 4.1 数据模型

除特别说明外，新表都放在 promotion 域：boot 模式在 `aryn_boot`，cloud 模式在 `aryn_promotion`。所有表都带 `tenant_id`、`del_flag` 和审计字段。

**`sales_staff` 销售员**

| 字段 | 说明 |
|---|---|
| `sys_user_id` | 后台员工账号，通过 `RemoteSysUserService` 校验 |
| `staff_name` / `phone` / `dept_id` / `dept_name` | 员工信息快照，便于报表 |
| `member_user_id` | 销售本人的小程序会员 ID，生成分享参数用；租户内唯一 |
| `commission_rate` | 个人提成比例（0–1），为空时取全局默认比例 |
| `status` | `0` 在职、`1` 离职 |
| `leave_time` | 离职时间 |

**`sales_customer_bind` 客户归属**

| 字段 | 说明 |
|---|---|
| `customer_user_id` | 客户会员 ID；租户内唯一，一个客户同时只归属一个销售 |
| `sales_staff_id` | 归属销售 |
| `bind_source` | 来源：`SHARE` 分享链接、`QRCODE` 推广码、`ADMIN` 后台指派、`TRANSFER` 离职交接、`CLAIM` 首单转交 |
| `bind_time` | 绑定时间 |

**`sales_customer_bind_log` 换绑日志**：记录客户、原销售、新销售、原因、操作人、时间。只追加，不删除。

**`sales_customer_claim` 待转交认领**：客户已归属分销员、又点击了销售分享链接时生成，记录客户、销售、来源、状态（`0` 待首单、`1` 已转交、`2` 已失效）。同一客户只保留最新一条销售认领。

**`sales_transfer_reward` 客户转交奖励**：客户从分销员转给销售后生成，记录客户、原分销员、接收销售、触发订单、首单实付金额、奖励比例、奖励金额、状态（`0` 待结算、`1` 已入账、`2` 已作废）。

**`sales_order` 销售业绩单**（参照 `distribution_order` 的设计）

| 字段 | 说明 |
|---|---|
| `biz_order_id` | 业务订单 ID；唯一，保证同一订单只生成一条，结算幂等 |
| `order_no` / `buyer_user_id` | 订单号、买家 |
| `sales_staff_id` / `staff_name` / `dept_id` | 取自订单上的销售快照 |
| `payment_amount` / `freight_amount` | 实付金额、运费 |
| `commission_base` | 提成基数，口径见 4.4 |
| `commission_rate` | 支付时的比例快照；之后改比例不影响已生成的业绩单 |
| `commission_amount` | 提成金额 |
| `refunded_base` / `refunded_commission` | 累计退款基数、累计扣回提成 |
| `status` | `0` 待确认（保留值，当前支付创建即 `1`）、`1` 可发放、`2` 已发放、`3` 已全额退款 |
| `pay_time` / `settle_at` / `settle_time` | 支付时间、计划可发放时间（仅退款风险观察期标记，不再是放行门槛）、实际可发放时间 |
| `payout_id` | 所属发放批次 |

**`sales_payout` 月度发放台账**：每个销售每月一条，记录发放月份（`yyyy-MM`）、业绩单数、成交额、应发提成、上期退款冲减、实发金额、状态（`0` 待确认、`1` 已发放）、确认人、发放时间。

**`sales_config` 全局配置**：默认提成比例、月度截止日、转交奖励比例。

**`distribution_coupon_pack` 券包配置**：券包名称、面额、使用门槛、有效期（天）、消耗佣金、状态、库存（可空表示不限）。

**`distribution_coupon_exchange` 兑换记录**：分销员、券包、消耗佣金、发放的优惠券 ID、状态、时间。

**`order_info` 新增字段**（order 域）：`sales_staff_id`、`sales_staff_name`，下单时写入，之后不随换绑变化。

### 4.2 绑定流程

1. 管理员在“销售员管理”中登记销售：选择员工账号，再按手机号关联销售本人的小程序会员账号。
2. 销售在小程序里分享商品，或出示个人推广码。分享参数沿用现有的 `shareUserId` / `sid`，值为销售的 `member_user_id`。
3. 客户登录后，前端照常调用 `/promotion/app/distribution/share/bind`。后端在 `AppDistributionController.shareBind` 先判断邀请人：
   - 邀请人是**在职销售**，客户原来没有归属：直接写入 `sales_customer_bind`，来源 `SHARE`。
   - 邀请人是**在职销售**，客户已归属普通分销员：写入 `sales_customer_claim`（待首单），**此时不改变归属**，原分销员仍可照常拿佣金。
   - 邀请人不是销售：客户未归属销售时走现有的分销绑定逻辑，行为不变；客户**已正式归属销售**时直接忽略，不再建立新的分销上级关系（§4.2 第 4 条）。
4. 归属规则的优先级：
   - 客户已正式归属销售：点击任何销售或分销员的链接都不改变归属，也不再建立新的分销上级关系；
   - 客户归属分销员：点击销售链接只生成或替换待转交认领，以最新一次认领为准，正式归属不变；但**下单后、支付前**认领被替换或过期时，已下单的订单仍按订单快照完成转交（见 §4.2.1）；
   - 改归属只能在后台操作。

### 4.2.1 转交与奖励

- **正式转交时机**：客户有销售认领、且产生**首笔支付成功的订单**时，系统同时完成三件事：
  1. 把 `sales_customer_bind` 改为该销售，来源记为 `CLAIM`，写换绑日志（原分销员 → 销售），认领状态改为已转交；
  2. 生成 `sales_transfer_reward`，原分销员获得一次性奖励；
  3. 此后该客户的订单只产生销售提成，不再产生分销佣金。
- **首单归属**：只要存在待转交认领，下单时就按该销售写入订单快照，即使客户当前仍绑定在分销员名下。支付时**以订单快照为准**：即使下单后认领被改到另一位销售或已过期，仍按快照完成转交（被替换/过期的其他待认领作废），避免"原销售拿提成但未转交、奖励丢失"。
- **奖励金额**：客户首单**实付金额（不含运费）× `sales_config.referralRewardRate`**，保留两位小数，向下取整；比例后台可配，默认 0 表示不启用。奖励金额和比例在转交时快照到 `sales_transfer_reward`。
- **奖励入账**：奖励先记 `status=0 待结算` 并计入原分销员的**待结算佣金**（`pendingCommission`），由分销结算任务按分销结算周期释放为可提现佣金（`status=1 已入账`、写结算时间，`totalCommission` 同步累加），之后只能兑换优惠券；佣金收入流水（备注“客户转交奖励”）在奖励入账时写入。**首单全额退款时自动扣回奖励**：按待结算/可提现/佣金欠款三态扣减（可提现不足部分记 `commission_debt`），写 EXPENSE 流水，按触发订单幂等，客户归属不回退。
- **幂等**：一个客户同时最多一条有效认领；转交奖励按客户和触发订单去重，重复支付回调不会重复发放。
- **失效**：客户转交前点击了另一位销售的链接，以最新认领为准；后台手动改归属时，未完成的认领作废。
- 转交前已经产生的分销佣金不受影响；转交时尚在待结算的旧佣金照常结算。

### 4.3 订单归属快照

- promotion-api 新增 Dubbo 接口 `RemoteSalesAttributionService.resolve(tenantId, userId)`，返回归属销售的 ID 和姓名（只返回在职销售）。归属判定顺序：已绑定的销售 → 待转交认领中的销售 → 无。
- 在 `OrderInfoServiceImpl.createOrder` 保存订单前调用该接口，把结果写入 `order_info.sales_staff_id` / `sales_staff_name`。调用失败时只告警，不阻断下单，该订单不计销售业绩。
- `OrderPaySuccessEvent` 增加 `salesStaffId`、`actualPayPrice` 两个字段。事件由 `BeanUtils.copyProperties` 从订单复制，字段同名即可自动带上。

### 4.4 提成计算

- 新增 `SalesPayHandler`，实现 `PromotionPayEventHandler`。事件中带有 `salesStaffId` 时：
  1. 若该订单对应一条待转交认领，先完成转交并生成分销员奖励（4.2.1）；
  2. 再按订单快照生成 `sales_order`。**以订单快照为准，不再现查绑定关系。**
- 提成基数为实付金额：
  - 在线支付：`paymentPrice`（**本仓库该字段本身含运费**，基数为 `paymentPrice - freightPrice`）
  - 货到付款：后台登记的 `actualPayPrice`（同样含运费，基数为 `actualPayPrice - freightPrice`；为空回退 `paymentPrice - freightPrice`）
  - 两种情况都以实付金额为基数，**运费不计入**
- 提成 = 基数 × 销售个人比例（为空取全局默认比例），保留两位小数，向下取整。
- **与普通分销互斥**：
  - 订单带有 `salesStaffId` 时，`DistributionPayHandler` 跳过，同一笔订单不会同时产生分销佣金和销售提成。
  - 分销绑定关系里，客户一旦归属销售，`DistributionPayHandler` 在结算时也要检查：当前客户是否已被销售接手，是则跳过（防止转交后继续产生分销佣金）。
- 退款：新增退款事件处理器，按 `refundBaseAmount / commission_base` 的比例扣回，按退款单号幂等：
  - 业绩单可发放（支付创建即该状态）：直接冲减；全额退款 → 已全额退款
  - 业绩单已发放：生成负数调整，结转到下月发放台账中扣除
  - 已生成未确认的台账：自动按批次净额重算应发/实发，财务确认前再重算一次兜底
- 发放节奏：**按自然月汇总，随基本工资发放**。系统在每月台账生成日（`monthly_cutoff_day`，默认 1 日）生成上月台账；当月未发放的业绩单（例如月末支付、次月才确认）顺延到下一期。取消“支付后 N 天自动可发放”的独立释放任务，`settle_at` 只作为退款风险观察期标记。

### 4.5 离职与换绑

- 后台把销售标记为离职时，必须选择接收人，系统一次性转移全部名下客户（来源记为 `TRANSFER`，写入换绑日志）。
- 支持对单个客户手动改归属，必须填写原因并写入日志；未完成的待转交认领随改归属作废。
- 离职销售名下未完成的首单认领一并作废。
- 离职后不再生成新业绩；已产生的业绩单仍归原销售，按原流程进入台账，是否发放由财务在台账中处理。
- 历史订单上的销售快照不变。

### 4.6 发放

- 每月台账生成日（`sales_config.monthly_cutoff_day`，默认 1 日）生成上月台账，汇总每个销售可发放且未入批的业绩单（按支付时间归属月份）和退款负数调整；只有退款冲减、没有业绩单的销售（含离职）也会生成负实发台账。手工生成只允许选择上月及更早月份；确认发放前系统会按最新退款重算并校验批次单数一致，异常时提示刷新重试。
- 财务在后台核对后标记“已发放”（可填写备注或凭证号），对应业绩单状态同步改为已发放；确认前系统会按最新退款情况再重算一次金额。
- 台账支持导出，交给工资核算使用。小程序不提供任何销售提成的提现接口。

### 4.6.1 分销佣金改为兑换优惠券

现状：分销员在 `/promotion/app/distribution/withdraw/apply` 申请提现，后台人工审核、线下打款。本次改造：

- **下线提现入口**：小程序分销中心去掉“申请提现”，改为“兑换优惠券”；`withdraw/apply` 接口下线（返回明确的业务错误）。
- **后台提现审核降级为只读历史**：`distribution_withdraw` 表和历史单据保留，菜单保留查询，审核和打款按钮下线。存量待审核单由运营一次性处理完（打款或拒绝解冻），不做自动迁移。
- **券包**：后台配置券包（名称、面额、使用门槛、有效期、所需佣金、库存、状态），可同时上架多个。
- **兑换**：分销员选择券包 → 校验可提现佣金足够 → 扣减 `available_commission` → 调用优惠券中心内部接口发一张券到该用户名下 → 写 `distribution_coupon_exchange` 和佣金支出流水。全过程一个事务，券发放失败则回滚佣金扣减。
- **优惠券中心**：复用现有优惠券模板/发券能力（`CouponUser`），券包关联一个或多个券模板；发放后出现在小程序“我的优惠券”。
- **退款不影响已兑换的券**：券已发放，不再回退佣金；如果兑换后发生佣金回退，按现有 `commissionDebt` 机制记欠款，从后续佣金中抵扣。
- **报表**：后台“兑换记录”页按分销员、券包、时间查询；月度营销费用里能看到券成本。

## 7. 已确认决策

| 问题 | 结论 |
|---|---|
| 提成基数 | 实付金额，不含运费 |
| 自购 | 销售本人自购不计业绩 |
| 销售离职 | 必须指定接收人，名下客户批量转交，历史订单归属不变 |
| 销售提成发放 | 按自然月汇总，随基本工资发放，小程序不可提现 |
| 客户从分销员转给销售 | 点击销售链接后进入待转交，**首单支付成功**才正式转交 |
| 转交奖励 | 按客户**首单实付金额 × 奖励比例**，一次性，后台可配 |
| 已发放提成后再退款 | 负数冲减放入下月台账；如果销售已离职无法扣回，记欠款由财务处理 |
| 转交奖励首单全额退款 | 自动扣回（先扣待结算/可提现佣金，不足记分销员佣金欠款）；客户归属不回退 |
| 分销员佣金 | 不能提现，改为兑换大额优惠券 |
| 存量待审核提现单 | 上线前由运营一次性人工处理完，不写迁移逻辑 |

## 8. 风险

- **推广小程序码**：需要已发布的小程序和对应页面才能生成；开发和体验版要指定 `env_version`。`scene` 限 32 个字符，`sid=<19 位 ID>` 可以放下。
- **订单表加字段**：`order_info` 是热表，加两个可空字段即可，不加索引；按销售查询走 `sales_order`。
- **存量客户**：上线前已存在的客户没有销售归属，需要管理员手动指派或批量导入（导入可放到 P3）。
- **券兑换的资金口径**：券是营销费用，兑换后佣金余额减少但公司没有现金流；财务对账要和提现区分开。
- **分销结算检查成本**：`DistributionPayHandler` 每次结算要多查一次销售归属，属于按订单的轻量查询，可接受；如量大可加缓存。
- **认领被滥用**：客户点击销售链接即产生待转交，虽然正式转交要等首单支付，仍建议给认领加有效期（默认 90 天），并由后台客户归属页展示“待转交”状态，方便运营巡查。
