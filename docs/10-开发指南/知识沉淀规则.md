# 知识沉淀规则

> 本文档定义项目中知识的管理方式：何时写文档、何时用工具、稳定知识如何回写。

## 1. 知识分类

| 类型 | 特征 | 沉淀方式 | 示例 |
|------|------|----------|------|
| **稳定知识** | 长期不变、团队共识 | 写入文档 | 架构分层、命名规范、数据库表结构 |
| **动态知识** | 频繁变化、上下文相关 | 代码 + 注释 | 业务逻辑分支、临时方案、TODO |
| **操作知识** | 执行步骤、命令序列 | 脚本 / Harness | 构建命令、部署步骤、验证流程 |
| **经验教训** | 踩坑记录、最佳实践 | Harness 记忆系统 | 依赖冲突、配置陷阱 |

## 2. 何时写文档 vs 何时用工具

### 写文档的场景

| 场景 | 目标文档 | 原因 |
|------|----------|------|
| 新增业务模块 | [功能到代码索引](../20-业务与数据/功能到代码索引.md) | 团队需要快速定位代码 |
| 新增数据库表 | [数据模型](../20-业务与数据/数据模型.md) | 理解数据关系 |
| 新增 API 接口 | [接口映射](../40-接口与风险/接口映射.md) | 前后端对齐 |
| 业务流程变更 | [业务流程](../20-业务与数据/业务流程.md) | 对齐业务理解 |
| 发现缺失模块 | [缺失模块清单](../40-接口与风险/缺失模块清单.md) | 跟踪待办 |
| 需求变更 | [需求记录](../90-记录归档/需求记录.md) | 可追溯 |

### 用工具的场景

| 场景 | 工具 | 原因 |
|------|------|------|
| 依赖层级违规 | `scripts/lint-deps.py` | 自动化检查比文档更可靠 |
| 代码质量 | `scripts/lint-quality.py` | 规则可执行 |
| 操作前验证 | `scripts/verify_action.py` | 即时反馈 |
| 构建验证 | `scripts/validate.py` | CI/CD 流水线 |

## 3. 稳定知识回写规则

### 3.1 回写触发条件

当以下事件发生时，应将稳定知识回写到对应文档：

| 事件 | 回写目标 | 回写内容 |
|------|----------|----------|
| 新增 Java 模块 | [Java后端](../30-端分析/Java后端.md) | 模块名、Controller、Service、RPC 接口 |
| 新增数据库表 | [数据模型](../20-业务与数据/数据模型.md) | 表名、字段、关系 |
| 新增前端页面 | [管理后台UI](../30-端分析/管理后台UI.md) 或 [移动端UniApp](../30-端分析/移动端UniApp.md) | 路由、组件、API |
| 新增 API 接口 | [接口映射](../40-接口与风险/接口映射.md) | 路径、方法、参数、响应 |
| 新增业务流程 | [业务流程](../20-业务与数据/业务流程.md) | 流程图、状态流转 |
| 新增术语 | [术语表](../00-项目总览/术语表.md) | 术语、定义、数据表 |

### 3.2 回写原则

1. **原子性**: 每次回写只涉及一个知识点的增/改
2. **一致性**: 回写内容与代码实现保持同步
3. **可追溯**: 回写时注明来源（PR/Commit/任务编号）
4. **不重复**: 同一知识点只在一处文档中定义，其他位置引用链接

## 4. 文档维护责任

| 文档 | 维护者 | 更新频率 |
|------|--------|----------|
| 项目总览 | 架构师 | 架构变更时 |
| 环境与启动 | DevOps | 环境变更时 |
| 术语表 | 全员 | 新概念引入时 |
| 开发工作流 | Tech Lead | 规范变更时 |
| 业务流程 | 产品/后端 | 业务变更时 |
| 数据模型 | 后端 | 表结构变更时 |
| 端分析 | 各端负责人 | 功能迭代时 |
| 接口映射 | 前后端 | API 变更时 |
| 缺失模块清单 | Tech Lead | 每个迭代 |
