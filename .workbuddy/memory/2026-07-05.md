### 修复登录 AES 解密报错 BadPaddingException: pad block corrupted
- 现象：`TobTokenController.login` 调 `AesUtils.decrypt` 解密前端密码时抛 `BadPaddingException: pad block corrupted`（hutool SymmetricCrypto，BC provider）。
- 根因：**前后端加密模式不匹配**。前端 `aryn-mall-ui/apps/web-ele/src/utils/aes.ts` 用 **CBC + IV(`aryn_iv_key_2025`) + Pkcs7**；后端 `AesUtils.decrypt`（被 login 调用）却是 **ECB（无 IV）+ PKCS7Padding**。密钥本身一致（`VyBcekSelErhMYN4`，来自 `.env` 的 `VITE_PWD_PRIVATE_KEY` 与 yml 的 `encode.key`），模式不对必然 padding 失败。
- 修复（保持前端 CBC 不回退到 ECB，因为 ECB 不安全）：
  - `aryn-auth/.../TobTokenController.java`：新增 `@Value("${encode.iv:aryn_iv_key_2025}") encodeIv`，login 改调 `AesUtils.decryptCBC(encodeKey, password, encodeIv)`。
  - `aryn-boot/src/main/resources/application-dev.yml` & `application-prod.yml`：`encode` 下显式补 `iv: ${ENCODE_IV:aryn_iv_key_2025}`，与前端 `DEFAULT_IV` 对齐。
  - nacos 初始化脚本 `db/cloud/3aryn_nacos.sql` 中 `aryn-auth-dev.yml` 未配 `encode.iv`，但 Controller 默认值兜底，微服务模式从 nacos 拉配置也能正常解密，未改 SQL（含 md5 校验，改需同步重算）。
- 验证：
  - `mvn -pl aryn-auth -am compile` 通过。
  - 前端 crypto-js 自洽：CBC 加密 `Test@123` → `fckxza3gjDzTb8RDI7b6vg==`，再解密还原成功（key/iv 各 16 字节，AES-128）。
  - **跨语言端到端**：将前端产出的密文交给后端 `AesUtils.decryptCBC`（临时 main，classpath 用 `dependency:build-classpath`）→ 还原 `Test@123`，`match=true`。
- 教训：AesUtils 同时存在 ECB(已 @Deprecated) 与 CBC 两套方法，调用方误用旧 ECB 方法导致与前端 CBC 不匹配。新代码应一律用 CBC，ECB 仅留作历史数据解密。
